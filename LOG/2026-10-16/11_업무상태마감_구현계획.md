# 업무 상태 마감 구현계획 정리 기록

기록일: 2026-10-16

로컬 `DOCX/2번_업무_상태_마감_구현계획.md`를 작성·수정한 내용을 독립적으로 요약한다.
아래 API·테이블·저장 규칙은 구현 제안이며 실제 서버·DB의 기존 계약이 아니다.
이번 LOG 게시는 문서 기록만 대상으로 하며 코드나 태그를 갱신하지 않는다.
기록 시점의 원격 `alpha`와 `0.0.2V`는 `0d06c7108`의 종전 코드이고 최신 5상태·관리자 본인 화면은 로컬 반영분이다.

## 작성 이유와 변경 내용

화면 뼈대 다음에 2번이 구현할 순서와 다른 담당자와 맞출 경계를 정리할 필요가 있었다.
계획서를 추가한 뒤 확정된 제출·검토 원칙과 관리자 본인 업무·5개 단일 상태 기준을 반영했다.
기존 진행·처리 상태 분리안은 단일 `task_status` 논리안으로 대체했다.
범용 진행 상태 PATCH 제안도 수락·제출·판단이라는 행동별 연결로 정리했다.
원본 기준 DOCX와 폼 수정사항은 보존했으며 API·DB·실제 업무 기능은 구현하지 않았다.

## 확정된 업무 기준

| 상태 | 의미 |
|---|---|
| 진행전 | 배정 후 미수락 |
| 진행중 | 담당자가 수락해 수행 |
| 제출완료 | 정식 제출·재제출 후 판단 대기 |
| 승인완료 | 검토 승인에 따른 최종 완료 |
| 반려완료 | 반려 판단 종료, 수정·재제출 필요 |

직원·관리자의 모든 정식 제출·재제출은 관리자 판단을 거친다.
관리자 본인 제출본은 상위 검토자가 판단하며 자기 승인·반려는 금지한다.
자동 결과 제출은 제외한다. 자동 검토 요청의 도입·조건은 별도 합의 필요다.
수락→진행중, 제출→제출완료, 판단→승인완료·반려완료라는 기본 전환은 확정됐다.

## 현재 로컬 반영

계획서에 상태 의미 표, 관리자 본인 업무의 경계, API 후보와 DB 논리안·검증 항목을 반영했다.
README에도 화면 뼈대의 범위와 필수 검토·자동 제출 제외 기준을 정리했다.
WinForms는 표준 컨트롤과 고정 샘플로 화면만 구성하며 실제 서비스·서버·DB는 연결하지 않았다.

## 이후 실제 구현의 권장 순서

1. 1번과 인증·사용자 ID·DB 연결·공통 응답·이력 규격을 확인한다.
2. 업무·배정 스키마를 검토하고 목록·상세 GET을 WinForms와 연결한다.
3. 초기 상태의 저장 코드를 맞춘 뒤 등록·최초 배정과 서버 검증을 연결한다.
4. 수정·재배정·취소의 허용 조건을 합의하고 수정 충돌을 처리한다.
5. 수락과 상태 표시를 연결하고 3번의 제출·판단 API와 상태 갱신을 맞춘다.
6. 요청 입력·조회 구조를 준비한다. 실제 연장 접수는 신청 조건 합의 후 연결한다.
7. 합의된 연장 반영·마감 알림을 연결한다. 자동 검토 요청은 도입 합의 후 검토한다.
8. 같은 API를 HTML에 연결하고 두 PC·웹에서 저장 후 재조회를 확인한다.

현재는 화면 뼈대다. 이 순서는 앞으로 구현할 단계이며 완료 목록이 아니다.

## API 후보

공통 접두사·응답 형식·사용자 식별자는 1번과 맞춘다. 아래 경로는 가칭이다.

| 메서드·경로 후보 | 목적과 경계 |
|---|---|
| `GET /tasks` | 본인/관리 범위, 상태·검색·날짜·담당자·페이지 조건의 목록 |
| `GET /tasks/{taskId}` | 기본 정보·현재 배정·수락·단일 상태·수정번호 |
| `POST /tasks` | 관리자 등록과 최초 배정을 함께 저장하는 안 |
| `PATCH /tasks/{taskId}` | 기본 정보 수정·재배정, `expectedVersion` 검사 |
| `POST /tasks/{taskId}/cancel` | 실제 삭제 대신 취소 기록을 남기는 안 |
| `PUT /tasks/{taskId}/assignments/{revision}/accept` | 현재 담당자인 직원·관리자의 배정 수락 |
| `POST /tasks/{taskId}/requests` | 검토·연장 접수. 유형 의미와 신청 조건 합의 필요 |
| `GET /task-requests` | 허용된 관리 범위의 요청 목록 |
| `GET /task-requests/{requestId}` | 권한이 있는 요청의 상세·처리 기록 |
| `POST /task-requests/{requestId}/decision` | 마감 연장 판단 전용 제안. 결과물 승인에 사용하지 않음 |

사용자 조회·인증은 1번, 공통 파일·제출·재제출·버전·승인·반려 API는 3번 계약을 사용한다.
기본 정보 수정이나 임의 상태 PATCH로 정식 제출·필수 판단·상위 검토자 검사를 우회할 수 없다.
관리자 화면의 범위 선택만으로 서버 조회·수정 권한이 늘어나지 않는다.

## DB 논리안 1 업무 기본 정보

| `tasks`의 컬럼 후보 | 목적 |
|---|---|
| `task_id`, `title`, `description` | 업무 식별·제목·내용 |
| `task_status` | 5개 업무 상태를 담는 단일 논리 상태 |
| `start_date`, `due_date` | 시작일·마감일 |
| `current_assignment_revision` | 현재 배정 차수 |
| `created_by`, `created_at`, `updated_at` | 등록자·기록 시각 |
| `row_version` | 오래된 화면의 수정 충돌 검사 |
| `cancelled_at`, `cancelled_by`, `cancel_reason` | 취소 기록 후보. 허용·표시 규칙 합의 필요 |

## DB 논리안 2 배정과 수락 기록

| `task_assignments`의 컬럼 후보 | 목적 |
|---|---|
| `task_id`, `revision` | 업무·배정 차수의 복합 식별자 |
| `assignee_id` | 담당자. 직원·관리자를 포함한 공통 사용자 참조 |
| `assigned_by`, `assigned_at` | 배정한 관리자와 시각 |
| `accepted_at` | 해당 배정을 수락한 시각 |

재배정은 이전 수락 기록을 덮어쓰지 않는 새 차수 기록을 제안한다.
실제 재배정 허용 조건과 결과물에 미치는 영향은 합의 필요다.

## DB 논리안 3 요청 기록

| `task_requests`의 컬럼 후보 | 목적 |
|---|---|
| `request_id`, `task_id`, `assignment_revision` | 요청과 발생 업무·배정 참조 |
| `request_type`, `requested_by`, `reason` | 유형·신청 담당자·사유 |
| `requested_due_date`, `base_due_date` | 희망 마감일·신청 당시 마감일 |
| `base_task_version`, `row_version` | 신청 전제와 처리 충돌 검사 |
| `request_state`, `created_at` | 요청 자체의 처리 상태와 접수 시각 |
| `idempotency_key`, `payload_hash` | 같은 전송의 재시도와 내용 일치 검사 |

요청 상태는 업무 상태와 별개다. 연장 판단자·시각·의견의 구체 구조는 합의 후 추가한다.
위 세 표는 실행 가능한 확정 DDL이 아니다. 상태 코드·DB 기본값·사용자 PK 타입도 합의 필요다.
결과물·파일·승인·이력 테이블과 관리자 계층·상위 검토자 매핑을 2번이 중복 설계하지 않는다.

## 충돌과 중복 방지 제안

- 업무·배정·필요 이력은 같은 트랜잭션에서 처리하고 실패하면 함께 되돌린다.
- 현재 배정 차수와 수정번호를 검사해 옛 배정 수락·수정이 최신 정보를 덮어쓰지 않게 한다.
- 같은 재시도 키·같은 내용은 최초 결과를 반환하고 같은 키·다른 내용은 충돌로 처리하는 안이다.
- 동시에 들어온 같은 요청은 UNIQUE 제약과 트랜잭션으로도 중복을 막는 안을 검토한다.
- 연장 접수만으로 마감일을 바꾸지 않고 판단 시 현재 배정·마감일을 다시 비교한다.
- 서버 저장 후 응답만 유실되면 재시도·재조회로 결과를 확인한다.

## 합의 필요와 검증 경계

- 1번·3번: 상태 저장 코드·연결 규격, 반려 후 재작업 복귀 시점, 상위 검토자 권한 매핑.
- 2번·3번: 제출 이후 수정·재배정·취소, 검토 요청의 의미, 연장 조건과 기한 후 직접 제출.
- 2번·3번: 자동 검토 요청의 도입·중복 회차·마감 기준 시각. 자동 제출은 제외로 확정.
- 1번: 사용자·관리 범위·공통 통신·이력·날짜 저장 규약. 4번: 마감 변경 알림과 협업 연결.
- 구현 후 권한 우회·자기 판단·오래된 수정·동시 재시도·필수 검토 누락·재조회 일치를 검증한다.
- 화면·빌드·실제 HTTP·DB 저장·재조회 성공은 서로 다른 확인 단계로 기록한다.

원본 계획서 경로는 로컬 참고 위치다. 이 요약만으로도 범위를 검토할 수 있으며 최신 원격 소스 링크로 취급하지 않는다.
