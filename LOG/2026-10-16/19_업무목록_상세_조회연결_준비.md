# 19. 업무 목록·상세 조회 연결 준비

기록일: 2026-10-16

[LOG 목록](../../README.md) · [17. alpha·0.0.2V 동기화](17_알파_0.0.2V_동기화.md) · [18. 합의문서·Word 정리](18_합의문서_최신화와_Word_정리.md)

## 변경 이유와 범위

사용자는 현재 alpha 구조를 유지하면서 2번 담당의 업무 목록·상세 연결을 시작하도록 요청했다.
먼저 1번의 인증 사용자·공통 HTTP·오류 응답·DB 규약을 확인하고, 계약이 없으면 인터페이스와 명시적 테스트 대역까지만 준비하는 조건이었다.
착수 전에는 업무 목록·상세가 고정 예시였고, 행 선택과 상태 필터가 조회에 연결되지 않았다.
이번에는 읽기 경계와 화면 표시를 연결했으며 실제 서버 연동이나 업무 처리 기능 완료로 보고하지 않는다.

## 공통 규약 감사와 확정 기준

- 착수 기준 alpha `2cd1a327`·DOCX `958f89ef` 및 로컬 2차 프로젝트에서 공통 인증·통신·서버·DB 계약을 찾지 못했다.
- `PreviewRole`과 이름·사번은 화면 예시이며 인증 사용자나 권한이 아니다. 외부 팀원의 별도 작업 유무는 이 감사로 단정하지 않는다.
- 계획서의 GET 경로·DTO·테이블은 제안이다. 예시 식별자·상태명을 실제 PK·저장 코드·API 규격으로 확정하지 않았다.
- 단일 업무 상태 **진행전 / 진행중 / 제출완료 / 승인완료 / 반려완료**와 기본 행동별 전환은 확정 기준으로 유지했다.
- 직원·관리자의 정식 제출·재제출은 모두 관리자 판단이 필수이며 승인완료만 최종 완료다. 관리자 본인 제출본은 상위 검토자가 판단한다.
- 마감 경과에 따른 자동 제출은 제외한다. 상태 코드·연결 규격·반려 후 복귀 시점 등은 합의 필요로 남겼다.

## 현재 반영한 구조와 화면

| 구분 | 반영 내용 |
|---|---|
| 기존 구조 | `LoginForm → MainForm → TasksControl` 및 표준 `.cs`·`.Designer.cs`·`.resx` 구조 유지 |
| 읽기 경계 | Tasks 내부 `ITaskQueryService`, 화면용 조회 모델과 실패 분류 추가. 공통 서버 계약을 대신 확정하지 않음 |
| 기본 실행 | `UnconfiguredTaskQueryService`로 조회 연결 필요 표시. 업무·첨부 예시로 자동 대체하지 않음 |
| 테스트 대역 | 생성자에 명시적으로 주입한 `TaskQueryTestDouble`만 사용. 데이터 출처를 화면에 계속 표시 |
| 목록·상세 | 목록 응답 표시, 선택한 행의 불투명 업무 ID로 상세 조회. 관리자 내 업무/관리 업무 조건 전달 |
| 상태 필터 | 전체와 5개 업무 상태를 조회 조건으로 전달. 테스트 대역에서 조건별 목록 표시 |
| 조회 상태 | 로딩·빈 목록·미연결·인증 만료·권한 없음·미존재·서버 오류를 구분하고 다시 조회 제공 |
| 늦은 응답 | 취소 토큰과 요청 세대로 이전 목록·상세 응답 무시. 선택 ID와 다른 상세 응답도 표시하지 않음 |
| 정리 | 새 조회·실패·선택 변경 시 이전 상세를 정리하고, 화면 종료 시 진행 중 요청 취소 |
| 첨부·처리 창 | 첨부 조회는 미연결로 비움. 기존 처리 창은 선택한 업무와 연결되지 않은 정적 화면임을 안내 |

`TaskDisplayStatus`는 화면용 논리값이며 서버 저장 코드가 아니다. 조회 범위 선택도 권한 증거가 아니다.
등록·수정·취소·수락·요청 저장과 3번의 결과 제출·재제출·버전·승인·반려·파일·이력, 4번의 협업·알림 저장은 구현하지 않았다.

## 검증 결과와 한계

| 구성 | 빌드 경고/오류 | 시나리오 | 검증 |
|---|---|---|---|
| Debug | 0 / 0 | 6개 통과 | 47개 통과 |
| Release | 0 / 0 | 6개 통과 | 47개 통과 |

- `Tests/TaskQueries.Tests`는 실제 `Application.Run` 메시지 루프와 WinForms 동기화 컨텍스트에서 실행했다.
- UI 스레드 교차 접근 검사를 활성화하고, 기본 실행과 명시적 대역·필터·선택·빈 목록·오류·재시도를 확인했다.
- 취소를 무시하고 늦게 도착하는 목록·상세 응답, 잘못된 상세 ID, 종료 중 응답을 검증했다.
- 기본 미연결·대역·오류·최소 크기 등을 PNG 13개로 생성하고 대표 화면을 시각 검수했다.
- 위 수치는 이번 조회 준비 검증이다. 이전 347개 화면 뼈대 검증 등과 합산하지 않는다.

| 실제 서버에서 필요한 권한 검증 | 현재 결과 |
|---|---|
| 직원 own 목록이 현재 본인 배정만 반환하고 필터로 범위가 확장되지 않음 | 미구현·미실행 |
| 관리자 own 목록은 본인, managed 목록은 허용된 관리 범위만 반환함 | 미구현·미실행 |
| 직원·관리자가 범위 밖 업무 ID로 상세에 직접 접근하는 우회 차단 | 미구현·미실행 |
| 인증 누락·만료와 범위 위조에 대한 서버 거부 | 미구현·미실행 |

테스트 대역의 Own/Managed는 고정 데이터 집합이며 사용자 인증·권한 매핑이 아니다.
실제 HTTP·공통 인증·DB 조회/저장·실제 서버 중단/인증 만료·두 PC·웹 통합은 실행하지 않았다.
화면에서 오류를 재현한 결과를 실제 서버의 수평 접근 통제나 통합 검증 완료로 해석하지 않는다.

## 남은 합의와 게시 근거

| 연결 담당 | 먼저 확인할 내용 |
|---|---|
| 1번 | 서버 실행법·주소, 사용자 PK·인증 컨텍스트, 공통 HTTP·응답/오류, 실제 GET 규격·페이지·날짜·관리 범위 |
| 1번·3번 | 상태 저장/응답 매핑, 행동별 상태 연결, 상위 검토자 권한·조회, 반려 후 재작업 복귀 시점 |
| 3번 | 별도 검토 요청 의미, 자동 검토 요청 도입·조건·중복 기준, 연장 신청/반영 조건, 마감 후 직접 제출 조건 |

공통 계약을 받은 뒤 실제 어댑터를 연결하고, 서버의 목록·상세 직접 접근 권한과 통합 흐름을 별도로 검증한다.
코드 게시본은 [커밋 8f09183](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/commit/8f09183ef992606ec4c2b7e3da79ef07983ba019)이며 alpha와 기존 `0.0.2V` 대상이 같은 커밋으로 확인됐다.
문서 게시본은 DOCX `5ee0998b81c6519b60fd380ac46c719d67a63d80`이며 태그 동기화와 Word 정리는 각각 17·18번 기록을 따른다.
코드 diff 16개는 Tasks 2개·Queries 6개·Tests 3개·README 1개·Preview 4개이며, 다른 담당 기능 소스나 공통 인증·서버·DB 코드를 추가하지 않았다.
검증 근거는 작업 감사자료 `code-verification.json`, `published-verification.json`, `code-changed-paths.json`과 해당 커밋 diff다.
원격 alpha·태그 대상·DOCX 및 파일 트리 일치 검증 후의 후속 기록이며, 이번 LOG 게시가 코드·태그·DOCX를 다시 변경하는 것은 아니다.
