## W1-01~04 — 쓰기 계약 제안과 실제 지원 구분

### 오류·입력·응답 제안

- 기존 공통 `401 AUTH_REQUIRED`(접속 만료/폐기/비활성), `403 FORBIDDEN`(현재 인증은 유효하지만 행동 권한 부족), `400 INVALID_INPUT`을 재사용한다. 재확인 시 비활성 수행자는401, 배정 후보가 비활성인 경우는 별도 입력/충돌 조건으로 구분한다.
- **미구현 제안:** `409 TASK_VERSION_CONFLICT`, `409 TASK_ASSIGNMENT_CHANGED`, `409 TASK_STATE_CONFLICT`, `409 IDEMPOTENCY_KEY_REUSED`, `409 ASSIGNEE_UNAVAILABLE`. 동일 멱등키·다른 본문은 성공으로 재사용하지 않는다. 존재/권한 오류는 M1의 TASK_NOT_FOUND404와403 구분을 보존한다. 후보 비활성의 HTTP/code와 충돌 우선순위는 2·3번과 확정할 항목이다.
- 예상 버전 검사는 타입·범위·현재 값의 세 단계로 처리한다. BIGINT 문자열은 부호/공백/소수 없는 양수, 최댓값9223372036854775807, 배정 차수 최댓값2147483647인 안이다. Python bool을 정수로 허용하지 않는다. 이 표기를 기존 읽기 DTO에 추가할지, 별도 쓰기 준비 DTO로 제공할지는 아직 결정하지 않았다.
- 성공 응답은 공통 `data` 아래 행동 결과와 서버의 확정 버전·배정 차수를 주는 방향이다. 실제 필드명·HTTP201/200·동일 행동 재요청 성공/충돌 표는 2번 API 제안 및 3번 제출/판단 계약을 대조해 확정한다. **아직 호출할 수 있는 업무 쓰기 경로는 없다.**

### 권한·잠금·원자성

[현 auth.py][auth]의 순서는 admin guard → 수행 User → AuthSession → 대상이며 `with_for_update()`와 `populate_existing=True`로 재확인한다. 이를 관리자 작업에 재사용하되, 일반 직원에게 관리자 권한을 요구하는 우회는 하지 않는다. [transaction][db]은 commit/rollback 도구이며 권한 검사 자체를 해 주지 않는다.

1번 공통 지원 설계안은 **guard/사용자·접속 잠금과 현재 인증 재확인 → 행동 대상·현재 배정/관리 관계의 잠금 조회 → 행동별 권한·예상 버전·상태 검사 → 쓰기·버전 증가·UTC updated_at·감사 → 한 번 commit**이다. 사용자 잠금 순서·다중 사용자 ID 정렬·재배정/지정 관리자 변경과의 공통 순서·존재하지 않는 관계행의 경합 처리는 2·3번의 모든 쓰기 경로와 함께 맞춰야 한다. 이 순서 초안만으로 deadlock 방지나 역할 회수 동시성 해결을 보증하지 않는다. 기존 snapshot/ORM 객체를 재사용해 최신 권한으로 간주하지 않는다.

현재 배정 당사자/지정 관리자는 서버의 현재 관계로 판정한다. 재배정은 새 revision 행과 현재 포인터를 함께 저장하고 과거 제출 소유를 덮어쓰지 않는다. 002에는 `row_version`, `created_at`, `updated_at`의 서버 기본값이 없으므로 서비스가 명시적으로 기록해야 한다. 실패/rollback은 성공 감사로 남기지 않는다. audit action/resource/details는 2·3번이 행동별 초안을 내고 1번이 공통 형식·비밀/본문 포함 여부를 검토한다. ID·변경 필드·전후 버전 중심으로 제한하고 파일 내용·비밀번호·토큰은 제외한다.

### 멱등성·응답 유실

현재 [ApiClient][client]는 자동 쓰기 재시도를 하지 않으며 임의 요청 헤더를 추가하는 공개 인자도 없다. 버튼 잠금만으로 서버 중복 저장을 막았다고 안내하지 않는다. 서버에 성공했을 수 있는 통신 실패는 ‘실패 확정’과 구분하고 같은 작업을 새 요청으로 무조건 재전송하지 않는다.

공통 저장소는 1번 담당으로 제안한다. 키 범위는 **수행 사용자·행동·대상·요청 키**, 본문 지문에는 예상 버전/배정 차수도 포함하며 결과·업무 변경은 같은 트랜잭션으로 저장하는 방향이다. 보존 기간·키 길이/형식·계정 전환·진행 중 중복의 응답·결과 재조회 경로·재전송 시 권한 재확인은 1·2·3번 미합의다. 만료 후 재전송 위험까지 정한 뒤 코드로 제공한다. 새 공통 테이블의 migration 번호는 002/003에 끼워 넣지 않고 별도 조정한다.

## 이번 검증·게시·남은 항목

실행 코드의 위 함수·API/DTO·002 SQL과 최신 요청의 대응을 정적으로 확인했다. 이번 문서의 경로·링크·표·W1 전 항목·차이/게시 범위를 검사한다. 프로그램 테스트/빌드·MySQL SQL/복구·실제 HTTP·공유 DB·두 PC를 이번 회신에서 재실행하지 않았다. 2번의 이전 테스트 보고를 1번의 새 실행 결과로 사용하지 않는다.

문서는 포크 LOG → 원본 LOG 검토 대상으로 게시한다. 문서 게시가 코드 수정/원본 병합/공동 합의는 아니다. 관련 코드 PR은 이번에 없으며, 후속 공통 지원 코드가 구현되면 커밋·검증·PR을 이 표에 추가해야 한다. 날짜별 기록은 팀장 전달용 로컬 요약으로 준비하고 `LOG/날짜/`에는 게시하지 않는다. 관련 공지 migration 조정은 [N4 회신](2026-10-17_공지DB_API_DDL_협의회신.md)과 함께 확인한다.
