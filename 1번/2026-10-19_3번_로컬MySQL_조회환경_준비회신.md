## 1. 별도 로컬 개발 환경 준비

기준 코드는 원본 alpha `a8d368ef06d284e0c554746d696e9ce4202304e2`를 포함한 최신 소스다. 3번의 미게시 로컬 화면 변경은 보존하고 최신 원본과 결합한다. [기존 SETUP][setup]을 기본으로 하되 아래 명시적 업무 활성화·SQL 순서를 추가한다. Windows·Python 3.11 이상·.NET8 SDK·MySQL과 mysql CLI가 필요하다.

기존 서버·DB를 재사용하거나 덮어쓰는 절차가 아니다. 별도 개발 소스 사본과 **새 DB 이름**을 사용한다. 아래 SQL은 MySQL 관리자가 새 전용 DB/계정을 만들 때 한 번 실행하며 비밀번호 예시는 자기 값으로 바꾼다.

```sql
CREATE DATABASE remote_work_member3_dev
  CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'rw_member3_dev'@'127.0.0.1'
  IDENTIFIED BY '<별도로_정한_긴_DB비밀번호>';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, INDEX, ALTER, REFERENCES
  ON remote_work_member3_dev.* TO 'rw_member3_dev'@'127.0.0.1';
```

이미 같은 이름이 있으면 멈추고 다른 새 이름을 정한다. DROP/기존 자료 초기화는 하지 않는다. 프로젝트 루트에서 `RemoteWork.Server`로 이동하고, 전용 가상환경이 없을 때만 생성한다.

```powershell
Set-Location .\RemoteWork.Server
if (-not (Test-Path .\.venv\Scripts\python.exe)) { python -m venv .venv }
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

`.env`가 없을 때만 `.env.example`을 복사한다. 기존 파일을 덮어쓰지 않는다. `.env`에는 새 DB의 MYSQL_HOST/PORT/USER/PASSWORD/DATABASE, 별도 무작위 32자 이상 SECRET_KEY, `HOST=127.0.0.1`, `PORT=5103`을 설정한다. `DATABASE_URL`이 이미 있다면 MYSQL_*보다 우선하므로 다른 DB를 가리키지 않는지 확인한다. 실제 값은 로컬에서만 보관한다.

## 2. 공통 초기화 → 002/004 → 계정 생성

첫 초기화 때는 기능 모델을 공통 init-db에 섞지 않는다. 같은 PowerShell에서 다음을 실행한다.

```powershell
$env:REMOTEWORK_ENABLE_TASK_QUERY_DRAFT='0'
$env:REMOTEWORK_ENABLE_COMMON_WRITE_DRAFT='0'
$env:REMOTEWORK_ENABLE_TASK_CREATE_DRAFT='0'
$env:REMOTEWORK_ENABLE_NOTICE_DRAFT='0'
$env:REMOTEWORK_ENABLE_CHAT_DRAFT='0'
.\.venv\Scripts\python.exe -m flask --app remotework init-db
```

그다음 **새 개발 DB임을 확인한 뒤** mysql에 접속해 아래 두 검토용 SQL만 순서대로 적용한다. 실행 폴더는 계속 `RemoteWork.Server`다. mysql 경로가 PATH에 없으면 설치 경로의 mysql.exe를 사용한다. 비밀번호는 mysql이 묻는 창에 입력한다.

```powershell
mysql --host=127.0.0.1 --port=3306 --user=rw_member3_dev --password --default-character-set=utf8mb4 --database=remote_work_member3_dev
```

```sql
SELECT DATABASE();
source migrations/002_task_queries.mysql.sql;
source migrations/004_write_receipts.mysql.sql;
exit;
```

중간 오류가 나오면 다음 SQL/단계를 진행하지 말고 중단한다. MySQL DDL은 한 트랜잭션으로 원복되지 않는다. 기존 테이블에 반복 적용하거나 init-db를 ALTER 대용으로 사용하지 않는다. 003/005·예약006은 이번 업무 조회 준비에 필요하지 않다. 전역 schema version은 1 유지다.

관리자 아이디는 사용자 요청에 따라 `admin`으로 통일한다. 아래 비밀번호는 각 PC의 소유자가 숨김 입력으로 지정한다. 사용자 PC에서 준비한 비밀번호를 문서에 복제하거나 다른 DB에 자동 배포하지 않는다. 일반 생성 규칙은 10~128자다.

```powershell
.\.venv\Scripts\python.exe -m flask --app remotework create-user --login-id admin --display-name 개발관리자 --employee-no M3-ADM --department 개발팀 --role admin
.\.venv\Scripts\python.exe -m flask --app remotework create-user --login-id m3-staff --display-name 개발직원 --employee-no M3-EMP --department 개발팀 --role employee
```

이미 존재하는 아이디라면 삭제/재생성하지 말고 기존 소유자·계정 상태를 확인한다. 공통 계정과 업무 계정이 따로 있는 구조가 아니다.

## 3. 업무 기능을 명시 활성화하고 실제 등록·조회

위 단계가 성공한 같은 PowerShell에서 다음을 실행한다. query만으로 조회는 가능하지만, **기존 생성 기능으로 검증 업무를 만들기 위해** common/create도 함께 켠다. flags는 이 프로세스의 개발 설정이며 공유 활성화 승인이 아니다.

```powershell
$env:REMOTEWORK_ENABLE_TASK_QUERY_DRAFT='1'
$env:REMOTEWORK_ENABLE_COMMON_WRITE_DRAFT='1'
$env:REMOTEWORK_ENABLE_TASK_CREATE_DRAFT='1'
.\.venv\Scripts\python.exe -m remotework.features.tasks.readiness
if ($LASTEXITCODE -ne 0) { throw '업무 조회 선행 조건을 먼저 확인하세요.' }
.\.venv\Scripts\python.exe run.py
```

새로 받은2번 readiness는 **그 명령 프로세스의** GET 등록·MySQL·필수 테이블/열·버전1·참조 누락만 읽는다. 성공 JSON도 전체 DDL·실제 계정별 권한·이미 켜진 서버를 검증한 것이 아니다. 실패 시 DDL/샘플을 자동 생성하지 않으므로 해당 단계부터 확인한다. [점검 명령 설명](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/8c297a06f7ead4a1e5f14a25fb3f09a78f034224/docs/TASK_QUERIES.md)을 따른다.

이 서버를 켜둔 채 새 터미널의 프로젝트 루트에서 최신 WinForms를 실행한다. 이전 Desktop 실행본은 최신 소스와 다를 수 있다. 소스를 받은 것만으로 이미 실행 중인 서버 프로세스가 갱신되는 것은 아니다.

```powershell
dotnet run --project .\RemoteWork.WinForms\RemoteWork.WinForms.csproj
```

서버 연결 설정은 **`http://127.0.0.1:5103/` 서버 루트**다. 이 주소는 자기 PC용이며 타 PC의 서버 주소가 아니다. `/api/v1`은 공통 클라이언트가 붙인다.

1. `admin`으로 로그인한다. 기존 업무 등록 화면에서 담당자가 `m3-staff`인 업무 A와 담당자가 `admin`인 업무 B를 각각 명시적으로 등록한다. 생성자가 필수 관리자로 포함된다. 자동 샘플/DB 직접 seed는 하지 않는다.
2. 직원 own에는 A, 관리자 own에는 B, 같은 관리자가 지정된 managed에는 A·B가 보이는지 확인한다. 다른 실제 자료가 있으면 기대 범위에 함께 포함해 대조한다. 서버 목록은 `data.items`이며 이 업무 API에 page/limit/total을 임의 추가하지 않는다.
3. 직원의 A 상세는 허용되고 B 상세는 거절돼야 한다. 조회할 업무가 없으면 정상 빈 목록으로 확인한다. managed를 실제 제출 검토자 권한으로 해석하지 않는다.
4. 기존 업무 화면으로 접속/조회가 확인된 뒤 3번 로컬 ReviewsControl의 동일 API 연결을 확인한다. 3번 미게시 화면 코드는 이번 1번 검증 대상에 없으므로 성공했다고 대신 보고하지 않는다.
5. 생성 직후는 진행전이다. 진행중 업무를 만들기 위해 DB 상태/accepted_at을 직접 바꾸거나 아직 없는 수락·제출을 성공으로 표시하지 않는다. 수락·재작업은 현재 읽기 전용 대상 확인까지만 제공한다.

진단은 health→로그인→own/managed→상세 순서로 한다. health200만으로 업무 기능 준비가 증명되지 않는다. 401은 인증, 403은 권한, 404는 주소/기능 등록, 503은 DB/테이블·기능 준비를 각각 확인한다. 조회 오류를 빈 목록으로 바꾸지 않는다.

## 이번에 실제 검증한 범위

- 최초 결합 기준 a8d368e의 별도 소유 MySQL8.2/RR에서 등록18·raw002/005/실제 dump/새 DB 복원6·채팅 ORM/실제 물리 옵션2·순수 KST 날짜39, **총65개 통과**, 실패/skip/선택제외0(22.61초). `python -m pytest -q tests/test_task_creation.py tests/test_task_creation_migration.py tests/test_chat_migration_draft.py tests/test_chat_collation.py tests/test_task_start_dates.py`. 그 후 기존 서버 파일 변경 없이 readiness와 해당 검사만 추가됐음을 Git으로 대조했다.
- 최신2번 `tests/test_task_query_readiness.py` **27통과(0.97초)**. 대역·비DB 경계·콜드 import 검사이며 MySQL 실행기 아래 돌렸다는 이유로 실제DB27건으로 표현하지 않는다.
- 별도 새 소유 MySQL에서 **추가 검증 1개 통과(내부24검사, 7.70초)**: 새 프로세스 공통 init-db만 생성→raw002/004→동일 create-user CLI의 Click 입력 runner→readiness 빈DB→Waitress 실제 TCP 로그인→기존 등록 API로 두 업무 생성→직원/관리자 own·managed/상세/403·문맥→readiness 두업무→최초 상태/수락 시각·로그아웃. readiness는 실제MySQL에2회 실행했다. 내부24개를 테스트1개와 중복 합산하지 않는다.
- 비대화형 Windows getpass의 콘솔 대기와 검사기가 기대한 잘못된 total 필드 때문에 초기 검증기가 실패했다. 검증기를 보완해 통과했으며 제품 인증/업무 코드는 변경하지 않았다. 실제 사람의 숨김 콘솔 입력·mysql 대화형 콘솔·3번 WinForms/물리 두 PC 시험까지 자동 검증했다는 뜻은 아니다.
- 사용자 PC에서는 일반 규칙으로 `admin` 생성 후 실제 서버 로그인·관리자 조회200, 업무 주소404를 확인했다. 기존 서버를 재시작하거나 업무 DDL/flag를 적용하지 않았다. 테스트용 DB/프로세스만 정리했다.

실제 공유 IP/가동 시간·직원/관리자 비공개 전달·공유 DDL/백업/복구·두 PC, 실제 ReviewsControl 및 제출/판단/파일/이력은 아직 별도다. 3번은 자기 PC 결과를 **기준 SHA / 초기화·계정 준비 여부 / own·managed 기대/실제 / 실행 명령 / 실패 단계 / 남은 범위**로 회신해 달라. 날짜 LOG는 게시하지 않고 로컬 팀장 전달 요약만 준비한다.
