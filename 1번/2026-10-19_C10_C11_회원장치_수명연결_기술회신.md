## 1. 메시지와 MAC — 바이트 수정안

HMAC은 공유키로 메시지를 인증하는 도구다([RFC2104](https://www.rfc-editor.org/rfc/rfc2104)). 이것을 전송 암호화·nonce 소비·실물 신원/장치 무결성 보장과 동일시하지 않는다. 제품 양 구간은 인증서를 검증하는 TLS로 준비하고 실제 키는 서버/Pi의 비공개 설정에만 둔다. 키를 보유한 장치가 침해되면 스캔 결과도 위조될 수 있다는 신뢰 경계를 유지한다.

**다음은 검토용 v1 수정안이며 아직 공동 확정 API가 아니다.** 외부 envelope는 `v,kind,device_id,key_id,payload_b64,mac_b64`만 허용한다. v는 JSON정수1, kind는 request/result, device_id는 서버 발급 소문자 UUID, key_id는 NUL 없는 `[A-Za-z0-9_-]{1,64}`다. MAC은 HMAC-SHA256 전체32바이트·패딩 없는 canonical base64url43자로 제안한다. JSON 중복/미지 필드·bool을 정수로 사용·NaN/Infinity·잘못된 UTF-8·공백/패딩/비정규 base64url은 거절한다. envelope·payload 최대 길이는 고정하고 공통32KiB를 늘리지 않는다.

```text
MAC 입력 = ASCII("RW-ID-v1") || 0x00 || ASCII(kind) || 0x00
         || ASCII(device_id) || 0x00 || ASCII(key_id) || 0x00
         || ASCII(payload_b64)
```

payload_b64는 발급한 UTF-8 JSON 원문 바이트를 감싼다. 중계PC가 JSON을 재직렬화하거나 숫자/시각을 변환하지 않는다. MAC 검증 뒤에도 필드/의미·현재 대상 관계를 검사하고 route가 기대한 kind와 일치해야 한다. key_id/device는 비밀키 조회 후보일 뿐 권한이 아니다. MAC 비교는 동종 바이트의 상수시간 비교를 사용한다([Python hmac](https://docs.python.org/3/library/hmac.html)).

- 티켓: challenge_id UUID·128bit 이상 nonce·mapping_revision 정규 BIGINT 문자열·purpose·issued_at/expires_at 서버UTC·불투명 접속 참조를 결합. 실제 회원은 현재 서버actor로 정하며 이름/점수·클라이언트user_id로 선택하지 않는다. 복수 매핑 선택이 필요하면 서버가 본인의 현재 허용 목록을 제공하고 클라이언트는 그 ID만 선택한다.
- 결과: challenge_id/nonce·mapping_revision·ticket_digest·고정 result_id·outcome·실제 slot을 결합. ticket_digest는 위 티켓 MAC 입력 바이트의 SHA256 등 **정의된 바이트**로 고정해 JSON envelope 공백 차이로 달라지지 않게 한다. 성공 matched에서만 엄격한 비음수 slot, 실패는 slot null·고정 실패 분류를 제안한다. 점수/실명/원본 지문은 증거 필드에서 제외한다. 실제 최대 슬롯은 하드웨어 회신 후 검증한다.
- 장치별 무작위32바이트 이상 키·key_id를 사용한다. 관리자 비밀번호·공통 SECRET_KEY·지문을 장치 키로 전용하지 않는다. 요청/결과 domain 분리는 필수이며 방향별 키를 HKDF-SHA256의 다른 info로 파생하는 안도 제안한다([RFC5869](https://www.rfc-editor.org/rfc/rfc5869)). 운영 root/파생키 형식·키 저장/배포·교체/폐기는1번/5번이 고정한다. 공개 벡터 키를 운영 키로 쓰지 않는다.

5번이 제안한 서버 challenges/complete 및 Pi identity/scan 경로는 이름 방향을 기술적으로 수용한다. 아직 등록된 경로가 아니며 새 DTO/오류명/상태 enum·실행 flag·보관 기간은 최종 명세에 함께 고정해야 한다. 인증된 현재 수행자와 기존 envelope를 재사용하고 지문으로 새 Bearer를 발급하지 않는다.

## 2. 중복·소비·만료·스캔 제한 수정안

1. 서버 challenge는 pending→검증된 terminal 완료를 같은 guard/actor/session 재확인·장치/키·매핑/challenge 잠금 트랜잭션에서 한 번 소비한다. 검증된 matched/no_match/센서 terminal 오류의 최초 결과는 불변으로 보존하는 안을 제안한다. **변조 서명·알 수 없는 장치/다른 actor가 보낸 결과로 정상 challenge를 소비시키지 않는다.** 전송 실패/장치busy/pending은 완료 성공으로 저장하지 않는다.
2. 같은 challenge+동일 인증 결과 바이트의 재전송은 최초 최소 결과, 다른 인증 결과는 충돌. nonce/resultId/digest 유일성만으로 현재 접속/키/매핑을 생략하지 않는다. 완료 상태를 먼저 확인하지 않고 새 스캔·새 result_id를 반복 만들지 않는다. 결과 보관과 조회 유효 기간·실패 소비 기준은 명세로 회신해 달라. 공통24시간 receipt를 모든 장치 완료에 무조건 복제하지 않는다.
3. Pi도 challenge별 in-flight/완료를 구분한다. 같은 티켓 재전송은 진행 중 상태 또는 **같은 인증 결과 바이트**를 반환하고 두 번째 물리 스캔을 시작하지 않는다. 실제 스캔 재시도는 새 challenge로 한다. 스캔 취소가 하드웨어 동작 중단을 자동 보장하지 않으므로 재진입·재연결도 관리한다.
4. 서버 유효성은 서버 시각·현재 접속·mapping revision/key 상태가 최종 근거다. Pi가 요청 MAC만 검증해도 만료/재사용이 해결되는 것은 아니다. 장치 재시작 시 중복 캐시가 사라지는 조건, 시계 불확실 시 처리·trusted 시간 또는 서버 freshness 확인 방법을5번이 제안해야 한다. 그전에는 오프라인 성공을 인증 결과로 승격하지 않는다. Pi 시각을 서버 만료 판정으로 사용하지 않는다.
5. 떼기/올리기 각15초와 공통HTTP12초 차이를 수신했다. **공통 HTTP timeout을 늘리지 않는 방향 수용.** Pi 전용 비동기 작업 시작→짧은 상태 조회/결과 회수 또는 별도 전용 timeout/취소를 검토한다. 서버TTL60초는 후보이며 발급/전달·최대스캔·결과회수·완료전송 여유를 함께 계측하고 정한다. 스캔을 공통DB 트랜잭션 안에서 기다리지 않는다.
6. 키 교체·폐기/매핑 교체는 새 키/epoch 준비→새 티켓 사용 전환→기존 pending 무효화·완료 효력 재검사 순서를 모델로 정의한다. 실물 센서 등록/삭제와DB는 원자적이지 않다. 기존 활성 슬롯 소유권을 먼저 차단하고 pending 등록/검증 단계를 거쳐 active로 전환하며 중간 실패를 기존 성공으로 되돌리지 않는다.

최초 pending 완료에는 만료를 검사한다. 이미 완료된 동일 결과의 조회는 별도 보관 창과 현재 접근 권한에 따라 **과거 결과**를 반환하는 계약으로 분리하고, 조회로 확인 시각·효력 만료를 갱신하거나 새 인증 효과를 만들지 않는다. 보관 창/성공 효력의 길이는5번·팀장 회신이 필요하다. 같은 티켓/장치/현재접속의 유효 서명이지만 검색 슬롯이 본인 매핑과 다르면 본인확인 실패로 terminal 소비하는 안을 제안한다. 이를 타인으로 계정 전환하거나 다른 슬롯의 이름을 반환하는 근거로 쓰지 않는다. 잘못된 서명/다른접속에 의한 소비 금지와 구분한다.

실패는 인증401·현재 관계/권한403·대상404·동일 challenge 다른 결과/상태409·만료410·장치/스키마미준비503 방향으로 구분하되 새 code 문자열은5번 구체안과 대조한다. 인증 실패 때문에 사용자 자료/키 존재 여부를 불필요하게 노출하지 않는다. 키·토큰·nonce/티켓/결과 원문·생체 자료를 일반 감사에 넣지 않는다.

## 3. 근무 세션 서비스와 MainForm 최소 접점

현 MainForm은 메뉴마다 currentPage를 Dispose하고 인증 만료/종료를 소유한다. 현 활동창은 닫을 때 카메라/조도 소스를 종료한다. 따라서 현재 모달에 타이머만 추가해서 메뉴와 독립적인 근무 수명을 만들었다고 표시할 수 없다.

- **소유 단위:** 실제 로그인된 MainForm 한 개가 해당 CaptureSession에 묶인 monitor/service 한 개를 소유하는 안을 기술 수용. 전역 static에 계정별 worker를 두지 않는다. 5번 Attendance에 구체 구현·인터페이스/대역을 준비하고 MainForm에는 생성/연결·중지/해제 접점만 주입한다. 미리보기/Designer 기본 생성자는 네트워크·센서를 시작하지 않는다.
- **시작·메뉴:** 서버 출근 저장 성공과 work_session_id 확인 뒤 정확히 한 번 시작한다. 지문 성공만으로 출근 저장을 대체하지 않는다. 메뉴는 상태 구독 view일 뿐이며 전환/창 닫기는 worker를 다시 만들거나 근무 감지를 끝내지 않는다. 독립 수동 점검 모드는 기존 종료 동작을 별도로 보존한다.
- **퇴근·종료:** 서버 퇴근 성공 뒤 근무 monitor 종료. 로그아웃/세션 취소/만료/서버 전환/앱 종료는 먼저 generation을 무효화하고 이후 bounded StopAsync를 한 번만 공유해 센서/파이프를 정리한다. 이것을 서버 퇴근으로 자동 저장하지 않는다. 불명 출퇴근 응답은 같은 작업/결과 확인으로 복구하고 새 키/재출근을 자동 실행하지 않는다.
- **UI/경합:** CaptureSession.IsCurrent + monitor instance/generation + work_session_id + Form 생존을 확인한 후 UI SynchronizationContext.Post로 알린다. 취소 콜백에서 UI 동기 Invoke/.Wait/.Result를 사용하지 않는다. 늦은 결과·이전 계정·동일 계정 재로그인·중지 뒤 재시작을 구분한다.
- **MainForm 변경 한계:** 기존 AuthenticationExpired→owned form 정리→안내→로그인 복귀·SignOutOnClosing의 단일종료/Logout 흐름을 교체하지 않는다. 새 수명 접점은1번/공통 화면 담당이 별도 diff와 회귀를 보고 연결한다. 5번이 MainForm/ApiClient/auth 전체를 바꾸는 승인은 아니다. LoginForm·공통ApiClient/DB 코드 수정은 현재 필요하다고 확정하지 않았다.

실제 출퇴근/연차 API·work_session 모델·시작 전 확인 조건·성공 유효기간·재로그인/재실행 복원·미종료 근무 처리·조회/보존은 **협의사항**이다. 서버 상태가 아직 없는 동안 mock monitor/고정 이벤트로 대역 시험은 준비할 수 있지만 실제 출근/퇴근/백그라운드 근무 기능 완료로 표시하지 않는다. 활동중/자리비움/연결오류를 자동 결근·퇴근·업무 상태 변경으로 저장하지 않는다.

## 4. DB/작성 책임과 다음 전달

1번은 공통 인증/guard/현재 관계·FK/타입·키/등록 경계와 MainForm 주입 접점을 검토·지원한다. 5번은 device/identity/attendance의 실제 모델·라우트/DTO·Pi 스캔/키 연동·monitor 구현과 시험을 작성한다. 새 모델은 가능하면 기능 모듈에 두고 공통 User/AuthSession을 복제하지 않는다. 기본off 모듈 import/행동 등록·독립초기화·현재 사용자 관계를 명시한다.

매핑의 현재 device+slot 단일 소유 행과 불변 이력, 장치/키 epoch·challenge/result 상태·work_session/근태 도메인을 분리하는 모델안을5번이 먼저 보낸다. 역사 결과는 만료 접속/24시간 receipt 정리 때문에 cascade 손실되지 않게 설계한다. 현재 접속 유효성은FK 존재만으로 판정하지 않는다. user FK INTEGER, mapping revision BIGINT 문자열·UUID 식별자 등의 타입은 선행안 유지. **SQL번호는 최종 모델 전 미예약**이며002~006을 재사용/수정하지 않는다.

5번이 먼저 회신할 것은 위 바이트/키 운영·장치 재시작/시계·중복 상태/결과 보관·전용 스캔 시간·모델/주입 인터페이스다. 팀장 결정은 등록/승인권·요청 주기/필수성·미응답 조치·출퇴근/정정/연차/보존 정책이다. 공동 결정 전 동작을 임의 연결하지 않는 최신2번 지침도 유지한다.
