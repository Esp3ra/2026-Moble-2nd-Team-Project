## W3-01/03 — 현재 흐름

not_started→본인수락→in_progress→최초제출성공→submitted→판단approved/returned. returned→본인재작업시작→in_progress→재제출성공→submitted다. 반려 직후·창 열기·편집으로 자동 복귀하지 않는다. 재작업 시작은2번, 제출/판단은3번이다. 최초/재제출은 현재 in_progress와 마지막 성공 제출/반려를 대조한다. 재작업은 최초 accepted_at·배정revision·제출 회차를 초기화/증가시키지 않는다. 상태별 일반 수정·재배정·취소·마감/연장 예외는 기존 공동 결정 항목을 유지한다.

## W3-02 — 같은 TX·잠금·버전·재응답 수용

1. 기존 authenticated_transaction의 guard→현재 수행자→현재 접속을 재사용한다. 협력하는2·3번 쓰기는 같은 guard를 반드시 사용한다. 이미 존재하는 대상은 부모 업무→현재 배정→정렬된 업무관리 관계→참조 사용자ID 오름차순→검토관계→제출/판단→첨부ID 정렬 순서로 현재 locking read/populate_existing을 맞춘다. 새 업무 등록은 기존부모가 없어 사용자 잠금 후 부모/배정을 생성하는 현재순서를 유지한다. guard 밖 수동 DB 변경까지 안전하다고 보증하지 않는다.
2. 판단 target이 submission_id라면 최초 비잠금 조회로 불변 parent task_id만 찾고, 부모부터 잠근 다음 제출을 다시 잠금/갱신해 같은 부모/배정인지 재확인한다. 자식을 먼저 잠가 순서를 역전하지 않는다. 현재 caller/관계 접근 검사를 마친 뒤 충돌 정보를 반환한다.
3. 등록 authorize는 현재 배정 당사자 또는 현재 활성 명시적 검토자 권한을 검사하고 정확히 True를 반환한다. 자기 판단은403. **상태·expected 버전·마감·유효 검토자 선행조건은 첫 mutate에 둔다.** 제출 성공 후 submitted가 되었다고 정상 재응답을 막거나 검토자 비활성 때문에 본인 성공 확인을 임의 무효화하지 않는다. 재응답/결과조회도 현재 수행자 접근 권한은 다시 검사한다.
4. ExpectedVersions로 assignment 불일치409 TASK_ASSIGNMENT_CHANGED→row 불일치409 TASK_VERSION_CONFLICT를 검사한다. 새 성공에서만 row_version을1회 증가·서버UTC updated_at 갱신한다. 제출/판단·재작업은 assignment_revision을 증가시키지 않는다. 버전/회차의 기술 상한은 증가 전에 검사해 wrap/초기화하지 않고 명시 오류로 중단한다.
5. 제출본/판단·업무상태·화면이력·성공감사·receipt를 동일 세션 한commit에 둔다. 예외면 모두 rollback. 같은키/같은본문은기존결과, 다른본문409, 만료410, 결과유실은기존action/target/key 조회. 파일I/O/네트워크/중첩commit을TX안에 넣지 않는다.

검토할 동시성: 2번수락/재작업/재배정/연장 vs3번제출/판단, 관계/역할회수, 동일키/다른키중복, 감사/receipt삽입실패, 실제MySQLRR에서옛 ORM snapshot. 현재 common 검사만으로 실제3번서비스 검증완료가 되는 것은 아니다.

## W3-04 — 타입·FK·회차·최소 결과

`POST /tasks/{task_id}/submissions`, `POST /submissions/{submission_id}/decisions`의제안형태는1번수용한다. 현재호출가능한경로라는뜻은아니다. 새 `submission.submitted` target=task_id, `submission.approved/returned` target=submission_id를기술수용하며첫제출/재제출은서버기록으로구분한다. 최소결과필드는 `task_id,submission_id,round_no,row_version,assignment_revision,task_status,updated_at`; 판단은 `decision_id`를추가할수있다. 본문·파일·사유·이름을receipt에넣지않는다. 각action별필수/타입은3번서비스가검사한다.

`register_write_action`을앱초기화에호출한다. 예를들어3번blueprint의record_once(state.app)에서정의한동일authorize함수와결과허용필드를등록할수있다. 미래 `ENABLE_RESULTS_DRAFT`/REMOTEWORK_ENABLE_RESULTS_DRAFT는기본off로제안하고 common-write/task-query 의존성을명시한다. registry의최소gated import변경을1번에게전달한다. common flag off인데모델을import하거나일반init-db에무조건제출모델을추가하지않는다. 콜드프로세스로조합별검사한다.

오류는공통401/403/400,대상없음404 SUBMISSION_NOT_FOUND/ATTACHMENT_NOT_FOUND,409 TASK_STATE_CONFLICT/REVIEWER_UNAVAILABLE/이미판단충돌·기존버전/키충돌,410키만료,503 DB/기능/스키마미준비로구분하는연결안을수용한다. 새code는실제서비스에추가/검증해야하며문서만으로응답이구현되지않는다.

## W3-05 — 검토자와 최소 열람

사용자는활성검토자미지정/비활성시**제출차단**기준을확정했다. 임의admin자동배정/제출후암묵대기는만들지않는다. 현재admin+업무지정관리자가제출자와다른활성admin1명을명시지정하는안은기존검토기준이다. 관리자본인제출의실제상위조직관계는팀장이확인하며단지다른admin이라는사실로대체하지않는다.

현재actor역할/활성·관계·배정/버전을저장직전에검사한다. 미판단제출의검토자교체시관계revision/업무row_version·이력동시갱신안수용,이전검토자열린창은거절한다. 자동대체없음. 자기승인/반려403은직원/관리자모두적용한다. 검토자전용조회는그대상제출ID·업무ID/제목·회차·설명·허용첨부·제출/판단시각·상태만,현재전체업무GET의403을풀지않는다. 과거판단후/관계회수후열람은공동정책전까지자동허용하지않는다.

## 첨부 — 승인된 개발 제한과 구현 경계

- 파일1개최대 **25MiB=26,214,400bytes**,제출당최대10개(중복ID거절),미연결임시업로드24시간뒤정리. 제출된첨부자동삭제없음. 실제운영보존기간은팀장·3번후속.
- 서버관리자가별도절대저장루트를설정하고static/프로젝트/Git밖에둔다. 미설정은503으로실패하고클라이언트PC경로/원본파일명을저장키로쓰지않는다. 불투명서버ID로저장·다운로드시현재소유/명시권한검사·attachment/nosniff를유지한다.
- 현재공통JSON본문제한32KiB를전체적으로25MiB로올리지않는다. **전용업로드경로만**업로드파일실측25MiB와multipart여유포함요청상한(예:26MiB),스트리밍·reverse proxy/서버상한을함께검증한다. 파일명·확장자/MIME는일치검사하며서버에서실행/인라인렌더하지않는다. 허용형식목록은3번파일안/팀장확인전미정으로명시한다.
- 파일기록은pending→ready·소유자·크기/해시·만료·불투명키를갖고,제출TX에서ready/현재소유·미만료·미사용상태를잠금확인해참조한다. 성공시연결된파일의제출원문/키를보존한다. 외부파일전송이DBrollback되는것처럼설명하지않는다.
- 정리작업은DB에서만료·미연결을잠금재확인하고삭제대상표시를commit한뒤파일I/O·재시도가능한완료표시로진행한다. 같은guard/정렬된첨부잠금으로제출과경합을조정한다. 이미연결된파일을단순mtime기준으로삭제하지않는다. 실패한파일단계/DB단계별재시도·고아정리·백업복구를시험한다.

## 화면용 이력·W3-06/07·다음 회신

2번은생성/수정/배정/수락/재작업/연장,3번은제출/재제출/승인/반려를각행동TX에기록한다. 한논리행동에안전한 operation_id UNIQUE·event_id BIGINT문자열,업무/배정·해당제출참조·actor_id·서버UTC·종류·허용상태전후/최소요약코드를권장한다. 24시간후삭제되는receipt에영구이력의필수FK를걸지않는다. 동일키재응답에서이력을다시추가하지않는다.
