# 4번 공지 DB 저장 연결 — 1번 등록·DB 협의 요청

작성: 4번 · 전달: 1번 공통 서버·DB 담당, 팀장 · 상태: 코드 Draft PR #7 게시·최신 결합 검증 완료 / 공지 API·DDL·공유 적용 미합의

## 배경과 범위

사용자가 오늘 구현한 공지 DB 저장·조회·삭제만 PR로 요청했다. 팝업·확인 기록·정렬 추가 조정은 제외한다. 초기 로컬 구현은 alpha9b8d00c에서 작성했고, PR은 최신 alpha 3b0948025c440b9d3a36da82f464b0bc08557493에 필요한 변경만 반영한다. 바탕화면 작업본은 덮어쓰지 않는다.

## 타 담당 파일 변경 전 확인

최신 registry는 get_blueprints(config) 지연 등록이며 업무는 ENABLE_TASK_QUERY_DRAFT 아래 기본 off다. 이를 예전 BLUEPRINTS 목록으로 교체하면 업무 연결을 잃으므로 기존 함수를 보존하고 공지를 별도 REMOTEWORK_ENABLE_NOTICE_DRAFT / ENABLE_NOTICE_DRAFT 선택으로 지연 추가한다. 공통 create_app/auth/ApiClient/MainForm/업무 코드는 변경하지 않는다.

## 변경 제안과 영향

- 공지 모델 notices는 공통 Base·users.id FK·UTC·트랜잭션·감사 기록을 사용한다. 등록/삭제는 기존 admin_transaction으로 수행자·접속·역할을 재확인한다.
- 제목·본문·대상·고정·작성자 ID/작성 당시 이름·시각·파일명 메타데이터만 보관한다. 파일 본문/로컬 경로 전송은 없다. 직원도 모든 부서를 조회한다는 사용자 결정을 유지한다.
- 명시적 활성화 전에는 공지 Blueprint/모델을 import하지 않는다. 활성화한 init-db는 새 테이블을 발견하므로 공유 DB에는 승인된 적용 순서가 필요하다. 요청 중 DDL·기존 데이터 삭제·스키마 버전 변경은 없다.
- 실제 번호가 예약된 업무002와 충돌하는 SQL 번호는 만들지 않는다. notices init-table은 로컬 개발용 명시적 CREATE 수단이며 공유 migration 승인을 대신하지 않는다.

## 확인 요청 / 합의 여부

공지 경로/DTO·users FK·작성자 이름 보존·POST 삭제 경로·migration 번호/버전 검사/백업/배포·기본 활성화 시점을 1번에게 확인 요청한다. 공통 프로토콜을 재사용한 사실과 공지 전용 계약이 팀 합의된 상태를 구분한다. 이 문서 작성은 승인 근거가 아니다. 공유 DB 적용은 하지 않는다.
