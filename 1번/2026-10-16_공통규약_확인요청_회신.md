서버의 공개 사용자 필드는 `id`, `login_id`, `display_name`, `employee_no`, `department`, `role`, `is_active`, `created_at`입니다. 현재 C# `UserInfo`는 이 중 업무상 사용하는 사용자 정보와 역할을 받으며 `created_at` 필드는 정의하지 않았습니다.

토큰은 무작위 접속 증표이며 JWT가 아닙니다. 원문 토큰은 클라이언트 메모리에만 보관하고 서버 DB에는 SHA-256 해시를 저장합니다. 기본 접속 시간은 발급 후 8시간이고 별도 refresh token이나 자동 연장은 없습니다. 만료·로그아웃·접속 폐기 후에는 재로그인합니다. 비밀번호 변경·초기화, 계정 비활성화, 역할 변경은 해당 계정의 모든 접속을 폐기합니다.

`PreviewRole`은 기존 기능 화면의 배치 선택에만 사용합니다. 로그인된 `UserInfo.Role`에서 화면 배치를 정하더라도 실제 권한은 Flask가 DB의 사용자·역할·활성 상태로 판단합니다. 클라이언트가 보낸 사용자 ID나 역할을 인증 근거로 사용하지 않습니다. 웹은 별도의 HttpOnly 쿠키 방식이며 API에 쿠키를 보내는 것으로 Bearer 인증을 대신할 수 없습니다.

**기존 조회 인터페이스는 유지할 수 있습니다.** 예를 들어 HTTP 구현 클래스가 생성자로 `ApiClient`를 받고, 화면을 구성하는 곳에서 `AppServices.Api`를 전달하는 방식입니다. `ITaskQueryService`, `TaskSummary`, `TaskDetail`과 `TasksControl`의 서비스 주입 생성자를 확인했습니다. 구체적인 HTTP 어댑터는 업무 계약을 확정한 뒤 연결합니다. 아직 2번 인터페이스에 주입한 상태는 아닙니다.

현재 동작하는 공통 API를 사용하는 예시는 다음과 같습니다. 관리자 로그인 후 호출하는 사용자 조회이며 업무 API 예시는 아닙니다.

```csharp
var api = AppServices.Api;
var page = await api.GetAsync<PageResult<UserInfo>>(
    "users?page=1&limit=20", cancellationToken);
var user = api.CurrentUser;
```

클라이언트 호출 경로에는 앞의 `/api/v1/`을 반복해서 붙이지 않습니다. 공통 클라이언트가 서버 루트에 `api/v1/`을 붙입니다.

## A4 본인·관리 범위와 목록·상세의 서버 권한

**상태: 합의 필요 — 공통 도구는 구현, 실제 업무 범위와 조회 검사는 미구현.**

근거: `remotework/auth.py`의 `login_required`, `remotework/common.py`의 `require_role`, `require_resource_access`, `grant_resource`, `models.py`의 `ResourceGrant`.

로그인 검사, 관리자 역할 검사, 사용자와 자원 간 grant 검사는 있습니다. 단, 이는 업무 배정·관리 범위 모델을 대신하지 않습니다. 현재 사용자의 `department`는 표시용 문자열이며 부서 PK·조직 계층·상위 검토자 관계는 구현되어 있지 않습니다.

**특히 현재 `require_resource_access(..., allow_admin=True)`는 관리자에게 grant 검사를 생략하는 기본 동작이 있습니다. 이 기본값을 업무에 그대로 적용하면 ‘관리자라도 관리 범위 밖 업무는 차단’ 요구를 충족하지 못합니다. 관리자 역할을 전체 업무 조회 권한으로 확정한 것이 아닙니다.**

업무 라우트는 관리 범위 합의 후 별도 범위 검사 또는 `allow_admin=False`와 적절한 grant 관리 등을 적용해야 합니다. `allow_admin=False` 하나만으로 업무 배정·상위 검토자 정책까지 완성되지는 않습니다.

- 목록: 인증한 `g.user.id`로 본인 배정 조건 또는 합의한 관리 범위를 SQL 조회 조건에 적용합니다.
- 상세: ID로 직접 요청해도 인증한 사용자의 해당 업무 접근 가능 여부를 별도로 검사합니다.
- 관리자 본인 업무 `Own`과 관리 업무 `Managed`를 같은 범위로 가정하지 않습니다.
- 관리 범위가 부서·배정·등록자·검토자 관계 중 무엇인지, 협업 참여가 Own에 포함되는지는 아직 합의가 필요합니다.
- 공통 grant 미보유는 현재 403입니다. 실제 업무에서 존재 여부 노출을 막기 위해 404로 숨길지는 미확정입니다.

담당/시점: 1번·2번, 관리 범위 정책은 팀장, 관리자 본인 제출본·상위 검토자는 3번 포함. 실제 업무 목록·상세 API를 구현하고 접근 차단 테스트를 작성하기 전에 결정합니다.

## B1 공통 HTTP 호출 수명과 설정

**상태: 확정 — 현재 구현 기준. 기존 생성자 주입 경계 확인, HTTP 구현과 구성 지점 연결은 후속 협의.**

- `AppServices.Api`는 프로세스에서 재사용하는 공통 `ApiClient`입니다. 각 조회마다 새 클라이언트를 만들지 않습니다. 개별 기능은 공유 인스턴스를 Dispose하지 않습니다.
- 내부 HttpClient 기본 timeout은 **12초**입니다. `GetAsync`, `PostAsync`, `PatchAsync`가 `CancellationToken`을 받습니다.
- 호출자가 취소한 경우 `OperationCanceledException`이 전달되므로 UI에서 취소로 처리합니다. timeout은 사용자 안내를 가진 `ApiException`으로 변환합니다.
- 서버 주소 우선순위: `REMOTEWORK_API_URL` → `%LOCALAPPDATA%\RemoteWork\client.json` → `http://127.0.0.1:5000/`.
- 로그인 화면의 서버 연결 설정에서 주소를 저장합니다. 로그인 중에는 서버 주소 변경을 거절합니다.
- 토큰은 클라이언트가 각 요청에 자동 첨부합니다. 기능 구현이 토큰을 별도로 저장·전달받을 필요는 없습니다.
- 유효한 공통 JSON으로 받은 401은 로그인된 토큰이 있을 때 컨텍스트를 비우고 `AuthenticationExpired` 이벤트를 발생시킵니다. 현재 메인 창이 재로그인을 안내합니다. 메인 창은 30초마다 사용자·접속을 재확인합니다.
- 자동 재시도나 refresh token 처리는 없습니다. 읽기 재조회는 2번의 재시도 UI에서 호출하고 등록·수정 요청을 자동 반복하지 않습니다.

## B2 성공·오류 응답과 UI 매핑

**상태: 확정 — 공통 API 기준. 업무 고유 오류는 아직 없음.**

실제 health 성공 응답 형태:

```json
{
  "ok": true,
  "data": {
    "status": "ok",
    "database": "connected",
    "schema_version": 1,
    "version": "1.0.0"
  },
  "request_id": "요청마다 생성되는 식별자"
}
```

공통 권한 거부 응답 형태:

```json
{
  "ok": false,
  "error": {
    "code": "FORBIDDEN",
    "message": "접근 권한이 없습니다."
  },
  "request_id": "요청마다 생성되는 식별자"
}
```

`request_id`와 `X-Request-ID` 응답 헤더로 요청을 식별합니다. C# `ApiException`은 `StatusCode`, `Code`, 사용자 안내 `Message`를 제공합니다.

| 상황 | 현재 HTTP·코드 | 2번 UI의 연결 기준 |
|---|---|---|
| 인증 없음·만료·폐기 | 401 `AUTH_REQUIRED` | 재로그인 필요 |
| 로그인 자격 증명 오류 | 401 `INVALID_CREDENTIALS` | 로그인 입력 확인 |
| 권한 거절 | 403 `FORBIDDEN` | 권한 없음 |
| 없는 일반 경로 | 404 `HTTP_404` | 주소·서버 계약 확인. 업무 상세 없음과 동일시하지 않음 |
| 사용자 등 구현된 자원 없음 | 404 `NOT_FOUND` | 대상 없음. 업무 고유 정책은 추가 합의 |
| DB 연결·초기화 오류 | 503 `DATABASE_UNAVAILABLE` | 서버/DB 이용 불가 안내 |
| 예상하지 못한 서버 예외 | 500 `SERVER_ERROR` | 서버 오류 안내 |
| 반복 로그인 실패 | 429 `LOGIN_THROTTLED` | 잠시 후 재시도 안내 |
| 클라이언트 통신 실패·timeout | `ApiException.StatusCode=0`, `Code` 없음 | 연결 실패 안내. 확정 서버 오류 코드처럼 취급하지 않음 |
| JSON 파싱 실패 | 실제 HTTP 상태를 담은 `ApiException`, `Code` 없음 | 응답 형식 오류 안내 |

현재 통신 실패·timeout·응답 형식 오류의 구조화된 별도 클라이언트 오류 enum은 없습니다. 메시지 문자열을 파싱해 유형을 확정하지 않습니다. `TaskQueryFailure`가 이들을 별도로 구분해야 하면 1번·2번이 공통 오류 분류 확장 여부를 먼저 정합니다.

## B3 접근 거부와 미존재

**상태: 공통 정책 확정, 업무 상세의 403/404 선택은 합의 필요.**

공통 인증 실패는 401, 역할·grant 부족은 403, 미존재 일반 경로는 404입니다. 업무 상세는 아직 없으므로 권한 없는 상세의 존재를 404로 감출지 확정하지 않았습니다. 2번에서 임의로 이 정책을 결정하거나 모든 404를 업무 없음으로 표시하지 않습니다.

웹 보호 화면의 미인증은 로그인 화면으로 redirect합니다. API는 redirect 대신 JSON 401입니다. 현재 공통 C# HttpClient도 자동 redirect를 허용하지 않습니다.

## B4 DB 연결과 스키마 관리

**상태: 공통 연결·모델·트랜잭션·이력 규약 확정. 업무 DDL과 이후 스키마 변경은 합의 필요.**

근거: `remotework/db.py`, `models.py`, `common.py`, `migrations/README.md`, `.env.example`.

- 클라이언트는 MySQL에 직접 접속하지 않습니다. Flask 서버만 DB 계정을 사용합니다.
- SQLAlchemy와 PyMySQL로 연결합니다. 요청별 `get_db()` Session은 요청 종료 시 닫고 미완료 작업은 rollback합니다. 연결의 `pool_pre_ping`을 사용합니다.
- `with transaction() as db:`는 성공 시 commit, 예외 시 rollback합니다.
- 사용자 PK는 `users.id`의 정수입니다. 공통 `AuthSession.user_id`, `ResourceGrant.user_id`, `AuditEvent.actor_id`는 같은 정수 FK입니다. 업무 담당자·검토자 FK도 사용자 PK를 참조하도록 DDL을 합의합니다.
- `audit(action, resource_type, resource_id, details)`는 commit하지 않습니다. 업무 변경·grant 변경·감사 이력을 같은 트랜잭션에 넣습니다. 수행자는 서버의 인증 사용자로 기록합니다.
- 사용자를 삭제하지 않고 비활성화하는 현재 정책을 유지합니다. 비활성 직원의 과거 업무·결과·근태 이력이 보존되고 허용된 관리자 조회에 남도록 각 기능이 연결해야 합니다.
- 스키마 버전은 1입니다. 최초 `init-db`는 공통 테이블을 생성하고 기존 데이터를 보존합니다. 기존 테이블 열을 수정하는 자동 마이그레이션은 없습니다.
- 변경 SQL은 `migrations/`에 번호·설명과 함께 추가하고 관련 담당 검토, 테스트 DB 검증, 공유 DB 백업 후 적용하는 절차를 문서로 제공합니다. 자동 배포·적용 도구가 구현된 상태는 아닙니다.
- 업무 테이블은 2번, 제출·버전·승인·반려 데이터는 3번이 정의하고 공통 사용자 FK·상태·이력과 맞춥니다.

## B5 날짜와 시간

**상태: 공통 기록 시각은 확정, 업무 시작일·마감일 의미는 합의 필요.**

- 공통 `created_at`, 접속 `expires_at` 등은 UTC 기준으로 저장하고 `YYYY-MM-DDTHH:mm:ssZ`로 전달합니다.
- 현재 MySQL 공통 DateTime 열에는 UTC 값을 시간대 오프셋 없이 저장합니다. 서버 코드에서 `models.utcnow()`을 사용하고 API의 `iso()`로 Z를 붙입니다. DB의 로컬 NOW()와 혼용하지 않습니다.
- 접속 만료는 C# `DateTimeOffset`으로 받습니다. 화면의 한국 시간 표시는 클라이언트에서 변환합니다.
- 업무 시작·마감은 아직 열이 없으므로 DateOnly인지 UTC 시각인지 확정되지 않았습니다. DateOnly를 쓰면 `YYYY-MM-DD` 형식, 기준 날짜는 Asia/Seoul로 할지 등을 2번·3번과 합의할 수 있으나 현재 확정 규약은 아닙니다.
- 마감 당일 종료 시각, 마감 후 제출 조건, 연장 후 현재 적용 마감일은 미확정입니다. DateOnly를 자정 UTC로 임의 변환하지 않습니다.

## 1번·3번 공동 합의와 요청서의 업무 원칙

요청서가 확정 기준으로 제시한 다음 내용은 현재 공통 서버가 구현한 업무 규칙이라고 보고하지 않습니다. 업무 API 연결 시 2번·3번이 유지할 기준으로 확인합니다.

- 진행전 / 진행중 / 제출완료 / 승인완료 / 반려완료의 5개 상태. C# 논리 상태와 배정→진행전 등 기본 행동 전환은 팀 LOG 기준으로 확인했습니다. 실제 서버 저장/전송 코드·전환 서비스는 아직 없습니다.
- 정식 제출·재제출은 권한 있는 검토자의 판단을 거치며 승인완료가 최종 완료.
- 관리자 본인 업무도 수락·제출하며 상위 검토자가 판단. 자기 승인·반려 금지.
- 마감 경과에 따른 자동 결과 제출 제외.

상위 검토자 사용자 매핑·관리 범위, 반려 후 진행중 복귀 시점·재제출, 자동 검토 요청 도입 여부와 중복 기준, 연장 조건·마감 후 제출 조건은 1번·2번·3번 및 정책 결정이 필요한 경우 팀장과 합의해야 합니다. 기존 공통 문서의 자동 마감 관련 미확정 설명을 실행 정책으로 사용하지 않습니다.

## 통합 검증 계정과 업무 데이터

- 로컬에서 관리자·일반 직원 로그인, 관리자 전용 API 차단, 비밀번호 변경·초기화와 기존 접속 폐기, 계정 비활성화·재활성화를 확인했습니다.
- 기존 로컬 운영 계정의 비밀번호나 DB 비밀번호를 이 회신에 첨부하지 않습니다. 팀 통합 환경에 별도 계정을 발급하고 계정 전달 채널을 정해야 합니다.
- 같은 역할 직원 2명, Own/Managed와 관리 범위 밖 관리자, 업무가 없는 사용자에 대한 **공유 테스트 세트는 아직 미준비**입니다.
- 업무 테이블·API가 없으므로 본인/타인 업무, 범위 밖 상세, 빈 목록·전체/5개 상태 필터, DB 값 일치, 두 PC·웹의 실제 업무 조회 검증은 아직 하지 않았습니다.
- 현재 공통 `admin` 역할이나 테스트 대역 성공을 실제 업무 접근 범위 검증 완료로 보고하지 않습니다.
