## 배경과 사용자 요청

초대 목록이 DB 사용자 대신 샘플 이름을 보여 실제 활성 사용자로 교체했다. 사용자는 직원·관리자 모두 활성 전원을 조회하도록 선택했고, 프로그램 종료/재실행 후 대화방·메시지 보존을 요청했다. 삭제는 최종 답변 “삭제 본인만 삭제되게 진행”에 따라 본인 목록 숨김으로 구현했다. 사용자 승인 범위와 1번/팀장 공동 계약·공유 배포 승인은 별개다.

기존 1번 W1 공통 쓰기 지원·공통 API/DB 문서, 2번 영역 수정 규약, 4번 LOG와 PR #1/#7 해결 이력을 확인했다. 기존 공지 N4 수용을 새 채팅 API/DDL 수용으로 확대하지 않는다. 아래 문서는 초대 목록과 저장의 대표 기록이며 서로 다른 초안을 중복 게시하지 않는다.

## 신규 API·DDL 제안과 구현

공통 서버 루트 + /api/v1 접두사를 한 번만 사용한다. 모든 API는 login_required, 쓰기는 authenticated_transaction을 사용하고 서버 g.user를 기준으로 작성자/참여자를 판단한다.

| API | 구현 동작 |
|---|---|
| GET /chat/participants | 활성 직원/관리자에게 활성 전원 중 본인 제외 id/display_name/department, page/limit/total |
| GET·POST /chat/rooms | 본인 숨김 제외 참여방 cursor 조회, 활성 상대와 방 생성 |
| GET·POST /chat/rooms/{id}/messages | 참여자만 seq cursor 전체 이력 조회·메시지 저장 |
| POST /chat/rooms/{id}/hide | 본인 chat_members.hidden_at 설정. 타인 행/메시지 물리 삭제 없음 |

- chat_rooms: UUID 문자열 PK·제목·그룹 여부·생성자 users INTEGER FK·UTC.
- chat_members: (room_id,user_id) PK·users FK·생성 당시 이름/부서 snapshot·본인 hidden_at.
- chat_messages: BIGINT seq 내부 저장 순서·UUID 공개 message_id UNIQUE·room/users FK·전송 당시 이름·본문·UTC.
- 관리자도 미참여 방은 조회하지 못한다. 숨긴 방은 타인 새 메시지로 자동 복원하지 않는다.
- 개인 상대1명, 그룹 상대2명 이상. 서버가 현재 활성 후보를 재검사한다.
- 동일 UUID 재요청은 수행자·방/대상·내용 동등성을 확인한다. 공통 write receipt를 확정적으로 대체한 계약이 아니라 채팅 리소스 기반의 구현 검토안이다.
- init-tables는 공통 테이블이 준비된 개발 DB에서 누락된 chat 테이블만 생성한다. 기존 chat 열 차이는 중단하며 기존 열 migration·전역 version 변경·DB/계정 생성은 하지 않는다. 일반 API 요청에서 DDL은 실행하지 않는다.
- Demo SQLite와 MySQL은 별개이며 기존 메모리/SQLite 기록 자동 이관은 없다.

## 검증과 재현

이번 저장 단계는 사용자 “테스트는 내가” 요청에 따라 **현재 게시본 빌드·실제 서버/DB 저장·재시작 복원·MySQL/두 PC·권한/동시성 테스트를 실행하지 않았다.**
이번 PR 준비에서 Python ast.parse 구문과 원본 tree 차이18파일/삭제0, 공통 auth.py 불변·MainForm 최소 주입 diff를 확인했다. 이를 런타임 성공으로 해석하지 않는다.

이전 초대 목록 단계의 SQLite test client6·C# HTTP대역/WinForms40·Release 통과는 이전 소스의 결과다. 저장 기능 추가 후의 게시본 통과 결과가 아니다. 이전 공지/공통 테스트 수치도 채팅 DB 저장 근거로 재사용하지 않는다.

검토자가 실행할 명령(이번 미실행):
- dotnet build RemoteWork.sln -c Release
- dotnet run --project Tests/ChatParticipants.Tests/ChatParticipants.Tests.csproj -c Release
- 서버 python -m pytest -q tests/test_chat_participants.py

추가 수동/통합 검증: 삭제 가능한 개발 DB에서 테이블 준비 → 두 활성 계정 방 생성·메시지 저장 → 재로그인/서버·앱 재시작 복원 → A 본인 숨김/B 기록 유지 → 비참여/비활성/만료 접속 거절 → 중복 UUID/실패/페이지/동시 요청. 실제 사용자/공유 DB를 테스트 fixture 대상으로 지정하지 않는다.
