현재 접근 권한은 최초/재응답/결과 조회에 검사한다. 상태·expected·날짜·데이터 정합성·버전 상한은 **최초 mutate**에서만 검사한다. 성공 후 상태가 바뀌거나 날짜가 지나도 동일 키의 정상 성공 확인을 새 상태 충돌로 바꾸지 않는다. 현재 역할/배정 접근이 회수됐다면 재응답도 거절한다.

새 실행의 검사 순서는 현재 인증/대상 접근→엄격한 입력→배정 버전→업무 버전→허용 상태→수락 기록 정합성→버전 상한→KST 날짜→변경/감사/receipt 저장으로 맞추는 안을 수용한다. 클라이언트는 준비창 성공만으로 실행을 허용하지 않는다. 같은 키·다른 본문 충돌과 결과 유실/24시간 규칙은 기존 계약을 따른다.

## 기존 action과 새 action 등록을 혼동하지 않기

- **task.accepted는 이미 공통 whitelist/현재 본인 authorizer가 있다.** register_write_action으로 기존 action을 다시 등록하면 거절된다. 기존 `app.extensions['write_authorizers']['task.accepted']`의 연결 함수를 확인해 사용하고 공통 등록을 덮어쓰지 않는다. 의존성 미준비는503으로 닫는다.
- **task.rework_started만 새 기능 계약으로 등록한다.** 2번 모듈에서 공개 `authorize_task(db, target)`를 호출하는 현재 본인 authorizer를 정의하고, 그 **동일 함수 객체**와 위5필드만 앱 초기화에 register_write_action으로 등록한다. 첫 HTTP 이후/매 요청 등록·상태 검사를 authorizer에 넣는 방식은 사용하지 않는다.
- 새 시작 기능은2번의 별도 기본off opt-in으로 묶고 query/common 의존성을 확인한 콜드 프로세스에서만 등록한다. 일반 init-db나 common flag만 켠 환경에 시작 경로/action을 자동 추가하지 않는다. 기존 auth/ApiClient·SQL/전역schema1을 바꾸는 작업이 아니다.
- 감사는 task.accepted/task.rework_started·resource=task·resource_id=task_id와 최소 이전/이후 상태·버전·배정 정보로 수용한다. 재응답에 감사/화면 이력을 다시 추가하지 않는다. 3번 화면용 이력 연결은 모델/계약 회신 후 별도다.
