## 2번이 바로 확인할 실제 API와 조립 순서

| 실제 경로 | 사용 목적·권한 |
|---|---|
| GET `/api/v1/tasks/assignment-candidates` | admin 새 업무 또는 task_id가 있으면 admin+그 업무 지정 관리자. active employee/admin |
| GET `/api/v1/tasks/manager-candidates` | 같은 호출 권한, active admin 후보. 제출 승인권자 목록 아님 |
| GET `/api/v1/tasks/{task_id}/write-context` | 현재 배정 당사자 또는 admin+지정 관리자. task_id/row_version문자열·assignment_revision/user ID정수·manager IDs·상태/UTC |
| POST `/api/v1/write-requests/keys` | action/target의 현재 권한을 검사한 서버 키 발급. created의 target=new, 나머지 연결된 업무 action은 task_id문자열 |
| POST `/api/v1/write-requests/result` | 같은action/target+Idempotency-Key로 현재 권한 재검사 후 성공 결과 또는 not_recorded |

공통 flag `REMOTEWORK_ENABLE_COMMON_WRITE_DRAFT=1`은 기본off, 후보/문맥은 기존 업무 flag도 필요하다. 공통/업무 테이블과004 검토용 저장소가 준비된 독립 MySQL에서 명시적으로 연결한다. flag는 공유 적용 승인이나 기존 DB 자동 migration이 아니다. 승인/반려 action은 등록된 권한 검사가 없어503 WRITE_ACTION_NOT_READY이며 admin이라는 이유로 열지 않았다.

권한 확인은 명시적 True를 반환해야 한다. 2번 서비스가 현재 업무·관계를 잠그고 행동 권한을 확인한 뒤 `perform_once`에 authorize/mutate를 연결한다. 버전/상태는 최초 mutate에서 검사하고 정상 replay 전에 옛 버전으로 거절하지 않는다. 업무 변경·버전·UTC updated_at·성공 감사·receipt는 한 transaction이다. [기술 계약과 예시][contract]를 먼저 읽는다. key/result API를 받은 것만으로 업무 수락/저장이 이루어지지 않는다.

후보는 최대100개씩 page/limit/total이며 이름→id 정렬, 이름/부서 부분 검색80자·와일드카드 문자 literal 처리다. 세 필드 외 login_id/전체 사번/생성시각을 노출하지 않는다. label은 동명이인 구분과 역할 표시용이고 선택은id다. 한 페이지 실패를 완성 목록으로 확정하지 않는다. 최종 저장에서 선택한ID·active/role·현재 범위를 다시 검사한다. 현재 후보 구현은정확한total을 위해후보ID를잠금조회하므로대규모최적화는별도다.
