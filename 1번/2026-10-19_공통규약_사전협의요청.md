업무·결과물·채팅·장치가 같은 사용자와 DB를 사용하므로 한 담당의 변경이 다른 담당의 권한·상태·저장 결과에 영향을 준다. 구현한 뒤 충돌을 고치기 전에 **누가 무엇을 정하고, 어떤 파일/API/DB를 바꾸며, 언제 연결할지** 먼저 맞추려 한다.

대상은 공통 인증/ApiClient/DB 연결, 업무 상태와 버전, 제출·검토·파일·이력, 공지·채팅, 회원·장치 연결 및 공유 환경이다. 이번 변경은 LOG 문서뿐이며 실제 기능·공유 DB·설정은 변경하지 않는다.

## 3. 담당별로 미리 답을 받고 싶은 항목

모든 항목의 현재 상태는 **제안 전달·담당 회신 대기**다. C 번호는 이 요청서의 추적 번호이며 기존 W1/W3/N4/D5 요청 번호를 대체하지 않는다. 다음의 ‘시점’은 일정 강제가 아니라 해당 변경에 들어가기 전에 합의할 경계다.

### C01 — 팀장·전원: 공유 서버와 DB 적용을 누가 어떻게 할까?

- **내 제안:** 공유 적용은 지정 실행자 1명이 승인된 코드 SHA·대상 DB·기능 flag·SQL 순서를 확인한 뒤 백업/별도 복원 시험→적용→검증 순서로 수행한다. 각 담당은 자기 기능 DDL과 전후 영향·복구안을 제출하고 1번이 공통 FK/버전을 검토한다.
- **답변 요청:** 공식 서버/DB 관리 담당, 적용 실행자, 적용할 기능과 시점, 실패 시 중단/복구 책임, receipt/임시 업로드 정리 실행자·주기를 정해 달라. 실제 비밀번호·키·접속 값은 공개 LOG에 적지 않는다.
- **대상/영향/시점:** 서버 설정·`migrations/`·스키마 기록·전체 기능 기동 / **공유 환경 적용 전**. 현재 전역 schema version은 1이며 SQL 번호와 전역 버전은 같지 않다. 002 업무·003 공지·004 receipt, PR #25의 005 채팅 개발 SQL과 예약만 된 006 결과물을 한꺼번에 적용 승인한 것이 아니다.

### C02 — 2번·3번: 상태별 수정·재배정·취소를 어디까지 허용할까? (W3-03/04)

- **내 제안:** 2번이 5상태 × 수정/재배정/관리자 변경/취소 허용표를 만들고 3번이 미판단 제출·이전 판단·첨부·회차에 미치는 영향을 표시한다. 1번은 공통 버전·FK·잠금 접점만 검토한다. 현재 admin+지정 관리자라는 역할 기준만으로 모든 상태 변경을 허용하지 않는다.
- **답변 요청:** 제출완료·승인완료에도 수정/재배정 가능한가? 가능하다면 기존 제출/판단은 어떻게 보존하고 누가 다시 열람하는가? 취소는 상태 추가인지 별도 표시인지 제안해 달라. **새 상태를 임의 추가하지 않는다.**
- **대상/영향/시점:** `features/tasks/`·2번 화면·3번 제출 참조·`row_version/assignment_revision` / **관련 쓰기 API 구현 전**.

### C03 — 팀장·2번·3번: 검토자를 누가 지정·교체하고 상위 관계는 어떻게 표현할까? (W3-05)

- **내 제안:** 현재 활성 admin이면서 업무 지정 관리자인 사람이 제출자와 다른 활성 admin 1명을 명시 지정하는 안으로 협의한다. 업무 조회 관리자와 제출 승인권자를 분리하고 자동 대리 승인자를 만들지 않는다. 이 안은 기존에 **협의 준비**를 승인받은 제안이다.
- **답변 요청:** 이 지정권 안을 수용하는가? 관리자 본인 제출의 ‘상위 검토자’는 실제 조직 관계를 무엇으로 판정하는가? 미판단 제출 중 교체·강등/비활성 시 이미 제출된 건의 검토자 변경과 과거 접근을 어떻게 할까?
- **대상/영향/시점:** 명시 검토 관계 모델·지정 API·최소 검토 조회·판단 권한 / **006 모델 확정·검토자 API 구현 전**. 자기 판단 금지와 미지정/비활성 시 새 제출 차단은 이미 확정이므로 유지한다.

### C04 — 3번, 접점 2번: 제출 모델·회차·API 계약을 최종 대조할까? (W3-02/04)

- **내 제안:** [1번 W3 기술 회신](2026-10-19_W3_제출DB_API_기술회신.md)의 부모 업무 우선 잠금·복합 FK·동일 트랜잭션·action/최소 결과를 기준으로 실제 모델과 차이를 대조한다. `round_no`는 signed BIGINT/JSON 문자열로 제안했고 기존 숫자 예시 수정을 요청한 상태다.
- **답변 요청:** 제출/판단/검토 관계·첨부·화면 이력 모델과 정확한 요청/응답·오류·필수 필드, 006 SQL 초안을 보내 달라. 회차 문자열 변경안을 수용하는가? 같은 제출의 판단 1회, 성공한 과거 제출 불변, 재응답의 단일 효과를 어떤 제약/시험으로 보장할까?
- **대상/영향/시점:** 3번 서버 모듈·006 예약·2번 업무/배정 FK·공통 행동 등록 / **006 SQL 및 제품 API PR 전**. 현재 제출·판단 경로는 제안이며 등록 완료된 API가 아니다.

### C05 — 3번·팀장: 파일 허용 형식·저장 위치·정리는 누가 관리할까?

- **내 제안:** 파일은 서버 관리 저장소에, DB에는 소유/참조/크기/해시/불투명 키 등 메타데이터를 저장한다. 전용 업로드 경로의 제한을 별도로 검증하고 기존 JSON 32KiB 제한은 유지한다. 연결된 첨부는 임시 정리 대상에서 제외한다.
- **답변 요청:** 허용 확장자/MIME 목록, 실제 저장소 운영 담당, 임시 정리 실행자·주기, 제출 파일/백업의 운영 보존·복구 정책을 제안해 달라. 구체 저장 경로·접속 값은 비공개 설정으로 전달한다.
- **대상/영향/시점:** 3번 업로드·다운로드·첨부 모델·외부 저장소·정리 작업 / **파일 API 구현·공유 배포 전**. 승인된 25MiB/10개/미연결 24시간/제출 후 자동 삭제 없음은 유지하되 구현 완료로 표시하지 않는다.

### C06 — 2번·3번: 화면용 이력과 과거 자료를 누가 볼 수 있을까? (W3-02/04/05)

- **내 제안:** 각 담당의 실제 행동 트랜잭션에서 최소 이력 이벤트를 기록하고 3번 화면이 조회한다. 24시간 receipt와 영구 이력을 분리하며 내부 감사 JSON을 그대로 노출하지 않는다. 현재 본인/지정 관리자 업무 접근과 검토자의 해당 제출 최소 접근을 구분한다.
- **답변 요청:** 재배정된 이전 담당자·교체된 검토자가 과거 제출/파일/이력을 볼 수 있는가? 필요한 화면 필드·필터·페이지/cursor·보존 범위를 제시해 달라.
- **대상/영향/시점:** 업무 이벤트 모델·이력 API·첨부 접근·2번 변경 이벤트 / **이력/과거 자료 조회 API 구현 전**.

### C07 — 팀장·2번·3번: 마감·연장·검토 요청의 기준은 무엇일까? (W3-06/07)

- **내 제안:** 사건 시각 UTC 저장은 유지하고 업무 마감의 시간대·당일 종료 시각은 별도 정책으로 정한다. 자동 결과 제출 제외를 유지하며 자동 검토 요청은 결정 전 도입하지 않는다.
- **답변 요청:** Asia/Seoul 당일 종료를 쓸 것인가? 기한 후 수락/재작업/제출·연장을 어느 상태까지 허용하는가? 연장 판단자와 승인 반영 시점, 수동 검토 요청 버튼의 의미·자동 검토 요청 도입 여부를 정해 달라.
- **대상/영향/시점:** 2번 수락/재작업/연장·3번 제출/판단·스케줄러/알림 / **관련 API 및 자동 처리 구현 전**.

### C08 — 4번, 검토 1번: 채팅 SQL·초기화 경로를 하나로 맞출까?

- **내 제안:** PR #25의 `005_chat_storage.mysql.sql`과 PR #21의 번호 미지정 SQL·ORM 초기화 설명을 대조해 한 적용 기준으로 맞춘다. InnoDB·utf8mb4·collation·FK/index/default를 명시하고 기존 테이블은 자동 덮어쓰지 않는다. 기존 SQL과 005를 중복 실행하지 않는다.
- **답변 요청:** 005와 초기화 문서를 이 기준으로 정리하는 데 동의하는가? 다른 물리 구조가 필요하면 차이를 알려 달라. 영속 UUID 단일 효과 방식과 별도 공통 receipt를 중복 강제하지 않는 1번 회신, 본인 숨김·자동 삭제 없음 개발 기준의 수신 여부도 회신해 달라.
- **대상/영향/시점:** 4번 채팅 모델·초기화 CLI/배치·README·005 SQL / **채팅 코드 최종 재검토·공유 적용 전**. 1번의 독립 기술 확인과 PR #21의 검토자 판정·병합은 별도다. 숨김 복원/탈퇴/운영 보존은 후속 정책으로 남긴다.

### C09 — 4번·팀장: 공지 삭제·팝업·확인 기록은 어떤 정책으로 확장할까? (N4-05/08/09)

- **내 제안:** 현재 공지 목록/상세/작성/삭제 계약은 보존한다. 새 팝업·확인 기록은 별도 모델/API와 공지 삭제 시 참조/보존 정책부터 맞춘다. 공지의 `attachment_names`는 파일명 메타데이터이며 실제 파일 업로드가 아니다.
- **답변 요청:** 공지/확인 기록 보존·삭제 방식, 최초 조회 실패 후 복구 기준, 부서/로그인 변경·새 고정 공지의 표시 조건, 표시 간격과 수정 후 재확인 기준을 제안해 달라. 15초 같은 수치를 기존 확정 규칙으로 간주하지 않는다.
- **대상/영향/시점:** 공지 후속 테이블·popup cursor·confirm API·첨부 / **후속 기능 PR·DDL 전**. [N4 상세 회신](2026-10-17_공지DB_API_DDL_협의회신.md)의 기존 수용/미합의를 유지한다.

### C10 — 5번·팀장, 검토 1번: 회원과 실제 장치를 어떻게 신뢰해 연결할까? (D5-01/02/05)

- **내 제안:** 서버 관리 user↔device↔slot 매핑과 revision, 서버 발급 단일사용 challenge, challenge 뒤 새 스캔, 장치별 서명/신뢰 확인을 결합한다. 단독 `/scan`의 이름·finger_id·confidence만으로 공통 로그인/본인 인증 성공 권한을 주지 않는다.
- **답변 요청:** 실제 슬롯 범위·장치 ID·등록/재등록 권한, challenge 요청/응답, HMAC 또는 서명 방식·키 배포/교체/폐기·오프라인 실패안을 보내 달라. 짧은 challenge TTL(예: 60초)은 기술 제안이며 아직 정책 확정이 아니다.
- **대상/영향/시점:** Pi API·장치 설정·공통 매핑/본인 확인 API·새 DB 모델 / **장치를 공통 인증에 연결하기 전**. [D5 상세 회신](2026-10-19_D5_회원장치_연결기술회신.md) 이후 모델을 보고 SQL 번호를 정한다. 생체 원본·장치 키/실명 슬롯 명부는 Git에 올리지 않는다.

### C11 — 팀장·5번·화면 담당: 언제 확인하고 어떤 결과를 보여줄까? (D5-03/04/05/06)

- **내 제안:** ‘센서 연결 오류/확인 불가’와 ‘본인 확인 성공/실패’, 단독 시연 화면 표시와 실제 근태 DB를 구분한다. 업무 조회·수락·제출에 임의 장치 조건을 추가하지 않는다.
- **답변 요청:** 요청 시작 주체·시점/주기·응답 제한·미응답 처리, 실제 화면 위치, 출퇴근/연차와 연결할지 여부 및 최소 결과/감사 보존을 정해 달라. 손/조도 미검출을 자동 결근으로 기록하는 정책은 만들지 않는다.
- **대상/영향/시점:** 장치 확인 UI·알림·근태 모델/승인 관계·2번 업무 경계 / **자동 확인·근태 저장 기능 구현 전**. 장치 독립 시연이나 카메라 기본 동작 보고는 이 정책의 합의·제품 통합 증거가 아니다.

## 4. 회신·변경을 남기는 방법

수신 담당은 자신의 LOG 번호 폴더에 다음 형식으로 회신하고 이 문서를 연결해 달라. 1번은 회신을 확인한 뒤 아래 표와 필요한 상세 기술 문서만 갱신한다. 제안이 바뀌면 이유·영향과 승인/확인 담당을 적고 과거 요청을 삭제하지 않는다.

| 요청 번호 | 수용 / 수정안 / 보류 | 구체 결정·다른 안 | 영향 파일·API·DB | 회신 담당·날짜 | 근거 커밋·PR / 실제 검증·미실행 | 다음 담당·결정 시점 |
|---|---|---|---|---|---|---|
| 예: C04 / W3-04 | 수정안 | round_no 전송 타입과 소비 DTO를 함께 제시 | 실제 경로와 필드 | 담당자·날짜 | 수행한 것만 기재 | 다음 확인 담당·구현 전 경계 |

| 요청 | 회신 대상 | 현재 상태 |
|---|---|---|
| C01 | 팀장·전원 | 제안 전달·회신 대기 |
| C02 / C03 / C06 / C07 | 팀장·2번·3번 중 각 절의 담당 | 제안 전달·회신 대기. 이미 확정된 상태 흐름·활성 검토자 조건은 유지 |
| C04 / C05 | 3번·2번 접점·팀장 운영 정책 | 제안 전달·회신 대기. 첨부 개발 제한은 유지 |
| C08 / C09 | 4번·팀장·1번 기술 접점 | 제안 전달·회신 대기. 기존 1번 검토 결과와 별개로 상대 수신 확인 필요 |
| C10 / C11 | 5번·팀장·관련 화면 담당 | 제안 전달·회신 대기. 실제 신뢰 연결·근태 정책 미구현 |

공통 API/DB/인증이나 타 담당 진행 코드에 영향이 있으면 이 요청서·상대 회신을 먼저 확인하고 필요한 합의를 받은 뒤 최소 범위로 수정한다. 담당자가 읽었다는 사실, 기술 수용, 사용자 정책 결정, 구현, 원본 병합, 공유 환경 검증은 각각 따로 기록한다.

## 5. Git 전달·검증 기준과 이번 게시 범위

- 매일 첫 작업과 업로드 전에 최신 원본 alpha·LOG·PR, 본인/관련 번호 폴더의 요청·회신·미해결 항목, 관련 GitHub PR 본문·리뷰·댓글·변경 파일을 확인한다. 미커밋 변경을 보존하고 필요한 최신 변경을 실제 작업 공간에 반영한다. fetch만으로 소스 반영 완료라고 쓰지 않는다.
- 코드는 포크 alpha→원본 alpha, 협업 문서는 포크 LOG→원본 LOG, 검토 요청/회신은 포크 PR→원본 PR로 분리한다. 기존 열린 같은 head PR을 갱신하고 원본 직접 push·자가 병합·강제 push를 하지 않는다. DOCX는 별도 요청된 범위만 게시한다.
- LOG의 담당 폴더는 브랜치 루트 `1번/`·`2번/` 등이다. `LOG/날짜/`는 팀장만 게시한다. 팀원은 실제 작업·테스트·남은 일을 로컬 팀장 전달용으로 준비한다. 비밀값·실제 .env·개인정보·DB 덤프·빌드 출력·불필요한 압축/임시 산출물을 커밋하지 않는다.
- PR에는 담당/목적·변경·실제 테스트 명령/환경/결과·미실행·타 담당 영향·관련 협업/수정 요청 링크·재현/검토 항목을 적는다. 다른 코드가 먼저 합쳐지면 최신 결합 상태를 관련 범위로 검증한다. 단순 mergeable 여부를 동작 검증으로 쓰지 않는다.
- 이번에는 **협의 요청서와 각 담당/루트 목차 연결만 추가**한다. API·DB·업무/장치 정책을 새로 구현하거나 공동 확정하지 않는다. 문서 경로/링크·표·diff·기존 원문 보존을 확인하며 프로그램/실제 DB/장치/두 PC 시험은 이번 문서 작업에서 재실행하지 않는다. 선행 실행 근거는 대표 기술 회신의 당시 코드 기준을 따른다.
