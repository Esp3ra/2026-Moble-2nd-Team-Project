## 수정한 동작

| 요청 | 변경 파일·처리 | 수정 후 결과 |
|---|---|---|
| R1 P1 동시 관리자 변경 | `auth.py`의 `admin_transaction()`으로 guard 획득 후 수행자·접속을 잠금 재조회하고 ORM 객체도 갱신. `api.py`의 사용자 생성·수정·비밀번호 초기화에 적용. 관리자 ID도 현재 잠금 조회로 확인 | A가 B의 권한·접속을 폐기한 뒤 B의 대기 요청은 401 `AUTH_REQUIRED`. A는 활성 관리자로 남고 거절된 변경은 이력에 남지 않음 |
| R2 P2 이전 접속 응답 | `ApiClient.cs`가 접속 세대·서버·Bearer를 캡처하고 세대 변경 시 취소. 늦은 결과는 상태 변경 전후 검사로 차단. 로그아웃은 로컬을 즉시 비우고 캡처한 이전 토큰으로 서버 폐기 요청 | 이전 A의 성공·각 형식 401이 B 사용자·Bearer·만료 이벤트를 변경하지 않음. 늦은 로그아웃·겹친 로그인·같은 사용자 재로그인도 차단 |
| R3 P2 비정상 본문 401 | 현재 접속의 HTTP 401을 JSON 역직렬화 전에 처리. 세대가 맞을 때만 상태 초기화·만료 이벤트 1회. 공통 화면은 이전 접속의 취소를 처리 | 정상 오류 JSON·HTML·잘못된 JSON·빈 본문 401 모두 만료 처리. 후속 Bearer 없음. 500·502·잘못된 성공 본문은 접속 유지 |

서버 거절은 변경 트랜잭션을 rollback합니다. 본인 관리자 해제는 400 `SELF_LOCKOUT`, 최종 관리자 보호의 방어 검사는 409 `LAST_ADMIN`을 유지합니다. 잠금 후 접속은 유효하지만 역할만 관리자가 아니면 403 `FORBIDDEN`입니다. 대기 중 강등·비활성화 재현에서는 기존 접속도 폐기되므로 401입니다. 단일 관리자에 이름 변경과 자기 강등을 함께 요청했을 때 이름과 감사 이력도 rollback하는 검증을 추가했습니다.

## 기존 코드와 수정본 비교

동일한 새 테스트에 수정 전 소스를 연결해 결함을 확인한 뒤 수정본을 실행했습니다. 실패를 단순한 환경 오류로 집계하지 않고 실제 assertion 위치를 확인했습니다.

| 비교 | 수정 전 | 수정 후 |
|---|---|---|
| MySQL B 대기→A가 B 강등/비활성화→B 재개 | 두 경우 모두 B가 HTTP 200, 기대한 401 검사 실패 | 두 경우 모두 B 401, 활성 관리자 1명 유지·성공 변경 이력만 1개 |
| A 조회 지연→로그아웃→B 로그인→A 성공/JSON 401 도착 | B 사용자 보존 검사 실패 | B 사용자·Bearer 유지·만료 이벤트 없음·이전 결과 취소 |
| 현재 접속 HTML 401 | 현재 사용자 제거 검사 실패 | 사용자·토큰 제거·이벤트 1회·후속 Bearer 없음 |

## 이번에 실행한 검증

| 항목 | 결과·범위 |
|---|---|
| Debug·Release 솔루션 빌드 | 각각 경고 0·오류 0 |
| 서버 SQLite | 24개 통과·MySQL 전용 2개 skip |
| 서버 MySQL | MySQL 8.2.0 / `REPEATABLE-READ`, 26개 통과 |
| C# 인증 회귀 | 실제 ApiClient·ApiModels 소스와 응답 제어 처리기, 18개 시나리오·88개 검증 통과 |
| 실제 공통 HTTP | C# → Waitress/Flask → MySQL, 기존 10개 점검 통과 |
| 기존 2번 조회 | 6개 시나리오·47개 검증 통과, 명시적 테스트 대역 |
| 공통 화면 | 로그인·관리자 메인·직원 메인·서버 설정·사용자 관리·비밀번호 변경 6개 렌더 |
| 기존 팀원 소스 | Features 전체·Tests/TaskQueries.Tests 변경 없음 |

R1은 별도 스레드의 B 요청이 인증을 끝내고 `admin_guard` 잠금을 얻기 직전 SQLAlchemy 이벤트에서 대기하도록 제어했습니다. A 요청 commit 뒤 Event를 풀어 B가 이전 인증 스냅샷을 가진 상태로 재개되도록 했습니다. 임의 sleep 순서에 의존하지 않습니다. 일반 SQLite 성공을 MySQL 잠금 검증으로 대신하지 않았습니다.

테스트 DB는 현재 프로젝트 `.local/` 아래 새 전용 데이터 디렉터리의 MySQL을 `127.0.0.1:13326`에 띄워 준비했습니다. 초기화한 서버 UUID와 연결 대상 UUID를 대조하고 `remote_work_test_` 전용 DB만 사용했습니다. HTTP 점검도 `127.0.0.1:15526`에 별도로 실행했습니다. `PYTHON_DOTENV_DISABLED=1`로 실제 `.env`를 테스트에 읽지 않았고 테스트 비밀번호는 임의 생성해 프로세스 환경으로만 전달했습니다. 전용 테스트 프로세스는 종료했습니다. Windows MySQL 실행기의 공백 경로 처리 문제는 전용 데이터 폴더를 작업 디렉터리로 지정해 해결했습니다.

## 실행 방법과 미검증 범위

```powershell
dotnet build .\RemoteWork.sln -c Debug
dotnet build .\RemoteWork.sln -c Release
dotnet run --project .\Tests\ApiClient.Tests\ApiClient.Tests.csproj -c Release
dotnet run --project .\Tests\TaskQueries.Tests\TaskQueries.Tests.csproj -c Release
cd .\RemoteWork.Server
.\.venv\Scripts\python.exe -m pytest -q
```

MySQL은 삭제 가능한 `remote_work_test_` DB를 만든 뒤 `MYSQL_TEST_URL`로 지정합니다. 상세는 [SETUP](https://github.com/jinkyu1452-cmd/Sang1/blob/a35c972f39091fec477024167e5e3e1194999b1e/docs/SETUP.md)과 [테스트 안내](https://github.com/jinkyu1452-cmd/Sang1/blob/a35c972f39091fec477024167e5e3e1194999b1e/Tests/README.md)를 따릅니다. 클라이언트 취소·401·관리자 트랜잭션 규약은 [INTEGRATION](https://github.com/jinkyu1452-cmd/Sang1/blob/a35c972f39091fec477024167e5e3e1194999b1e/docs/INTEGRATION.md)에 갱신했습니다.

이 기록의 결과는 R1~R3와 기존 공통 기능의 회귀 검증입니다. 전체 사용자 조작 자동화·실제 업무 API·Own/Managed·타인/관리 범위 밖 상세·업무 저장/상태/제출/승인/파일·두 PC/웹 업무 흐름·운영 DB는 검증하지 않았습니다. 4번 공지 필터는 이번 수정 범위가 아닙니다. 수정 완료 보고는 팀장의 재검토 승인·코드 병합을 뜻하지 않습니다.
