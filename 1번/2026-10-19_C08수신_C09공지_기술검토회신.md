## 시작 경계·cursor의 구체 설계 제안

1. 공지 등록과 같은 트랜잭션에 최소 notification event를 기록하고, **공지 발행과 로그인 경계를 같은 조정 순서로 직렬화하는 전용 counter/경계 행**을 검토한다. 단순 auto-increment 번호 발급은 commit 순서를 보증하지 않는다. 로그인 성공 시 경계도 같은 트랜잭션에 기록해야 첫 조회 실패 전의 신규 공지를 놓치지 않는다.
2. 기존 authenticate는 User를 먼저 잠근다. 여기에 뒤늦게 guard 잠금을 덧붙이면 기존 guard→User와 역순이 된다. **현재 로그인 코드를 즉석 변경하지 않는다.** 공통 인증 훅·counter/접속 경계 모델·잠금 순서는1번이4번 초안을 받은 뒤 전체 경로로 검토한다. 기존 감사 ID를 수신 cursor로 전용하거나 감사 원문을 클라이언트에 노출하지 않는다.
3. 서버가 발급하는 서명 cursor에는 버전·불투명 구독 문맥·현재 actor/접속 바인딩·부서 generation·after_seq·페이지 상한·만료를 결합하는 안을 제안한다. seq는 정규 BIGINT 문자열, 만료는 실제 접속 만료를 넘기지 않는 방향이다. 원문 token/비밀번호/일반 감사/불필요한 개인정보는 넣지 않는다. HMAC 서명은 암호화가 아니므로 본문 자체도 최소화한다.
4. 다음 페이지의 고정 상한과 정렬은 이벤트 seq 오름차순으로 제안한다. cursor 변조/다른접속/만료/부서 변경이면 재사용을 거절하고 새 문맥 준비를 안내한다. 요청 실패·서버 오류에 경계를 전진시키지 않는다. 검사한 seq와 실제 표시 대기/명시 확인은 분리한다. HTTP 응답 성공만으로 사용자가 봤다고 기록하지 않는다.
5. **정확히 한 번 팝업 표시**는 cursor만으로 보장하지 못한다. 표시 직후 앱 종료·확인 응답 유실·여러PC를 고려해 표시/닫기/명시 확인·재표시 허용을 팀장이 정해야 한다. GET으로 전역 확인 완료를 저장하는 방식은 사용하지 않는다. 문맥/이벤트가 아직 없는 기존 접속의 복구 방침도 함께 정한다.

이는4번이 요청한 서버 시작 경계·복구의 기술 검토안이다. 새 login 응답 필드·cursor URL/DTO/오류 code·TTL/정리 기간·테이블/SQL 번호를 확정하거나 공통 인터페이스를 변경한 것이 아니다. 전용 notice event/counter/접속 경계·확인 모델안을4번이 제시하면1번이 FK/현재 읽기/잠금/기존 인증·삭제 호환을 대조한다.

## 확인 저장·삭제 경합 검토안

인증된 현재 본인→현재 공지 잠금/대상 확인→확인 유일성 잠금/INSERT→최소 성공 감사의 같은 TX를 제안한다. 같은 논리 확인 재요청은 최초 확인 시각을 그대로 반환하고 감사/화면 이력을 더 만들지 않는다. UNIQUE 경합 후 현재 권한과 기존 성공을 다시 읽어 일관된 응답으로 끝내야 한다. 일반 DB 장애를 이미 확인된 성공으로 숨기지 않는다.

notice_id/user_id는 기존 signedINTEGER FK 타입을 유지한다. 확인 이력은 만료되는24시간 receipt나 삭제되는 AuthSession에 영구 필수FK로 연결하지 않는다. 후속 논리 삭제 시점/열람 정책이 승인되기 전 cascade 삭제·기존 삭제 API 변경은 하지 않는다. 새 확인 API는 서버 성공 확인 후에만 화면을 완료로 바꾼다. 재확인·취소·운영 보존은 별도 정책이다.
