## 3. API·DTO·오류 규약 — M1-01~03·05

### 3.1 주소와 응답

| 항목 | 1번 확정 공통 연결 기준 |
|---|---|
| 목록 | `GET /api/v1/tasks?scope=own\|managed&status=코드` |
| 상세 | `GET /api/v1/tasks/{task_id}` |
| 기본값 | scope 생략=own, status 생략=전체 |
| 목록 성공 | 공통 `ok/data/request_id` 안의 `data.items` 배열. 빈 결과는 빈 배열 |
| 상세 성공 | 같은 envelope 안의 `data.task` 객체 |
| 목록 필드 | task_id, title, assignee_id, assignee_name, task_status, start_date, due_date |
| 상세 추가 필드 | description |
| 목록 정렬 | due_date ASC, task_id ASC |
| 페이지·검색 | 1차 연결은 전체 목록. 현재 미지원 조건은400. 임의 절단 후 전체처럼 반환하지 않음 |

필드는 현재 계약대로 필수·NULL 불가로 유지합니다. task_id는 서버가 발급한 ID의 문자열 표현이며 C# 화면은 불투명 문자열로 다룹니다. assignee_id는 공통 users.id의 정수입니다. 제목·담당자 표시명·날짜 등의 현재 검증을 유지하며, description은 누락/NULL을 거절하되 빈 문자열까지 금지하는 새 규칙은 추가하지 않습니다.

알 수 없는/빈 scope·status, 중복 조건·미지원 조건은400입니다. 요청의 사용자 ID·role·부서로 조회 범위를 확장하지 않습니다. 클라이언트는 서버 루트만 설정하고 상대 경로 `tasks...`를 공통 ApiClient에 전달합니다.

근거: [routes][routes], [조회 SQL·DTO 변환][queries], [공통 응답][success], [C# 어댑터][adapter].

### 3.2 오류 분류

- 400: 입력·조건 오류. 401: 인증 누락·만료·폐기. 403: 유효 사용자지만 조회 권한 없음.
- 404 `TASK_NOT_FOUND`: 업무가 없음. 404 `HTTP_404`: 일반 미등록 경로/조회 연결 필요. 두404를 합치지 않습니다.
- 503: DB 장애. 통신·timeout·형식 오류 등은 기존 클라이언트 Unavailable 범주를 사용합니다. 메시지 문자열을 파싱해 오류 종류를 정하지 않습니다.
- 현재 ‘존재하나 허용되지 않은 상세는403’ 정책을 수용합니다. 팀장이 존재 은닉404 정책을 별도로 정하면 전용 코드·서버·화면·테스트를 함께 바꾸는 후속 변경으로 관리합니다.
- 현재 계약을 위해 공통 오류 enum을 새로 추가할 필요는 없습니다. 401과 이전 접속 취소는 기존 ApiClient 규약을 재사용합니다.

근거: [상세 검사][detail], [C# 오류 매핑][failure].

## 4. 인증·상태·날짜·FK 기준 — M1-04·06·07

### 4.1 조회 권한

- 인증 기준은 서버 `g.user`입니다. 공통 접속·사용자 활성 여부 확인을 그대로 사용합니다.
- own: 현재 배정 담당자만. managed: 현재 admin이면서 그 업무의 task_managers 지정자만.
- 목록과 직접 상세에 각각 서버 조건을 적용합니다. 과거 배정, 등록자, 같은 부서, 일반 ResourceGrant, 관리자 역할만으로 우회시키지 않습니다.
- 현 업무 조회의 권한 원천은 현재 배정·지정 관리자 관계입니다. 같은 권한을 공통 grant에 중복 저장하도록 요구하지 않습니다.
- 공통 `require_resource_access(..., allow_admin=True)`의 관리자 예외를 업무별 지정 관리자 검사 대신 사용하지 않습니다.
- 상위 검토자는 지정 관리자와 별개입니다. 검토자 기본정보 열람 계약이 오기 전 조회 범위를 자동 확대하지 않습니다.

근거: [공통 인증][auth], [현재 배정·관리자 조회][queries]. 쓰기 요청 중 권한 변경의 재확인·잠금 조건은 후속 쓰기 계약에서 검토합니다.

### 4.2 상태·날짜 표현

공통 직렬화·스키마 지원 기준으로 다음 코드와 타입을 수용합니다.

| 화면 의미 | DB/JSON 코드 |
|---|---|
| 진행전 | not_started |
| 진행중 | in_progress |
| 제출완료 | submitted |
| 승인완료 | approved |
| 반려완료 | returned |

시작·현재 마감 날짜는 NULL 없는 DB DATE, JSON `YYYY-MM-DD`, C# DateOnly입니다. 생성·수정 등의 기록 시각은 기존 UTC 규약을 유지합니다. 날짜를 임의로 UTC 자정 시각으로 변환하거나 enum 정수로 상태를 저장하지 않습니다.

**공동 확인 대기:** 최초 저장 기본값, 수락/제출/재제출/판단의 갱신 책임, 반려 후 복귀, 업무 날짜의 시간대·마감 시각·연장·마감 후 직접 제출. 2·3번은 [M3-01·02·04·06][request3]에 답해 주세요. 5개 의미·필수 검토·자기 판단 금지·자동 결과 제출 제외라는 기존 원칙은 그대로입니다.

### 4.3 DB와 이력

- 공통 Base·요청별 get_db·transaction·UTC·같은 트랜잭션의 감사 이력을 재사용합니다.
- users.id와 이를 참조하는 열은 MySQL INTEGER, 업무 PK와 이를 참조하는 열은 BIGINT로 맞춥니다. JSON 문자열 업무 ID와 DB BIGINT를 구분합니다.
- 사용자 이력은 비활성화 방식으로 보존하고, 사용자·업무·배정·제출 이력을 일괄 cascade 삭제하는 변경을 임의 추가하지 않습니다. 물리 삭제·보관 정책 변경은 관련 담당과 별도 합의합니다.
- tasks.current_assignment_revision과 task_assignments의 `(task_id, revision)` 관계를 유지해야 합니다. 현재 역방향 복합 FK가 없으므로, 2번은 쓰기에서 배정 행·현재 포인터를 같은 트랜잭션으로 변경하고 잠금/버전·불일치 검사안을 준비해야 합니다.
- 새 순환 FK 추가 여부, 제출본의 배정 차수 참조, row_version/updated_at 갱신 책임은 2·3번의 쓰기/제출 계약과 함께 확정합니다. row_version 필드 존재만으로 동시성 제어 완료로 표시하지 않습니다.

근거: [공통 모델][models], [업무 모델][taskmodels], [DB 트랜잭션][db]. 타입 호환 검토와 정식 DDL 채택·실행은 구분합니다.

## 5. Migration·기능 등록 절차 — M1-08·09

### 5.1 번호와 역할

- 현재 원본 migrations에는 안내 README만 있고 공통 기준 버전은1입니다. **1번은 다음 업무 변경 번호 `002_task_queries.mysql.sql`을 예약**합니다. 2번은 이 이름으로 DDL·검증·복구안을 준비하고, 다른 담당은 같은 번호를 쓰기 전에 1번과 조정합니다.
- **적용 후 목표 공통 스키마 버전은2로 계획**하되, 아래 조건을 통과하기 전에는 실제 버전1을 변경하지 않습니다. 파일 번호 예약은 DDL 승인·공유 적용 승인이 아닙니다.
- 작성: 2번(업무 DDL·데이터 영향·회귀). 공통 검토: 1번(FK·번호·기대 버전 검사·적용 순서). 공유 적용 일정/운영 창구 확인: 팀장. 제출 FK 영향: 3번 공동 확인.
- 현재 check_schema는 버전1 행 존재만 확인합니다. 버전2 행만 추가해 끝내지 않고, 1번이 기대 버전 확인·적용 기록 지원을 별도 코드 검토로 준비해야 합니다. 이 회신은 해당 코드의 구현 완료 보고가 아닙니다.

### 5.2 적용 게이트

1. 코드 SHA·현재 스키마·담당 FK·기존 데이터 영향과 DDL/복구안을 문서에 기록합니다.
2. 상태·날짜·배정/제출 관계의 남은 공동 항목을 확인합니다.
3. 기존 데이터를 가진 전용 테스트 MySQL에서 DDL 전후·권한·이력·실패/복구를 검증합니다.
4. 공유 DB 백업과 복구 절차를 확인하고, 팀장이 확인한 운영 창구에서 코드/DB 적용 순서와 시간을 정합니다.
5. 합의된 코드/DDL을 적용하고 실제 버전·커밋·실행자·결과를 기록한 뒤 기능과 데이터 보존을 확인합니다.

init-db/create_all은 기존 열 migration이 아닙니다. 일반 transaction만으로 모든 DDL 실패가 복구된다고 가정하지 않습니다. 실제 .env·비밀번호·DB 덤프를 Git에 넣지 않습니다.

근거: [현재 DB 초기화·버전 검사][db], [migrations 안내][migration]. 예약한 SQL 파일과 버전2 지원 코드는 아직 만들거나 적용하지 않았습니다.

### 5.3 기능 등록

현재 factory → get_blueprints(app.config)의 지연 등록 방식을 수용합니다. 기본 off를 유지하고, 위 계약/DDL/환경 준비와 검증 후 1·2번이 정식 활성화 변경을 별도로 검토합니다. 다른 기능의 등록을 덮어쓰거나 업무 플래그 아래 묶지 않습니다.

새 프로세스에서 off는 모델7개/업무 경로0개, on은 모델10개/경로2개임을 확인했습니다. 이는 등록 점검이며 공유 DB 생성 검증이 아닙니다. 근거: [factory][factory], [registry][registry].

## 6. 서버·계정·통합 검증 — M1-10

1번이 확정한 연결 방식은 다음과 같습니다.

- C# 서버 주소는 `http(s)://서버주소:포트/`의 루트이며 `/api/v1/`은 공통 클라이언트가 한 번 붙입니다.
- 기본 포트5000, 다른 PC 접속이 필요하면 서버 수신 주소0.0.0.0과 사설 네트워크 방화벽을 설정합니다. 0.0.0.0을 클라이언트 접속 주소로 입력하지 않습니다.
- 클라이언트는 Flask에 접속하고 MySQL에 직접 접속하지 않습니다. 같은 서버 PC의 MySQL은 로컬 주소를 사용합니다.
- 공식 서버 PC·실제 IP·접속 가능 시간은 팀장·1번이 정하고 별도 전달합니다. 로컬 health 성공을 두 PC 접속 성공으로 보지 않습니다.
- 1번은 승인된 통합 환경과 계정 발급, 2번은 업무·배정·지정 관리자 fixture를 준비합니다. 비밀번호·토큰·실제 .env는 승인된 별도 채널로 전달합니다.

**환경 확인의 시점 구분:** 회신 준비 단계의 이전 로컬 점검에서는 health200·DB connected·schema_version1과 TCP0.0.0.0:5000 수신을 확인했습니다. 그러나 **이번 문서 업로드 후 재확인에서는 `http://127.0.0.1:5000/api/v1/health` 연결이 거부됐습니다.** 현재 공유 검증에 바로 접속할 수 있다고 안내하지 않습니다. 실행 중 코드 SHA, 공식 공유 환경 지정, 실제 외부 접속과 통합 계정 발급은 이번 회신에서 완료하지 않았습니다. 서버를 새로 시작하거나 기존 프로세스·DB를 중지/초기화하지 않았습니다.

**검증 계획:** 직원2명·지정/비지정 관리자·관리자 본인 업무·이전 배정자·업무 없는 사용자를 구분해 두 PC에서 로그인/목록/직접 상세/필터/권한 회수/만료/DB 장애를 확인합니다. 웹 업무·제출/파일 통합은 별도 기능이 준비된 뒤 진행합니다.
