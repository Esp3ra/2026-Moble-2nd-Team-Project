# 2번 업무 취소·마감 연장 클라이언트 검증

```powershell
dotnet run --project Tests/TaskLifecycle.Tests/TaskLifecycle.Tests.csproj -c Release
```

명시적인 HTTP·워크플로 테스트 대역을 사용합니다. 실제 서버, 공유 DB, 실계정 검증으로 간주하지 않습니다.

2026-10-22 복구 화면과 현재 조회의 권한 상실 보완 후 **기존 검사 포함 171개 통과**, Release 빌드 경고0·오류0입니다. 수정 전 실제 STA 폼에서 `recovery restores exact original reason and requested date: Cancel` 실패로 원래 사유·날짜 표시 누락을 재현했습니다. 수정 후 취소·연장 신청·승인·반려·철회 다섯 동작에서 원래 사유/희망일·업무/신청을 읽기 전용으로 표시하고, 복구창 열기만으로 조회·새 키·POST가 발생하지 않음을 확인했습니다. 명시 `not_recorded` 뒤 재전송은 같은 요청 객체·키를 유지합니다.

30줄 원사유의 공백·줄바꿈 보존, 최소창의 스크롤 입력·재전송/결과 확인 버튼 접근, 403·접속 변경 후 원문 제거, 닫힌 창의 재표시 차단, 확정 실패 뒤 새 사유 편집 보존도 검사합니다. 같은 변경으로 기존 일반수정 첨부 실제폼/명시HTTP 149검사도 재통과했으며 이 수치와 합산하지 않습니다. 서버·DB·공유 배포·운영 ACK는 이번 실행에서 변경하거나 검증하지 않았습니다.

입력·대상 확인의 현재 조회가403을 반환할 때 이전 사유·업무가 남고 확인 버튼이 다시 활성화되는 문제도 수정 전 실패로 재현했습니다. 현재 조회에서 권한을 잃으면 입력·대상·확인값을 지우고 명시적인 최신 조회를 요구합니다. 일시적 서버 오류는 편집 내용을 유지합니다. 별도의 지연 응답 검사로 이전 조회 차수·닫힌 폼의403이 새 입력을 지우지 않고, 접속 변경 뒤 늦은403이 접속 만료 안내를 덮어쓰지 않는지 확인합니다. 이 읽기 실패는 새 키/POST를 만들거나 기존 불명확 요청 복구 규칙을 변경하지 않습니다. 앞선156개 실행은 중간 결과이며 최종171개와 합산하지 않습니다.

- 확정된 5개 상태별 취소·신청·승인·반려·철회 입력 조건, 자기 판단 금지, 현재 배정, KST 날짜, UTF-8 사유 및 전체 JSON 32KiB 상한.
- 공통 키·결과 조회를 쓰는 정확한 API 경로·본문·최소 8개 응답 필드, 숫자/문자 ID와 별도 취소 표시.
- 응답 유실 시 본문·키 보존, 결과 확인 전 재시도 금지, `not_recorded` 뒤 동일 요청 재전송, 권한 상실 및 계정 변경.
- `write_enabled=false` 기술 연결 안내와 실행 잠금, 입력 확인/실행 분리, 세션 변경 전후 늦은 성공 차단, 읽기 전용 요청함 및 미확인 요청 복구.
- 기존 업무 조회의 취소 포함 opt-in 및 구형 서버 호환, 취소 상세의 원래 상태 유지, 새 행동 비활성, Designer 최소 크기 배치.

선택적으로 `--layout-dir <절대폴더>`를 전달하면 테스트 대역 화면의 PNG를 저장합니다. `lifecycle-recovery-minimum.png`에는 최소 크기의 긴 사유 복구창이 포함됩니다. DrawToBitmap과 실제 컨트롤 경계의 자동 검사이며 사람의 수동 조작이나 공유 서버 화면 증거가 아닙니다. 테스트 안에서 실제 취소나 연장 요청을 실행하지 않습니다.
