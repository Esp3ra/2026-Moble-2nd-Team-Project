## 3. C10 — 회원·장치·슬롯 등록 제안

1. 장치 ID는 서버가 발급하는 불투명 ID를 사용한다. IP·호스트명·표시 이름·센서 슬롯 번호로 장치를 식별하지 않는다. IP 변경은 장치 ID 변경과 분리한다.
2. 서버 권한이 있는 등록자가 실물 장치와 직원 본인을 확인한 뒤 장치를 등록/활성화하고 회원·슬롯을 연결하는 안을 제안한다. 일반 직원 클라이언트가 임의 user_id/slot을 보내 본인 매핑을 등록하지 못하게 한다. 등록 담당 권한과 승인자는 팀장 결정 대기다.
3. user_id는 기존 users의 signed INTEGER FK, device_id는 불투명 ID, slot은 실제 장치가 지원하는 정수, mapping_revision은 양의 BIGINT 문자열이라는 1번 기준을 수용한다. 활성 device+slot의 중복 계정 연결은 금지한다. 직원당 장치 수·장치 공유/복수 손가락 허용 여부는 제안하지 않고 정책 확인을 받는다.
4. **센서 모델·저장 용량·0번 슬롯 지원·유효 상한은 아직 실물 확인 전이다.** 사용자 이전 등록 예시는 1부터 찾았지만 실제 하드웨어 전체 범위를 증명하지 않는다. 저장소 이름표 로더의 0~65535 검사도 센서 용량 규약이 아니다. 5번은 모델/제조사 자료와 장치 파라미터를 확인해 범위를 회신하고, 그 전까지 등록 API의 범위를 확정하지 않는다. 지문 원본·실명 슬롯 명부는 Git/협업 문서에 올리지 않는다.
5. 재등록/장치 교체는 기존 매핑 비활성화→revision 증가·진행 중 확인 무효화→실물 재등록→새 매핑 활성화 순서를 제안한다. 센서 삭제/저장과 DB를 하나의 트랜잭션으로 묶을 수 없으므로 중간 실패 때 활성 매핑을 만들지 않고 등록 미완료로 남겨 관리자가 재확인한다. 슬롯 초기화 성공을 회원 탈퇴/근태 삭제로 연결하지 않는다.

## 4. C10 — PC 중계 방식의 본인 확인 프로토콜 제안

다음은 **구현 전 검토안**이다. 제안 경로/필드·TTL·키 방식은 실행 API나 확정 계약이 아니다. 원격 직원의 Pi가 사설망에 있을 수 있으므로 공통 서버가 임의 Pi주소에 접속하는 방식 대신 **Windows PC가 메시지만 중계**하는 안을 제안한다. 인증 성공 판단과 계정 선택은 서버가 한다.

1. 로그인된 PC가 현재 `ApiClient.CaptureSession()`으로 공통 서버에 본인 확인 요청을 보낸다. 서버는 현재 actor/접속·활성 매핑·장치 상태를 검사하고 단일사용 challenge를 발급한다. 클라이언트가 보낸 회원 ID를 인증 근거로 사용하지 않는다.
2. 서버는 challenge를 현재 actor/접속·device/mapping_revision·용도에 묶어 저장한다. 최소128bit 무작위 nonce·challenge_id·서버 발급/만료 시각을 포함한다. 기술 TTL은 1번 제안의60초를 **협의 후보**로 두며 지문 확인 주기나 성공 결과의 유효 기간과 혼동하지 않는다.
3. PC가 서버 발급 티켓을 Pi의 별도 검증 경로에 전달한다. Pi가 서버 발급/장치 대상을 검증할 수 있도록 **장치별 공유키 HMAC-SHA256으로 서버 요청과 Pi 결과를 각각 인증하는 안**을 제안한다. 요청/결과에는 서로 다른 용도 식별자를 사용한다. 1번이 비대칭 서명을 선호하면 키 운영과 함께 재협의한다.
4. Pi는 검증된 새 요청을 센서 잠금 안에서 처리하고 기존 손가락 떼기→올리기로 **요청 이후 새 스캔**을 한다. 완료된 성공 결과를 다음 challenge에 재사용하지 않는다. 진행 중에는 동시에 다른 스캔을 시작하지 않고 재전송/중복 요청의 처리 상태를 구분한다.
5. Pi는 challenge 참조·device/key/mapping 참조·실제 검색 슬롯 또는 실패 분류를 인증된 결과로 반환한다. PC는 이를 변경하지 않고 서버에 전달한다. Pi에는 공통 계정 Bearer를 보내지 않는다. 현재 이름표/점수는 본인 확인 증거·회원 선택·권한 부여에 사용하지 않는다.
6. 서버는 같은 현재 접속/회원·매핑 revision·장치/키 활성·결과 인증·서버 시각 만료·미사용 challenge·실제 슬롯 일치를 재검사한다. 검증과 challenge 소비·최소 결과/감사 기록은 공통 guard/트랜잭션 안에서 처리한다. 다른 계정/옛 접속/변경 매핑의 결과는 거절한다. 동일 완료 요청의 재시도는 같은 효과만 반환하고 다른 결과로의 변경은 거절한다.

### 메시지·전송 검토 요청

| 구간/제안 경로 | 제안 입력·출력 | 1번 확인 요청 |
|---|---|---|
| PC→서버 `POST /api/v1/device-verifications/challenges` | 서버가 현재 세션으로 본인을 선택. 출력: challenge_id·장치 대상·인증된 불투명 티켓·만료 시각 | 매핑 선택 방법, 기존 envelope/오류 규약, 서버 상태/행동 용도 바인딩 |
| PC→Pi `POST /identity/scan` | 입력: 서버 티켓. 출력: device/key/challenge 참조·인증된 결과 묶음. 이름/점수/영상은 증거 필드에서 제외 | 요청 위조/재사용 방어, 결과 바이트 규약·장치 설치/키 운영 |
| PC→서버 `POST /api/v1/device-verifications/complete` | 입력: challenge_id와 변경하지 않은 인증 결과. 출력: 본인 확인 결과 ID/상태·서버 확인 시각 | 현재 접속 검사·단일 효과/재응답·결과 유효 기간·실패 분류 |

서명 대상 바이트의 C#/Python 차이를 막기 위해, 인증된 JSON 본문을 base64url로 감싼 원문을 그대로 중계하고 그 원문과 프로토콜 버전/요청·결과 구분을 MAC에 묶는 안을 제안한다. PC가 JSON을 다시 직렬화하지 않는다. 필수 필드·허용 문자/길이·숫자/시각 형식·중복 키/미지 필드·base64url/MAC 인코딩·상수시간 비교는 1번과 메시지 규약/공통 테스트 벡터로 확정한다. 이 초안에는 실제 nonce·키·실명·슬롯 배정값을 싣지 않는다.

PC↔공통 서버와 PC↔Pi의 제품 경로는 인증서를 검증하는 TLS 전송을 전제로 협의한다. 현재 HTTP:8080 시연을 인증 완료로 승격하지 않는다. 원격망 연결/인증서 배포 방법은 확인 대기이며 공인망 노출·자동 포트 개방을 요청하지 않는다. 서버 연결용 별도 flag는 기본off로 제안한다.

### 키·만료·오류 처리 제안

- 장치별로 다른 키와 key_id를 사용하고 1번의 서버 비공개 키 저장/발급 방법에 맞춘다. 승인된 실물 설치 시 Pi의 서비스 계정 전용 비공개 설정에 배포하는 절차를 합의한다. Git·일반 로그·공통 감사·URL·Windows 개인 설정에는 키를 두지 않는다. 키 교체/분실/장치 폐기는 기존 키·진행 중 challenge·매핑/확인 상태를 무효화하며, 완료 결과의 후속 효력도 현재 상태를 재검사한다. 실제 키 생성/설치는 이번에 하지 않는다.
- 입력 시간 초과·미등록/다른 슬롯·센서 오류·장치 사용 중·통신 실패·서명 오류·만료·변경된 접속을 구분한다. 불분명한 응답/비서명 HTTP 성공을 본인 확인 성공으로 저장하지 않는다. offline 성공 캐시를 인증 근거로 나중에 제출하지 않는다.
- 결과 전송 중 응답이 사라지면 같은 challenge/동일 결과로 완료 조회/재시도하는 계약을 제안한다. 결과를 임의로 바꿔 재전송하지 않는다. 새 지문 입력은 새 challenge를 발급받는 별도 시도다. 같은 challenge의 완료/실패를 언제 소비할지는 1번 상태 계약에서 확정한다.
- 현 Pi는 떼기/올리기 각 최대15초이며 공통 ApiClient의 HTTP 기본 제한은12초다. 긴 스캔은 PC↔Pi 전용 클라이언트에서 수행하고, 공통 서버 발급/완료 요청은 짧게 유지하는 안을 제안한다. Pi 스캔·PC 대기 제한·서버 TTL은 함께 합의하며 공통 HTTP 제한을 임의로 늘리지 않는다. 서버 만료는 서버 시각이 권위이고 장치 시각은 성공 유효성 근거로 사용하지 않는다.

### 수명·상태 접점

5번은 카메라/조도 처리를 활동 창 밖의 근무 세션 소유 서비스로 분리하는 안을 제안한다. MainForm이 합의된 서비스의 연결/해제 접점만 가지며 개별 업무 화면에서 카메라를 소유하거나 재시작하지 않는다. 기존 활동 창은 상태/설정 확인 화면으로 사용할 수 있지만 창 닫기가 근무 중 감지를 종료하는 현재 동작은 공동 합의 후 변경한다. MainForm/로그인 코드는 이번에 수정하지 않는다.

- **출근 요청:** 공통 서버가 현재 로그인 회원·근태 상태를 검사하고 저장 성공을 반환한 뒤 감지를 시작한다. 지문 확인을 출근 필수 조건으로 둘지는 별도 정책이며, 지문 성공을 출근 저장 성공으로 표시하지 않는다.
- **다른 메뉴:** 같은 근무 세션의 감지를 유지한다. 로그아웃/세션 만료/앱 종료 시 소유 장치는 정리하지만 이를 서버의 퇴근으로 자동 기록하지 않는다. 재로그인/재실행 후 서버의 진행 중 근무 상태를 조회해 복구하는 방식은 1번/팀장과 합의한다.
- **퇴근 요청:** 서버 퇴근 저장 성공 후 감지를 종료하는 흐름을 제안한다. 통신 실패·불확정 응답은 성공으로 표시하지 않고 동일 요청 키/상태 조회로 확정한다. 앱 종료/네트워크 단절 때 미종료 근무의 처리 정책은 팀장 결정 대기다.
- **카메라/Pi 단절:** 연결 오류·확인 필요로 표시하고 무감지30초 누적을 끊는 기존 기준을 유지한다. 기존 업무 상태·서버 출퇴근·결근/연차 상태를 센서만으로 바꾸지 않는다.

본인 확인 성공의 유효 범위/시간과 출근 허용 조건, 하루 중복 출근·재출근·날짜 경계·진행 중 근무·퇴근 권한/정정, 관리자 조회, 연차 신청/승인·일수 계산은 별도 근태 계약이 필요하다. 이번 초안에서 연차 API/승인 정책을 임의 확정하지 않는다. 근태 API 경로와 신규 테이블/마이그레이션 번호도 미정이며 기존002~006을 사용/예약하지 않는다.

## 7. 저장·검증 계획·이번 작업 결과

검증 저장은 1번 최소안(actor/불투명 device·mapping revision/challenge digest·소비 상태/서버 발급·만료·확인 시각/성공·실패 분류)을 수용한다. nonce 원문·키·생체 템플릿·원본 지문·손/얼굴 영상·실명 이름표/점수는 일반 감사나 Git에 저장하지 않는다. 임시 challenge 정리와 결과/근태 감사의 보관 기간을 분리해 합의한다. 센서 원시값/영상 프레임을 근태 DB에 계속 쌓는 안은 제안하지 않는다.

합의 후 공동 검증 항목: 본인/타인 슬롯, 변조/옛 nonce/만료/다른 로그인·동시 중복/같은 재시도·다른 결과 재시도, 키 교체/장치 폐기/매핑 변경, 로그아웃 경합/트랜잭션 rollback, Pi/PC/네트워크 단절·재연결, 출근·퇴근 재요청/불확정 응답·메뉴 이동/재실행·근무 중 만료, 건강한 세 입력30초와 오류 구분이다. 모의 입력/loopback/실제 서버·소유 DB/실장비·다른 PC의 검증 결과를 나눠 기록한다.

이번 실제 수행은 최신 코드·LOG/PR 원문 대조, 협업 초안/목차 작성과 문서 링크·표·diff 검사다. 코드·API·DB·서비스·장치 설정을 변경하지 않았고 프로그램/장치/보안/DB 테스트는 이번 문서 작업에서 실행하지 않았다. 기존264검증/30개 결과는 PR23 검토 이력이며 신규 프로토콜/근태 통합 시험이 아니다. 팀장 전용 날짜LOG·다른 번호 문서는 수정하지 않았다.
