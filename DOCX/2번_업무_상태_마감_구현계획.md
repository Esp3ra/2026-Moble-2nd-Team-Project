# 2번 담당: 업무·상태·마감 관리 구현계획

작성일: 2026-10-16 · 구현 전 검토안

이 문서는 2번 담당 기능을 어떤 순서로 구현할지, 어떤 API와 DB 데이터가 필요한지 정리한 계획이다. 현재 프로젝트는 WinForms 화면과 읽기 연결 준비 단계이며, 아래 API·테이블·파일명은 **구현 제안**이다. 실제 서버나 DB에 이미 존재하는 계약으로 간주하지 않는다.

**사용자가 확정한 업무 규칙은 기준으로 반영하고, 공통 권한·상태 연결 등 미확정 세부 사항은 ‘1번·3번과 합의 필요’로 표시한다.** 상대 담당 코드는 변경하지 않는다. 확정된 변경은 기준 DOCX에 반영하고 이전 Word 사본은 별도 감사 보관한다. 이번에는 목록·상세·필터를 연결할 읽기 인터페이스와 명시적 테스트 대역, 비동기 화면 상태를 준비한다. 기본 실행은 서버 미연결이며 실제 HTTP·DB·업무 저장 기능을 구현하거나 검증한 것으로 취급하지 않는다.

## 1. 기준과 담당 범위

기준은 같은 폴더의 `원격 근무용 업무 처리 확인 시스템.docx`, `폼 수정사항.md`, 현재 프로젝트 README와 이후 사용자 수정사항이다. 이전 문서의 우선순위·숫자 진행률보다 최신 수정사항을 우선한다.

원본 DOCX·PDF·폼 수정사항과 이 구현계획서는 별도 [DOCX 브랜치](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/tree/DOCX/DOCX)에서 관리한다. `alpha`와 `0.0.2V`에는 솔루션·화면 소스·미리보기를 게시하며 `DOCX` 폴더는 포함하지 않는다. 실행·화면 구성은 [alpha README](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/alpha/README.md)를 따른다. 문서 목록은 [문서 브랜치 README](../README.md)에서 확인한다. Word는 확정 변경을 반영한 최신 기준본 1개를 유지하며 이전 Word 사본은 별도 감사 보관한다.

- 업무 우선순위는 사용하지 않는다.
- 업무 상태는 **진행전 / 진행중 / 제출완료 / 승인완료 / 반려완료** 5개로 통일한다. 진행과 처리를 별도 상태로 나누지 않는다.
- 새 업무는 **진행전** 개념으로 시작한다. 정식 제출은 **제출완료**, 관리자 승인·반려는 각각 **승인완료·반려완료**로 구분하며, 업무의 최종 완료는 승인완료일 때만 인정한다. 반려완료는 반려 판단이 끝났다는 뜻이며 최종 완료가 아니다.
- 5개 상태의 표시와 관리자 검토 필수 원칙은 확정됐다. 저장 코드·DB 기본값·API/DB 연결 규격 및 반려 후 재작업의 복귀 시점은 **1번·3번과 합의 필요**다.
- 관리자도 본인에게 배정된 업무를 수락하고 결과를 제출·재제출할 수 있다. 관리자의 본인 업무는 **상위 검토자**가 승인·반려하며 자기 결과물을 스스로 판단할 수 없다. 상위 검토자와 계정·권한을 연결하는 방식은 **1번·3번과 합의 필요**다.
- 현재 로그인 화면의 직원·관리자 선택은 화면 검토용이다. 실제 권한은 1번의 서버 인증 결과를 사용한다.

| 업무 상태 | 확정된 의미 |
|---|---|
| 진행전 | 배정됐으나 담당자가 아직 수락하지 않음 |
| 진행중 | 담당자가 업무를 수락해 수행함 |
| 제출완료 | 결과를 정식 제출하고 검토자의 판단을 기다림 |
| 승인완료 | 검토자가 승인했으며 업무가 최종 완료됨 |
| 반려완료 | 반려 처리가 끝났으며 수정·재제출이 필요함 |

**배정 후 진행전 → 담당자 수락 시 진행중 → 정식 제출·재제출 시 제출완료 → 검토자의 승인 또는 반려 시 승인완료·반려완료**라는 기본 전환은 확정됐다. 반려완료 후 재작업을 위해 진행중으로 복귀시키는 시점과 저장·연결 코드는 합의 필요다.

### 확정된 결과 제출·검토 원칙

- **직원과 관리자를 포함한 담당자가 결과를 정식 제출·재제출하면 반드시 권한 있는 관리자의 승인 또는 반려 과정을 거친다.** 관리자의 본인 제출본은 상위 검토자가 판단하며, 검토 여부를 선택 사항으로 두지 않는다.
- 제출 직후 업무 상태는 **제출완료**이며 검토자의 판단을 기다린다. **관리자 승인 후 승인완료일 때만 업무를 최종 완료로 처리한다.** 제출 성공이나 반려완료만으로 최종 완료가 되지 않는다.
- 반려 후 수정한 결과를 재제출해도 다시 관리자의 승인 또는 반려를 거친다.
- **마감기한 경과에 따른 자동 결과 제출은 기능 범위에서 제외한다.** 담당자가 직접 결과를 제출하며, 마감 경과만으로 제출 기록·제출 시각·버전·제출완료 상태를 만들지 않는다.
- 마감 시 자동 검토 요청의 도입 여부와 생성 조건은 별도로 **3번과 합의 필요**다. 자동 검토 요청을 생성하더라도 결과물이 제출된 것으로 처리하지 않는다.
- 별도의 검토 요청 버튼을 누르지 않았다는 이유로 제출 결과가 관리자 검토에서 누락되면 안 된다. 결과 제출을 관리자 검토 대상으로 연결하고 관리자 본인의 결과물을 상위 검토자에게 배정하는 구체적인 API·DB·권한 방식은 **1번·3번과 합의 필요**다.

| 구분 | 2번이 담당할 내용 | 연결 담당 |
|---|---|---|
| 화면 | 업무 목록·상세, 등록·수정, 수락, 검토 요청, 마감 연장 요청, 관리자 요청 확인 | 공통 로그인·메인은 1번 |
| API | 업무 조회·등록·배정·수정·취소, 수락, 업무 상태 조회와 행동별 전환 연결, 요청 접수·조회, 마감 처리 | 공통 인증·응답 규격은 1번, 상태·검토자 연결은 1번·3번과 합의 필요 |
| DB | 업무 기본 정보, 배정과 수락 기록, 업무 관련 요청 기록 | 사용자·공통 이력 규격은 1번 |
| HTML | 위 업무 기능에 대응하는 웹 화면과 동일 API 연결 | 공통 웹 틀은 1번 |
| 다른 담당 기능 호출 | 공통 첨부파일, 결과물·승인 정보 참조, 협업 요청 창, 마감 변경 전달 | 파일·결과물·승인·이력 조회는 3번, 협업·채팅·알림은 4번 |

업무 화면에 첨부파일이나 협업 요청 버튼이 있어도 해당 저장 구조까지 2번이 중복 구현하지 않는다. 업무 변경 이력은 1번의 공통 기록 방식을 호출하고, 이력 조회 화면은 3번 범위를 따른다.

## 2. 권장 구현 순서

**첫 목표는 ‘업무 목록·상세 한 기능을 WinForms → HTTP → Flask → MySQL까지 실제로 연결하기’다.** 이후 저장 기능을 하나씩 추가하면 오류가 화면·서버·DB 중 어디에 있는지 확인하기 쉽다.

| 순서 | 구현할 내용 | 완료 확인 | 합의가 필요한 지점 |
|---|---|---|---|
| 1 | 1번의 서버 실행법, DB 연결, 사용자 ID·역할, 인증 전달, 오류 응답, 공통 이력 규격 확인. 업무 입력 항목과 조회 DTO 초안 작성 | 관리자·직원 테스트 계정을 구분하고 API 인증 실패를 확인 | 사용자 PK·관리자 조회 범위·API 공통 규약은 1번과 합의 필요 |
| 2 | 업무 기본 정보와 배정 데이터의 스키마 초안 검토. `GET` 목록·상세부터 구현하고 화면에 연결 | DB에 있는 업무만 표시. 직원은 현재 본인 배정만, 관리자는 내 업무와 허용된 관리 업무를 구분해 조회. 빈 목록·타인 업무·서버 중단 확인 | 5개 상태의 저장 코드·응답 필드와 상위 검토자의 조회 권한은 1번·3번과 합의 필요. 화면 예시를 실제 응답으로 간주하지 않음 |
| 3 | 관리자 등록·최초 배정. 제목·내용·담당자·시작일·마감일 입력과 서버 검증 | 직원 또는 관리자에게 배정한 업무가 등록 후 재조회·프로그램 재실행에도 같은 데이터로 표시 | 최초 상태는 진행전 개념으로 확정. 저장 코드·DB 기본값과 배정 가능한 사용자 범위는 1번·3번과 합의 필요 |
| 4 | 수정·재배정·취소 구조와 수정 충돌 처리. 재배정은 새 배정 차수로 기록 | 두 관리자의 동시 수정, 옛 배정으로 수락하는 요청이 최신 정보를 덮어쓰지 않음 | 수락·제출 이후 변경 가능 항목, 취소 가능한 상태는 3번과 합의 필요 |
| 5 | 직원·관리자 본인 업무의 수락과 5개 업무 상태 표시를 위한 DTO·서비스 위치 준비 | 수락·정식 제출·승인·반려의 행동별 연결 후 권한과 현재 상태를 서버에서 검사. 임의 상태 변경으로 제출·검토를 우회하지 못함 | 기본 전환은 확정. 상태 저장 코드·행동별 연결 규격·반려 후 재작업 복귀 시점·상위 검토자 권한 매핑은 1번·3번과 합의 필요 |
| 6 | 마감 연장 요청의 입력·접수 인터페이스·관리자 조회 준비. 실제 접수는 신청 조건 합의 후 연결. 검토 요청은 의미도 먼저 합의 | 합의 후 연장 요청 접수만으로 기존 마감일이 변하지 않음. 동일 전송 재시도 시 요청이 중복 생성되지 않음 | 검토 요청 의미, 업무 상태별 신청 조건, 연장 승인 반영 조건은 3번과 합의 필요 |
| 7 | 합의된 연장 반영과 4번 알림 연결. 자동 검토 요청은 도입 여부 합의 후 연결 | 연장 후 모든 화면이 저장된 마감일을 조회. 자동 검토 요청 도입 시 반복·동시 실행의 중복 검사 | 자동 검토 요청 도입·생성 조건·처리 회차·중복 기준은 3번과 합의 필요. 변경 알림 방식은 4번과 합의 필요 |
| 8 | 같은 API를 HTML에 연결하고 두 PC에서 전체 흐름 검증 | 한 PC의 변경을 다른 PC와 웹에서 재조회해 같은 담당자·날짜·상태 확인 | 자동 갱신 주기나 실시간 전달 방식은 1번·관련 담당과 합의 필요 |

각 단계는 화면 표시, API 응답, 실제 DB 저장을 함께 확인한다. 합의가 필요한 기능도 입력 모델·호출 위치·확인할 질문까지 준비할 수 있으며, 업무 규칙은 합의 후 연결한다.

## 3. 화면과 코드 연결 구조

```text
기존 LoginForm → MainForm → TasksControl
                            ├─ TaskEditForm
                            ├─ ReviewRequestForm
                            ├─ DeadlineExtensionForm
                            └─ TaskRequestsForm

업무 화면 → TaskService → 1번 공통 ApiClient → Flask 업무 API
                                               ↓
                                       업무 서비스 → MySQL
```

기존 화면은 `RemoteWork.WinForms/Features/Tasks`의 `.cs`, `.Designer.cs`, `.resx`를 유지한다. 배치는 디자이너로 관리하고, 기능 연결 시 `.cs`에서 입력 수집·응답 표시·이벤트 연결을 담당한다.

화면 뼈대에서 관리자는 업무 화면의 **내 업무 / 관리 업무**를 선택한다. 내 업무에는 수락·검토 요청·마감 연장, 관리 업무에는 등록·수정·취소·요청 확인을 배치한다. 결과물 화면의 **내 결과물 / 결과물 검토**는 3번 담당이며, 내 결과물에서 제출·재제출하고 결과물 검토에서 승인·반려한다. 직원에게는 본인 화면만 표시한다. 관리자의 내 업무·관리 업무 구분과 행 선택, 전체·5개 업무 상태 필터는 읽기 인터페이스에 조건을 전달하도록 준비한다. 기본 실행은 서버 미연결 상태이며, 명시한 테스트 대역을 사용하는 검증에서만 예제 목록·상세·필터와 비동기 상태를 확인한다. 실제 서버 조회·저장·권한 검사가 연결됐다는 뜻은 아니다. 결과물 화면의 범위 전환은 3번 담당의 기존 고정 예시 구성을 유지한다. 검토 요청 창은 제출완료된 결과의 검토 예시를 표시하며, 관리자 요청 화면의 요청 자체 상태는 업무 상태와 구분한다.

생성할 파일의 예시는 다음과 같다. 실제 폴더명은 1번의 공통 구조를 확인한 뒤 맞춘다.

| 위치 제안 | 역할 |
|---|---|
| C# `Models/Tasks/TaskDto.cs`, `TaskRequestDto.cs` | 조회 데이터와 요청 데이터 형식 |
| C# `Services/Tasks/TaskService.cs` | 공통 ApiClient를 통한 업무 API 호출 |
| Flask `features/tasks/routes.py` | 인증된 요청의 입력과 HTTP 응답 처리 |
| Flask `features/tasks/service.py` | 권한·날짜·배정·상태 검사, 트랜잭션 경계 |
| Flask `features/tasks/repository.py` | 매개변수를 사용하는 SQL 실행 |
| 공통 웹 폴더의 업무 템플릿 | 데스크톱과 같은 API·권한·검증 규칙 사용 |

Form에 DB 계정이나 SQL을 넣지 않는다. HTTP 인증·오류 해석은 공통 통신 계층을 사용한다. 공통 계층에서 `HttpClient` 연결을 재사용하는 구성은 [Microsoft 지침](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/http/httpclient-guidelines)을 따른다.

## 4. 필요한 API 제안

아래 경로는 가칭이며, `/api/v1` 같은 공통 접두사와 응답 포맷은 1번 규약에 맞춘다. **경로 제안이 곧 구현 승인이나 업무 규칙 확정을 뜻하지 않는다.**

| 메서드·경로 | 용도·주요 입력 | 권한·연결 조건 |
|---|---|---|
| `GET /tasks` | 업무 목록. 내 업무·관리 업무 조회 범위, 업무 상태·검색·날짜·담당자·페이지 조건 | 직원은 본인 현재 배정만. 관리자도 내 업무를 조회할 수 있으며 관리 업무는 허용된 범위만 조회. 선택값·필터로 권한 확장 불가 |
| `GET /tasks/{taskId}` | 기본 정보·현재 배정·수락 기록·단일 업무 상태·수정번호 조회 | 목록과 같은 서버 권한 검사. 5개 상태의 저장 코드·결과물 연결은 합의된 계약으로 표시 |
| `POST /tasks` | 제목·내용·담당자·시작일·마감일 등록 | 관리자. 업무와 최초 배정을 함께 저장하며 담당자는 직원 또는 관리자. 최초 상태는 진행전이며 저장 코드·DB 기본값은 1번·3번과 합의 필요 |
| `PATCH /tasks/{taskId}` | 기본 정보 수정 또는 재배정, `expectedVersion` | 관리자. 필드별 변경 가능 조건과 제출 이후 정책은 3번과 합의 필요 |
| `POST /tasks/{taskId}/cancel` | 취소 사유, `expectedVersion` | 관리자. 실제 삭제 대신 취소 기록 제안. 취소 조건은 3번과 합의 필요 |
| `PUT /tasks/{taskId}/assignments/{revision}/accept` | 해당 배정 수락, `expectedVersion` | 직원·관리자 구분 없이 현재 담당자. 수락과 진행중 상태의 저장 연결 규격은 1번·3번과 합의 필요 |
| `POST /tasks/{taskId}/requests` | `type`, 사유, 배정 차수, 업무 수정번호, 재시도 식별키. 연장 요청은 희망 마감일 추가 | 현재 담당자인 직원·관리자의 요청 접수용. `REVIEW` 의미와 각 신청 조건은 3번과 합의 필요 |
| `GET /task-requests` | 관리자 관리 업무의 요청 목록, 요청 유형·업무·페이지 조건 | 관리자는 허용된 관리 범위. 본인 요청 조회를 제공한다면 직원·관리자 모두 본인 요청 범위만 |
| `GET /task-requests/{requestId}` | 요청 사유·신청 당시 정보·처리 내역 조회 | 요청 및 관련 업무의 조회 권한 확인 |
| `POST /task-requests/{requestId}/decision` | 연장 요청의 승인·거절, 의견, 요청·업무 수정번호 | **마감 연장 판단 전용 제안**. 적용 조건은 3번과 합의 필요. 결과물 승인 API로 사용하지 않음 |

담당자 선택에 필요한 배정 가능 사용자 목록(직원·관리자)은 **1번의 사용자 조회 API**를 사용한다. 별도 사용자 테이블이나 인증 API를 만들지 않는다. 업무별 첨부·결과 제출·재제출·버전·승인·반려 API는 3번 계약을 따른다. 모든 정식 제출·재제출을 필수 관리자 검토로 연결하고, 관리자의 본인 제출본은 상위 검토자만 승인·반려한다.

범용 상태값 변경 경로 대신 수락·정식 제출·승인·반려의 행동에 따라 서버가 단일 업무 상태를 갱신하도록 연결한다. 수락은 위 API, 제출·재제출·승인·반려는 3번 API 계약을 사용한다. 기본 정보 수정이나 임의 상태값 PATCH로 제출 기록 생성·관리자 판단·상위 검토자 검사를 우회할 수 없으며, 자기 제출본의 승인·반려 요청은 관리자 계정이어도 거부한다. 상태 갱신의 트랜잭션·저장 코드와 반려 후 재작업 복귀 시점의 연결 규격은 **1번·3번과 합의 필요**다.

자동 결과 제출은 제외한다. 마감 시 자동 검토 요청을 도입한다면 서버 내부 작업으로 설계하며, WinForms가 켜져 있어야 실행되는 타이머에 의존하지 않는다. 도입 여부·실행 시점·생성 조건·미제출 업무의 표시는 **3번과 합의 필요**다. 마감 후 직접 제출 허용 여부와 연장이 필요한 조건도 합의한 뒤 적용한다.

### 요청 예시: 마감 연장 접수

아래는 계약 검토용 JSON이다. 날짜는 예시이며, 실제 허용 조건을 정한 것은 아니다.

`POST /tasks/101/requests`

```json
{
  "type": "DEADLINE_EXTENSION",
  "assignmentRevision": 2,
  "expectedTaskVersion": 8,
  "reason": "추가 자료를 반영할 시간이 필요합니다.",
  "requestedDueDate": "2026-10-26",
  "idempotencyKey": "07d50336-2685-4a38-9219-0b69f25d1f89"
}
```

접수 성공 응답 후보:

```json
{
  "requestId": 501,
  "taskId": 101,
  "type": "DEADLINE_EXTENSION",
  "requestedDueDate": "2026-10-26",
  "createdAt": "2026-10-16T03:00:00Z"
}
```

신청자 ID·역할·현재 마감일·접수 시각은 서버가 결정한다. 접수 응답은 **마감일 변경 완료**를 의미하지 않는다. `REVIEW`는 의미를 합의한 뒤 같은 접수 형식의 사용 여부를 확정하고, 결과 제출이나 제출 버전 생성을 임의로 연결하지 않는다.

### 응답·실패 처리

- 조회 대상이 없을 때 목록은 빈 배열로 반환하는 안을 사용한다. 상세의 접근 거부·미존재 응답은 1번 규약에 맞춘다.
- 입력 오류, 인증 실패, 권한 없음, 수정 충돌을 화면에서 구분한다. 예를 들어 수정번호·배정 차수 충돌은 `409` 응답을 제안한다.
- 저장에 실패하면 입력 창을 유지한다. 서버 저장 후 응답만 유실된 경우는 재시도 키 또는 재조회로 결과를 확인하고 성공·실패를 단정하지 않는다.

## 5. DB 구조 제안

기본 구조는 **업무 1개 → 배정 기록 여러 개 / 요청 여러 개**다. 처음부터 결과물·파일·승인 테이블을 복제하지 않는다. 아래는 논리 설계이며 **DB에 실행할 확정 DDL이 아니다.**

업무 ID와 요청 ID는 `BIGINT` 계열을 후보로 제안한다. 사용자 참조 컬럼은 1번 사용자 PK와 타입·부호를 맞춘다. 문자열 길이도 아래 검토안을 공통 규격과 비교해 확정한다.

### 5-1. `tasks`: 업무 기본 정보

| 컬럼 후보 | 타입 후보 | 용도 |
|---|---|---|
| `task_id` | `BIGINT`, PK | 업무 식별자 |
| `title` | `VARCHAR(200)` | 업무 제목, 공백만 입력 불가 |
| `description` | `TEXT` | 업무 내용 |
| `task_status` | `VARCHAR(30)` 후보 | 단일 업무 상태. 진행전·진행중·제출완료·승인완료·반려완료에 대응하며 저장 코드·DB 기본값은 1번·3번과 합의 필요 |
| `start_date`, `due_date` | `DATE` | 시작일·마감일 |
| `current_assignment_revision` | `INT` | 현재 배정 차수 |
| `created_by` | 공통 사용자 PK와 동일 | 등록 관리자 |
| `created_at`, `updated_at` | `DATETIME(6)` | 서버가 기록하는 생성·변경 시각 |
| `row_version` | `BIGINT` | 오래된 화면의 덮어쓰기 방지용 수정번호 |
| `cancelled_at`, `cancelled_by`, `cancel_reason` | 시각·사용자 PK·`TEXT`, NULL 허용 | 취소 기록 후보. 허용 조건과 5개 업무 상태·조회 표시의 관계는 1번·3번과 합의 필요 |

업무 상태는 논리적으로 **단일 `task_status`**로 관리하며 진행과 처리를 위한 중복 상태 컬럼을 만들지 않는다. 최초 상태의 의미는 진행전으로 확정됐고, 실제 저장 코드·DB 기본값·기존 공통 구조와의 매핑은 **1번·3번과 합의 필요**다. 화면 문구를 그대로 MySQL ENUM으로 확정하지 않으며, 우선순위·숫자 진행률 컬럼도 추가하지 않는다.

관리자 본인의 제출본을 판단할 상위 검토자와 권한 매핑은 1번·3번의 공통 계약으로 연결한다. 2번이 독자적인 관리자 계층·검토자 테이블을 만들거나 관리자 역할만으로 자기 결과물 판단을 허용하지 않는다.

### 5-2. `task_assignments`: 배정과 수락 기록

| 컬럼 후보 | 타입 후보 | 용도 |
|---|---|---|
| `task_id` | 업무 PK와 동일 | `tasks` 참조 |
| `revision` | `INT` | 배정 차수. `(task_id, revision)` 복합 PK |
| `assignee_id` | 공통 사용자 PK와 동일 | 배정받은 담당자(직원·관리자) |
| `assigned_by` | 공통 사용자 PK와 동일 | 배정한 관리자 |
| `assigned_at` | `DATETIME(6)` | 배정 시각 |
| `accepted_at` | `DATETIME(6)`, NULL 허용 | 해당 배정의 수락 시각 |

재배정 시 이전 행을 덮어쓰지 않고 차수를 증가시켜 새 행을 만든다. 예를 들어 A 직원의 1차 배정을 수락한 기록이 있어도, B 직원으로 바뀐 2차 배정의 `accepted_at`은 별개다. **재배정을 허용하는 업무 상태 자체는 3번과 합의 필요**다.

`task_assignments → tasks` FK를 두고, `tasks.current_assignment_revision`은 업무 서비스가 같은 트랜잭션에서 유지하는 현재 배정 포인터로 제안한다. 이 초안에는 역방향 FK를 추가하지 않는다. 등록 시 업무+1차 배정을 함께 저장하고, 현재 배정을 조회할 때 업무 ID와 차수를 함께 사용한다.

### 5-3. `task_requests`: 검토·마감 연장 요청

| 컬럼 후보 | 타입 후보 | 용도 |
|---|---|---|
| `request_id` | `BIGINT`, PK | 관리자 요청 목록에서 사용하는 공통 요청 ID |
| `task_id`, `assignment_revision` | 배정 PK와 동일 | 어느 업무·배정에서 발생한 요청인지 참조 |
| `request_type` | `VARCHAR(30)` | 검토·연장 구분. `REVIEW`, `DEADLINE_EXTENSION`은 코드 후보 |
| `requested_by` | 공통 사용자 PK와 동일 | 신청 담당자(직원·관리자) |
| `reason` | `TEXT` | 검토 요청 내용 또는 연장 사유 |
| `requested_due_date` | `DATE`, NULL 허용 | 연장 요청의 희망 마감일. 검토 요청은 사용하지 않음 |
| `base_due_date` | `DATE` | 신청 당시 마감일. 서버가 업무에서 복사 |
| `base_task_version` | `BIGINT` | 신청 당시 업무 수정번호 |
| `request_state` | `VARCHAR(30)` | 요청 자체의 처리 상태. 값과 기본값은 합의 후 확정 |
| `created_at` | `DATETIME(6)` | 접수 시각 |
| `row_version` | `BIGINT` | 요청 처리의 동시 변경 검사 |
| `idempotency_key` | `CHAR(36)` | 같은 전송을 재시도할 때 사용하는 UUID |
| `payload_hash` | `CHAR(64)` | 같은 키로 다른 내용을 보냈는지 비교할 정규화 내용 해시 |

요청 처리 상태는 단일 업무 상태 `task_status`와 별개다. 연장 판단을 연결할 때는 `handled_by`, `handled_at`, `decision_code`, `decision_reason` 같은 처리 기록도 필요하다. 해당 값·반복 처리 정책·실제 마감 변경 조건은 합의 후 추가한다. **관리자가 검토 요청을 읽었다는 기록을 결과물 승인으로 해석하지 않는다.**

### 5-4. 관계·조회 인덱스·날짜

- 사용자 FK는 공통 사용자 테이블을 참조한다. 요청은 `(task_id, assignment_revision)`으로 배정 기록을 참조한다. 업무·배정·요청 기록을 연쇄 삭제하는 구조는 사용하지 않는 안을 제안한다.
- 조회 인덱스 후보: `tasks(due_date, task_id)`, `task_assignments(assignee_id, task_id, revision)`, `task_requests(task_id, created_at)`, `task_requests(request_state, created_at)`. 실제 검색 조건과 실행계획을 보고 조정한다.
- `(requested_by, idempotency_key)`는 UNIQUE 후보다. 동일 사용자가 같은 키·같은 내용으로 재시도하면 기존 요청을 반환한다. 같은 키·다른 내용이면 충돌로 처리한다. 이것은 전송 재시도 방지이며, 서로 다른 키로 신청한 같은 내용이나 자동 요청의 중복 기준까지 정하지 않는다.
- 시작일·마감일은 현재 날짜 입력 화면에 맞춰 `DATE`를 제안한다. 기록 시각은 서버에서 UTC로 만든 `DATETIME(6)`를 제안한다. `DATETIME`은 자동으로 UTC 변환하지 않으므로 공통 저장 규약이 필요하다. [MySQL 날짜 타입 문서](https://dev.mysql.com/doc/refman/8.4/en/datetime.html)
- 마감일 당일 포함 여부·마감 시각·업무 기준 시간대는 **1번·3번과 합의 필요**다. 날짜만 저장한 상태에서 임의의 자동 처리 시각을 정하지 않는다.

## 6. 저장·동시 수정 규칙 제안

1. 변경 요청은 인증 정보로 사용자·역할을 판단한다. 본문의 사용자 ID를 신청자 신원으로 믿지 않는다. 내 업무·관리 업무 선택도 권한 증거로 사용하지 않는다.
2. 업무 변경은 트랜잭션 안에서 업무 행을 먼저 잠그고, 권한·현재 배정·수정번호·합의된 상태 조건을 검사한다.
3. 업무와 배정 변경, 필요한 공통 이력 기록을 함께 성공시키고 수정번호를 증가시킨다. 실패하면 전체를 되돌린다. 공통 이력의 저장 방식은 1번과 맞춘다.
4. 같은 현재 배정을 다시 수락한 요청은 기존 수락 결과를 반환하는 안을 제안한다. 재배정 후 옛 차수로 수락하면 충돌로 처리한다. 수락 재시도 처리 순서와 상태 연동은 합의 후 구현한다.
5. 요청 접수의 재시도 키는 현재 권한을 확인한 뒤 기존 기록을 먼저 확인한다. 같은 키·같은 내용이면 최초 접수 결과를 반환하고, 새로운 요청일 때 현재 배정·업무 버전을 검사한다. 동시에 들어온 요청은 DB UNIQUE 제약으로도 중복을 막는다.
6. 연장 승인 반영 시 신청 당시 배정·마감일과 현재 정보를 다시 비교한다. 다른 변경으로 전제가 달라졌다면 재검토하게 하며, 옛 신청 내용으로 최신 마감일을 덮어쓰지 않는다. 제목만 바뀐 경우 등 재검토 범위도 합의해 정한다.
7. 업무 등록 같은 다른 생성 API도 1번의 공통 재시도 처리 방식을 재사용한다. 공통 기능이 없다면 생성 요청 식별키 저장 구조를 함께 정한다.
8. 제출·재제출·승인·반려 시 대상 제출본, 담당자, 판단자와 상위 검토자 권한을 서버에서 확인한다. 제출자와 판단자가 같은 자기 판단 요청을 거부하며, 제출 기록·판단 결과·업무 상태의 일치 방식은 1번·3번과 합의한다.

InnoDB의 `FOR UPDATE` 잠금은 트랜잭션 안에서 사용하고, 커밋·롤백 시 해제된다. 위 규칙은 그 특성을 이용한 설계 제안이다. [MySQL 잠금 읽기 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

## 7. 1번·3번과 합의 필요 목록

아래는 **함께 정해야 하는 세부 질문 목록**이다. 5개 단일 업무 상태, 모든 정식 제출·재제출의 관리자 판단 필수, 관리자 본인 제출본의 상위 검토자 판단은 확정됐다. 위 기본 상태 전환도 확정됐으며, 상태에 관한 합의 대상은 저장 코드·연결 규격·반려 후 재작업 복귀 시점과 상위 검토자 권한 매핑이다. 다른 기능의 미확정 신청·변경 조건은 아래 질문으로 구분한다. 상대 담당의 제출·승인·파일·이력 코드는 이번 작업에서 변경하지 않는다.

| 합의할 질문 | 영향을 받는 API·데이터 |
|---|---|
| 단일 `task_status`의 5개 상태를 어떤 저장 코드로 표현하며 진행전의 DB 기본값은 어떻게 둘 것인가? | 업무 등록, 상태 컬럼·기본값, 기존 공통 구조와의 매핑 |
| 수락·정식 제출·승인·반려 API에서 상태를 갱신하는 공통 규격과 트랜잭션은 무엇인가? | 2번 수락 API와 3번 제출·검토 API의 연결 |
| 관리자 본인 업무의 상위 검토자는 어떤 계정·권한으로 매핑하고 누가 조회·판단할 수 있는가? | 1번 인증·사용자 계약, 3번 검토자 조회·승인·반려 API |
| 정식 제출을 필수 관리자 검토로 어떻게 연결하는가? 별도 수동 검토 요청은 중간 피드백까지 포함하는가? | `REVIEW` 접수, 제출과 검토 대상의 연결 방식, 관리자 요청 화면 |
| 제출 버전과 승인·반려 결과를 어떻게 연결하는가? 검토 중 새 버전 제출과 동시 판단은 어떻게 처리하는가? | 3번 제출·검토 API 계약, 판단할 관리자의 권한 범위 |
| 결과물이 있는 업무를 수정·재배정·취소할 수 있는가? 기존 제출·수락 기록은 어떻게 보이는가? | 수정·취소 API, 배정 차수, 결과물 참조 |
| 어떤 상태에서 연장을 신청·승인할 수 있는가? 제출·검토 중 마감 변경은 어떤 영향을 주는가? | 연장 신청·판단, 실제 `due_date` 변경 |
| 마감 시 미제출 업무를 자동 검토 요청 대상으로 올릴 것인가? 도입한다면 생성 조건과 표시는 무엇인가? | 서버 자동 검토 요청. 결과 제출 기록 생성과 구분 |
| 마감 후 직접 제출을 허용할 것인가? 제출하려면 먼저 연장이 필요한가? | 3번 제출 API와 2번 마감·연장 규칙 |
| 수동·자동 요청이 겹치거나 자동 작업이 반복될 때 동일 처리 회차를 어떻게 식별하는가? | 중복 키·회차 구조·자동 작업 트랜잭션 |
| 반려완료 후 수정 작업을 위해 진행중으로 복귀시키는 시점과 API·DB 연결 규격은 무엇인가? | 단일 업무 상태, 3번 재제출·버전 API 계약. 재제출 시 제출완료 전환 자체는 확정 |
| 공통 파일·이력에 어떤 업무·배정·요청 ID를 전달하는가? | 3번 파일·이력 조회, 1번 공통 이력 기록 |

4번과는 **저장 완료된 마감 변경을 전달하는 방식, 기존 마감 알림 취소·재계산, 협업 요청에서 전달할 업무 ID**를 별도로 맞춘다. 2번의 업무 데이터와 4번의 알림·채팅 저장 구조를 각각 유지한다.

## 8. 구현 완료를 확인하는 기준

| 검증 범위 | 확인할 사례 |
|---|---|
| 화면 | 목록 선택→상세, 입력 오류, 빈 목록, 긴 내용, 로딩·실패·재시도 표시. 업무 상태가 5개로 통일되고 이전의 이중 상태·우선순위가 없음. 업무 행 선택·상태 필터·상세 및 비동기 화면 상태는 명시적 테스트 대역 검증과 실제 서버 검증을 구분함. 첨부 영역은 3번 계약 미연결로 목록을 비우고 조회 연결 필요 안내만 표시함 |
| 화면 범위 | 직원은 본인 화면만, 관리자는 내 업무/관리 업무·내 결과물/결과물 검토를 구분. 업무 읽기 화면의 기본 실행은 서버 미연결이며, 명시적 테스트 대역과 결과물 고정 예시 전환을 실제 권한 검증과 구분 |
| API 권한 | 직원의 타인 업무 직접 조회·수정, 직원의 관리자 등록·취소 요청, 타인 업무·옛 배정에 대한 요청 접수를 서버에서 거부. 관리자 내 업무의 수락·제출은 허용하되 관리 범위 선택으로 권한이 확대되지 않음 |
| DB 저장 | 등록·수정 후 재로그인·프로그램 재실행·별도 조회에서도 값 유지 |
| 입력 검사 | 빈 제목, 존재하지 않는 담당자, 잘못된 날짜, 시작일보다 빠른 마감일을 서버에서 거부 |
| 동시 처리 | 두 관리자의 수정 충돌, 재배정과 옛 배정 수락 경합, 동일 요청의 동시 재시도, 같은 재시도 키·다른 내용의 충돌 |
| 마감 요청 | 접수만으로 마감일 불변, 합의 후 연장 판단의 중복 처리와 오래된 신청 검사 |
| 필수 결과 검토 | 직원·관리자의 모든 정식 제출·재제출이 검토 대상으로 연결됨. 제출완료에서 승인완료 또는 반려완료로 판단하며 승인 전 최종 완료 불가 |
| 관리자 본인 결과물 | 본인 제출·재제출은 상위 검토자의 판단 대상. 관리자 자기 승인·반려 직접 API 호출 거부. 구체적인 상위 검토자 매핑은 합의 후 검증 |
| 자동 제출 제외 | 마감 경과만으로 제출 기록·제출 시각·버전·제출완료 상태가 생성되지 않음 |
| 기본 전환 | 배정 후 진행전, 직원·관리자 담당자의 수락 후 진행중, 정식 제출·재제출 후 제출완료, 권한 있는 검토자의 판단 후 승인완료·반려완료로 연결됨 |
| 상태 연결 | 확정된 기본 전환과 합의된 세부 연결 조건만 성공. 직원·관리자가 기본 정보 수정 또는 임의 상태 PATCH로 제출완료·승인완료·반려완료를 직접 설정하거나 필수 판단을 우회하지 못함. 반려 후 재작업 복귀 시점은 합의 후 검증 |
| 통합 | 실제 HTTP로 WinForms·서버·DB 연결, 두 PC와 HTML 재조회 일치, 인증 만료·응답 유실 처리 |

Flask 테스트 클라이언트는 실행 중인 실제 서버 없이 요청을 시험한다. 따라서 서버 내부 테스트 통과와 WinForms의 실제 네트워크 연결 성공은 나누어 확인한다. [Flask 테스트 문서](https://flask.palletsprojects.com/en/stable/testing/)

지금 착수할 묶음은 **① 공통 규약 확인 → ② 기본 정보·배정 스키마 검토 → ③ 목록·상세 GET → ④ WinForms 표시 연결**이다. 등록·수정·요청의 입력 구조는 이어서 준비한다. 5개 단일 상태와 필수 검토·상위 검토자 원칙을 기준으로 하되, 실제 API·DB·업무 규칙의 연결은 합의된 규격에 따라 이후 구현한다. 이번 읽기 화면 연결 준비는 실제 HTTP·DB 조회나 업무 저장 기능의 완료를 뜻하지 않는다.


## 9. 이번 읽기 화면 연결 범위와 공통 규약 감사

2026-10-16 공통 코드 감사에서 `alpha`와 로컬 프로젝트에는 실제 인증 사용자 문맥, 공통 HTTP 클라이언트·오류 응답 규약·DB 연결 규약 및 Flask 서버가 없는 것을 확인했다. 다른 프로젝트의 공통 코드를 이 프로젝트의 확정 계약으로 가져오지 않는다.

이번 범위는 업무 읽기 인터페이스, 기본 미연결 구현, 명시적으로 선택하는 테스트 대역과 WinForms 비동기 목록·상세·필터 연결 준비다. 기본 실행이 예제 데이터를 실제 조회 성공처럼 자동 표시하지 않도록 한다. 행 선택·조회 조건·상세 표시와 로딩·빈 값·오류·재시도 흐름은 명시한 테스트 대역으로 확인하고 실제 서버 검증과 구분한다. 첨부 영역은 3번 계약이 연결되지 않아 목록을 비우고 조회 연결 필요 안내만 표시한다.

실제 HTTP 호출, MySQL 조회·저장, 인증 및 서버 권한 검사는 이번 검증에 포함하지 않는다. API·테이블은 여전히 제안이며, 업무 등록·수락·제출·판단 등의 변경 기능은 연결하지 않는다. 표준 Designer와 화면 담당 범위도 유지한다.

| 함께 확인할 항목 | 합의가 필요한 질문 |
|---|---|
| 1번 공통 사용자·권한 | 실제 사용자 PK·역할은 어떤 형태인가? 내 업무·관리 업무의 서버 조회 범위를 어떻게 검사하는가? |
| 1번 HTTP·응답 | 공통 ApiClient, 기본 주소와 목록·상세 endpoint, 필터·페이지 조건, 응답 envelope·빈 값·오류 코드는 무엇인가? |
| 1번 DB·날짜 | DB 연결·변경 절차와 사용자 FK, 날짜·시간의 저장·전송 규약은 무엇인가? |
| 1번·3번 상태 연결 | 확정된 5개 상태의 wire·저장 코드, 기본값과 행동별 갱신 규격은 무엇인가? |
| 1번·3번 검토 권한 | 관리자 본인 결과의 상위 검토자를 어떻게 매핑하고 자기 판단을 서버에서 차단하는가? |
| 1번·3번 미확정 정책 | 자동 검토 요청의 도입·생성 조건·중복 회차, 반려 후 재작업 복귀 시점, 마감 시각·시간대·기한 후 제출·연장 조건은 무엇인가? |

기본 상태 전환, 모든 정식 제출·재제출의 필수 검토, 관리자 본인 제출본의 상위 검토자 판단과 자동 결과 제출 제외는 확정 기준이다. 위 질문은 그 원칙을 구현할 세부 계약이며 확정 규칙을 다시 선택 사항으로 돌리지 않는다.

공통 규약을 합의한 뒤 인터페이스를 실제 공통 HTTP 경로에 연결한다. 이후 실제 계정으로 목록·상세를 읽고 타인 업무 접근 거부, 인증 실패·서버 중단과 DB 재조회를 별도로 검증해야 실제 연결 완료로 기록할 수 있다.
