# 업무 목록·상세 조회 연결 경계

작성일: 2026-10-16

이 문서는 2번 담당의 목록·상세 조회 연결에 앞서 확인한 계약과 합의 질문을 정리한다.
범위는 현재 alpha 화면 구조를 유지하는 읽기 연결 준비이며, 다른 담당 기능을 구현하지 않는다.

## 1. 확인한 소스와 감사 결론

- 감사 기준은 alpha `2cd1a32724ecec8c21cd8ddd659dbbf30d43dcaf`, DOCX `958f89ef3ee443fd867262cc33a0cbc79950658e`와 로컬 2차 프로젝트다.
- 기준 소스에는 공통 인증 사용자, 공통 HTTP 클라이언트, 서버 API, 오류 응답 계약, DB 연결 구현이 없다.
- `Ui/PreviewRole.cs`는 화면 구분용이며 인증된 사용자나 권한을 뜻하지 않는다.
- `Shell/LoginForm.cs`의 역할 선택과 `MainForm.cs`의 이름·사번은 고정 화면 데이터다.
- 기존 `TasksControl`의 업무 행·상세도 고정 데이터이며 서버 응답이 아니다.
- 프로젝트는 .NET 8 Windows Forms이며, 감사 기준 csproj에 HTTP·DB용 외부 패키지나 서버 프로젝트 참조가 없다.
- 이는 조사한 저장소와 로컬 소스의 결과다. 외부 팀원 작업이나 별도 서버가 없다고 단정하지 않는다.

[DOCX 브랜치 구현계획](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/DOCX/DOCX/2번_업무_상태_마감_구현계획.md)의 API·DTO·테이블은 **제안**이다.
`GET /tasks`, `GET /tasks/{taskId}`와 테이블 후보를 이미 존재하거나 합의된 계약으로 사용하지 않는다.
화면의 `EMP-001`, `TASK-001`, 한글 상태명을 서버 PK나 저장 코드로 확정하지 않는다.

## 2. 사용자 확정 규칙

| 업무 상태 | 의미 |
|---|---|
| 진행전 | 배정됐으나 담당자가 아직 수락하지 않음 |
| 진행중 | 담당자가 수락해 수행함 |
| 제출완료 | 정식 제출·재제출 후 검토 판단을 기다림 |
| 승인완료 | 권한 있는 검토자가 승인했으며 최종 완료됨 |
| 반려완료 | 반려 판단이 끝났으며 수정·재제출이 필요함 |

- 단일 업무 상태 5개를 사용하며 우선순위·숫자 진행률·별도 진행/처리 상태를 추가하지 않는다.
- 배정→진행전, 수락→진행중, 정식 제출·재제출→제출완료, 검토 판단→승인완료/반려완료의 기본 전환은 확정이다.
- 직원과 관리자의 모든 정식 제출·재제출은 관리자 판단이 필수이며, 승인완료만 최종 완료다.
- 관리자는 본인 업무도 수락·제출할 수 있다. 본인 제출본은 상위 검토자가 판단하며 자기 승인·반려는 금지다.
- 마감 경과에 따른 자동 제출은 제외한다. 마감만으로 제출 기록·시각·버전·제출완료 상태를 만들지 않는다.
- 요청 자체의 확인·처리 상태는 업무 상태와 구분하며, 요청 확인을 결과물 승인으로 해석하지 않는다.

## 3. 이번에 준비하는 경계

- 목록·상세 조회용 인터페이스와 화면용 모델, 명시적 테스트 대역을 Tasks 내부에 둔다.
- 이 경계는 공통 인증·HTTP·오류 응답·DB 규격을 대신 확정하는 공개 서버 계약이 아니다.
- 미구성 상태, 빈 목록, 선택한 상세, 조회 실패와 재시도를 구분한다.
- 기본 실행의 미구성 상태와 테스트 대역 사용 여부를 명확히 표시한다. 실패 시 샘플로 조용히 대체하지 않는다.
- `ITaskQueryService.SourceDescription`으로 조회 데이터의 출처를 항상 표시한다.
- 테스트 대역의 Own/Managed는 고정 데이터 집합 구분이며 인증 사용자·권한 매핑이 아니다.
- `TaskDisplayStatus`는 화면용 논리값이다. 실제 사용자 신원과 상태 코드는 향후 공통 계약으로 연결한다.
- HTTP·인증·Flask·MySQL·SQL·사용자 테이블·공통 오류 규약은 이번에 구현하지 않는다.
- 업무 등록·수정·취소·수락·요청 저장·제출·승인·반려도 이번 읽기 연결의 구현 범위가 아니다.
- 기존 업무 처리 창은 정적 화면이며 선택한 조회 업무에 연결되지 않았다. 창을 열어도 해당 업무를 처리하지 않는다.
- 3번의 공통 파일·결과물·버전·판단·이력 조회와 4번의 협업·알림 저장을 중복 구현하지 않는다.

## 4. 1번에게 먼저 확인할 계약

| 질문 | 필요한 확인 |
|---|---|
| 실행할 서버가 있는가? | 소스 위치, 실행법, 개발 주소, 테스트 계정, 실제 연결 가능 여부 |
| 현재 사용자를 어떻게 받는가? | 사용자 PK의 타입·형식, 인증 결과와 역할, 신뢰할 사용자 컨텍스트 |
| 인증을 어떻게 전달하는가? | 공통 HTTP 주입 방식, 세션/토큰 규약, 만료·로그아웃 처리 |
| 공통 통신·오류 규격은 무엇인가? | 응답 구조, 오류 식별자, 취소·시간 초과, 인증 실패와 접근 거부 표시 |
| 조회 계약은 무엇인가? | 실제 경로·필드·식별자·페이지·검색/상태 필터·빈 목록 규격 |
| 관리자 관리 범위는 무엇인가? | 조직/배정/권한 기준, 직원·관리자 본인 범위와의 구분 |
| DB·날짜 공통 규약은 무엇인가? | 사용자 FK, 날짜/시각 타입, 시간대, 스키마 관리 방식; 2번이 독자 생성하지 않음 |
| 상세 미존재·접근 거부를 어떻게 응답하는가? | 401/403/404 등 실제 정책과 정보 노출 방지; 문서 예시를 확정값으로 사용하지 않음 |

## 6. 실제 서버에서 반드시 검증할 조회 권한

화면의 역할·범위·필터나 요청 본문의 사용자 ID는 권한 증거가 아니다. 서버는 인증 사용자로 판단해야 한다.

| 서버 검증 사례 | 현재 증거 |
|---|---|
| 직원 목록은 현재 본인 배정만 반환하고 타인 담당자 필터로 확장되지 않음 | 실제 서버 미실행 |
| 직원이 타인 taskId로 상세에 직접 접근해도 거부됨 | 실제 서버 미실행 |
| 관리자 내 업무 목록·상세는 본인 현재 배정 범위를 따름 | 실제 서버 미실행 |
| 관리자 관리 목록은 허용된 관리 범위만 반환함 | 실제 서버 미실행 |
| 관리자도 범위 밖 taskId의 상세를 직접 요청하면 거부됨 | 실제 서버 미실행 |
| 인증 누락·만료와 관리 범위 위조가 조회 권한을 우회하지 못함 | 실제 서버 미실행 |

테스트 대역에서 같은 사례를 검사해도 실제 서버의 수평 접근 통제 검증을 완료한 것은 아니다.

## 7. 완료 주장과 남은 검증

소스 감사와 인터페이스·테스트 대역 준비는 실제 업무 기능 또는 원격 연결 완료를 뜻하지 않는다.
실제 HTTP 요청, 인증된 조회, DB 조회·저장, 두 PC/웹 일치, 실제 서버 중단·인증 만료 검증은 아직 수행하지 않았다.
공통 계약을 받은 뒤 실제 어댑터를 연결하고 위 권한 검증과 통합 검증을 별도로 실행·기록한다.
