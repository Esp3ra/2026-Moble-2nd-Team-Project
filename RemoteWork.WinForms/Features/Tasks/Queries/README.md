# 업무 목록·상세 조회 경계

최신화: 2026-10-22 · 조회·등록·시작·관리/lifecycle와 접속 고정 읽기 제공 / PR52 소비 코드·PR64 탐색 조립 제공, 공유 통합 검증은 별도

실제 로그인한 MainForm은 `HttpTaskQueryService(AppServices.Api)`를 주입한다. 기본 TasksControl 및 PreviewRole 미리보기 생성자는 `UnconfiguredTaskQueryService`를 유지한다. `TaskQueryTestDouble`은 테스트에서 명시적으로 주입한다. 실패 시 샘플로 대체하지 않는다.

서버 업무 API는 개발용 명시적 활성화가 필요하며 기본 서버에서는 꺼져 있다. 활성화·테스트 DB 준비는 아래 개발 계약을 따른다. API가 비활성일 때 HTTP_404를 업무 연결 필요로 표시하며 실제 데이터 연결 성공으로 표시하지 않는다.

## 현재 연결

- 외부 알림의 내 업무 열기에는 `TasksControl.CaptureOwnTaskNavigator()`로 로그인/화면에 고정된 콜백을 제공합니다. 내 업무·전체 상태·취소 제외 목록의 정확한 행과 현재 상세를 다시 조회하며 대상이 없으면 다른 행을 대신 열지 않습니다. [UI 수명/호출 조건](../../../../docs/TASK_QUERIES.md#captured-own-task-navigation)을 따르고, MainForm의 로그인별 명시 탐색 조립은1번 PR64에서 제공됐습니다. 실제 알림 source·확인 저장은 후속입니다. 알림 현재 사건/배정 검사를 대신하지 않습니다.
- `ITaskQueryService`·TaskSummary·TaskDetail·DateOnly·불투명 TaskId를 유지한다.
- 목록은 `GET tasks?scope=own|managed`와 선택한 5개 상태 조건으로 전체 목록을 받는다. 첫 연결은 페이지·검색을 지원하지 않으며 첫 페이지만 전체처럼 표시하지 않는다.
- 행 선택은 `GET tasks/{taskId}`를 호출한다. 기존 전체/5상태·로딩·빈 목록·오류·늦은 응답 차단·종료 중 취소를 사용한다. 같은 조건의 전체 재조회는 선택 ID를 유지하고 조건 변경·업무 삭제·빈 목록은 그에 맞춰 초기화한다.
- 상세 실패 후 버튼은 선택한 상세만 재시도한다. 성공 후 버튼은 전체 목록 재조회로 돌아가며, F5는 항상 전체 목록을 재조회한다. 공통 접속 취소는 이전 목록·상세를 지우고 취소로 안내하며 서버 오류·실제401과 구분한다.
- 목록·상세 필수 필드와 상태·날짜·중복 ID·요청/응답 상세 ID를 검증한다. 요청 상태와 목록 응답이 다르면 전체를 거절하고 로컬에서 조용히 걸러내지 않는다. 상세의 이후 상태 변경은 허용한다.
- 공통 ApiClient의 Bearer·접속 세대·취소·401 처리를 재사용한다. 서버 루트만 설정하고 상대 경로에 api/v1을 중복하지 않는다. 공유 인스턴스를 Dispose하지 않는다.
- 다른 담당자의 읽기에는 명시 `CaptureReadSession()`으로 같은 로그인에 고정된 `TaskReadSession`을 제공한다. 쓰기/준비 인터페이스나 토큰을 노출하지 않는다. 소비자는 성공과 오류를 화면에 반영하기 직전 접속/화면 수명을 검사하며,현재 배정·특정 scope의 권한이나 마지막 GET 이후 표시 경합을 로컬 현재성으로 증명하지 않는다.
- 401은 인증 만료, 403은 권한 없음, 업무 전용 `TASK_NOT_FOUND` 상세404만 업무 없음이다. 미등록 경로 `HTTP_404`는 연결 필요이며 통신/서버/DB/형식 오류는 이용 불가다.

## 서버 권한과 담당 경계

사용자가 확정한 관리 범위는 **업무별 지정 관리자만**이다. Own은 직원·관리자의 현재 본인 배정, Managed는 현재 관리자 역할과 해당 업무 관리자 지정이 모두 필요하다. 직접 상세도 같은 관계를 검사한다. 클라이언트 역할·사용자 ID·scope는 권한 증거가 아니다. 과거 배정·동일 부서·공통 grant만으로 허용하지 않는다.

성공한 현재 상세는 [입력·대상 확인](../../../../docs/TASK_INPUT_PREPARATION.md)에 전달한다. 로딩·실패·취소·선택 변경 시 문맥을 초기화하고 새 대상 의존 버튼을 비활성화한다. 신규 등록·수락/재작업·일반 수정/재배정/관리자 변경은 별도 개발 API·서비스·명시 실행 폼에 연결됐다. 취소·연장은 모델/저장·조회·요청함/폼을 제공하되 PR52의3번 소비 코드 제공과 별개로 같은 공유 배포의 통합 검증·ACK 확인 전 변경503을 유지한다. 기존 TaskEditForm·DeadlineExtensionForm의 로컬 입력 준비와 실제 실행 폼을 구분한다. 불명확한 실행 결과의 복구는 선택/목록이 없어도 원본 요청으로 열 수 있다. 기본 생성자·미리보기에 실행 서비스를 자동 주입하지 않는다.

반려 후 흐름은 `반려완료 → 본인 재작업 시작 → 진행중 → 재제출 성공 → 제출완료`로 확정했다. 최초 수락·재작업 시작은 KST 시작일00:00 이상~마감일 다음날00:00 미만만 허용하며 시작일 전·마감 후 예외는 없다. 이 정책은1번 PR34 기술 수용 후 별도 기본off 시작 API의 최초 상태 변경에 연결됐으며 서버가 현재 날짜·권한·배정·버전·상태를 다시 검사한다. HttpTaskQueryService는 별도 ITaskStartSource로 captured 세션의 실행/복구 workflow를 제공하며 기존 ITaskQueryService는 변경하지 않는다. 상세 날짜와 별도 write-context는 서로 다른 조회 시점이므로 현재 실행 자격으로 취급하지 않는다. 자세한 경계는 [수락·재작업 대상 확인](../../../../docs/TASK_START_PREPARATION.md)을 따른다.

내 진행중 업무의 결과 제출은 기존3번 SubmissionForm을 같은 접속·선택 업무로 열고,성공 후 현재 GET/필터를 재조회한다.3번 파일·제출/재제출·회차·검토자·승인/반려·이력의 저장은 대신 구현하지 않는다. 연장 D/E 정책은 팀장 확정이며3번 pending/취소 소비 코드는 PR52로 제공됐다. 같은 공유 배포의 경합 검증·통합 ACK는 남는다. 별도 수동 검토 요청은 2026-10-26 확정하여 기존 지정 검토자에게 독립 요청을 저장하고 업무 상태를 유지한다. 자동 검토 요청은 추가하지 않으며 자동 결과 제출은 제외한다.

## 계약과 검증 범위

조회 API·전체 목록 정책·명시적 상태 매핑·DB 모델·남은 연결은 [업무 조회 계약](../../../../docs/TASK_QUERIES.md), 공통 규약은 [INTEGRATION](../../../../docs/INTEGRATION.md)을 따른다. 기존1번 기술 수용과 팀장 확정 A~E를 적용했고 PR51의 실제009·공통 성공 결과 읽기도 제공됐다.3번 취소/pending 소비·공용 첨부 제공부는 PR52로 제공됐다. PR68 제공부를 이용한 [일반수정 첨부 교체](../../../../docs/TASK_MANAGEMENT.md#task-management-attachments-ui)와 [웹 첨부·결과물 진입/복귀](../../../../docs/TASK_WEB.md#task-web-t3-consumers)는 연결했다. 공용 이벤트·같은 공유 배포의 경합 통합은 후속이다.2026-10-21 알림 A1~A6·협업 B1~B7도 진행 기준으로 채택됐으나 새 DTO/endpoint·관계/기한 사건 정보는 기술 대조가 필요하다. 협업 수락만으로 own/managed·파일 권한을 확장하지 않는다. [002 DDL·검증/복구안](../../../../RemoteWork.Server/migrations/002_task_queries.md)의 공유 적용은 별도이며 공통 버전1·기본 off를 유지한다. 기술 회신이나 격리 환경 검증을 공유 DB·두 PC·제출 통합 완료로 표시하지 않는다.

- [기존 TaskQueries.Tests](../../../../Tests/TaskQueries.Tests/README.md): 실제 WinForms 컨트롤과 명시적 테스트 대역.
- [TaskQueries.Http.Tests](../../../../Tests/TaskQueries.Http.Tests/README.md): 공통 HTTP 어댑터 및 명시적 격리 서버를 사용하는 opt-in 실제 HTTP 검증.
- 서버 `tests/test_task_queries.py`: 인증 사용자·업무별 지정 관리자·현재 배정·상세 직접 접근과 실제 DB 조회.

격리 DB에 주입한 데이터는 테스트 fixture이다. 실제 SQL/HTTP 검증과 공유 DB·기존 운영 업무·두 PC·웹 연결을 구분한다. 초기 미연결 감사는 [이전 LOG 기록](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/LOG/2번/업무_구현검증.md#r006)에 보존한다.

타 담당이 이 경계나 업무 화면을 수정할 때는 [2번 영역 수정 협업 규약](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/LOG/2번/2026-10-17_2번_영역수정_협업규약.md)을 참고한다. Tasks 폴더 안에도 검토·협업의 공동 접점이 있으므로 변경 동작별 담당과 계약을 확인하고, PR에 파일·계약 영향·실행/미실행 검증을 남긴다.
