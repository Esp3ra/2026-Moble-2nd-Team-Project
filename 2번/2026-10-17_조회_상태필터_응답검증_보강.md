# 업무 조회 — 상태 필터 응답 검증 보강

작성일: 2026-10-17 · [alpha 329d4a3](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/commit/329d4a32ff316ed2ae208a40e5b1ba0f743d958c)

## 문제와 수정

상태를 지정해 목록을 요청해도 서버 응답이 다른 상태를 담으면 기존 어댑터는 정상 결과로 전달했다. 필터가 적용된 것처럼 보이는 화면에 다른 상태 업무가 표시될 수 있었다.

`HttpTaskQueryService`에서 요청한 상태와 각 응답 상태를 비교한다. 한 건이라도 다르면 기존 `TaskQueryFailure.Unavailable`로 전체 응답을 거절한다. 앞부분만 성공으로 반환하거나 클라이언트가 다른 상태를 조용히 걸러내지 않는다.

전체 조회는 5개 상태를 그대로 허용하고 필터의 빈 결과도 정상이다. 상세는 목록 조회 이후 상태가 바뀔 수 있으므로 이전 목록 상태와 같아야 한다는 제약을 추가하지 않는다. 소유/관리 권한은 서버 책임이며 클라이언트에서 담당자 ID로 새 권한 정책을 만들지 않는다.

## 변경 파일

- `RemoteWork.WinForms/Features/Tasks/Queries/HttpTaskQueryService.cs`: 기존 필터와 응답의 일치 검사만 추가.
- `Tests/TaskQueries.Http.Tests/Program.cs`: 필터 응답 무결성과 공통 접속 취소→실제 화면 시나리오 추가.
- `Tests/TaskQueries.Http.Tests/README.md`, 조회 문서/README: 실제 검증 범위 최신화.

상태 코드·경로·필드·오류 enum·서버·DB·공통 ApiClient는 변경하지 않았다. 저장 코드 최종 합의나 3번 상태 전환을 구현한 것으로 취급하지 않는다.

## 실제 실행한 검증

HTTP 최종6시나리오·103 assertion PASS(기존4/77 포함). 전송은 명시적 HttpMessageHandler 대역이고 공통 ApiClient와 TasksControl은 실제 코드다.

- 5개 상태 각각의 다른 상태 응답·정상/불일치 혼합 목록 거절.
- 필터의 빈 결과, 전체5상태 목록, 목록 이후 새로운 상태의 상세 정상 처리.
- 기존 필수/NULL·형식·중복 ID·날짜·상세 ID·오류 분류·취소·무단 자동 재시도 없음 회귀.
- 공통 ClearIdentity로 대기 중 목록/상세를 취소하고, 실제 화면의 취소 안내·이전 데이터 제거·버튼 복구·새 로그인 후 재시도를 확인.

원본07e444d+새 테스트는 필터 불일치 검사에서 exit1로 실패했다. 필터 검사만 새 코드로 교체하고 원본 TasksControl을 유지하면 공통 접속 취소의 화면 안내 검사에서 exit1로 실패했다. 현재 코드에서는 둘 다 통과했다. 실패는 결함 검출을 위한 격리 회귀 실험이며 운영 서버/DB를 사용하지 않았다.

기존 공통 ApiClient18시나리오·88 assertion도 통과했고 개발·로컬 Release 빌드는 경고0·오류0이다. 이번에는 실제 HTTP 서버·MySQL·공유 DB·두 PC·웹을 재실행하지 않았다. 이전 실제SQL/HTTP 검증은 [이전 조회 개발 기록](2026-10-17_업무목록_상세_실제조회_개발초안.md)에 보존한다.
