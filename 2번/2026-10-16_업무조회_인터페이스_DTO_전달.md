# 업무 조회 인터페이스 DTO와 상태 정의 전달

작성: 2번 담당 · 전달 대상: 1번 공통 담당 · 기준일: 2026-10-16

요청하신 현재 업무 조회 인터페이스·목록/상세 DTO·5개 상태 정의를 전달드립니다. 기준은 alpha·0.0.2V의 [8f09183](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/commit/8f09183ef992606ec4c2b7e3da79ef07983ba019)입니다. 아래 선언은 실제 C# 소스에서 XML 설명 주석만 생략해 옮겼으며, HTTP·DB의 확정 데이터 규격은 아닙니다.

공유해 주신 공통 로그인·Bearer 인증·응답 규약을 재사용하는 방향으로 연결하려고 합니다. 먼저 이 구조와 실제 업무 API의 요청·응답을 대조해 규약을 맞춰 주세요. **공통 INTEGRATION 문서의 업무 API 예시는 등록된 업무 API로 간주하지 않습니다.**

## 1. 조회 인터페이스

[ITaskQueryService.cs](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/8f09183ef992606ec4c2b7e3da79ef07983ba019/RemoteWork.WinForms/Features/Tasks/Queries/ITaskQueryService.cs)

```csharp
namespace RemoteWork.WinForms.Features.Tasks.Queries;

public interface ITaskQueryService
{
    string SourceDescription { get; }

    Task<IReadOnlyList<TaskSummary>> GetTasksAsync(
        TaskListQuery query, CancellationToken cancellationToken = default);

    Task<TaskDetail> GetTaskAsync(
        string taskId, CancellationToken cancellationToken = default);
}
```

- 목록은 요청한 범위·상태의 요약 목록을 반환하고, 상세는 선택한 업무의 ID로 조회합니다.
- `SourceDescription`은 화면에 계속 표시하는 데이터 출처입니다. 테스트 대역은 실제 서버 데이터처럼 표시하지 않습니다.
- `CancellationToken`은 화면 종료·범위/필터/선택 변경 시 이전 조회를 취소하는 데 사용합니다. 늦게 도착한 응답도 화면에서 무시합니다.
- 현재 인터페이스에 사용자 ID·역할·토큰을 요청 데이터로 넣지 않았습니다. 실제 인증 정보는 1번 공통 사용자 컨텍스트와 HTTP 클라이언트에서 전달해야 합니다.

## 2. 목록·상세 DTO와 조회 조건

[TaskQueryModels.cs](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/8f09183ef992606ec4c2b7e3da79ef07983ba019/RemoteWork.WinForms/Features/Tasks/Queries/TaskQueryModels.cs)

```csharp
namespace RemoteWork.WinForms.Features.Tasks.Queries;

public enum TaskQueryScope
{
    Own,
    Managed
}

public enum TaskDisplayStatus
{
    NotStarted,
    InProgress,
    Submitted,
    Approved,
    Returned
}

public sealed record TaskListQuery(TaskQueryScope Scope, TaskDisplayStatus? Status = null);

public sealed record TaskSummary(
    string TaskId,
    string Title,
    string AssigneeName,
    TaskDisplayStatus Status,
    DateOnly StartDate,
    DateOnly DueDate);

public sealed record TaskDetail(TaskSummary Summary, string Description);
```

| 현재 화면 필드 | 의미 | 업무 API에서 함께 확정할 항목 |
|---|---|---|
| `TaskId` | 선택한 업무를 식별하는 불투명 문자열 | 실제 업무 PK·JSON 필드/타입·URL 전달 형식. 인증 사용자 정수 ID와는 별개 |
| `Title` | 업무 제목 | 응답 필드·필수 여부 |
| `AssigneeName` | 화면에 표시할 담당자 이름 | 실제 담당자 식별자와 표시명의 필드·NULL 정책 |
| `Status` | 아래 5개 화면용 논리 상태 | wire/저장 코드에서 화면 상태로의 명시적 매핑 |
| `StartDate` | 화면의 업무 시작일 | 날짜/시각·NULL 허용 여부와 전송 형식 |
| `DueDate` | 화면에 표시할 현재 마감일 | 연장 반영 후 현재 마감일인지, 날짜/시각·시간대·NULL 정책 |
| `Description` | 상세 본문 | 실제 상세 응답 필드·누락/빈 값 기준 |

`DateOnly`와 현재 필수 필드는 화면 내부 모델의 타입입니다. 공통 응답의 UTC ISO 8601 원칙만으로 업무 시작일·마감일의 날짜/시각 구분까지 확정하지 않습니다. 실제 업무 응답에 맞춰 변환 규칙을 정해야 합니다.

목록 반환형은 현재 `IReadOnlyList<TaskSummary>`이며 페이지 번호·전체 개수·다음 커서 같은 메타가 없습니다. 정렬·페이지 처리 규약을 먼저 정하고, 페이지 메타가 필요하면 인터페이스 유지 방법 또는 필요한 변경 범위를 함께 확인하겠습니다. 임의로 첫 페이지를 전체 목록으로 처리하지 않습니다.

## 3. 화면의 5개 상태 정의

| C# 논리값 | 화면 표시 | 확정된 의미 |
|---|---|---|
| `NotStarted` | 진행전 | 배정됐으나 담당자가 아직 수락하지 않음 |
| `InProgress` | 진행중 | 담당자가 수락해 수행함 |
| `Submitted` | 제출완료 | 정식 제출·재제출 후 검토자의 판단을 기다림 |
| `Approved` | 승인완료 | 권한 있는 검토자가 승인했으며 최종 완료됨 |
| `Returned` | 반려완료 | 반려 판단이 끝났으며 수정·재제출이 필요함 |

`TaskListQuery.Status == null`은 화면의 **전체 업무 상태**입니다. 실제 API에서 전체 조건을 생략할지 별도 값으로 전달할지는 아직 정하지 않았습니다. C# enum의 이름·정수 순서를 HTTP·DB 상태 코드로 그대로 채택하지 않습니다. 실제 상태 코드는 1번·3번과 합의가 필요합니다.

배정→진행전, 수락→진행중, 정식 제출·재제출→제출완료, 검토 판단→승인완료/반려완료의 기본 전환과 모든 정식 제출의 필수 검토는 확정 기준입니다. 관리자 본인 제출본은 상위 검토자가 판단합니다. 반려 후 진행중 복귀 시점과 구체적인 저장 연결은 합의 필요이며 자동 결과 제출은 제외합니다.

## 4. 조회 범위와 서버 권한

- `Own`: 현재 화면의 내 업무입니다. 직원·관리자 본인 배정 기준과 직원의 협업 업무 포함 여부·별도 범위 필요성을 함께 정해야 합니다.
- `Managed`: 현재 관리자 관리 업무입니다. 전체·부서·팀·기타 권한 중 어느 범위를 허용하는지 아직 확정되지 않았습니다.
- 현재 enum에는 협업 전용 범위가 없습니다. 협업 업무 조회 규칙과 식별 방법은 1번 및 관련 담당과 합의한 뒤 반영합니다.
- 화면 역할과 요청 범위를 권한 근거로 사용하지 않습니다. 서버는 인증 사용자로 목록과 상세 직접 접근을 각각 검사해야 합니다.
- 테스트 대역의 두 데이터 집합을 나눈 것은 실제 서버 권한 검증이 아닙니다.

## 5. 현재 UI 실패 분류

[TaskQueryFailure.cs](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/8f09183ef992606ec4c2b7e3da79ef07983ba019/RemoteWork.WinForms/Features/Tasks/Queries/TaskQueryFailure.cs)

```csharp
namespace RemoteWork.WinForms.Features.Tasks.Queries;

public enum TaskQueryFailure
{
    NotConfigured,
    AuthenticationExpired,
    Forbidden,
    NotFound,
    Unavailable
}

public sealed class TaskQueryException : Exception
{
    public TaskQueryFailure Failure { get; }

    public TaskQueryException(
        TaskQueryFailure failure, string? message = null, Exception? innerException = null)
        : base(message ?? failure.ToString(), innerException)
    {
        Failure = failure;
    }
}
```

| UI 분류 | 공통 규약 회신에 따른 연결 기준·남은 확인 |
|---|---|
| `NotConfigured` | 실제 조회 서비스가 연결되지 않은 로컬 상태. 서버 오류 코드로 사용하지 않음 |
| `AuthenticationExpired` | 회신의 401 로그인 필요·만료를 이 범주의 안내로 연결할 예정. 세부 공통 오류 코드·클라이언트 처리 위치 확인 필요 |
| `Forbidden` | 회신의 403 권한 없음. 업무 상세 접근 거부·미존재 구분 정책은 추가 확인 |
| `NotFound` | 선택한 업무 미존재. 업무 API의 실제 HTTP/오류 코드와 정보 노출 정책은 아직 합의 필요 |
| `Unavailable` | 서버·통신·잘못된 응답 등의 조회 실패. 회신의 503 DB 연결·초기화 문제도 이 범주로 연결하는 기준이며 실제 어댑터는 미구현 |

공통 응답의 `ok`, `data`, `error.code`, `error.message`, `request_id`는 공유받을 공통 클라이언트의 실제 메서드·오류 타입에 맞춰 사용하겠습니다. 공통 HTTP·인증 처리와 UI 예외 매핑을 중복 구현하지 않도록 해당 클래스·주입·호출 예시도 부탁드립니다.

## 6. 규약 확정을 위해 부탁드리는 답변

1. 실제 업무 목록·상세의 메서드·경로와 성공/실패 응답 JSON은 무엇인가요? 문서 연결 예시와 실제 등록 API를 구분해 주세요.
2. 전체·5개 상태의 요청/응답 값, 기본 정렬·페이지 방식과 페이지 메타는 어떻게 할까요?
3. 직원의 본인·협업 업무와 관리자 관리 업무의 정확한 조회 범위는 무엇인가요? 범위 밖 ID로 상세를 직접 요청할 때 어떤 응답을 줄까요?
4. 위 DTO 필드의 실제 wire 필드명·타입·NULL·현재 마감일·시간대 매핑은 어떻게 할까요?
5. 공통 서버·C# HTTP 클라이언트·인증 컨텍스트·오류 타입이 있는 저장소/브랜치/파일과 호출 예시를 공유해 주실 수 있나요? 기본 주소에 포함된 `/api/v1`과 개별 요청 경로를 결합하는 규칙도 알려 주세요.
6. 업무 API 구현, 공통 자원 접근 도구 적용·테스트와 실제 HTTP 어댑터 연결의 담당·진행 순서를 함께 정해 주세요.

공유해 주신 `C:/Users/moble/.../docs/INTEGRATION.md` 경로는 현재 2번 작업 PC에서 열 수 없었습니다. GitHub 브랜치·저장소 경로 또는 이 PC에서 접근 가능한 공유 위치로 해당 문서와 공통 소스를 부탁드립니다. `127.0.0.1`은 실행 중인 각 PC 자신의 주소이므로 두 PC 연결 주소·서버 설정은 별도 검증이 필요합니다.

규약과 공통 소스를 받은 뒤 기존 조회 경계를 유지하는 실제 HTTP 구현을 연결하고, 인증된 목록·상세·타인 업무 직접 접근 차단·상태 필터·오류·DB 재조회를 검증하겠습니다. 아직 실제 연결 완료로 표시하지 않습니다. 제출·재제출·제출 차수 표시·승인/반려·파일 기능은 3번 담당 범위로 유지합니다.
