## 2. R1 — P1: 동시 강등으로 활성 관리자가 0명이 됨

코드: [api.py 95–116](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/2d3cc480c4ab5eb9a3466c9034cfdaf256102df3/RemoteWork.Server/remotework/api.py#L95-L116), 핵심은 115–116의 마지막 관리자 수 검사입니다.

독립 MySQL 8.2의 기본 `REPEATABLE-READ`에서 실제로 재현했습니다. `load_identity()`의 일반 조회가 만든 이전 스냅샷을 관리자 수 검사에서도 사용합니다. `admin_guard` 잠금만으로는 이후 COUNT가 최신 관리자 상태를 읽도록 보장하지 못합니다.

재현 순서:

1. 전용 테스트 DB에 활성 관리자 A·B만 만들고 각 API 접속을 준비합니다.
2. B가 A를 직원으로 바꾸는 PATCH를 시작합니다. 인증 조회·역할 확인 후, `admin_guard` 잠금을 얻기 직전에 요청을 대기시킵니다.
3. A가 B를 직원으로 바꾸는 PATCH를 실행해 commit합니다. B의 기존 접속도 폐기됩니다.
4. 대기 중인 B 요청을 재개합니다. 이전 인증·스냅샷으로 A를 강등합니다.
5. **두 요청 모두 HTTP 200이며 최종 활성 관리자 수는 0명**입니다.

영향: 관리자 화면으로 계정·권한을 복구할 수 없게 되어 서버 측 복구 절차가 필요합니다.

수정 요청: 권한 변경을 직렬화하는 구간에서 수행자의 유효 권한과 최신 관리자 상태를 함께 확인해 주세요. 이전 스냅샷의 일반 COUNT에 의존하지 않도록 트랜잭션·잠금·재조회 방식을 점검하고, 실제 MySQL 동시성 회귀 테스트를 추가해 주세요. 구현 방식은 1번 공통 DB·인증 규약 안에서 결정합니다.

재검증 완료 조건:

- 위 상호 강등에서 활성 관리자가 항상 1명 이상 남습니다.
- 이미 권한·접속이 폐기된 수행자의 대기 중 변경 요청은 정책에 맞게 거절됩니다.
- 거절 응답의 상태·오류 코드와 rollback 동작을 명시하고, 성공한 변경만 감사 이력에 남는지 확인합니다.
- 정상 사용자 정보 수정·직원 계정 비활성화·단일 마지막 관리자 보호도 유지됩니다.

## 3. R2 — P2: 이전 접속의 늦은 응답이 새 로그인을 변경함

코드: [ApiClient.cs 53–57](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/2d3cc480c4ab5eb9a3466c9034cfdaf256102df3/RemoteWork.WinForms/Infrastructure/ApiClient.cs#L53-L57), [88–91](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/2d3cc480c4ab5eb9a3466c9034cfdaf256102df3/RemoteWork.WinForms/Infrastructure/ApiClient.cs#L88-L91). 실제 `ApiClient`·`ApiModels`를 연결한 .NET 8 재현에서 확인했습니다.

재현 순서:

1. A 로그인 후 A의 `auth/me` 요청을 보내고 응답을 지연시킵니다.
2. 로그아웃한 뒤 B로 로그인합니다.
3. A의 이전 응답을 도착시킵니다.

| 이전 A 응답 | 실제 결과 | 기대 동작 |
|---|---|---|
| 정상 사용자 JSON | `CurrentUser`는 A로 바뀌지만 이후 Bearer는 B | B의 사용자 정보·토큰 유지 |
| 401 오류 JSON | B의 사용자 정보·토큰 삭제, 만료 이벤트 발생 | 이전 A 접속의 응답이 B에 영향 없음 |

`MainForm`의 타이머를 중지해도 이미 진행 중인 HTTP 요청은 남을 수 있습니다. 화면의 폐기 여부 확인보다 공통 클라이언트의 상태 변경이 먼저 일어납니다.

수정 요청: 요청 당시의 접속 세대 또는 인증 문맥을 기록하고, 응답이 도착했을 때 현재 접속과 일치하는 경우에만 `CurrentUser`·토큰·만료 이벤트를 변경해 주세요. 로그아웃·재로그인 시 이전 요청의 취소와 늦은 응답 무시를 함께 점검해 주세요. 요청 취소만으로 응답의 순서를 보장한다고 간주하지 않습니다.

재검증 완료 조건:

- 이전 A의 성공·401 응답 모두 B의 상태와 만료 이벤트에 영향을 주지 않습니다.
- 현재 B 접속의 정상 사용자 갱신은 적용되고, 현재 B의 401은 한 번의 재로그인 안내로 이어집니다.
- 로그아웃·메인 창 종료·재로그인을 반복해도 사용자 정보와 Bearer가 서로 다른 접속을 가리키지 않습니다.

## 4. R3 — P2: 잘못된 형식의 401에서 만료 처리가 누락됨

코드: [ApiClient.cs 85–91](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/2d3cc480c4ab5eb9a3466c9034cfdaf256102df3/RemoteWork.WinForms/Infrastructure/ApiClient.cs#L85-L91).

로그인 후 401 본문을 정상 오류 JSON·HTML·잘못된 JSON·빈 본문으로 각각 돌려주는 테스트를 실행했습니다. HTML·잘못된 JSON·빈 본문은 역직렬화 예외가 먼저 발생하여 `ClearIdentity()`와 `AuthenticationExpired`가 실행되지 않았습니다. 사용자 정보가 남고 다음 요청에도 기존 Bearer가 전달됩니다. `MainForm`은 401을 연결 끊김 표시에서도 제외하므로 재로그인 안내로 이어지지 않습니다.

수정 요청: HTTP 401 여부를 JSON 파싱 성공과 독립적으로 처리해 주세요. **R2의 요청 접속 일치 확인을 함께 적용한 뒤**, 현재 접속의 401이면 본문 형식과 관계없이 인증 상태를 비우고 만료를 알리도록 해 주세요. 오래된 접속의 401로 새 접속을 지우면 안 됩니다.

재검증 완료 조건:

- 현재 접속에서 정상 JSON·HTML·잘못된 JSON·빈 본문 401 모두 사용자 정보·토큰이 제거되고 만료 이벤트가 1회 발생합니다.
- 만료 후 후속 요청에 기존 Bearer가 실리지 않습니다.
- 500·502·잘못된 성공 응답 등 인증 만료가 아닌 오류는 접속 상태를 임의로 지우지 않고 기존 안내를 유지합니다.

## 5. 이미 확인한 공통 사용법과 남은 업무 합의

공통 소스와 호출법은 PR #2·#3에서 확인했습니다. 이전 [공통 규약 회신 정리](2026-10-16_1번_공통규약_회신정리.md)의 “이 PC에 공유 소스 없음”은 당시 경로 확인 결과로 보존합니다. 이제 공통 구현 부재를 이유로 같은 자료를 다시 요청하지 않습니다. alpha에 병합되어 실제 사용 가능한 기준이 되는 것과 PR 코드를 검토한 것은 구분합니다.

- 공통 공유 인스턴스는 `AppServices.Api`입니다. `REMOTEWORK_API_URL`에는 `http://서버IP:5000/`처럼 **서버 루트**를 설정합니다. API 기준 주소가 `/api/v1`이라는 설명과 C# 설정값을 혼동하지 않습니다.
- `GetAsync<T>("users?page=1&limit=20", cancellationToken)`처럼 요청에는 `/api/v1/` 없는 상대 경로를 넘깁니다. 접두사는 클라이언트가 붙입니다. 개별 화면에서 공유 인스턴스를 Dispose하지 않습니다.
- 공통 로그인·사용자·오류·DB 연결은 1번 담당이며, 업무 모델·조회 API·기존 `ITaskQueryService`에 연결할 HTTP 어댑터는 규약 합의 후 2번 담당이 구현합니다. 업무 API를 1번이 대신 완성해 달라는 요청은 아닙니다.
- 업무 목록·상세 경로와 wire DTO·상태 코드·정렬·페이지·날짜/NULL·현재 적용 마감일·Own/Managed·협업 포함·상세 403/404는 **합의 필요**입니다. 공통 문서의 업무 API는 등록된 기능이 아닌 연결 예시입니다.
- `require_resource_access(..., allow_admin=True)`는 관리자 grant 검사를 생략합니다. 실제 업무 목록·상세에는 인증 사용자 기준 범위 조건 또는 합의한 grant 정책이 필요하며 직접 상세 요청도 별도로 검사해야 합니다.
- 제출·재제출·제출 차수 표시·승인/반려·파일·상위 검토자와 관련 상태 연결은 3번과 합의합니다. 5개 표시 상태와 정식 제출의 필수 검토는 유지하고 자동 결과 제출은 제외합니다. 자동 검토 요청·반려 후 복귀 시점 등은 합의 전 구현하지 않습니다.

당시 미병합이던 [문서 PR #3](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/pull/3)은 현재 LOG에 병합됐습니다. [1번 DTO 회신](../1번/2026-10-16_업무조회_인터페이스_DTO_회신.md)과 [공동 합의 목록](../1번/2026-10-16_공동합의_필요항목.md)의 C02~C12를 기존 2번 전달문과 대조해 확정 내용과 근거 커밋을 기록합니다.
