C# 모델의 정확한 필드는 다음과 같다. 업무 ID는 서버에서 받은 문자열을 그대로 전달한다. 예전 폼의 `WRK-2026-...` 표시 예시를 실제 DB 업무 ID로 간주하거나 숫자를 잘라 생성하지 않는다.

```csharp
public sealed record TaskSummary(
    string TaskId, string Title, string AssigneeName, TaskDisplayStatus Status,
    DateOnly StartDate, DateOnly DueDate);
public sealed record TaskDetail(TaskSummary Summary, string Description);
```

**서버 GET JSON에는 assignee_id가 이미 포함된다.** HttpTaskQueryService의 내부 wire record도 이를 양의 int로 검사하지만 반환하는 C# TaskSummary에는 담지 않는다. 현재 C# 모델에 assignee ID·row_version·assignment_revision·제출 회차는 없다. 이름에서 ID를 추측하거나 기존 모델에 새 필드를 임의 추가하지 않는다. 버전/배정 차수 공급을 기존 GET에 넣을지 별도 쓰기 준비 DTO로 제공할지는 W1-01/03과 W3-04에서 공동 확인한다.

### 소비 방법 예시 — 기존 GET만 사용

아래는 로그인된 공통 ApiClient로 읽기 서비스를 만드는 방법과, 이미 선택한 업무 ID로 상세를 조회하는 소비 예시다. 이 문서에서 새 Results 생성자·제출 서비스·파일 API를 구현/등록한 것이 아니다. 3번이 결과물 폼에 서비스를 주입할 생성자/수명 변경안을 준비하고 MainForm 변경은 해당 담당과 함께 검토한다.

```csharp
using RemoteWork.WinForms.Features.Tasks.Queries;
using RemoteWork.WinForms.Infrastructure;

// 실제 로그인 이후 기존 공통 인스턴스를 재사용한다.
ITaskQueryService taskQueries = new HttpTaskQueryService(AppServices.Api);

// 아래 메서드는 소비 예시이며 기존 업무 인터페이스를 변경하지 않는다.
static async Task<TaskDetail?> ReadSelectedOwnTaskAsync(
    ITaskQueryService queries, string? selectedTaskId, CancellationToken token)
{
    IReadOnlyList<TaskSummary> own = await queries.GetTasksAsync(
        new TaskListQuery(TaskQueryScope.Own), token); // Status null: 전체5상태
    if (selectedTaskId is null || !own.Any(task => task.TaskId == selectedTaskId))
        return null; // 예시 목록/다른 사람 업무로 대체하지 않는다.
    return await queries.GetTaskAsync(selectedTaskId, token);
}
```

관리 업무가 필요한 읽기 소비는 `new TaskListQuery(TaskQueryScope.Managed)`를 요청할 수 있지만 서버가 admin+업무별 지정 관리자 관계를 검사한다. 이 목록을 곧바로 ‘승인 가능한 제출물’로 사용하지 않는다. 목록 이후 상태가 바뀔 수 있으므로 상세는 다른 최신 상태를 정상 반환할 수 있고, 조회 성공을 제출/수정 가능 판정으로 사용하지 않는다.

목록은 현재 허용된 범위의 전체 결과이며 페이지/검색 계약을 추가하지 않았다. TaskQueryException은 NotConfigured·AuthenticationExpired·Forbidden·NotFound·Unavailable를 구분한다. OperationCanceledException은 취소로 처리하고 이전 접속/선택의 응답을 새 화면에 반영하지 않는다. 결과물 폼의 요청 CancellationTokenSource·현재 요청 세대·화면 종료 정리는3번이 적용할 영역이다. 기존 ApiClient의 접속 취소/인증 만료 처리를 복제하지 않는다.

## 상태·저장·두 화면 재조회에 대한 2번 답변 — W3-02/03/06

현재2번 서버의 실제 등록 경로는 GET뿐이다. 등록·수정·수락·연장 폼의 입력 확인은 로컬이며 제출/수락/연장 저장 서비스가 아니다. TaskBasicInputDraft/DeadlineExtensionInputDraft는 서버 요청 DTO가 아니고 row_version/배정 차수·멱등 계약도 없다. 이번 회신으로 2번에 상태 변경 호출을 추가하지 않는다.

정식 제출·재제출·승인/반려를 담당하는 **3번 서버 행동 서비스가 제출/판단 기록·단일 업무 상태·합의된 업무 이력/성공 감사를 같은 DB 트랜잭션에서 처리**하는 연결안을 제안한다. 2번 UI가 제출 성공 후 별도 상태 PATCH를 또 보내는 이중 저장은 만들지 않는다. 공통 재인증·잠금·버전·멱등·응답 유실 처리와 첨부 파일 실패/보상 경계는1번 지원 및1·2·3번 합의가 필요하다. 이 설계안만으로 파일까지 원자 저장되거나 재시도가 안전해졌다고 주장하지 않는다.

실제 행동 성공 응답이 온 뒤 각 화면이 서버를 다시 읽는 방향을 제안한다. 현재 업무 화면은 `TasksControl.RefreshAsync()`로 목록·선택 상세를 다시 읽고, MainForm은 메뉴 이동 때 이전 페이지를 Dispose한 뒤 새 업무 페이지를 연다. 결과물/이력 화면의 새 조회 서비스·성공 이벤트·재조회 시점은3번과 조정할 후속이며 현재 자동 동기화/푸시 기능은 없다. 서버 반영 여부를 모르는 통신 실패를 성공으로 표시하거나 새 요청으로 무조건 재전송하지 않는다.

## 업무 이력과 검토 권한에 대한 답변 — W3-02/04/05

**업무 생성·변경·수락·제출·승인/반려를 조회할 실제 업무 이력 서비스/API는 현재2번에 없다.** HistoryControl은 alpha 기준 예시 화면이다. 공통 AuditEvent/audit()는 있어도 이를3번 업무 이력 화면의 저장 모델/완성된 조회 API로 간주하지 않는다. 공통 감사는 비밀/본문 최소화·접근 제한 목적이며 화면에 필요한 업무별 전후값/설명·정렬·필터·권한은 별도 계약이 필요하다.

이력안은 행동을 저장하는2·3번이 자신의 성공 결과와 함께 남길 이벤트/업무·배정·제출 참조를 제시하고, HistoryControl 소비 계약은3번이 준비하며,1번이 감사/DB·보존/권한을 검토하는 방향을 제안한다. 로그 action/resource/details는 기존 [W1 후속 제안](2026-10-17_W1_후속_행동별API_사용자선택_제안.md)의 W1-04를 이어서 검토한다. 이 문서에서 새 업무 이력 테이블/API/회차를 만들어 합의 처리하지 않는다.

task_managers는 업무 관리 조회 관계다. **상위 검토자라는 이유만으로 현재 업무 상세403을 풀지 않는다.** 본인 배정 또는 admin+해당 지정 관리자 관계가 없는 상위 검토자에게 필요한 최소 업무 정보는3번의 검토 흐름·명시적 검토 관계/접근 필드·별도 조회안 중 무엇으로 제공할지 팀장·1·2·3번이 W3-05에서 정한다. 그 과정에서 새 경로·후보 조회·권한 조건을 제안하면 실제 구현 전에 검토하며 전체 업무를 공개하는 우회는 하지 않는다.

## 후속 확인 순서와 이번 검증 범위

1. 3번이 W3-03/04/06의 상태별 허용 표·제출 모델/API/FK·마감/연장 충돌안을 기존 ID로 보완하고 검토자 지정/접근은 W3-05에서 팀장과 맞춘다. 로컬 구현과 서버 계약은 계속 구분한다.
2. 1번의 W1-02/03/04/05/07 실제 공통 지원·버전/멱등·후보/DB와2번 행동별 제안,3번 제출/판단안을 대조한다. 부족한 공통 기능을2·3번이 각각 복제하지 않는다.
3. 합의와 지원이 확인된 등록/배정 → 본인 수락 → 마감 관리 행동부터2번이 연결한다.3번 제출/판단은3번이 구현하고 서버 단일 결과와 읽기 재조회로 통합한다.
4. 격리 MySQL에서 현재/옛 배정·검토자 권한·자기 판단 거부·버전 충돌·중복·응답 유실·rollback·제출/연장 경합을 검증한다. 정식 DDL·공유 환경/복구·두 PC는 별도 게이트다.

이번 문서는3번74줄 회신 전체와 현재 서비스/모델/MainForm·서버 GET·공통 감사의 **정적 대조 및 연결 안내**다. 새 프로그램 빌드·HTTP/MySQL·제출/판단·장치·두 PC 검증을 이 문서 작성에서 실행하지 않았다. 앞선 목록/상세 차이 안내 작업의 검증은 해당 별도 구현 기록이며 이번 W3 계약 통합 테스트로 합산하지 않는다. 실행 코드·3번 폼·공통 지원·DB/DDL·DOCX·태그는 이 회신으로 변경하지 않았다.
