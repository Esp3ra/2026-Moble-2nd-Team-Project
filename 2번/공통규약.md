# 팀 공통규약 및 담당별 협의 현황

관리: 팀장·2번 · 기준일: 2026-10-19 · 대표 위치: LOG/2번

이 문서는 현재 원본 코드와 담당별 회신을 대조한 기준입니다. **사용자 확정**, **기존 공통 지원**, **2번 개발 계약**, **담당자 합의 필요**, **1번 기술 확인 필요**를 구분합니다. 문서 게시를 상대 담당자의 수용이나 공유 환경 적용으로 해석하지 않습니다. 1번 부재 중에는 기존 공통 기능을 재사용하며 공통 인증·DB·HTTP 구현을 대신 변경하지 않습니다.

## 확정한 공통 기준

| 구분 | 현재 기준 |
|---|---|
| 인증·식별 | Bearer access token, 서버의 현재 사용자 ID·역할·활성 상태로 판단. 이름이나 화면 역할을 권한 근거로 사용하지 않음 |
| 통신 | `/api/v1`, UTF-8 JSON, snake_case, 공통 ok/data 또는 error/request_id. C# 공통 ApiClient와 로그인 세대·취소 규약 재사용 |
| 날짜·시각 | 업무 날짜는 DATE/`YYYY-MM-DD`, 사건 시각은 서버 UTC ISO 8601. 한국 시간 표시와 마감의 업무 의미는 별도 |
| DB·쓰기 | MySQL, 같은 요청 Session/트랜잭션에 업무·관계·감사·성공 결과 저장. 현재 권한 재검사·요청 키·중복 방지·결과 조회·버전 검사 재사용. 자동 쓰기 재시도 없음 |
| 정보 보관 | 비밀번호·토큰·실제 환경 설정·개인 장치값·원본 파일/영상은 저장소나 일반 감사에 남기지 않음. 공통 성공 요청 결과 보관은 24시간 |
| 업무 조회 | 본인의 현재 배정 또는 현재 admin이면서 업무별 지정 관리자인 범위. 관리자 역할만으로 전체 업무를 허용하지 않음 |
| 업무 상태 | 진행전/진행중/제출완료/승인완료/반려완료. 승인완료가 최종 완료. 관리자도 본인 업무를 수락·제출하고 자기 제출을 판단하지 않음 |
| 최초 관리자 | 신규 업무 관리자 최소 1명, 등록자 자동 포함, 최초 등록에서 등록자 제외 불가. 업무 관리자와 제출 검토자는 별개 |
| 반려 후 흐름 | 반려완료 → 본인의 명시적 재작업 시작 → 진행중 → 재제출 성공 → 제출완료. 재작업 시작은 회차를 올리지 않음. 최초/재제출은 기존 성공 제출·반려 기록으로 구분 |
| 자동 처리 | 마감 후 자동 결과 제출 제외. 자동 검토 요청은 별도 합의 필요 |
| 장치 | 지문은 로그인 후 원격 근무 본인 확인 수단. 업무 조회·수락·제출에 장치 조건을 임의 추가하지 않음. 손/조도 미검출을 자동 근태 기록·이석/결근 판단으로 처리하지 않음. 독립 시연의 화면 표시와 근태 저장을 구분 |

실제 공통 지원은 [INTEGRATION](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/alpha/docs/INTEGRATION.md), [WRITE_SUPPORT](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/alpha/docs/WRITE_SUPPORT.md), [RESULTS_INTEGRATION](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/alpha/docs/RESULTS_INTEGRATION.md)를 따릅니다. 과거 문서의 ‘공통 쓰기/실제·요구 버전 검사 미구현’은 후속 코드로 해결된 이전 상태입니다.

## 2번 개발 계약 — 신규 등록만 먼저 연결

기존 사용자 결정과 업무 3테이블을 이용하는 **2번 개발용 실행 계약**입니다. 초기 수치·새 API 세부 사항에 대한 1번의 공동 기술 검토 완료나 정식 migration 승인을 뜻하지 않습니다. 공유 활성화는 하지 않습니다.

- `POST /api/v1/tasks`. 기존 업무 조회 활성화에 더해 `ENABLE_TASK_CREATE_DRAFT=True` 또는 `REMOTEWORK_ENABLE_TASK_CREATE_DRAFT=1`을 명시해야 경로를 등록합니다. 기본 off이며 공통 쓰기 활성화·기존 002/004 개발 테이블도 필요합니다. 요청 중 DDL을 실행하거나 전역 스키마 버전을 올리지 않습니다.
- 입력은 `title`, `description`, `start_date`, `due_date`, `assignee_id`, `manager_user_ids` 여섯 필드입니다. 수행자·상태·시각·버전을 클라이언트가 지정하지 않습니다. 최초 생성에는 기존 업무의 expected version을 요구하지 않습니다.
- 제목은 공백만인 값을 거절하고 Unicode 코드 포인트 200개까지, 설명은 문자열이며 빈 값도 허용합니다. 원문을 임의로 trim하지 않습니다. 공통 요청 크기 32KiB를 사용하고 별도 설명 길이 사업 규칙을 만들지 않습니다.
- 날짜는 유효한 `YYYY-MM-DD`, MySQL DATE 범위인 1000~9999년, 시작일≤마감일입니다. 과거 날짜 금지·마감 후 수락/제출 같은 미정 정책을 새로 적용하지 않습니다.
- 담당자는 활성 employee/admin 1명입니다. 요청 관리자는 양의 JSON 정수 목록이며 중복을 거절합니다. 서버가 인증된 등록자를 관리자에 자동 포함하고 현재 활성 admin 여부를 저장 직전에 다시 검사합니다. 빈 요청 관리자 목록도 서버 등록자가 포함되어 최소 1명이 됩니다.
- 최초 저장값은 `not_started`, `row_version=1`, `assignment_revision=1`, `accepted_at=NULL`입니다. 이 1/1은 이번 2번 개발 계약이며 공통 스키마 버전 1과 다른 값입니다. 업무·최초 배정·관리자·감사·receipt를 같은 트랜잭션에 저장합니다.
- 기존 `task.created`/target=`new` 요청 키를 사용합니다. 같은 키·같은 원문 본문은 저장된 결과로 재응답하고 다른 본문은 409입니다. 최초 실행의 후보 검사는 mutate 내부에서 하며 재응답 전에 현재 수행자의 권한은 다시 검사합니다. 키나 성공 결과 확인을 자동으로 새 생성 요청으로 바꾸지 않습니다.
- HTTP 201 최소 결과는 `task_id`·`row_version`의 정규 BIGINT 문자열, `assignment_revision` 정수, `task_status`, `updated_at` 서버 UTC입니다. 담당자/관리자/본문을 receipt 결과에 추가하지 않습니다. 정상 GET으로 업무 상세를 재조회할 수 있습니다.
- 기능/테이블 미준비는 503, 로그인 필요·만료는 401, 직원 생성은 403, 현재 배정/관리 후보 불가는 409로 구분합니다. 상세 오류 코드는 코드 문서를 따릅니다.

WinForms 신규 등록 화면도 위 개발 계약에 연결했습니다. CheckedInput과 PreparedSelection을 확인해 별도 불변 TaskCreationRequest를 만들며, 입력 확인 자체는 저장이 아닙니다. 등록 버튼에서만 공통 키를 발급하고 POST합니다. 현재 세션·현재 후보/관리 권한의 최종 판단은 서버가 수행합니다. 기존 ITaskQueryService·공통 인증/HTTP·DB 코드는 변경하지 않았습니다.

결과가 불명확하면 본문과 키를 해당 ApiClient의 로그인 세션 메모리에 보관하고 입력·새 등록을 잠급니다. 등록 창을 닫거나 다른 메뉴를 거쳐 돌아와도 같은 요청을 복원하며, 처리 중 일반 닫기는 막습니다. 사용자가 결과를 확인해 not_recorded가 반환된 뒤에만 같은 키·같은 본문 재전송이 가능합니다. 자동 재전송·새 키 재생성은 하지 않습니다. 생성/재전송410은 보관 결과를 먼저 조회할 수 있고, 결과 조회410 또는 키 충돌은 수동 내역 확인으로 남깁니다. 401/403·접속 교체/종료는 이전 선택·키·결과를 폐기하며 같은 접속의403 차단은 메뉴 재진입으로 우회되지 않습니다. 앱 재시작/재로그인 후 요청 복원은 구현하지 않았으므로 다시 등록하기 전 기존 목록·처리 내역을 확인해야 합니다.

확인된 성공만 기존 범위·5상태 필터를 유지해 목록/상세를 재조회합니다. 새 업무가 현재 조건에 없으면 기존 선택과 저장 완료/필터 범위 밖 안내를 유지합니다. 공통 ApiClient는 성공 데이터만 제공하므로 직접 POST의 성공 HTTP 상태를 클라이언트에서 추가 검사하지 못합니다. 서버201 계약과 실제 HTTP 경로를 별도 검증했으며, 보관 결과 조회의 http_status는201로 엄격 검사합니다. 공통 HTTP를 임의 확장하지 않았습니다.

이번 연결은 수락·재작업·연장·결과 제출·판단 API를 추가하지 않습니다. 최초1/1·기술 접점의 1번 공동 검토, 정식 migration·공유 활성화는 남아 있습니다. 실제 실행과 미실행은 [업무 구현·검증](업무_구현검증.md)을 따릅니다.

## 수락·재작업 시작 — 확정과 다음 합의

원본 alpha `bbbe43a`와 LOG `0333a37`을 확인한 시점에 새1·3번 회신은 없었습니다. 기존 W1/W3 번호를 유지합니다. 이번에는 **읽기 전용 대상 확인**까지만 구현하며 공통 서버·3번 제출/판단·회차·파일·이력은 변경하지 않습니다.

| 구분 | 현재 확정·실제 지원 | 합의/검토가 필요한 내용 |
|---|---|---|
| 수락 | 현재 배정 당사자의 명시 수락: 진행전→진행중. 관리자 본인도 동일. 공통 task.accepted 권한·키·결과 지원은 있음 | 실제 수락 경로·요청/결과·오류·버전 처리. 공통 도구가 제품 API 구현을 뜻하지 않음 |
| 재작업 시작 | 현재 배정 당사자: 반려완료→명시적 재작업 시작→진행중. 재제출 성공 전까지 제출완료로 바꾸지 않음 | 별도 경로/action·감사·receipt 등록. task.accepted를 재작업으로 전용하지 않음 |
| 기존 자료 | 재작업 때문에 최초 accepted_at·배정 번호·제출 회차·과거 결과/판단을 초기화하지 않는 방향은3번도 수신 | 최초 수락 저장 시각/중복·반려인데 최초 수락 기록이 없는 이상 자료·기존 버전 증가/동시 충돌·원자 저장 방식 |
| W3-01/06 날짜 | 업무는 DATE, 사건 시각은 서버 UTC | 시작일 전·마감 후 최초 수락/재작업 허용, 판단 시간대·마감 당일/시각. 제한을 빼거나 보수적 제한을 임의 적용하는 것도 새 정책이므로 이번에는 선택하지 않음 |
| W1-03/04·W3-02/04 | 현재 사용자/관계 잠금·ExpectedVersions·중복/결과·감사 도구 재사용 | 행동별 요청/필수 결과, row_version 증가 수치·시점/배정 차수 유지, 상태 충돌·이미 처리/이상 자료 응답, 재작업 action 공동 기술 확인 |
| 3번 접점 | 2번이 수락·재작업 시작,3번이 최초/재제출·판단/회차를 담당. 재작업 시작 자체는 회차 증가 없음 | 이후 양쪽의 상태/버전/성공 재조회·동시 제출 경합 검증. 제출 성공 후2번의 별도 상태 변경 요청을 추가하지 않음 |

최신 대상 확인은 기존 `GET /api/v1/tasks/{id}/write-context`만 사용합니다. 본인 ID·진행전/반려완료·원본 상세 상태를 비교하고 별도 불변 CheckedTarget을 보관하며 키/결과/제품 상태 쓰기는 실행하지 않습니다. 지정 관리자의 조회 권한을 타인의 수락 권한으로 해석하지 않습니다. 관리 업무 화면에는 해당 행동을 열지 않습니다.

기존 상세의 제목/표시명/날짜와 문맥의 ID/버전/상태는 별도 조회 시점입니다. 제목·날짜·accepted_at의 일관된 원본이나 실행 가능 시점을 보증하지 않습니다. 불일치면 확인값을 만들지 않고 같은 범위/필터로 목록·상세를 다시 읽습니다. 로그인 변경·401/403·실패·재조회·종료는 이전 확인값을 지우며 이전 로그인 창이 새 접속으로 부모 조회를 시작하지 않도록 검사합니다. 실제 서버 저장에서는 현재 권한·배정·버전·상태와 합의된 날짜 조건을 다시 검사해야 합니다.

회신은 위 기존 W번호별 **수용/수정안/합의 필요, API·DB 영향, 실제 코드·검증, 다음 담당**으로 요청합니다. 질문 정리나 조회 확인을 상태 쓰기 합의·공유 적용 완료로 표시하지 않습니다.

## 3번 — 수신 상태와 회신 요청

작업 중 [3번의 새 수신 회신](../3번/2026-10-19_2번_재작업흐름_수신회신.md)이 `24d6ada`로 올라왔고 목차 `251a852`까지 확인했습니다. **재작업 시작 후 진행중에서 재제출, 담당 분리, 저장 후 재조회 방향을 수신했습니다.** 실제 서버 저장·화면 연결·로컬 조건 수정은 아직 구현 전이라고 명시했습니다. 과거의 ‘반려완료에서 바로 재제출’은 최신 사용자 결정으로 대체됐습니다. 남은 질문은 [기존 요청표](../3번/2026-10-19_팀원들과_합의해야_하는_기준.md)와 같은 W3 번호로 이어갑니다.

| 기존 ID | 2번이 전달할 기준·확인 요청 | 상태 |
