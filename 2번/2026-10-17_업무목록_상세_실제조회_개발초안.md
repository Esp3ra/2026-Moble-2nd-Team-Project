# 2번 업무 목록·상세 실제 조회 개발 초안

작성일: 2026-10-17 · 코드: [alpha 07e444d](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/commit/07e444dfa33a35ffbdce12d0120a77c05b027703)

공통 인증·HTTP·DB 규약을 재사용해 2번 GET 목록·상세와 기존 WinForms 화면을 연결했다. 사용자 확인에 따라 관리 업무는 **업무별 지정 관리자만** 조회한다. 격리 MySQL의 명시적 fixture를 실제 HTTP로 조회하는 화면 검증까지 통과했다.

**개발 초안의 읽기 연결 완료**와 공유 DB·운영 업무 데이터·1번/3번 최종 합의를 구분한다. 업무 API는 명시적 개발 활성화가 필요하고 기본 실행에는 등록하지 않는다. 공유 DB는 접속·변경하지 않았다. 3번의 제출·검토·파일·차수·이력 및 상태 전환은 변경하지 않았다.

실제 HTTP 검증은 삭제 가능한 별도 DB에만 5개 상태별 업무·배정·지정 관리자를 명시적으로 주입했다. 직원/관리자 로그인, 목록/상세/5상태, 직원 관리 범위 거절·타인 상세403, 관리자 본인/관리 범위, 실제 화면 행선택·상세·필터/범위 전환을 확인했다. 운영 데이터를 사용한 것이 아니다.

서버 테스트는 이전 배정 제외·지정 관리자 회수·관리자 역할/grant 단독 우회 차단·직원 관리자 지정 위조·미지원/반복 조건400·70건 전체 목록 무절단·401·403/404·DB503·서버500·조회 중 업무 무변경·GET외405 등을 확인했다. HTTP 대역에서는 누락/NULL·중복/빈 ID·알 수 없는 상태·잘못된 날짜·상세 ID 불일치·빈 목록·오류 매핑·취소를 확인했다.

독립 검토에서 무조건 모델 등록 시 일반 init-db가 합의 전 테이블을 만들 수 있는 문제를 발견했다. 명시적 활성화+지연 import로 수정한 뒤 별도 새 프로세스 초기화까지 재검증했고 추가 결함은 발견하지 못했다. 모든 임시 HTTP/MySQL 프로세스를 종료하고 임시 연결 자격 파일도 삭제했다.

## 실행하지 못한 테스트

- 공유 서버·공유 DB·기존 운영 업무 데이터 연결과 migration/권한 데이터 이관.
- 두 PC, 웹 업무 화면·실제 장치·네트워크/방화벽 조건에서의 업무 일치.
- 업무 등록·수정·배정·관리자 지정 저장 UI/API. 이번에는 읽기 모델과 명시적 fixture만 사용.
- 수락·제출·재제출·승인·반려·연장과 업무 상태 갱신, 3번 파일/차수/이력 통합.
- 실제 마감 연장 데이터·대량 운영 데이터의 페이지/검색·성능. 첫 연결은 전체 목록이며 페이지는 미지원.
- 사람의 전체 디자인 검수. 메시지 루프에서 실제 컨트롤의 동작을 확인한 결과와 구분.

## 남은 합의·실행 기준

[API·DB 합의 정리](2026-10-17_업무조회_API_DB_합의초안.md)에 공통 확정/사용자 회신/개발 코드/팀 합의를 구분했다. 상태 코드·날짜/현재 마감일·상세403/404·업무 FK/migration/schema version·공유 DB 적용은 관련 담당 확인이 필요하다. 협업 범위는 4번과 별도다.

관리자 계층·상위 검토자·반려 후 복귀 시점·자동 검토 요청·마감 후 직접 제출은 질문으로 유지하며 3번 대신 구현하지 않는다. 마감 경과 자동 결과 제출은 제외한다.

실행 시 공통 서버 설정과 명시적 개발 활성화·테스트 DB 준비는 alpha의 `docs/TASK_QUERIES.md`를 따른다. 업무가 없는 DB는 빈 목록을 반환하며 샘플을 조용히 표시하지 않는다. 기본 비활성 서버의404는 연결 필요로 구분한다.
