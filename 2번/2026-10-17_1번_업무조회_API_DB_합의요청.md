# 1번 담당 전달용 — 업무 조회 API·DB·공통 연결 합의 요청

작성일: 2026-10-17 · 요청: 2번 업무·상태·마감 담당 · 대상: 1번 공통 인증·사용자·서버 담당

1번 담당자님, 공통 인증·HTTP·DB 연결을 재사용해 2번의 업무 목록·상세 조회를 개발 초안으로 연결했습니다. 공유 서버·DB에 반영하기 전에 아래 조회 계약과 공통 연결 접점을 확인 부탁드립니다. **업무 모델·조회 API·HTTP 어댑터의 구현은 2번이 계속 담당**하며, 1번께는 공통 규약과의 충돌 여부 및 공유 적용 절차를 요청드립니다.

현재 코드 기준은 [alpha 07e444d](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/tree/07e444dfa33a35ffbdce12d0120a77c05b027703)입니다. 코드가 존재하거나 격리 테스트를 통과했다는 이유로 팀 합의가 완료됐다고 보지 않습니다. 이 요청서를 게시해도 업무 API 활성화·공유 DB 변경을 진행하지 않습니다.

## M1-07 스키마 검토 지점

현재 모델은 [tasks/models.py](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/07e444dfa33a35ffbdce12d0120a77c05b027703/RemoteWork.Server/remotework/features/tasks/models.py)입니다. 이 표는 공유 DDL 확정을 요청하기 위한 현황입니다.

| 테이블 | 현재 개발 모델 | 확인할 부분 |
|---|---|---|
| tasks | task_id BIGINT PK, title VARCHAR(200), description TEXT, task_status VARCHAR(30), start_date/due_date DATE, current_assignment_revision INT, row_version BIGINT, created_by → users.id, UTC created_at/updated_at | ID 타입·문자열 길이·5상태/날짜 제약, 현재 배정 포인터 정합성, 사용자 이력 보존에 맞는 FK 삭제 정책 |
| task_assignments | `(task_id, revision)` PK, task_id → tasks, assignee_id/assigned_by → users.id, UTC assigned_at, nullable accepted_at | current_assignment_revision과의 연결, 배정 이력 보존, 사용자 PK 타입. 수락·재배정 쓰기/동시성 처리는 이번 조회 구현에 없음 |
| task_managers | `(task_id, user_id)` PK, tasks/users FK | 업무별 지정 관리자 관계 보존·회수 기준. 사용자 역할 변경 후 현재 admin 검사와 관계 데이터 정리 책임 |

지정 관리자는 조회 관계이며 제출본의 검토자 계층을 대신하지 않습니다. row_version이 있다는 이유로 낙관적 동시성 제어·쓰기 API가 구현됐다고 보지 않습니다. 현재 GET DTO에는 배정 차수와 row_version이 노출되지 않습니다. 상태 기본값을 조회 모델이 암묵적으로 생성하지 않습니다.

## 3번에게 별도로 전달하는 내용

상위 검토자 매핑·자기 승인/반려 방지·제출/재제출/판정의 상태 갱신·반려 후 복귀·현재 마감 의미·자동 검토 요청은 [3번 전달용 합의 요청](2026-10-17_3번_업무상태_제출검토_연결합의요청.md)에서 다룹니다. 상위 검토자로만 지정된 계정은 현재 업무 상세 GET에서403이므로, 검토에 필요한 업무 기본정보의 열람 방식·필드·권한 조건은 M3-03과 함께 **1번·2번·3번 공동 확인**이 필요합니다. 지정 관리자와 검토자 권한을 자동으로 합치지 않습니다. 이 문서에서 1번께 3번의 기능 구현을 요청하지 않습니다. 1번은 위 M1-06~08 중 공통 FK·트랜잭션·오류·migration 지원만 함께 확인 부탁드립니다.

## 검증 근거와 공유 적용 전 조건

이전 조회 구현 회차에서 Release 빌드 경고0·오류0, 서버 SQLite 35 passed/2 skipped, 격리 MySQL 37 passed, 이후 추가한 활성화 가드 별도1 passed를 확인했습니다. 실제 C#→Waitress→격리 MySQL→STA 화면은 직원19개·관리자21개 assertion을 통과했습니다. 숫자를 합산해 하나의 suite 결과로 표시하지 않습니다. 이번 요청서 작성 중 해당 실행 테스트를 다시 돌렸다는 뜻은 아닙니다.

세부 검증과 미실행 범위는 [구현 기록](2026-10-17_업무목록_상세_실제조회_개발초안.md)을 참고해주세요. 공유 DB·운영 데이터·두 PC·웹·migration은 미검증이며, 공유 환경의 접속정보/비밀번호/토큰/.env 원문은 Git 문서에 올리지 않고 별도 전달 채널을 정합니다.

M1-01~09 합의 후 2번이 계약/DDL/테스트를 수정하고, M1-10 환경이 준비되면 1번과 다음을 확인하고자 합니다: 본인 목록·직접 상세, 전체/5상태·빈 목록, 지정/비지정 관리자·관리자 본인 업무, 재배정 후 과거 담당자 차단, 일반 grant/역할만으로 우회 불가, 401·403/404·DB 장애, DB 값과 화면 일치. 웹 업무 기능이 없는 상태에서 웹 연동 완료로 보고하지 않습니다.

## 회신 양식

각 ID에 **기준 수용 / 변경안 / 확인 필요** 중 하나와 담당·근거·예상 확인 시점을 적어주세요. 변경안이면 경로/필드/DDL/정책의 바뀌는 값을 써주시면 2번이 반영하겠습니다. 확인 필요이면 확인할 담당자와 시점을 남기며, 회신이 없거나 제안만 있는 항목은 ‘합의 필요’로 유지합니다.

```text
ID: M1-01
회신: 기준 수용 / 변경안 / 확인 필요
결정 또는 변경 내용:
담당·공동 확인자:
근거 문서/커밋/회신:
확인일 또는 예상 확인 시점:
```

전체 추적표는 [API·DB 합의 정리](2026-10-17_업무조회_API_DB_합의초안.md), 이전 ID는 [C01~C12 공동 합의 목록](../1번/2026-10-16_공동합의_필요항목.md)을 따릅니다. 회신 반영 시 확정 항목과 남은 항목을 분리해서 갱신하겠습니다.
