# 2번 영역 수정 협업 규약

현재 기준은 [공통규약](공통규약.md), 구현·게시와 실행/미실행은 [업무 구현·검증](업무_구현검증.md), PR 상태는 [통합 검토 기록](PR_검토기록.md)을 먼저 확인합니다. 아래 본문은 기존 전달 경로를 유지하는 작성 당시 기록입니다. 신규 관리자 준비 UI·별도 개발 등록 API의 후속 게시 상태가 당시의 미게시 표현보다 우선합니다.

작성·최신화: 2026-10-17 · 관리 담당: 2번 업무·상태·마감 관리

다른 팀원이 2번 영역을 수정하거나 자신의 기능을 연결할 때 사용할 기준이다. 변경 목적과 파일·계약 영향을 공유하고, 작업 브랜치의 결과를 2번 및 영향 담당자가 검토할 수 있게 전달한다. 이 문서는 2번 영역의 협업 기준이며, 상대 담당의 기능이나 아직 합의하지 않은 공통 계약을 대신 확정하지 않는다.

확인한 기준 코드는 alpha `3b0948025c440b9d3a36da82f464b0bc08557493`이다. 이후 코드는 최신 alpha에서 확인한다. 현재 목록·상세 조회는 구현됐지만 등록·수락·상태 저장·마감 관리 창은 아직 뼈대다. 기존 화면이 있다는 이유로 실제 저장 기능이나 제출·검토 연결이 완료됐다고 해석하지 않는다.

## 1 변경 전후에 공유할 내용

1. 수정 목적과 영향을 받는 담당 번호를 정리한다. 수정할 파일, 기존 동작, 바뀔 동작, 필요한 API/DTO/DB 변경과 미확정 항목을 적는다.
2. 원본 저장소의 최신 alpha를 확인하고 작업 기준 SHA를 남긴다. 포크를 사용하면 원본 alpha와 포크의 작업 브랜치를 구분한다. PR 대상은 기본 main으로 두지 말고 실제 통합 대상 alpha인지 확인한다.
3. 수정은 작업 브랜치에서 준비하고 관련 없는 파일 정리·전체 포맷 변경을 섞지 않는다. 다른 팀원의 진행 중인 변경은 덮어쓰지 않는다.
4. 기존 계약을 유지하는 문구·레이아웃·버그 수정은 범위를 공유하고 진행한다. 이미 허용된 작업 범위에 대해 매번 허가를 다시 받는 절차로 확대하지 않는다.
5. API·DTO·권한·상태/날짜 의미·DB·공통 연결이나 다른 담당의 동작을 바꾸려면 아래 담당과 계약을 먼저 맞춘다. 합의 전에는 영향 분석·독립적인 준비와 명시적 테스트 대역까지 구분해 진행한다.
6. PR에 변경 결과·실행한 검증·미실행 검증·남은 합의를 남기고 2번 및 영향 담당에게 검토를 요청한다. 검토에서 확인한 계약으로 통합한다. 사용자·팀이 이미 명시한 직접 반영 요청은 해당 범위에 우선 적용한다.

현재 브랜치 보호·필수 리뷰어가 자동 설정되어 있다는 뜻은 아니다. PR·검토 요청과 최종 병합은 실제 저장소 권한과 팀의 운영 방식에 맞춰 수행한다.

## 3 유지할 조회 계약

전체 필드와 동작의 기준은 [조회 계약](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/alpha/docs/TASK_QUERIES.md)과 [조회 경계 README](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/alpha/RemoteWork.WinForms/Features/Tasks/Queries/README.md)다. 아래 항목을 변경하려면 계약·서버·클라이언트·테스트·문서를 함께 수정한다.

| 구분 | 유지 기준 |
|---|---|
| 공개 경계 | ITaskQueryService.SourceDescription, GetTasksAsync(TaskListQuery, CancellationToken), GetTaskAsync(string, CancellationToken). 목록은 IReadOnlyList 전체 반환 |
| 식별자·날짜 | 화면 TaskId는 불투명 문자열. DB 업무 ID는 signed BIGINT·JSON 문자열, 사용자 ID는 공통 정수. 날짜는 DATE/YYYY-MM-DD/DateOnly, 기록 시각 UTC와 구분 |
| 조회 API | GET /api/v1/tasks와 /api/v1/tasks/{task_id}. scope=own 또는 managed, status 생략은 전체. 잘못된/반복/미지원 조건400 |
| 목록 결과 | due_date ASC, task_id ASC의 전체 목록. 페이지/검색 도입 전 임의 절단·첫 페이지만 전체로 표시하지 않음 |
| 응답 | 공통 envelope의 data.items/data.task, snake_case, 필수/NULL 규칙 유지. description은 빈 문자열 허용·누락/NULL 거절 |
| 본인 범위 | 직원·관리자 모두 현재 본인 배정만. 과거 배정 이력은 현재 조회 권한이 아님 |
| 관리 범위 | 현재 admin 역할과 해당 업무의 task_managers 지정이 모두 필요. 상세 직접 요청도 서버에서 별도 검사 |
| 다른 관계 | 관리자 역할·일반 grant·같은 부서·등록자·협업 참여·상위 검토자만으로 조회 범위를 확장하지 않음. 중복 ResourceGrant를 임의 요구하지 않음 |
| 오류 | 401 공통 인증 만료,403 권한 없음,TASK_NOT_FOUND 상세404는 업무 없음,미등록 HTTP_404는 연결 필요. 서버/DB/통신/형식 오류와 취소를 구분 |
| 공통 HTTP | AppServices.Api 재사용, 서버 루트+api/v1 접두사 한 번. 화면별 토큰 보관/인증 우회/공유 인스턴스 Dispose를 추가하지 않음 |

화면 상태도 계약에 포함한다. 실제 로그인 MainForm만 HttpTaskQueryService(AppServices.Api)를 주입하며 기본 생성자·Designer·미리보기는 미구성 상태를 유지한다. 대역의 출처를 표시하고 오류를 샘플 결과로 바꾸지 않는다. 같은 조건의 선택 유지, 조건 변경 시 초기화, 상세만 재시도, F5 전체 조회, 로딩·빈 목록·오류·취소 구분, 늦은 응답과 종료 후 응답 차단을 보존한다. 요청 상태와 다른 목록을 조용히 재필터링하거나 부분 성공으로 표시하지 않는다.

## 4 상태·DB·다른 담당 연결

| 화면 상태 | DB/JSON 문자열 |
|---|---|
| 진행전 | not_started |
| 진행중 | in_progress |
| 제출완료 | submitted |
| 승인완료 | approved |
| 반려완료 | returned |

C# enum의 정수 순서로 저장하지 않는다. 기본 의미는 배정 후 진행전→수락 시 진행중→정식 제출/재제출 시 제출완료→검토 후 승인완료/반려완료이며 승인완료만 최종 완료다. 모든 정식 제출은 권한 있는 검토자의 판단을 거친다. 관리자 본인 업무도 같은 흐름을 사용하고 상위 검토자가 판단한다. task_managers의 조회 관계를 제출 검토자 계층으로 바꾸지 않는다.

**표현 형식은 1번이 수용했지만 쓰기 계약은 별도다.** 초기 저장 기본값·상태 갱신 책임·제출/판단 트랜잭션·반려 후 복귀·검토자 열람·마감 시간대/시각·연장·마감 후 직접 제출은 [3번 합의 요청](공통규약.md#r017)에 따라 확인한다. 자동 결과 제출은 제외하고 자동 검토 요청은 합의 필요로 유지한다.

DB는 공통 Base·get_db·transaction·UTC·감사 이력을 재사용한다. 기존 사용자/업무/배정/제출 이력을 일괄 cascade 삭제하지 않는다. 현재 배정 포인터와 배정 차수의 쓰기 정합성·새 FK·row_version/updated_at 갱신 책임·잠금/재시도는2·3번 공동 확인 후 구현한다. row_version 필드만으로 동시성 제어 완료를 주장하지 않는다.

현재 **공통 schema version1·업무 기본 off**를 유지한다. `REMOTEWORK_ENABLE_TASK_QUERY_DRAFT=1`은 삭제 가능한 개발/테스트 DB의 명시적 활성화다. [예약002 SQL/검증·복구안](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/alpha/RemoteWork.Server/migrations/002_task_queries.md)은 검토 초안이며 공유 DB 적용 승인이나 버전2 지원이 아니다. init-db/create_all은 기존 열 migration을 대신하지 않는다. migration 번호는 1번과 조정하고, 기대 버전 검사·공유 백업/복구·적용 순서는 1번 및 팀장과 확인한다. 실제 .env·계정·토큰·덤프·DB·장치 원본 데이터는 게시하지 않는다.

## 5 변경 범위에 맞춘 검증

문서·주석 변경은 링크·경로·합의 표현·diff 검사로 확인한다. 실행 코드가 바뀌면 영향에 맞는 검증을 수행하고, 관계없는 대규모 테스트를 통과 근거처럼 반복하지 않는다.

| 변경 | 필요한 확인 |
|---|---|
| Designer·TasksControl·조회 화면 상태 | Release 빌드와 TaskQueries.Tests. 화면 배치 변경은 기본/최소 크기에서 잘림·겹침 확인 |
| HTTP 어댑터·DTO·취소/세션 연결 | TaskQueries.Http.Tests와 영향받는 UI 회귀. 공통 접속 변경은 1번 ApiClient.Tests도 확인 |
| 서버 조회·권한·오류·정렬/필터 | 서버 test_task_queries.py와 관련 공통 회귀. 본인/타인·지정/비지정 관리자·재배정·직접 상세·만료·오류를 포함 |
| 모델·DDL·migration | 새 전용 MySQL에서 실제 SQL 전후·기존 행·FK/제약·권한·실패/복구. 모델 create_all만으로 migration 성공이라고 표시하지 않음 |
| 제출/검토·협업·장치 접점 | 관련 담당과 허용/거절·실패·중복/재시도 등 연결 규칙을 확인하고 기존 조회 회귀 수행. 준비 전 대역은 대역으로 명시 |

Windows의 저장소 루트에서 해당 범위에 필요한 명령을 선택한다.

```powershell
dotnet build .\RemoteWork.sln -c Release
dotnet run --project .\Tests\TaskQueries.Tests\TaskQueries.Tests.csproj -c Release
dotnet run --project .\Tests\TaskQueries.Http.Tests\TaskQueries.Http.Tests.csproj -c Release
dotnet run --project .\Tests\ApiClient.Tests\ApiClient.Tests.csproj -c Release
```

서버는 RemoteWork.Server 폴더에서 준비한 가상환경 Python으로 실행한다.

```powershell
python -m pytest -q tests/test_task_queries.py
```

MySQL 테스트는 삭제 가능한 전용 DB와 명시적 설정이 필요하다. 공통 테스트의 MYSQL_TEST_URL은 기존 행을 비울 수 있으므로 공유 DB를 지정하지 않는다. 002 실DB 검사는 별도의 MYSQL_MIGRATION_TEST_URL과 REMOTEWORK_RUN_TASK_MIGRATION_DRAFT_TESTS를 사용하는 위 실행 절차를 따른다.

UI 대역, HTTP 전송 대역, Flask test client, 실제 TCP 서버→C#→DB/WinForms, 두 PC 검증을 구분한다. 빌드나 대역 통과를 실서버·공유 DB·장치·제출 통합 완료로 기록하지 않는다. 실패한 검증과 미실행 검증도 남긴다.

## 6 PR 및 전달 양식

아래 양식을 PR 본문과 변경 기록에 사용한다. 수정 사항이 있으면 요약만 추가하지 말고 최종 변경 상태로 갱신한다.

```markdown
## 변경 목적
- 작업자/담당 번호:
- 원본 기준 브랜치와 SHA:
- 연결할 기능과 변경 이유:

## 변경 내용과 영향
- 변경 파일:
- 기존 동작 → 변경 후 동작:
- 유지/변경하는 API·DTO·권한·상태·날짜 계약:
- DB·migration·기존 데이터 영향:
- 함께 확인할 담당 번호와 합의 근거:

## 검증
- 실행 명령·결과:
- 검증 환경/데이터 출처(대역·격리 DB·실제 서버 등):
- 실패/미실행 검증:
- 남은 합의:
- 관련 LOG 문서:
```

코드는 alpha의 작업 흐름으로 제안하고 구현/협의 기록은 LOG 브랜치의 `2번/날짜_주제.md`에 남긴다. 푸시마다 해당 브랜치 README를 실제 상태에 맞춘다. 코드 브랜치의 `/DOCX/` 제외를 유지하고, 문서 갱신은 별도 문서 작업으로 진행한다. 개인 fork의 브랜치 목록에 원본 LOG/PR 브랜치가 자동 복제된다고 가정하지 않는다.

## 7 이번 문서 작성의 확인 범위

기준 코드·조회 계약·실제 인터페이스·MainForm 주입·테스트 README·1번 회신·3번 질문을 대조했다. 담당 경계와 문서 링크·Markdown 표·변경 파일을 확인했다. 이번에는 실행 코드·DB·장치·브랜치 보호 설정을 바꾸지 않았고 프로그램 테스트를 재실행하지 않았다. 과거 회귀 수치는 해당 구현 기록의 결과로 구분한다.
