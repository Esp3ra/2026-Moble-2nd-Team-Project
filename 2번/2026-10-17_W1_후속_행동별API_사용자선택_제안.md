# 2번 제안 — W1 후속 행동별 API·사용자 선택·감사 경계

작성일: 2026-10-17 · 작성: 2번 업무·상태·마감 담당 · 검토 요청: 1번 공통 담당, 3번 제출·검토 담당, 팀장

**이 문서의 API·쓰기 DTO·권한·오류·감사 이름은 2번 제안이며 공동 합의나 구현 완료가 아니다.** [1번 W1 회신][w1]의 W1-01/03/04/07에서 요청한 행동별 초안을 한 문서로 제시한다. 기존 W1/W3 ID로 추적하며 같은 질문을 새 ID로 늘리지 않는다. 3번 W3 회신은 기준 LOG에서 확인되지 않아 해당 결정은 합의 필요로 남긴다.

대조 기준은 alpha [c56f3c8][alpha], LOG [64662e5][log]다. 구현·DB 규약·지속관리·주요 검증은 MySQL 기준이다. SQLite는 DEMO 임시 구성으로 종료 후 삭제 예정이며 이 제안의 별도 지원 대상으로 추가하지 않는다.

## 그대로 전달할 담당별 요약

**1번께:** [기존 W1 요청][w1-request]과 [W1 회신][w1]의 같은 ID로 이어서 확인 부탁드립니다. 직원 본인 수락/연장에 쓸 공통 재인증 트랜잭션(W1-02), 버전·멱등키 전달/저장·결과 확인 지원(W1-03), 배정 후보 조회와 실제 선택 권한 계약(W1-07)의 구현 커밋·공개 인터페이스·검증 범위를 준비되는 대로 연결해 주세요. 아직 지원이 없으면 구현 전으로 유지하겠습니다. 아래 2번 행동별 API·오류/감사·선택 정책 **제안**을 W1-01/03/04/07 기준으로 검토해 주시고, 정식 DDL/버전 적용(W1-05)과 공유 환경(W1-06)은 별도 단계로 확인하겠습니다.

**3번께:** [기존 W3 요청][w3]에 같은 ID로 답변 부탁드립니다. W3-01/02의 초기 저장·본인 수락 예외와 상태/버전 원자성, W3-03/04의 상태별 수정·재배정/반려 복귀·제출 FK/배정 차수, W3-05/06의 상위 검토자와 연장 판단·업무 시간대/기한·제출 경합 조건이 필요합니다. 미정은 ‘합의 필요’로 적어 주세요. 자동 검토 요청은 W3-07 도입 여부부터 확인하고 자동 결과 제출은 제외합니다. 제출·재제출·차수·파일·승인/반려 구현은 3번 범위로 유지합니다.

**2번이 제공하는 범위:** 이 문서에 등록·기본정보 수정·재배정/조회 관리자 변경·본인 수락·연장 신청/판단을 나눈 API/입출력·오류·최소 후보 선택·감사 **제안**을 담았습니다. 기존 GET DTO/로컬 CheckedInput은 바꾸지 않았습니다. 신규 쓰기 경로·후보 API·멱등/버전 지원이 이미 구현됐거나 공동 확정된 것으로 해석하지 않습니다. 원문 W1/W3가 질문 목록이며 이 문서는 그 회신 검토에 필요한 2번 초안 하나입니다.

## 실제 코드와 이번 제안의 차이

## W1-01/03 — 공통 입력·결과 제안

기존 `/api/v1`, snake_case, 성공 `ok/data/request_id`, 실패 `ok/error/request_id`, Bearer와 서버 로그인 문맥을 재사용한다. 수행 사용자·역할·`created_by`·`assigned_by`·판단자·감사 수행자는 요청 본문의 값을 믿지 않고 서버가 결정한다. 지원하지 않는 필드와 임의 상태 입력을 거절하는 방향을 제안한다.

| 항목 | 제안과 미결정 사항 |
|---|---|
| 업무 ID | W1-03의 양의 10진 문자열, signed BIGINT 최댓값9223372036854775807 제안을 따른다. 부호·공백·소수·0 금지. UI는 여전히 불투명 문자열로 취급하고 ID를 생성하지 않음 |
| `expected_row_version` | W1-03의 같은 범위 양의 10진 문자열 제안. 기존 업무를 바꾸는 모든 행동에서 검사하는 안. 업무 신규 등록에는 기존 버전이 없으므로 보내지 않음 |
| `expected_assignment_revision` | W1-03의 양의 signed INTEGER JSON 정수, 최댓값2147483647 제안. bool·소수·문자열 대체 금지. 기존 업무 행동에서 현재 배정과 대조 |
| 사용자 ID | 기존 공통 signed INTEGER 식별을 재사용하는 JSON 정수 안. 후보 응답 ID를 선택하고 서버가 활성/역할/선택 범위를 재검사. 표시명에서 ID 추정 금지 |
| 날짜·시각 | 업무 날짜는 `YYYY-MM-DD`/DATE/DateOnly, 기록 시각은 서버 UTC ISO 8601. DATE를 UTC 자정으로 변환하지 않음. 마감 당일 종료·업무 시간대는 W3-06 합의 필요 |
| 제목·설명 | 현재 입력/모델의 제목200문자 범위와 시작일≤마감일을 대조. Unicode 코드 포인트 검사와 공백/정규화·설명 상한·빈 설명 허용 정책은 서버 계약 검토 시 명시. 서버는 화면 검사 통과를 신뢰하지 않음 |
| 성공 결과 | `data`에 행동 결과 ID·`task_id`·서버 확정 `row_version`·`assignment_revision`·`task_status`·`updated_at`을 포함하는 방향. 필드 이름/필수성·HTTP201/200은 아래 안과 함께 확인 필요. 일반 조회 DTO를 무단 교체하지 않음 |
| 멱등키 | 수행 사용자·행동·대상·요청 키 범위, 본문 지문에 예상 버전/배정 차수 포함이라는 W1-03 안을 추적. 헤더 이름/길이/수명·새 등록 대상 범위·진행 중 중복·결과 조회 경로·권한 재확인·만료 후 처리 모두 1·2·3번 합의 필요 |

별도 `GET /api/v1/tasks/{task_id}/write-context`를 **제안**한다. 원본 업무 ID, 현재 assignee_id·manager_user_ids, row_version·assignment_revision과 실제 서버에서 허용한 행동의 준비 정보를 최소로 제공하는 방향이다. **assignee_id는 기존 GET 서버 JSON에 이미 존재하는 필드이며 새 서버 식별 필드 제안이 아니다.** 기존 GET 계약은 유지하고, 버전·배정 차수·관리자 식별자 등 추가 정보의 공급 방식과 C# 쓰기 준비 DTO 연결을 W1-01/03/07 및 W3-04에서 공동 확인한다. 노출 권한·준비 응답과 실제 쓰기 사이 변경을 처리할 조건도 확인이 필요하다. 준비 정보를 받은 사실은 저장 권한·최신성 보증이 아니며 쓰기 시 다시 검사한다. 이 경로는 현재 호출할 수 없다.

## W1-01/04 — 행동별 API·입출력 제안

아래 경로는 모두 `/api/v1` 기준 **제안**이다. 상태를 임의 지정하는 범용 `set_status` 경로를 만들지 않는다. 모든 기존 업무 변경의 `기대값`은 위 두 expected 필드다. 결과의 배정 차수 증가 여부와 row_version 증가 규칙은 W3-02/04 공동 확인 전까지 실행하지 않는다.

| 행동·담당 | 메서드·경로 제안 | 입력 제안 | 성공 결과·저장 경계 제안 | 남은 확인 |
|---|---|---|---|---|
| 최초 등록·배정 / 2번 | `POST /tasks` | `title`, `description`, `start_date`, `due_date`, `assignee_id`, `manager_user_ids` | HTTP201, 새 업무 ID와 확정 버전·배정 차수. 업무·최초 배정·조회 관리자 관계·성공 감사를 한 트랜잭션. not_started와 accepted_at NULL 초기 저장안 | W1-01/04/07, W3-01/04. 생성 권한·관리자 필수 수·초기 버전/배정 차수·순환 FK 생성 순서 미확정 |
| 기본정보 수정 / 2번 | `PATCH /tasks/{task_id}` | 기대값과 변경할 `title`, `description`, `start_date`, `due_date`만 | HTTP200, 확정 결과. 기본정보와 updated_at·버전·감사를 함께 기록. 담당자/관리자/상태 변경은 이 요청에서 제외 | W3-03/06. 상태별 허용·직접 due_date 변경 허용 여부 필요. 연장 승인 경로를 우회하는 수정은 허용하지 않는 안이며 확정 전 due_date 쓰기 미연결 |
| 재배정 / 2번 | `POST /tasks/{task_id}/assignments` | 기대값, `assignee_id` | HTTP201 또는200 검토. 새 배정 revision과 현재 포인터를 원자적으로 바꾸고 과거 배정·제출 소유를 보존. 이전 사람의 accepted_at을 새 배정으로 복사하지 않음 | W1-04/07, W3-01~04. 동일 담당자 재지정의 무변경/충돌·수락 이력·상태·제출 중 재배정 미확정 |
| 조회 관리자 지정/해제 / 2번 | `POST /tasks/{task_id}/manager-changes` | 기대값, `add_user_ids`, `remove_user_ids` | HTTP200, 확정 관리자 식별자와 버전. 한 요청은 전부 성공 또는 전부 rollback. 중복 ID·동일 ID 추가/삭제 동시 지정 검증 | W1-04/07, W3-05. 실제 지정 권한·최소 관리자 수·자기 회수·마지막 관리자 회수·재시도 규약 필요. 검토자 지정 API가 아님 |
| 본인 명시 수락 / 2번 | `POST /tasks/{task_id}/accept` | 기대값. 수락할 사용자 ID나 임의 목표 상태를 받지 않는 안 | HTTP200, 서버가 현재 배정 당사자를 재확인 후 in_progress·accepted_at·버전·감사를 원자 기록하는 안 | W1-02~04, W3-01/02. 같은 행동 재요청·시작 전/마감 후·반려 이후 허용 조건 미확정 |

| 연장 반려 / 2번 | `POST /tasks/{task_id}/deadline-extensions/{extension_id}/reject` | 기대값, 판단 사유 필드/필수성은 확인 필요 | HTTP200, 신청 판단 결과. 현재 due_date 유지안. 업무5상태의 returned와 구분하며 새 상태 코드를 업무 상태에 추가하지 않음 | W3-06. 판단자·신청 상태·판단 중복/경합·업무 버전 증가/별도 신청 버전 필요 여부 미확정 |

연장 신청의 내부 상태/테이블/식별자·신청 버전은 이 표로 확정하지 않는다. 현재 조회 DB에 해당 모델이 있는 것으로 표시하지 않는다. 업무 취소·반려 후 재작업 시작은 W3-03의 조건과 담당 확인 후 별도 논의하며 이번 경로에 슬쩍 포함하지 않는다. **3번 정식 제출·재제출·파일·제출 차수·검토 판단 API/DDL은 이 문서에서 정의하지 않는다.**

### 오류 제안 — W1-01/03과 연결

W1 회신의 기존 `401 AUTH_REQUIRED`, `403 FORBIDDEN`, `400 INVALID_INPUT`, 기존 업무 `404 TASK_NOT_FOUND`, DB/초기화 `503` 분리를 유지한다. 1번 제안인 `409 TASK_VERSION_CONFLICT`, `409 TASK_ASSIGNMENT_CHANGED`, `409 TASK_STATE_CONFLICT`, `409 IDEMPOTENCY_KEY_REUSED`, `409 ASSIGNEE_UNAVAILABLE`는 **아직 미구현·합의 필요**다. 후보 관리자가 비활성/역할 변경된 경우와 연장 신청 자체의 없음·이미 처리됨을 어느 HTTP/code로 줄지도 함께 확정해야 한다.

허용되지 않은 사용자가 버전/배정 정보로 다른 업무를 추측하지 못하도록 대상 존재/접근과 행동 권한을 검사한 뒤 상세 충돌 정보를 주는 방향을 제안한다. 인증·권한·배정·버전·상태·후보 비활성 조건이 동시에 바뀐 경우의 우선순위와 응답에 최신 값을 넣을 권한은 1·2·3번 공동 확인 사항이다. `ASSIGNEE_UNAVAILABLE`는 서버의 재검사 결과이며 현재 사용자의 세션이 비활성인401과 구분한다.

서버 반영 여부를 모르는 통신 실패는 실패 확정과 구분한다. 공통 결과 확인·멱등 지원 전에는 새 키로 무조건 다시 제출하거나 성공 안내를 하지 않는다. 동일 키·다른 본문은 성공 재사용하지 않으며, 동일 키·동일 본문도 계정 전환/권한 회수 이후 재응답 조건을 확정해야 한다.

## W1-07 — 선택 권한과 후보 조회 제안

**현재 관리 업무 조회는 admin 역할과 해당 업무별 지정 관리자 관계를 모두 충족해야 하는 범위다.** 관리자 role만으로 전체 업무의 수정·재배정·관리자 지정을 허용하지 않는다. 다음은 2번의 쓰기 권한안으로, 1번·3번·팀장 확인 전 실행 코드에 넣지 않는다.

| 행동 | 2번 제안 | 반드시 결정할 범위 |
|---|---|---|
| 새 업무 개설 | 활성 관리자에게 개설 권한을 부여하는 방향 | 모든 활성 관리자인지, 별도 개설 권한/조직 범위인지. 직원 자기 업무 개설 허용 여부. 미확정이므로 기본 허용하지 않음 |
| 기존 업무 기본정보 수정·재배정 | 현재 업무별 지정 관리자에게 허용하는 방향 | 관리자 role도 동시에 필요한지, 지정 관계만으로 가능한지. 역할 강등/관계 회수 시점 및 상태 조건. 조회 관계의 자동 전용으로 확정하지 않음 |
| 업무 관리자 지정·해제 | 기존 업무 개설/변경과 별도의 관리 권한 결정 필요 | 지정 관리자가 다른 관리자에게 권한을 줄 수 있는지, 생성자 전용/상위자/별도권한인지. 최종 관리자 삭제·자기 회수·생성자의 후속 권한 |
| 본인 수락·연장 신청 | 서버가 현재 배정 당사자를 확인하는 방향. 관리자 본인 업무도 같은 원칙 | 연장 신청 주체 추가 허용 여부·상태/기한 조건은 W3-01/06. 관리자 role만으로 타인 대신 수락 불가 |
| 연장 승인·반려 | 업무별 허용 판단자를 별도로 확인 | 지정 관리자 중 누구인지, 자기 신청 판단 금지인지, 상위 검토자 관계를 재사용하는지. task_managers를 제출 승인권자로 자동 전용하지 않음 |

후보 API는 1번이 공통 사용자 식별/권한 기준과 함께 제공할 영역이다. 아래는 **2번의 소비 계약 제안**이며 `GET /users`를 개방/수정하거나 새 API를 2번이 대신 구현하는 작업이 아니다.

| 용도 | 경로·조건 제안 | 반환·화면 원칙 |
|---|---|---|
| 배정 후보 | `GET /api/v1/tasks/assignment-candidates` + 새 등록 문맥 또는 기존 `task_id`, `q`, `page`, `limit` | 활성 employee/admin 중 서버가 해당 개설/재배정 범위에 허용한 사람만. 관리자 본인도 업무 수행자로 선택 가능하되 조직/관계 범위는 합의 필요 |
| 조회 관리자 후보 | `GET /api/v1/tasks/manager-candidates` + 같은 문맥·검색/페이지 | 활성 admin을 우선 제안. 위 관리자 지정 권한이 없는 호출자에게 조회도 개방하지 않는 방향. 자기 지정·상위자 지정 범위는 합의 필요 |

최소 공개 필드는 `id`, `display_name`, 동명이인을 구분할 서버 제공 `selection_label` 안이다. label에 필요한 부서/일부 식별자의 구체 범위는 1번과 정하고, login_id·전체 사번·계정 생성 시각·비활성 계정 목록을 기본으로 노출하지 않는다. 표시가 같아도 선택은 id로 보존한다. 관리자는 역할을 숨긴 채 직원으로 오인되지 않도록 필요한 최소 역할 구분을 label/필드 중 어떻게 제공할지 확인한다. 후보 조회는 전체 조직 인명부 권한이 아니다.

페이지 envelope는 기존 공통 page/limit/total 형태를 우선 제안하되 후보 정렬·검색 길이/범위·동일 표시명 tie-breaker·페이지 간 변경 일관성은 1번이 확정할 항목이다. 처음 페이지를 전체 허용 인원으로 표시하지 않는다. UI가 후보 전체를 모으는 방식을 택하면 **한 페이지라도 실패/취소/인증 변경/중복 또는 불일치가 생겼을 때 일부 결과를 완성 목록이나 저장 가능한 선택으로 확정하지 않는다.** 서버 페이징 UI를 택하면 현재 페이지/다음 페이지 존재를 명시하고 전체 적재 완료를 주장하지 않는다. 빈 결과·조회 실패·권한 없음·이전 페이지를 각각 구분한다.

후보에서 선택한 뒤 비활성화·강등·관계 변경이 생길 수 있으므로 실제 쓰기에서 후보 ID·현재 활성/역할·허용 범위를 다시 검사한다. 첫 페이지 조회, label 표시, 클라이언트 캐시, 사전 준비 응답이 서버의 최종 권한 검사를 대체하지 않는다.

## W1-04 — 감사·정합성 초안

감사는 기존 공통 `audit()`/AuditEvent와 업무 변경을 같은 트랜잭션에서 기록한다. 별도 공통 감사 테이블이나 인증/멱등/잠금 도구를 2번이 만들지 않는다. 아래 action/resource/details는 **1번 형식 검토를 위한 이름 제안**이다.

| 행동 | action / resource 제안 | 최소 details 제안 |
|---|---|---|
| 등록 | `task.created` / `task` / task_id | 결과 버전·배정 revision, assignee_id·조회 관리자 ID, 변경 필드 이름 |
| 기본정보 수정 | `task.updated` / `task` / task_id | 변경 필드 이름·전후 버전/배정 revision. 제목·본문 원문 제외 |
| 재배정 | `task.reassigned` / `task` / task_id | 전후 assignee_id·배정 revision·업무 버전. 과거 제출 소유 변경 없음 |
| 관리자 변경 | `task.managers_changed` / `task` / task_id | 실제 추가/삭제 ID·전후 업무 버전·배정 revision |
| 본인 수락 | `task.accepted` / `task` / task_id | 현재 배정 revision·전후 업무 버전·상태 변화. 수행자는 서버 문맥 |
| 연장 신청 | `task.deadline_extension_requested` / `task` / task_id | 신청 ID·현재/희망 날짜·전후 버전 처리 결과. 사유 원문 제외 |
| 연장 판단 | `task.deadline_extension_approved` 또는 `task.deadline_extension_rejected` / `task` / task_id | 신청 ID·판단 결과·전후 유효 날짜/업무 버전. 판단 사유 원문 제외 |

ID도 접근 제한된 감사 정보로 취급하며 일반 후보 응답에 감사 내용을 노출하지 않는다. 비밀번호·토큰·멱등키 원문·파일 내용·제목/설명/사유 원문은 감사 details에 넣지 않는 안이다. 기존 scrub 도구만 믿고 임의 본문 전체를 전달하지 않는다. 무변경/동일 멱등 재응답에 성공 감사를 중복 생성할지 여부는 W1-03에서 단일 효과와 함께 결정한다. rollback·거절을 성공 감사로 남기지 않는다.

최초 등록은 업무/배정/관리자·감사, 재배정은 새 행/현재 포인터/상태·버전/감사, 연장 승인은 신청 판단/유효 마감/버전/감사를 각각 하나의 원자 처리로 제안한다. 다중 사용자 잠금 정렬·존재하지 않는 관계행 경합·관리 권한 회수와의 잠금 순서는 W1-02의 공통 도구와 3번 쓰기 경로를 대조한다. 이 문서로 교착 방지나 역할 회수 경합 해결을 보증하지 않는다.

업무/현재 배정의 복합 FK·초기 포인터 생성 순서·3번 제출 FK/배정 revision 보존은 W1-04/05와 W3-04 합의 필요다. 제출 테이블을 예상해 FK를 임의 추가하거나 삭제 cascade를 도입하지 않는다. `row_version`·UTC 시각·배정 초기값은 정식 서비스/DDL 계약에서 명시하고 현재 초안 DB 기본값이 모두 존재한다고 가정하지 않는다.

각 담당은 기존 W1/W3 ID와 근거 문서/코드 커밋을 연결해 변경안·합의 필요를 답하면 된다. 제안 승인과 실제 공통 지원 배포는 구분한다. **권한/초기 저장·공통 지원/FK가 확인된 등록·배정 → 본인 수락 → 날짜/연장 조건이 확인된 마감 관리** 순서로 실제 구현하고, 3번의 정식 제출/검토는 3번 계약이 제공된 접점만 연결한다. 일부만 확인되면 독립 가능한 행동만 진행한다.

함께 검증할 항목은 MySQL에서 직원/관리자 본인 수락, 타인/옛 배정 차단, 지정 관리자 회수·강등·비활성/접속 폐기, 버전 충돌·중복·응답 유실, 등록/재배정/연장 실패 rollback과 감사 단일 효과, 제출/연장/재배정 경합이다. 공유 DB/두 PC는 공식 환경 인계 뒤 별도 실행한다.

이번 문서는 소스/규약 정적 대조와 제안 작성이다. 실행 코드·조회 DTO·CheckedInput·API 등록·DB/DDL·공유 환경을 변경하지 않았고, 프로그램 테스트/빌드·MySQL 쓰기·실제 HTTP 쓰기·공유/두 PC 검증은 실행하지 않았다. 이 문서의 경로와 결과 표를 실제 연동 완료로 사용하지 않는다.
