# 1번 담당 공통 규약 확인 요청

작성: 2번 업무·상태·마감 담당 · 확인 요청 대상: 1번 공통 담당 · 정리일: 2026-10-16

업무 목록·상세 조회를 기존 공통 구현에 맞춰 연결하려고 합니다. 아래 규약의 확정 여부와 사용해야 할 소스·문서를 알려주세요. 이미 정한 규약이 있다면 그 규약을 우선 적용하겠습니다. 미확정 항목은 **초안·없음·합의 필요**로 답변하고, 확인할 담당과 결정 시점을 함께 적어주시면 됩니다.

## 1. 현재 준비 상태와 요청 범위

확인 기준은 alpha·0.0.2V의 [8f09183](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/commit/8f09183ef992606ec4c2b7e3da79ef07983ba019)입니다. 이 저장소와 로컬 2차 프로젝트에서 공통 인증 사용자·HTTP 클라이언트·서버 API·오류 응답·DB 연결 규약을 찾지 못했습니다. 별도 브랜치나 팀원 작업에 구현돼 있다면 위치부터 부탁드립니다.

2번은 기존 WinForms 구조를 유지하고 목록·상세 조회 인터페이스와 명시적 테스트 대역, 행 선택·상태 필터·로딩·빈 목록·오류·재시도 표시까지 준비했습니다. 기본 실행은 미연결 상태입니다. 실제 인증·HTTP·DB·서버 조회 권한은 아직 연결하거나 검증하지 않았습니다.

계획서의 `GET /tasks`, `GET /tasks/{taskId}`와 테이블 이름은 **제안**입니다. 아래 질문의 경로·필드·오류 코드도 회신받기 전에는 확정 규약으로 사용하지 않겠습니다. 공통 기능과 다른 담당 기능은 각 담당의 규약을 확인한 뒤 연결합니다.

우선 **A1~A4**만 답변받아도 읽기 연결의 출발점을 정할 수 있습니다. 각 항목은 `확정 / 초안 / 없음 / 합의 필요` 중 현재 상태와 근거 링크를 먼저 알려주세요.

## 2. 우선 확인할 공통 규약

| 번호 | 확인할 내용 | 부탁드리는 답변·자료 |
|---|---|---|
| A1 | 공통 서버 소스와 실행 방법 | 사용할 저장소·브랜치·기준 커밋·진입 파일, 실행 명령과 환경 설정 예시, 개발 API 기본 주소, 현재 실행 가능 여부 |
| A2 | 인증 사용자와 공통 HTTP 연결 위치 | 로그인 후 사용자 컨텍스트를 받는 방법, 사용자 PK 타입·역할 값, 공통 ApiClient의 파일·사용 예시·주입 위치, 채택한 인증 전달 방식과 만료 처리 |
| A3 | 실제 업무 목록·상세 조회 계약 | 실제 메서드·경로·요청 조건, 성공 응답 JSON 예시, 상태 코드와 빈 목록·상세 미존재 규격, 현재 업무 API의 구현 여부와 담당 |
| A4 | 서버의 본인·관리 업무 조회 권한 | 직원 본인 배정 기준, 관리자 본인 업무와 관리 범위의 구분 기준, 목록·상세 각각의 서버 검사 위치, 범위 밖 접근 응답 정책 |

A2에서는 화면 선택용 `PreviewRole`, 이름·사번 예시를 인증 정보로 사용하지 않습니다. 실제 사용자 식별과 인증 전달은 1번 공통 컨텍스트를 따르겠습니다. 조회 요청 본문의 사용자 ID나 역할 선택값을 서버가 신원·권한 근거로 신뢰하지 않도록 연결해야 합니다.

A4의 관리 범위는 부서·등록자·배정·조직 권한 중 무엇을 기준으로 하는지 알려주세요. 관리자 역할만으로 모든 업무를 조회할 수 있는 것으로 가정하지 않겠습니다. 목록에서 숨긴 업무도 ID를 직접 넣어 상세 요청할 수 있으므로 **상세 API에서도 별도 권한 검사**가 필요합니다.

## 3. 목록·상세 모델에서 맞춰야 할 항목

현재 2번의 읽기 경계는 다음과 같습니다. 아래 타입은 **화면 내부 모델**이며 서버·DB의 확정 타입이 아닙니다.

| 현재 화면 모델 | 공통 규약에서 확인할 사항 |
|---|---|
| `TaskListQuery.Scope`: Own / Managed | 실제 요청에서 두 범위를 표현하는 방법, 허용 범위를 결정하는 서버 기준 |
| `TaskListQuery.Status`: 전체 또는 화면용 5개 상태 | 전체 조회 조건, 상태 전송 코드와 응답 코드의 5개 화면 상태 매핑 |
| `TaskSummary.TaskId`: 불투명 문자열 | 실제 업무 ID 타입·JSON 표현과 URL 전달 형식. 화면용 예시 ID를 PK로 사용하지 않음 |
| 제목·담당자 표시명·업무 상태 | 실제 응답 필드명, 담당자 식별자와 표시명의 구분, 누락·NULL 허용 여부 |
| 시작일·마감일: `DateOnly` | 날짜/시각 구분, 전송 형식·NULL·시간대, 마감일이 현재 적용 마감일인지 여부 |
| `TaskDetail`: 요약 정보와 상세 내용 | 상세 응답 구조, 필수 필드, 목록과 상세의 상태·담당자·날짜 기준 |
| 목록 결과: `IReadOnlyList<TaskSummary>` | 페이지 방식·기본 정렬·페이지 크기·전체 개수/다음 페이지 정보, 첫 페이지와 전체 목록의 의미 |

현재 조회 경계에는 사용자 ID·인증 토큰·페이지 메타를 임의로 넣지 않았습니다. 실제 API가 페이지를 사용하면 공통 응답에 맞춰 목록 모델과 화면 연결 방식을 함께 정하겠습니다. 임의로 처음 몇 건만 조회하고 전체 결과라고 표시하지 않겠습니다.

업무 첨부파일·제출본·제출 차수·승인/반려 이력은 3번 담당과 연결할 항목입니다. 이번 목록·상세 계약 확인에서 2번이 별도 파일·결과물 API나 테이블을 만들지 않습니다.

## 4. HTTP·오류·DB·날짜 규약

| 번호 | 확인할 내용 | 부탁드리는 답변·자료 |
|---|---|---|
| B1 | 공통 HTTP 호출 수명과 설정 | ApiClient 생성·재사용·주입 방법, 기본 주소 설정 위치, 취소·시간 초과·통신 실패 처리, 인증 갱신/로그아웃과 재시도 책임 |
| B2 | 성공·오류 응답 | 사용 중인 응답 구조와 실제 JSON 예시, 오류 식별 필드, 인증 누락·만료·권한 거부·미존재·서버 오류·잘못된 응답의 구분 |
| B3 | 접근 거부와 미존재 | 현재 401/403/404 등의 정책, 인증 만료의 화면 전달 방식, 권한 없는 상세를 미존재로 응답하는지 여부 |
| B4 | 공통 DB 연결·스키마 관리 | 서버 DB 연결 계층·설정 템플릿·변경 절차, 사용자 테이블/PK와 FK 타입, 스키마 변경 담당, 업무 API가 재사용할 트랜잭션·공통 이력 규약 |
| B5 | 날짜·시간 기준 | 시작일·마감일과 기록 시각의 저장/전송 타입·형식, 기준 시간대, 마감 당일·시각의 해석 중 확정된 범위 |

현재 `TaskQueryFailure`의 미연결·인증 만료·권한 없음·미존재·서버 오류는 **UI 의미 분류**입니다. 특정 HTTP 숫자나 서버 오류 코드를 확정한 것이 아니므로, 실제 공통 응답에서 어떤 값으로 매핑해야 하는지 부탁드립니다. UI는 내부 예외 원문을 사용자 안내로 그대로 표시하지 않습니다.

DB에는 문서의 제안 테이블이나 DDL을 먼저 생성하지 않겠습니다. 실제 사용자 PK·연결 계층·스키마 변경 절차를 받은 뒤 2번 업무 데이터 구조를 맞추겠습니다. 클라이언트는 합의한 공통 HTTP 경로로 연결합니다.

## 5. 확정 규칙과 1번·3번 공동 합의 항목

다음 업무 원칙은 이미 확정된 기준입니다.

- 업무 상태는 **진행전 / 진행중 / 제출완료 / 승인완료 / 반려완료** 5개입니다. 배정·수락·정식 제출·검토 판단의 기본 전환을 따릅니다.
- 직원·관리자의 모든 정식 제출·재제출은 권한 있는 검토자의 승인 또는 반려를 거칩니다. 승인완료만 최종 완료입니다.
- 관리자도 본인 업무를 수락·제출하며, 본인 제출본은 상위 검토자가 판단합니다. 자기 승인·반려는 허용하지 않습니다.
- **마감 경과에 따른 자동 결과 제출은 제외**합니다.

아래는 1번 단독으로 새 업무 정책을 확정해 달라는 요청이 아니라, 3번과 함께 확인할 연결 사항입니다.

| 공동 확인 항목 | 필요한 합의 |
|---|---|
| 단일 업무 상태 | 실제 저장/응답 코드와 초기값, 행동별 API·트랜잭션 연결 |
| 상위 검토자 | 관리자 본인 제출본의 검토자 계정·조회·판단 권한 매핑 |
| 반려 후 재작업 | 진행중 복귀 시점과 재제출 연결 규격 |
| 자동 검토 요청 | 도입 여부·생성 조건·시점·중복 기준. 결과 제출 기록 생성과 구분 |
| 검토·연장·기한 후 제출 | 별도 검토 요청 의미, 연장 조건, 마감 후 직접 제출 조건 |

이번 요청의 우선 범위는 **목록·상세 읽기 연결**입니다. 제출·재제출·제출 차수 표시·승인/반려 기능 구현은 3번 범위로 유지합니다.

## 6. 실제 연동 검증에 필요한 준비

공통 규약을 받은 뒤 실제 서비스 연결과 다음 검증을 진행하려고 합니다. 사용할 테스트 계정·업무 데이터의 준비 여부와 전달 방법도 알려주세요.

- 직원 본인 배정 업무, 같은 역할의 다른 직원 업무와 빈 목록 사례.
- 관리자 본인 업무, 허용된 관리 업무와 관리 범위 밖 업무.
- 타인/범위 밖 ID로 상세를 직접 요청했을 때 서버가 거부하는 사례.
- 인증 누락·만료, 서버 중단·오류, 상세 미존재와 전체·5개 상태 필터 사례.
- 실제 DB 조회 결과와 화면의 담당자·상태·현재 마감일 일치 확인.

현재 테스트 대역의 Own/Managed 구분과 오류 표시 검증은 실제 인증·서버 권한 검증을 대신하지 않습니다.

## 7. 회신 양식

기존 문서·코드 링크가 있다면 해당 링크와 아래 요약만 주셔도 됩니다. 아직 없는 항목은 현재 상태와 담당/확인 시점만 부탁드립니다.

```text
회신 기준 브랜치/커밋:
A1 서버 위치·실행법·기본 주소: [상태] / 근거 링크:
A2 인증 사용자·공통 ApiClient 주입: [상태] / 근거 링크:
A3 목록·상세 요청/성공·실패 응답: [상태] / 근거 링크:
A4 본인·관리 범위와 상세 서버 권한: [상태] / 근거 링크:
B1~B3 공통 HTTP·오류 응답 정책: [상태] / 근거 링크:
B4~B5 DB·날짜·시간 기준: [상태] / 근거 링크:
1번·3번 공동 합의가 필요한 항목:
통합 검증용 계정·업무 데이터 준비 여부/전달 방법:
아직 없는 항목의 담당과 확인 시점:
```
