## 실제 확인한 검증

| 실제 실행 | 결과 | 범위/구분 |
|---|---|---|

| alpha·실제 로컬 Release 빌드 | 각각 경고0/오류0 | dotnet build RemoteWork.sln -c Release --no-restore |

서버 검사는 개발 의존성이 설치된 기존 Python 가상환경에서 `python -m pytest -q`로 실행했다. DDL 단독은 `tests/test_task_migration_draft.py`를 지정했다. 테스트 가드 없는 오프라인 실행과 두 가드를 켠 전용 MySQL 실행을 구분했다. 전체 MySQL 수치에 DDL23개가 포함되므로 중복 합산하지 않는다. 마지막 오류 출력 보호 보완은 오프라인/부정 설정 검사로 재확인했으며 전체61개를 다시 실행했다고 표시하지 않는다.

- 새 loopback MySQL8.2.0/REPEATABLE-READ, attempt 전용 datadir·임의 포트만 사용했다. 공유 MySQL/서버를 시작·정지·초기화하지 않았다.
- 테스트 가드 두 개(MYSQL_MIGRATION_TEST_URL, REMOTEWORK_RUN_TASK_MIGRATION_DRAFT_TESTS=1)를 명시해야 한다. 잘못된 대상/불완전 설정은 연결 전 거절한다. 일반 DATABASE_URL·실제 .env를 연결 원천으로 사용하지 않는다.
- 공통7개 테이블만 먼저 생성하고 사용자·인증 접속·grant·로그인 실패·감사 이력·버전1을 넣었다. 업무 ORM create_all 대신 실제 SQL을 순서대로 실행했다.
- 생성 결과의 signed 타입·길이·NULL·PK/FK/CHECK·인덱스·InnoDB·utf8mb4를 검사했다. 공통 행 전후 동일·비활성 사용자/이력·버전1 보존을 확인했다.
- 잘못된 사용자/업무 FK·상태·역전 날짜·0차수·0버전·필수값 생략 거절과 cascade 없는 이력 보호를 확인했다.
- **Flask test client(in-process)**로 실제 raw DDL 위의 공통 Bearer 인증·본인/지정/비지정 관리자·관리자 본인 업무·과거 배정자·빈 목록·5상태·직접 상세·비활성/미인증·쓰기405를 검증했다. 별도 TCP/WinForms 실행과 구분한다.
- 재실행·기존 테이블 충돌 거절, 두 번째 생성에서 실패한 뒤 첫 테이블이 rollback으로 없어지지 않는 상태를 확인했다.
- DDL 전 공통 fixture를 실제 mysqldump로 백업→중간 충돌→새 소유 DB에 mysql 복원→행 일치→DDL 재적용을 확인했다. 기존 DB를 덮어쓰지 않았다. 임시 자격 파일·fixture dump는 제거하고 생성 소유권이 확인된 DB만 정리했다.

첫 전용 MySQL 실행은21통과/1실패였다. 상속 collation 표기와 ORM 타입 비교 차이로 발생한 **검사 코드 문제**를 수정했고 SQL/업무 모델은 변경하지 않았다. 문자셋 표기 정규화가 상태 문자열까지 지울 수 있다는 독립 검토 지적도 실제 prefix만 처리하도록 수정하고 회귀를 추가했다. 위 결과는 수정 후 새 attempt 환경에서 실행한 결과이며 이전 실패를 통과 수치에 섞지 않았다.
