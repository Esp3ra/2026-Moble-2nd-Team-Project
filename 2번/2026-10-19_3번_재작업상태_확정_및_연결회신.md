## W3-01/03 — 사용자 확정: 재작업 시작을 거친 재제출

```text
진행전 → 본인 수락 → 진행중 → 최초 제출 성공 → 제출완료
제출완료 → 관리자 승인 → 승인완료
제출완료 → 관리자 반려 → 반려완료
반려완료 → 본인이 ‘재작업 시작’ → 진행중 → 재제출 성공 → 제출완료
```

| 현재 상태 | 행동 | 성공 후 상태 | 제출 회차 |
|---|---|---|---|
| 진행전 (`not_started`) | 본인 업무 수락 | 진행중 (`in_progress`) | 생성하지 않음 |
| 진행중 (`in_progress`) | 기존 성공 제출이 없는 업무의 최초 제출 | 제출완료 (`submitted`) | 최초 성공 시 1차 |
| 제출완료 (`submitted`) | 권한 있는 검토자의 반려 | 반려완료 (`returned`) | 증가하지 않음 |
| 반려완료 (`returned`) | 현재 배정 당사자의 명시적 재작업 시작 | 진행중 (`in_progress`) | 증가하지 않음 |
| 진행중 (`in_progress`) | 반려 후 재작업한 결과의 재제출 | 제출완료 (`submitted`) | 재제출 저장 성공 시에만 다음 차수 |
| 제출완료 (`submitted`) | 권한 있는 검토자의 승인 | 승인완료 (`approved`) | 증가하지 않음 |

- 반려 직후 자동으로 진행중으로 바꾸지 않습니다. 사용자가 재작업 시작을 선택하기 전까지 반려완료입니다. 창을 열거나 내용을 편집하는 것만으로 상태를 바꾸지 않습니다.
- 반려완료 상태에서 재작업 시작을 건너뛰어 바로 재제출하는 기존 3번 로컬 조건은 이번 확정 정책과 다릅니다. 실제 연결에서는 재작업 시작 성공 후 진행중에서 재제출합니다.
- 최초 제출과 재제출 모두 제출 전 상태가 진행중입니다. **진행중이라는 값만으로 최초 제출로 판단하지 않고, 서버의 기존 성공 제출·반려 기록으로 최초/재제출을 구분합니다.** 화면에서 회차를 직접 선택하지 않습니다.
- 재작업 시작은 기존 업무의 최초 수락이나 새로운 담당자 배정과 구분합니다. 재작업을 이유로 최초 수락 기록·배정 차수·이전 제출/판단을 초기화하거나 덮어쓰지 않는 방향으로 연결합니다. 해당 저장 필드·버전 처리는 1번과 검토합니다.
- 재작업 시작 취소·실패는 반려완료를, 재제출 저장 실패는 진행중을 유지합니다. 통신 응답을 받지 못한 경우에는 실패로 단정해 되돌리지 않고 공통 결과 조회와 업무 재조회로 실제 저장 여부를 확인합니다.
- 새 상태를 추가하지 않습니다. 업무 상태는 기존 5개이며 승인완료만 최종 완료입니다. 직원과 관리자 본인의 업무에 같은 흐름을 적용하고, 관리자 본인 제출도 권한 있는 상위 검토자의 판단을 받습니다.

## 추가 확정: 신규 업무 관리자 지정

사용자가 확정한 신규 등록 기준은 **업무 관리자 최소 1명, 등록자 자동 포함, 최초 등록 시 등록자 제외 불가**입니다. 추가 관리자는 기존 활성 관리자 후보에서 선택합니다.

업무 관리자와 제출 검토자는 별개입니다. 이 결정은 기존 업무의 관리자 교체/제외 권한이나 관리자 본인의 상위 검토자를 확정한 것이 아닙니다.

현재 로컬 선택 준비 화면에 등록자 필수 포함·해제 차단을 반영했으나 아직 코드 커밋/원격 게시 및 실제 생성 API·DB 저장은 완료하지 않았습니다. 이 LOG 게시에 해당 코드를 섞어 올리지 않습니다.

## W3-02 — 2번 수용: 단일 저장과 성공 후 재조회

3번의 제출 서비스가 제출본·회차·제출완료 상태를, 판단 서비스가 판단 기록·승인완료/반려완료 상태를 같은 DB 처리에서 저장하는 방향을 2번은 수용합니다. 관련 성공 이력·공통 감사·중복 요청 결과도 같은 세션으로 연결하며, 세부 잠금·버전·기록 필드는 1번 검토가 필요합니다. 파일 전송까지 DB와 자동으로 함께 되돌아가는 것으로 가정하지 않습니다.

2번 화면에서 제출 성공 후 별도 상태 변경 요청을 보내지 않습니다. 3번의 서버 저장 성공 또는 공통 결과 조회의 성공 확인 후, 현재 로그인 세션과 화면 수명을 확인하고 UI 스레드에서 `TasksControl.RefreshAsync()`로 목록·상세를 재조회하는 방향으로 연결합니다. 통지 전달 위치와 화면 생성/종료 시점은 실제 폼 연결 전에 맞춥니다.

현재 범위·상태 필터를 유지합니다. 예를 들어 진행중 필터에서 제출한 업무는 제출완료가 되어 목록에서 빠질 수 있으며 정상입니다. 창을 닫았다는 사실만으로 저장 성공을 추정하거나 화면 상태를 먼저 바꾸지 않습니다.

## 함께 확인할 검증과 이번 게시 범위

합의 후 연결 검증:

1. 진행전 → 수락 → 진행중 → 최초 제출 1차 → 제출완료 → 반려완료.
2. 반려완료에서 재제출 직접 호출은 거절. 현재 담당자의 재작업 시작 성공 시 진행중이며 회차는 그대로.
3. 진행중에서 재제출 성공 시 다음 차수와 제출완료를 함께 저장. 다시 필수 검토를 거쳐 승인완료/반려완료.
4. 직원과 관리자 본인의 같은 흐름, 타인/옛 배정/권한 회수/자기 판단 거절.
