## 최신 — 잔여 순차 정리와 서버 내부 전이 계획, 2026-10-19

팀장 요청에 따라2번 잔여를 개별 작업으로 흩뜨리지 않고 **조회/등록 유지 → 수락·재작업 → 수정/재배정 → 연장 → 이벤트 접점 → 공유 통합** 순서로 대조했습니다. 최신 원본 alpha `8c297a0`·LOG `22eea1a`에서 새1·3번 행동 계약 회신은 없었습니다. 업무 수정·담당자 변경은 팀장 직접 답변인 **3번과 협의 후 결정**으로 유지합니다. 관련 미확정 정책/API를 독자 구현하지 않습니다.

이번 변경 파일은2번의 `features/tasks/start_transition.py`·전용 Python 단위 검사, 수락 폼 안내1곳, Tasks/Queries README, alpha README와 TASK_START/INPUT/WRITE_PREPARATION 문서, tasks 패키지/모델/등록의 낡은 설명입니다.1번 공통·3번 Results/제출/파일/이력과4·5번 파일은 변경하지 않았고 PR도 이 채팅에서 처리하지 않았습니다.

- 새 순수 함수는 인증/현재 본인 권한·잠금 후 읽었다는 전제의 불변 snapshot과 명시UTC 시각을 받습니다. expected 배정→업무 버전 충돌·대상 상태·KST 기간을 구분하고, 성공할 때만 진행중/업무버전+1/배정유지·최초 수락 시각 또는 재작업의 기존 수락 시각 보존 계획을 반환합니다. 자동 시계·DB·네트워크·ORM/action/route 등록을 하지 않습니다.
- 타입/범위·모순된 수락 기록은 내부 입력 오류로 거절하며 자동 복구하지 않습니다. 이 검사는 외부 HTTP 오류/상태 정책 확정이 아닙니다. UTC-aware 계획과 DB의 naive UTC를 잇는 어댑터·실제 권한/잠금·원자 저장은 아직 없습니다. READY를 저장 완료로 표시하지 않습니다.
- 수락 화면에 남은 ‘마감 조건 합의 필요’ 안내를 확정 KST 날짜와 미연결 실행 규약으로 구분했습니다. 수정 전에 사용자에게 차이를 알렸습니다. 상세 날짜는 이전 조회 시점이며 현재 실행 자격을 보증하지 않는다는 안내를 유지합니다. 신규 등록1/1·서버 연결은1번 기술 수용됐다는 점도 문서/설명에 맞췄습니다.

## 이어서 구현할 순서

1. 신규 등록 초기1/1·공통 트랜잭션/결과·새 DB DDL의1번 기술 수용은 수신했습니다. 남은 공통 HTTP 성공상태 미노출·공유 migration/환경 질문을 C01로 확인합니다. 실제 POST·결과 확인·성공 재조회는 위 이번 회차에서 연결했습니다.
2. 읽기 확인과 확정된 KST 날짜 판정은 유지합니다. 1번에 제안한 경로/action·요청/최소 결과·정확한 오류·이상 최초 수락 기록 처리, 3번의 보존/성공 재조회 접점을 맞춘 뒤 실제2번 수락/재작업 상태 전환을 구현합니다. 날짜·버전 증가를 미합의로 되돌리지 않고 task.accepted 공통 도구도 실제 수락 API로 표시하지 않습니다.
3. 마감·연장 정책 합의 후 요청/판단을 연결합니다. 연장 판단자를 기본 admin 전체로 임의 개방하지 않습니다.
4. 3번의 제출·판단 성공 통지를 받아 현재 로그인/필터/화면 수명을 지키며 조회를 갱신합니다. 검토·파일은 3번 담당입니다.
5. 정식 migration·공유 서버·두 PC·업무 수동 GUI는 별도 적용과 검증으로 남깁니다.
