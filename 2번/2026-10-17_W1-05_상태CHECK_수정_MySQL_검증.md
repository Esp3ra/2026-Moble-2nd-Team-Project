## 요청과 DB 기준

1번 W1-05는 문자열 collation에 따라 대문자까지 허용할 수 있는 상태 CHECK를 정확한 다섯 소문자 코드만 허용하도록 수정해 달라고 요청했습니다. 이미 수용된 읽기 코드의 표현을 강제하는 수정이며 상태 전환·3번 제출 정책을 결정하지 않습니다.

사용자 추가 결정에 따라 **실제 구현·DB 규약·지속 관리·주요 검증은 MySQL 기준**입니다. SQLite는 DEMO용 임시 구성으로 DEMO 종료 후 삭제 예정입니다. 아래 이미 끝낸 SQLite 검사는 데모 참고 이력으로만 보존하며 별도 SQLite 기능/스키마 관리 대상으로 확대하지 않습니다.

## 수정 내용과 변경 파일

ORM과 실제002 SQL에 동일한 `기존 IN (...) AND HEX(...) IN (...)` CHECK를 적용했습니다. MySQL이 대소문자·뒤 공백을 같게 비교해도 다섯 소문자 코드와 정확히 같은 값만 허용합니다. 잘못된 값을 자동 소문자화하거나 잘라내지 않으며 DB/열 collation도 변경하지 않습니다.

중간 HEX 단독 안은 SQLite에서 문자열과 같은 바이트의 BLOB를 허용하는 경우가 있었습니다. 독립 읽기 검토의 지적을 실제 INSERT/UPDATE로 재현한 뒤 기존 IN 조건도 함께 유지했습니다. 최종 회귀는 문자열 변형과 이 타입 경계의 거절·rollback을 확인했습니다. 이 데모 방어를 추가 제품 기능으로 세지 않습니다.

## 실행하지 않은 검증과 남은 합의

전체 서버 회귀·실제 C#→MySQL·공유/운영 DB·정식 migration/version 지원·공유 복구·두PC·웹·장치·수동 전체GUI·제품 쓰기/제출/승인 통합은 이번 수정에서 실행하지 않았습니다. 전용 dump→새DB 복원은 공유 DB를 덮어쓰는 검증이 아닙니다.

1. 1번은 이 W1-05 수정/검증안과 정식002·버전 지원을 검토합니다. 직원 쓰기 재인증·멱등 저장/전송·후보 조회 등의 공통 지원은 여전히 미구현입니다.
2. 3번 W3의 상태/제출 원자성·배정/제출 FK·수정 허용·마감 의미 회신은 필요합니다. 확정 후 등록/배정 → 수락 → 마감 신청/판단 순서로 연결합니다.
3. 제출/재제출·차수·승인/반려·파일·이력은3번 범위입니다. 자동 결과 제출은 제외하고 자동 검토 요청·미확정 전환은 질문으로 유지합니다.
