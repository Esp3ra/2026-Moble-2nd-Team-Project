## 이번 범위와 결과

사용자는 1번·3번의 쓰기 규약 답변이 아직 없다고 확인했습니다. 기존 GET 계약·화면 배치·Designer를 유지하며 로컬 형식 검사를 통과한 값을 불변 record로 보관할 수 있게 했습니다. 실제 서버 등록·수정·수락·연장 접수·마감 변경을 연결하지 않았습니다.

- TaskEditForm.CheckedInput: 원본 업무 ID(새 등록은 null), 제목·내용 원문, 시작일·마감일 DateOnly를 TaskBasicInputDraft에 보관합니다.
- DeadlineExtensionForm.CheckedInput: 원본 업무 ID·현재 마감일, 희망 마감일 DateOnly·사유 원문을 DeadlineExtensionInputDraft에 보관합니다.
- 확인 전·검사 실패 후에는 null이며 입력 변경 시 무효화합니다. 이미 꺼낸 record는 변하지 않고, 다시 확인하기 전에는 새 record를 만들지 않습니다.
- 값 조회 시 현재 입력·원본 문맥을 다시 대조합니다. DateTimePicker.Checked를 코드로 변경해 이벤트가 발생하지 않아도 이전 확인값을 반환하지 않습니다.

이 record는 **서버 요청 DTO·배정/버전 규약·저장 권한이 아닙니다**. 제목·내용·사유의 공백을 임의로 잘라내거나 표시명에서 사용자 ID를 추측하지 않습니다. 연장 가능 날짜/상태를 새로 결정하지 않으며 입력 확인 후 창을 성공 결과로 닫지 않습니다.

처음 추가한 날짜 체크 해제 검사는 실패했습니다. 코드로 Checked=false를 설정할 때 ValueChanged가 발생하지 않는 경우를 재현했고, 두 폼의 getter에서 현재 값과 재대조하도록 수정한 뒤 최종12/140 전체를 통과했습니다. 최초 실패를 통과 수치에 합산하지 않습니다.

실제 HTTP 검증은 새 임시 DB·합성 계정·임의 loopback 포트만 사용합니다. 원본 업무 ID/DATE가 모달에 전달되는지와 입력 확인 후 DialogResult.OK로 접수/저장 처리되지 않는지를 검사했습니다. 업무/배정/관리자 행과 감사 이력의 보존도 실행기가 대조했습니다. 권한 회수·재배정은 검사 fixture 안에서만 수행했고 제품 쓰기 API를 만들지 않았습니다. 성공 후 소유 서버/임시 DB는 정리됐습니다.
