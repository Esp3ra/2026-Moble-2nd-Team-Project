기존 TaskEditForm의 등록/수정 입력 확인은 공백 제목·현재 모델의200문자 범위·필수 날짜·시작일보다 이른 마감일을 로컬에서 검사합니다. 문자 수는 UTF-16 코드 단위가 아닌 Unicode 코드 포인트로 세고 내용의 빈 문자열을 임의로 금지하지 않습니다. 최초 날짜는 미선택이며 예전 고정 날짜를 입력값으로 간주하지 않습니다. 입력 확인 후에도 창과 값을 유지하고 입력/선택 변경은 이전 확인값을 무효화합니다. 신규 등록은 후보 ID·필수 등록자를 함께 확인한 뒤 별도 등록 버튼을 사용합니다. 기존 수정 미리보기는 로컬 준비이며, 실제 일반 수정·관계 변경은 별도 TaskManagementForm에서 확정 A/B/C 정책과 현재 문맥을 검사합니다.

기존 DeadlineExtensionForm도 확정 정책에 따라 진행중·반려완료에서만 로컬 입력을 확인합니다. 희망일을 명시적으로 선택하고 현재 마감일보다 뒤이면서 현재 KST 날짜 이상인지, 사유가 공백이 아닌지 검사합니다. 이 확인은 현재 담당자·다른 판단 관리자·대기 신청 중복이나 서버 접수 성공을 보장하지 않습니다. 연결된 TaskLifecycleForm/API의 사유·직렬화 크기·권한·날짜 재검사와 실제 변경503 조건은 [lifecycle 계약](TASK_LIFECYCLE.md)을 따릅니다.

수락·재작업 대상 확인 창은 실제 로그인 서비스가 전달되면 최신 정보 다시 조회와 대상 확인을 제공한다. 내 업무의 진행전은 수락, 반려완료는 재작업 시작 대상으로 구분하고 현재 담당자 ID가 로그인 사용자와 같은지 확인한다. 관리자 본인 업무도 동일하며 관리 업무 조회 권한만으로 대상 확인을 허용하지 않는다. 상세와 별도 조회의 상태가 달라졌거나 본인 배정이 아니면 확인을 막고 닫은 뒤 목록·상세 재조회를 요청한다. 기본/상세만 받는 기존 생성자는 닫기 전용 화면을 유지한다. 어느 생성자도 상태 변경·마감 판정·수락 가능 여부를 서버 저장 권한처럼 확정하지 않는다.

## 확인된 로컬 입력값

`Preparation/TaskInputDrafts.cs`의 불변 record는 입력 확인 성공 시점의 값을 보관합니다. 이 record 자체는 서버 요청 DTO·DB 모델·배정/버전 계약이 아니며 직접 HTTP 직렬화하지 않습니다. 신규 등록은 현재 입력과 PreparedSelection의 ID를 다시 대조해 별도 불변 TaskCreationRequest를 만듭니다. 시작·관리 변경·lifecycle 실행은 각각의 별도 요청 모델과 workflow를 사용합니다.

| 폼의 CheckedInput | 보관하는 값 |
|---|---|
| TaskEditForm | TaskBasicInputDraft: 원본 TaskId(새 등록은 null), 제목·내용 원문, 시작일·마감일 DateOnly |
| DeadlineExtensionForm | DeadlineExtensionInputDraft: 원본 TaskId·현재 마감일, 희망 마감일 DateOnly·사유 원문 |

수락·재작업의 TaskAcceptanceForm.CheckedTarget은 위 CheckedInput과 별개입니다. TaskStartTarget에 확인 종류·업무 ID·로그인/담당자 ID·업무 버전·배정 차수·상태·UTC 변경 시각을 불변으로 보관합니다. 최초 표시만으로 확인값을 만들지 않고 현재 조회 조건이 일치한 뒤 사용자가 대상 확인을 눌러야 합니다. 재조회·실패·로그인 만료/권한 없음·접속 교체·창 닫기/Dispose는 이전 확인값을 지웁니다. 요청 세대·취소 검사로 늦은 응답을 배제하고 읽는 시점에도 현재 접속을 확인합니다. **대상 확인 단계**는 업무 쓰기·키 발급·결과 조회를 호출하지 않습니다. 연결 생성자의 별도 수락/재작업 실행에서는 CheckedTarget을 다시 대조해 TaskStartRequest를 만들고 [시작 workflow](TASK_START_PREPARATION.md)를 사용합니다. 기존 읽기 전용 생성자는 이 실행을 연결하지 않습니다.

확인 전·검사 실패 후에는 null이다. 입력 변경 시 이전 확인값을 무효화하고, 값을 읽을 때도 현재 입력·원본 문맥과 대조한다. DateTimePicker의 Checked를 코드로 바꿔 변경 이벤트가 발생하지 않는 경우에도 이전 확인값을 반환하지 않는다. 다시 값을 확인하려면 입력 확인을 명시적으로 눌러야 한다. 이전 record를 이미 읽은 호출자의 값은 불변이므로 변하지 않으며 저장 권한이나 최신 서버 상태를 보장하지 않는다. 제목·내용·사유의 공백을 임의로 잘라내지 않는다.

입력 확인 후에도 모달을 성공 결과로 닫거나 업무 상태를 바꾸지 않는다. 신규 등록의 별도 요청은 현재 공통 후보 ID와 서버 발급 키를 사용하고, 생성 성공 또는 같은 키의 저장 결과 확인 후에만 성공 처리한다. 결과가 불확실하면 같은 로그인 세션의 창·메뉴 재진입에서 요청을 이어가며 명시적 결과 조회 후에만 같은 요청 재전송을 허용한다. POST 410과 결과 조회 410의 구분·앱 종료/접속 변경 시 정리는 [등록 복구 규칙](TASK_CREATION.md#winforms-등록과-결과-확인)을 따른다. 최초 배정/업무 버전1/1은 서버의 2번 개발 계약이며 입력 record에 추측한 값을 추가하지 않는다. 수정·수락·연장 계약은 이 신규 생성 규칙으로 대신 확정하지 않는다.

### 입력 확인값의 로그인·창 수명

기존 DeadlineExtensionForm의 연결 생성자는 캡처 ITaskPreparationService의 **접속 수명만** 빌리며 업무 조회·키·결과·쓰기를 추가 호출하지 않습니다. 기본/기존 상세 미리보기 생성자에는 서비스를 자동 연결하지 않습니다. 현재 실제 HTTP TasksControl은 lifecycle source가 있으면 별도 TaskLifecycleForm으로 진입해 최신 문맥을 GET 조회하고 write_enabled에 따라 실행을 제어합니다. 두 폼의 역할을 혼동하지 않습니다.

등록/수정·연장 준비의 CheckedInput은 읽는 즉시 접속·취소·종료 상태를 검사하므로 UI 취소 콜백을 기다리는 동안에도 이전 로그인 확인값을 반환하지 않습니다. 등록은 별도 creationWorkflow 수명도 검사합니다. UI 콜백에서는 이전 제목/날짜/사유와 선택·확인값을 지우고 확인 버튼을 막습니다. 닫기/Dispose에서는 확인값과 빌린 접속 토큰 구독을 해제하며 공유 로그인 서비스는 Dispose하지 않습니다. 한 번 만료된 창을 새 로그인으로 재사용하지 않습니다.

이 접속 수명 보완 자체가 연장 저장은 아닙니다. 기존 로컬 준비창의 확정 상태·날짜 입력 검사와 별도 lifecycle 서버의 최종 권한/날짜·저장 검사를 구분합니다. 호출자가 이미 읽어간 불변 record는 바꾸지 않으며 서버 저장 권한으로 사용할 수 없습니다. [전용 회귀](../Tests/TaskInputSession.Tests/README.md)의 기존 누락 재현과 실제 WinForms/명시적 로그인 대역 검증은 당시 범위로 보존합니다.

## 선택 문맥과 날짜 보존

TasksControl은 현재 행의 상세 조회가 성공하고 ID가 일치해야 새 입력/대상 진입을 허용합니다. 취소된 업무의 새 쓰기는 막고, 수락·재작업은 내 업무의 진행전/반려완료, 관리 변경은 현재 관리 범위의 허용 상태로 구분합니다. 선택/범위/상태 변경·새 조회·로딩·상세 실패·인증 실패·취소·빈 목록·종료에서는 이전 상세 캐시를 지웁니다. 늦은 응답은 새 선택의 문맥이 될 수 없습니다. 입력 표시만으로 원래 업무를 바꾸지 않으며, 보관된 요청의 명시적 결과 복구는 선택 행 없이 별도 진입할 수 있습니다.

수락 창의 제목·담당자 표시명·날짜는 상세 조회 당시 값이고 현재 담당자·상태·버전은 별도 write-context의 응답이다. 두 시점을 하나의 스냅샷으로 간주하지 않는다. 상태 불일치에서는 확인값을 만들지 않고 재조회를 안내하며 날짜를 현재 실행 가능 여부로 해석하지 않는다. 상세 동작·오류·미합의 목록은 [수락·재작업 읽기 확인](TASK_START_PREPARATION.md)을 따른다.

기존 화면 요약 DTO는 담당자 표시명과 선택적 취소 표시를 사용하고, 버전·배정 차수·후보 ID/관리자 관계는 별도 W1 후보·write-context로 조회합니다. 표시명으로 ID를 추측하거나 공통 관리자용 GET /users를 배정 허용 목록으로 전용하지 않습니다. 기존 필수 조회 필드는 유지하고 취소 표시에는 호환 기본값을 사용합니다. 첨부와 검토·제출 기능은3번 계약에 맡깁니다.

DateOnly의 범위는 WinForms DateTimePicker보다 넓다. 조회 날짜가 Picker 범위 밖이면 원본 날짜를 표시하고 해당 입력과 입력 확인을 비활성화한다. 다른 날짜로 자동 보정하지 않는다. 날짜를 UTC 자정으로 변환하거나 임의의 마감 시각을 만들지 않는다.
