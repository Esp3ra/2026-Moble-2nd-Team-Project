# 2번 업무 입력 확인과 등록·수락·마감 연결 범위

2026-10-19 현재: 후보/문맥·등록자 필수 관리자 선택과 불변 입력 확인을 유지하며, 신규 등록만 [개발 API·WinForms](TASK_CREATION.md)에 연결했습니다. **입력 확인은 저장하지 않으며**, 확인된 입력·선택으로 별도 등록 버튼을 눌러야 POST합니다. [수락·재작업 대상 확인](TASK_START_PREPARATION.md)은 기존 write-context GET으로 현재 본인 배정·상태·버전을 읽도록 연결했습니다. 수정·수락·재작업·마감 연장의 실제 저장은 미연결입니다. 현재 공통 지원은 [WRITE_SUPPORT](WRITE_SUPPORT.md)를 따릅니다.

## 2026-10-17 W1 연결 후속

[후보·쓰기 준비 연결](TASK_WRITE_PREPARATION.md)을 추가했습니다. 실제 로그인된 업무 화면에서는 등록/수정 창의 별도 버튼으로 담당자·업무 관리자 후보와 현재 쓰기 문맥을 조회·선택할 수 있습니다. 기본/미리보기 생성자는 미연결 상태를 유지하며, 기존 CheckedInput은 변경하지 않고 선택값은 별도 PreparedSelection에 보관합니다. 당시에는 실제 업무 저장·수락·마감 변경을 연결하지 않았습니다. 10월 19일 신규 등록만 별도 계약으로 연결했고, 아래 표는 그 이후 현재 범위입니다.

초기 입력/대상 확인·불변 확인값 구현: 2026-10-17. 신규 등록 연결 최신화: 2026-10-19.

1번이 수용한 [기존 조회 계약](TASK_QUERIES.md)을 유지하며, 조회 성공한 업무를 수정 입력 준비, 수락 대상 확인, 마감 연장 입력 준비에 연결한다. 신규 등록은 빈 입력에서 시작한다. 입력 확인 자체는 등록·수정·수락·접수나 실제 마감 변경이 아니다. 새 업무의 명시적 등록 외에 기존 업무 상태를 바꾸는 HTTP 쓰기는 연결하지 않는다.

## 동작

| 화면 | 현재 가능한 동작 | 남은 연결·합의 |
|---|---|---|
| 업무 등록 | 제목·내용·날짜와 후보 ID 선택·입력 확인 후 명시적 POST. 성공 확인 후 목록/상세 재조회, 불확실 결과의 명시 확인·같은 요청 재전송 | 초기값·서버/DB 접점의1번 기술 수용 수신. 정식 migration·공유 서버 배포는 별도 |
| 업무 수정 준비 | 성공 상세의 제목·내용·담당자 표시명·날짜, 별도 후보·쓰기 문맥 조회, 로컬 기본 형식 확인 | 수정/재배정 허용 조건·기존 배정/버전 재검사·PATCH |
| 업무 수락·재작업 대상 확인 | 상세 당시 정보와 별도 write-context의 현재 담당자·상태·버전을 표시. 현재 본인의 진행전/반려완료 대상만 별도 CheckedTarget에 확인 | 성공 row_version+1·배정 차수 유지 등1번 기술 수신. KST 시작일~마감일 내만 허용하는 날짜는 팀장 확정. API/action·오류 최종 대조와 실제 진행중 저장은 별도 |
| 마감 연장 입력 준비 | 실제 대상·현재 마감일 표시, 희망일·사유 입력 형식 확인 | 신청 가능한 상태·연장 가능한 날짜·신청/판단 API·실제 마감 변경 |

등록/수정은 공백 제목·현재 모델의200문자 범위·필수 날짜·시작일보다 이른 마감일을 로컬에서 검사한다. 문자 수는 UTF-16 코드 단위가 아닌 Unicode 코드 포인트로 센다. 내용의 빈 문자열을 임의로 금지하지 않는다. 최초 날짜는 미선택이며 예전 고정 날짜를 입력값으로 간주하지 않는다. 입력 확인 후에도 창과 값은 유지한다. 신규 등록은 후보 ID·필수 등록자를 함께 확인해야 별도 등록 버튼을 사용할 수 있으며, 수정은 계속 로컬 준비로 표시한다. 입력이나 선택이 바뀌면 이전 확인값을 무효화한다.

연장은 희망일을 명시적으로 선택하고 사유가 공백이 아닌지만 검사한다. 현재 마감일보다 늦어야 하는지, 어떤 상태에서 신청 가능한지, 사유 최대 길이 등 미합의 정책은 추가하지 않는다. 입력 형식 확인 성공은 연장 가능·접수 완료·마감 변경을 뜻하지 않는다.

수락·재작업 대상 확인 창은 실제 로그인 서비스가 전달되면 최신 정보 다시 조회와 대상 확인을 제공한다. 내 업무의 진행전은 수락, 반려완료는 재작업 시작 대상으로 구분하고 현재 담당자 ID가 로그인 사용자와 같은지 확인한다. 관리자 본인 업무도 동일하며 관리 업무 조회 권한만으로 대상 확인을 허용하지 않는다. 상세와 별도 조회의 상태가 달라졌거나 본인 배정이 아니면 확인을 막고 닫은 뒤 목록·상세 재조회를 요청한다. 기본/상세만 받는 기존 생성자는 닫기 전용 화면을 유지한다. 어느 생성자도 상태 변경·마감 판정·수락 가능 여부를 서버 저장 권한처럼 확정하지 않는다.

## 확인된 로컬 입력값

`Preparation/TaskInputDrafts.cs`의 불변 record는 입력 확인 성공 시점의 값을 보관한다. 이 record 자체는 서버 요청 DTO·DB 모델·배정/버전 계약이 아니며 직접 HTTP 직렬화하지 않는다. 신규 등록만 현재 입력과 PreparedSelection의 ID를 다시 대조해 별도 불변 TaskCreationRequest를 만든다.

| 폼의 CheckedInput | 보관하는 값 |
|---|---|
| TaskEditForm | TaskBasicInputDraft: 원본 TaskId(새 등록은 null), 제목·내용 원문, 시작일·마감일 DateOnly |
| DeadlineExtensionForm | DeadlineExtensionInputDraft: 원본 TaskId·현재 마감일, 희망 마감일 DateOnly·사유 원문 |

수락·재작업의 `TaskAcceptanceForm.CheckedTarget`은 위 CheckedInput과 별개다. `TaskStartTarget`에 확인 종류·업무 ID·로그인/담당자 ID·업무 버전·배정 차수·상태·UTC 변경 시각을 불변으로 보관하며 요청 DTO로 사용하지 않는다. 최초 표시만으로 확인값을 만들지 않고, 현재 조회 조건이 일치한 뒤 사용자가 대상 확인을 눌러야 한다. 재조회·실패·로그인 만료/권한 없음·접속 교체·창 닫기/Dispose는 이전 확인값을 지운다. 요청 세대·취소 검사로 늦은 응답을 배제하며, 읽는 시점에도 현재 접속을 확인한다. 업무 POST/PATCH·키 발급·결과 조회를 호출하지 않는다.

확인 전·검사 실패 후에는 null이다. 입력 변경 시 이전 확인값을 무효화하고, 값을 읽을 때도 현재 입력·원본 문맥과 대조한다. DateTimePicker의 Checked를 코드로 바꿔 변경 이벤트가 발생하지 않는 경우에도 이전 확인값을 반환하지 않는다. 다시 값을 확인하려면 입력 확인을 명시적으로 눌러야 한다. 이전 record를 이미 읽은 호출자의 값은 불변이므로 변하지 않으며 저장 권한이나 최신 서버 상태를 보장하지 않는다. 제목·내용·사유의 공백을 임의로 잘라내지 않는다.

입력 확인 후에도 모달을 성공 결과로 닫거나 업무 상태를 바꾸지 않는다. 신규 등록의 별도 요청은 현재 공통 후보 ID와 서버 발급 키를 사용하고, 생성 성공 또는 같은 키의 저장 결과 확인 후에만 성공 처리한다. 결과가 불확실하면 같은 로그인 세션의 창·메뉴 재진입에서 요청을 이어가며 명시적 결과 조회 후에만 같은 요청 재전송을 허용한다. POST 410과 결과 조회 410의 구분·앱 종료/접속 변경 시 정리는 [등록 복구 규칙](TASK_CREATION.md#winforms-등록과-결과-확인)을 따른다. 최초 배정/업무 버전1/1은 서버의 2번 개발 계약이며 입력 record에 추측한 값을 추가하지 않는다. 수정·수락·연장 계약은 이 신규 생성 규칙으로 대신 확정하지 않는다.

### 입력 확인값의 로그인·창 수명

실제 로그인한 TasksControl은 마감 연장 준비창에도 기존 캡처 ITaskPreparationService를 빌려줍니다. 연장창은 이 서비스의 접속 수명만 검사하며 업무 조회·키·결과·쓰기를 추가 호출하지 않습니다. 기본/기존 상세 미리보기 생성자에는 서비스를 자동 연결하지 않습니다.

등록/수정·연장 준비의 CheckedInput은 읽는 즉시 접속·취소·종료 상태를 검사하므로 UI 취소 콜백을 기다리는 동안에도 이전 로그인 확인값을 반환하지 않습니다. 등록은 별도 creationWorkflow 수명도 검사합니다. UI 콜백에서는 이전 제목/날짜/사유와 선택·확인값을 지우고 확인 버튼을 막습니다. 닫기/Dispose에서는 확인값과 빌린 접속 토큰 구독을 해제하며 공유 로그인 서비스는 Dispose하지 않습니다. 한 번 만료된 창을 새 로그인으로 재사용하지 않습니다.

이 변경은 날짜별 연장 자격이나 상태 쓰기를 구현하지 않습니다. 이전에 호출자가 이미 읽어간 불변 record는 바꾸지 않으며 서버 저장 권한으로 사용할 수 없습니다. [전용 회귀](../Tests/TaskInputSession.Tests/README.md)에서 기존 누락 재현과 수정 후 실제 WinForms/명시적 로그인 대역을 구분합니다.

## 선택 문맥과 날짜 보존

TasksControl은 현재 행의 상세 조회가 성공하고 ID가 일치할 때만 수정·수락·연장 대상 버튼을 활성화한다. 수락·재작업은 내 업무의 진행전/반려완료에 추가로 제한한다. 선택/범위/상태 변경·새 조회·로딩·상세 실패·인증 실패·취소·빈 목록·종료에서 이전 상세 캐시를 지운다. 늦게 도착한 응답은 새 선택의 준비 문맥이 될 수 없다. 모달 입력은 불변 TaskDetail을 복사해 표시하며 원래 업무를 수정하지 않는다.

수락 창의 제목·담당자 표시명·날짜는 상세 조회 당시 값이고 현재 담당자·상태·버전은 별도 write-context의 응답이다. 두 시점을 하나의 스냅샷으로 간주하지 않는다. 상태 불일치에서는 확인값을 만들지 않고 재조회를 안내하며 날짜를 현재 실행 가능 여부로 해석하지 않는다. 상세 동작·오류·미합의 목록은 [수락·재작업 읽기 확인](TASK_START_PREPARATION.md)을 따른다.

기존 화면 조회 DTO에는 담당자 ID·배정 차수·수정번호가 없다. 표시명으로 ID를 추측하거나 기존 GET DTO를 임의로 확장하지 않는다. 별도 W1 후보·write-context 계약으로 ID와 버전을 조회하며 공통 관리자용 GET /users를 배정 허용 목록으로 전용하지 않는다. 첨부와 검토·제출 기능은 3번 계약에 맡긴다.

DateOnly의 범위는 WinForms DateTimePicker보다 넓다. 조회 날짜가 Picker 범위 밖이면 원본 날짜를 표시하고 해당 입력과 입력 확인을 비활성화한다. 다른 날짜로 자동 보정하지 않는다. 날짜를 UTC 자정으로 변환하거나 임의의 마감 시각을 만들지 않는다.

[3번 W3 회신](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/LOG/3번/README.md)의 로컬 구현·제안을 수신했으며 상태별 수정·배정/제출 참조·검토자·제출/연장 날짜·실제 저장 접점은 공동 확인이 남아 있다. 업무 수정·담당자 변경은2026-10-19 팀장 답변에 따라3번과 협의 후 결정한다. [2번 수신·조회 연결 안내](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/LOG/2번/공통규약.md#r015)와 기존 W1/W3 번호로 이어서 확인한다.

신규 등록 연결 이후 수락/재작업의 읽기 확인부터 연결했다. 최신1번 W3 기술 회신에서 새 성공 mutation의 row_version+1·UTC updated_at·배정 차수 유지·잠금/재응답·같은 TX 기준을 수신했다. 2026-10-19 팀장은 수락·재작업 시작을 KST 시작일00:00~마감일이 끝날 때까지 허용하고 기간 밖은 허용하지 않는 기준을 확정했다. 3번 제출·연장 날짜는 별도다. 남은 것은 행동별 경로·요청/결과·오류, 재작업 별도 action과 이상 최초 수락 자료 처리의 최종 대조다. 재작업에서 최초 accepted_at·배정 번호·제출 회차/과거 자료 보존은 최신3번 회신에서도 수신했다. 공통 실제/요구 버전 비교 도구와 신규 등록 초기1/1의1번 기술 수용은 있으며 정식 DDL·전역 버전 변경·공유 적용은 별도다. 3번의 제출·차수·승인/반려·파일·이력은 2번이 대신 구현하지 않는다. 자동 결과 제출은 제외하고 자동 검토 요청은 합의 질문으로 유지한다.

## 검증

[TaskQueries.Tests](../Tests/TaskQueries.Tests/README.md)에서 실제 WinForms 메시지 루프로 입력 형식·미전송 표시·확인값 보존/무효화·선택 문맥 수명·대상별 실제 모달 연결을 검증한다. 기존 [조회용 격리 HTTP 실행기](../Tests/TaskQueries.Http.Tests/README.md)는 실제 조회 업무에서 준비 창을 열고 행 보존을 검사하며 쓰기를 수행하지 않는다. 신규 등록은 별도 [TaskCreation.Tests](../Tests/TaskCreation.Tests/README.md)에서 검증한다. 앞선 신규 등록 회차의 제어79개·실제 C# HTTP10개·독립 MySQL24개, 후보87개·조회171개 회귀는 각각의 실행 결과이며 이번 수락·재작업 읽기 검증으로 재사용하거나 합산하지 않는다.

새 [TaskStartPreparation.Tests](../Tests/TaskStartPreparation.Tests/README.md)는 수락·재작업의 대상 판정·실제 WinForms/통제 HTTP·접속/응답 수명과 별도 명시적 MySQL/HTTP 읽기를 검사한다. 이번 통제149개·실제 C# HTTP20개·독립 MySQL13개를 통과했다. 업무 POST/PATCH·키 발급·저장 결과 조회0회와 업무·배정·관리자 행 보존을 확인했으며, 실제 수락/재작업 상태 전환을 검증한 것은 아니다. 자동화된 실제 WinForms 검사는 사용자 수동 전체 GUI 검수를 대신하지 않는다. 실행한 결과와 미실행 범위는 전용 테스트 안내와 [LOG/2번](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/tree/LOG/2번)에 기록한다.
