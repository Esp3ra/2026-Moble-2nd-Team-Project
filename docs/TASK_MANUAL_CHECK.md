## 이전 2026-10-20에 직접 조작한 범위

실제 제품 WinForms·워크플로를 저장소 밖 임시 실행기에 올리고 마우스·키보드로 조작했다. 서비스는 **명시적 TEST DOUBLE이며 메모리만 사용**한다. 각 시나리오는 독립 초기 상태이고, 등록 업무를 다음 메뉴의 수락·제출까지 이어간 통합 시험이 아니다. 실제 HTTP·DB·인증·권한·1번/3번 소비 연결의 증거로 사용하지 않는다. 제품 로그인은 자동 조작하지 않았다.

| 직접 점검한 화면·동작 | 확인한 결과 |
|---|---|
| 신규 등록 | 제목·시작/마감일을 입력하고 실제 후보 창에서 담당자 선택. 등록자가 필수 관리자로 유지되고 후보 선택만으로 저장하지 않음. 입력 확인 후 별도 등록 활성화, 성공 후 창 닫힘 |
| 업무 수락 | 진행전 본인 대상 확인→별도 업무 수락→진행중 성공 표시. 확인만으로 상태 변경 없음, 성공 후 반복 실행 비활성 |
| 재작업 시작 | 반려완료 대상 확인→별도 재작업 시작→진행중 성공 표시. 수락과 버튼/대상 구분 |
| 취소·결과 복구 | 빈 사유 거절. 입력 확인→실행→불명확 결과에서 새 실행 비활성. 명시 결과 확인의 not_recorded 뒤 같은 요청 재전송→성공·중복 실행 비활성 |
| 기술 연결 전 취소 | write_enabled=false일 때 기술 연결 안내·입력 확인/실행 비활성. 실제 배포 게이트 해제 없음 |
| 마감 연장 신청·승인 | 현재 기한 이후 희망일/사유 확인→별도 신청 실행. 다른 지정 관리자의 신청 대상/읽기 전용 희망일 확인→별도 승인 실행. 성공 뒤 반복 실행 비활성 |
| 연장 요청함 | 전체5신청 상태 표시. 관리자 승인·반려 활성, 본인 아닌 신청의 철회 비활성. 최소 창 크기에서 버튼 표시·긴 사유 스크롤 확인 |
| 업무 목록·상세 | 전체/진행전/진행중/제출완료/승인완료/반려완료 필터 각각 조작. 행 변경에 맞는 상세·수락/재작업 및 연장 활성 조건 확인 |
| 취소 포함 조회 | 기본 제외→취소 포함 체크→취소 행 선택. 원래 상태와 취소 표시, 상세 유지·새 수락/연장 비활성 확인 |
| 작은 업무 화면 | 임시 호스트의 최소 크기1100×720에서 목록·상세·기능 버튼 표시 확인. 연장 요청함은 제품 MinimumSize에서 확인 |
| 빈 목록·오류 | 조회된 업무0개 / 서버 오류 후 재시도 / 인증 만료 후 로그인 안내가 구분됨. 상세·행 의존 행동은 비활성 |

연장 성공에도 취소 설명을 공통 표시하던 문구를 행동별로 보완했다. 신청은 승인 전 기존 기한 유지, 승인은 적용 마감일, 반려/철회는 기존 기한 유지를 안내한다. API·상태/권한·쓰기 차단은 변경하지 않았다. 후속 `TaskLifecycle.Tests`119검사는 실제 폼/명시 대역 회귀이며 서버 통합 수치와 합산하지 않는다.

## 실제 환경에서 이어갈 순서

아래는 **미실행 공동 점검 절차**다. 공유 서버·계정 준비 완료와1·3번 실제 연결을 확인한 뒤 각 담당이 자기 영역에서 실행한다. 테스트 대역 값을 일반 실행의 배포 확인으로 설치하지 않는다.

1. **1번 준비:** 서버 코드 SHA, 공통/업무/receipt/결과물/취소·연장 스키마와 요구 버전, 개발 flag, 백업/복원·설치 책임을 확인한다. 실제009 검토 SQL·공통 결과 읽기는PR51로 제공됐지만 공유 적용·백업/복구·실제3번 소비/통합ACK는 완료가 아니다. 직원/관리자 계정과 주소는 비공개로 전달한다.
2. **기존 흐름:** 지정 관리자 업무 등록→본인 수락→3번 결과 제출→지정 검토자 반려→본인 명시 재작업→재제출→승인을 실제 서버에서 확인한다. 과거 제출/첨부·최초 수락·차수와 현재 상태/버전을 각각 대조한다.
3. **3번 소비 적용 확인:** 병합된 취소 helper와 실제 대기 신청 facts의 제출·판단·legacy multipart/JSON 첨부 연결을 같은 배포에서 확인한다. 취소/제출·첨부, 연장 대기/제출 경합과 과거 읽기를 실제 코드에서 확인한다. 2번이 결과물 코드를 대신 수정하지 않는다.
4. **연장·취소:** 진행중/반려완료·마감 전후 신청, 자기 판단 금지·다른 지정 관리자 승인/반려·본인 철회, 단일 대기·관리자 변경·기한 승인 반영, 취소 뒤 새 행동 차단과 허용된 과거 읽기를 확인한다.
5. **실패·복구:** 타인 업무 직접 접근, 현재 관리자 회수·재배정,401/403/409/503, 동일 키·동시 요청·응답 유실·not_recorded 뒤 동일 요청 재전송을 확인한다. 이미 성공한 요청과 새 변경을 구분한다.
6. **공유 검증:** 직원/관리자 두 PC에서 같은 업무의 목록·상세·현재 권한·기한을 대조하고 계정 변경·로그아웃 뒤 늦은 응답이 반영되지 않는지 확인한다.1·3번 실제 연결 증거가 모인 뒤에만 정식 배포 확인을 검토한다.

각 결과는 코드 SHA·역할/기능 옵션·실행 동작·기대/실제 결과·DB 효과·정리 여부로 기록한다. 비밀번호·토큰·실제 주소·업무 본문·파일 원본은 Git에 남기지 않는다.

## 이전 2026-10-20 회차에서 확인하지 않은 범위
