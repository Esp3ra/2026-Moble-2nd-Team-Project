# 2번 수락·재작업 시작 대상의 읽기 확인

2026-10-19. 기존 업무 상세와 W1 `write-context`를 이용해 현재 본인 배정·상태·버전을 확인하는 화면 연결입니다. **수락·재작업 시작 API나 상태 저장 기능을 추가한 것은 아닙니다.** 공통 서버·인증·기존 조회 계약과 3번 제출·검토·파일·이력 기능은 변경하지 않습니다.

## 화면에서 확인하는 내용

실제 로그인한 업무 화면의 **내 업무**에서 상세 조회가 성공한 대상을 사용합니다. 직원과 관리자 본인 업무에 같은 기준을 적용합니다.

| 상세의 상태 | 화면 진입 | 현재 정보 확인 기준 |
|---|---|---|
| 진행전 / `not_started` | 업무 수락 | 별도 조회의 현재 담당자 ID가 로그인 사용자와 같고 상태도 진행전 |
| 반려완료 / `returned` | 재작업 시작 | 별도 조회의 현재 담당자 ID가 로그인 사용자와 같고 상태도 반려완료 |
| 진행중·제출완료·승인완료 | 위 대상 확인 버튼 비활성화 | 상태 전환을 추측하거나 실행하지 않음 |

관리 업무를 조회할 수 있다는 사실은 본인 수락 권한을 뜻하지 않습니다. 지정 관리자도 현재 담당자가 아니면 대상 확인값을 만들지 않습니다. 표시명에서 사용자 ID를 추측하지 않고, 공통 로그인 세션의 사용자 ID와 서버가 반환한 `assignee_id`를 비교합니다.

연결된 `TaskAcceptanceForm`은 열릴 때 기존 `ITaskPreparationService.GetContextAsync(taskId)`를 호출합니다. 실제 HTTP 구현은 `GET /api/v1/tasks/{task_id}/write-context`이며 현재 담당자·배정 차수·업무 버전·상태·UTC 변경 시각을 받습니다. 이 기존 경로에는 W1 공통/업무 조회 활성화와 DB 준비가 필요합니다. 새 서버 경로·테이블·플래그는 추가하지 않습니다.

`최신 정보 다시 조회`는 같은 대상의 읽기를 반복합니다. `대상 확인`은 확인값을 이 창에 보관하고 창을 유지합니다. 두 버튼 모두 수락·재작업 시작을 실행하거나 저장 성공으로 창을 닫지 않습니다. 대상 준비 경로에서는 업무 POST/PATCH, 요청 키 발급, 저장 결과 조회를 호출하지 않습니다. 별도의 [신규 등록](TASK_CREATION.md)은 기존 계약을 유지합니다.

## 조회 시점과 불변 확인값

위쪽 제목·담당자 표시명·날짜는 **창을 열 때 전달받은 상세 조회 시점**의 값입니다. 현재 배정·상태·버전은 이후의 별도 `write-context` 조회값입니다. 두 조회를 하나의 원자적 스냅샷으로 표시하지 않습니다. 상세 날짜를 UTC 자정으로 바꾸거나 수락 가능한 날짜로 판정하지 않습니다.

`TaskStartTargetPreparation.Check`는 먼저 정규 BIGINT 업무 ID/버전·양수 사용자/배정 번호·정의된 상태·UTC·동일 업무 ID를 검사합니다. 그 뒤 현재 본인 배정 여부 → 상세와 현재 상태의 일치 여부 → 선택한 행동의 대상 상태 순서로 비교합니다.

- 현재 담당자가 본인이 아니거나 상세와 현재 상태가 다르면 확인을 막고 변경 안내를 표시합니다. 창을 닫으면 부모 화면이 목록·상세를 다시 조회하도록 요청합니다.
- 상태가 일치해도 수락의 진행전 또는 재작업의 반려완료가 아니면 해당 대상 확인값을 만들지 않습니다.
- 조건이 맞으면 `대상 확인`으로 별도 `CheckedTarget`을 보관합니다. 업무가 이후 다시 변경될 수 있으므로 확인값은 최신 상태나 최종 실행 권한을 보증하지 않습니다.

`CheckedTarget`의 타입인 `TaskStartTarget`은 `Kind`, `TaskId`, `UserId`, `AssigneeId`, `RowVersion`, `AssignmentRevision`, `Status`, `UpdatedAt`을 읽기 전용으로 보관합니다. 기존 `CheckedInput`·`PreparedSelection`과 별개이며 **요청 DTO·DB 모델·마감 판정·저장 권한이 아닙니다.** 이 값을 직접 직렬화해 전송하지 않습니다.

## 로딩·오류·접속 수명

다시 조회를 시작할 때 이전 준비값과 `CheckedTarget`을 지우고 로딩 안내를 표시합니다. 실패한 조회를 빈 성공이나 대상 확인 완료로 처리하지 않습니다. 로그인 만료·권한 없음·업무 없음·연결 필요·서버 오류는 기존 준비 서비스의 오류 구분을 사용합니다. 401/403과 접속 변경은 해당 창의 추가 확인을 막고 이전 확인값을 폐기합니다.

요청 세대와 취소 토큰으로 이전 조회의 늦은 응답을 무시합니다. 로그인 교체·창 닫기·Dispose에서도 확인값을 지우고 진행 중 읽기를 취소합니다. `CheckedTarget`은 읽는 시점에도 현재 접속과 조회 진행 여부를 확인합니다. 요청 취소나 조회 실패가 실제 업무 상태를 바꾸지는 않습니다.

기존 기본 생성자와 상세만 받는 생성자는 닫기만 제공하는 읽기 전용 화면을 유지합니다. Designer/미리보기에 로그인 서비스나 네트워크 호출을 자동 주입하지 않습니다. 실제 로그인 화면에서 서비스를 전달한 생성자만 최신 정보 조회와 대상 확인을 제공합니다.

## 실제 상태 저장 전에 필요한 합의

사용자가 확정한 흐름은 `진행전 → 본인 수락 → 진행중`, `반려완료 → 본인 재작업 시작 → 진행중 → 재제출 성공 → 제출완료`입니다. [3번 최신 수신 회신](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/LOG/3번/2026-10-19_2번_재작업흐름_수신회신.md)은 재작업 때문에 최초 수락·배정 번호·제출 회차를 초기화하지 않고 과거 결과를 보존하는 방향도 확인했습니다. 그 수신을 아직 없는 서버 저장 계약으로 확대하지 않습니다.

| 기존 항목 | 남은 확인 |
|---|---|
| W3-01·06 | 시작일 전·마감 후 수락/재작업 허용 여부, 판단 시간대·마감 시각. 기존 보수적 날짜안도 제안이며 이 화면에서 선택하지 않음 |
| W1-03·04 / W3-02·04 | 성공 시 업무 버전 증가 수치·시점, 행동별 요청/필수 결과·상태 충돌 오류, 중복/응답 유실과 원자 저장 계약 |
| 재작업 행동 | 별도 action·감사·receipt 등록과 공통 접점 공동 검토. 기존 `task.accepted`를 재작업 action으로 대신 사용하지 않음 |
| 최초 수락·과거 자료 보존 | 재작업에서 기존 `accepted_at`·배정 차수·제출 회차/과거 자료를 보존하는 방향은 확인됨. 반려 상태인데 최초 수락 기록이 없는 등 이상 자료 처리와 실제 원자 저장 방식은 검토 필요 |
| 환경·배포 | 정식 migration·공유 환경 적용·두 PC 및 실제 상태 쓰기 통합 검증은 별도 |

기존 공통 도구에는 `task.accepted`의 현재 본인 권한·키·결과 지원이 있습니다. 이는 실제 수락 경로가 있다는 뜻이 아닙니다. 재작업 action과 행동별 서버 경로도 이번 작업에서는 등록하지 않습니다. 이후 저장을 연결할 때는 서버가 현재 인증·배정·버전·상태와 합의된 날짜 조건을 다시 검사해야 합니다. [WRITE_SUPPORT](WRITE_SUPPORT.md)와 [RESULTS_INTEGRATION](RESULTS_INTEGRATION.md)의 공통 도구를 재사용하고 3번의 제출/판단과 상태를 이중 저장하지 않습니다.

## 검증 범위

전용 [TaskStartPreparation.Tests](../Tests/TaskStartPreparation.Tests/)에서 대상 판정, 실제 WinForms와 통제 HTTP, 기본 생성자 보존, 별도 명시적 MySQL/HTTP 읽기 경로를 구분합니다. Windows 소스 루트에서 기본 검사를 실행하는 명령은 다음과 같습니다.

```powershell
dotnet run --project .\Tests\TaskStartPreparation.Tests\TaskStartPreparation.Tests.csproj -c Release
```

대상 준비의 검사 기준에는 업무 POST/PATCH·키 발급·저장 결과 조회가 0회이고 업무·배정·관리자 행이 변하지 않는다는 점을 포함합니다. 테스트 fixture의 로그인·합성 자료 준비와 제품의 상태 쓰기는 구분합니다. 이번 통제 HTTP/실제 WinForms149검사, 별도 실제 HTTP/WinForms20검사·독립 MySQL13검사를 통과했습니다. 반려 상태와 과거 수락 시각은 직접 seed한 조회 자료이며 실제 제출/반려 전환을 검증한 것이 아닙니다. 자세한 실행과 미실행은 [전용 테스트 안내](../Tests/TaskStartPreparation.Tests/README.md) 및 [LOG/2번](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/tree/LOG/2번)의 해당 회차 기록을 따릅니다.

수락·재작업 실제 POST/DB 상태 변경, 마감 정책, 3번 제출·차수·판단·파일·화면용 이력, 공유 서버·두 PC·사용자 수동 전체 GUI는 이 읽기 연결의 완료 범위가 아닙니다. 자동 결과 제출은 추가하지 않습니다.
