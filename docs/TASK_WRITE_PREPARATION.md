# 2번 W1 후보·쓰기 준비 연결

최신화: 2026-10-19. **팀장과 2번 담당자는 사용자 본인**입니다. 정책 확인이 필요하면 사용자에게 확인합니다. 10월 17일 후보/문맥 연결을 유지하면서 신규 등록만 [별도 등록 서비스·UI](TASK_CREATION.md)로 연결했습니다. 이 문서의 후보 선택·입력 확인은 여전히 저장 동작과 구분합니다.

## 2026-10-17 후보·문맥 연결 기록

1. `Preparation/TaskPreparationModels.cs`에 후보·페이지·쓰기 문맥·키/결과 모델과 별도 서비스 계약을 추가했습니다. 기존 업무 GET DTO와 CheckedInput은 유지합니다.
2. `HttpTaskPreparationService`는 공통 ApiClient.Session에 묶여 후보·write-context·키 발급/결과 조회만 호출합니다. 계정 전환·같은 사용자 재로그인·서버 변경 후 옛 창이 새 접속으로 요청하지 않습니다.
3. HttpTaskQueryService의 선택적 ITaskPreparationSource를 TasksControl이 사용하므로 MainForm·공통 파일·기존 ITaskQueryService는 변경하지 않았습니다. 미리보기/기본 조회 대역에는 자동 주입하지 않습니다.
4. 업무 화면 ‘업무 연결 정보’에서 성공한 현재 상세의 ID로 준비 정보를 조회합니다. 등록/수정 창의 ‘담당자 · 업무 관리자 선택’으로 검색·페이지·담당자 단일/관리자 복수 선택·해제를 제공합니다. 이름 대신 서버 ID로 보관합니다.
5. 페이지/검색 중 선택 유지, 로딩/실패 중 선택 확정 차단, 빈 결과 구분, 다시 조회 시 초기화, 권한 회수/로그인 변경 시 정보 삭제와 늦은 응답 차단을 구현했습니다.

## 신규 업무의 관리자 지정 기준 — 2026-10-19

사용자가 신규 등록 기준을 확정했습니다. 업무 관리자는 최소 1명이며, 등록자는 자동 포함하고 최초 등록에서는 제외할 수 없습니다. 추가 관리자는 기존 활성 관리자 후보에서 선택합니다. 업무 관리자와 제출 검토자는 별개입니다.

신규 업무 선택 창은 현재 로그인 등록자의 ID를 기본 관리자 선택에 넣고 `(등록자 · 필수)`로 표시합니다. 검색·페이지 이동 후에도 유지하며 등록자 선택 해제를 막고, 선택값을 가져올 때도 필수 관리자 포함 여부를 확인합니다. 정보를 다시 조회하면 추가 선택은 초기화하고 등록자는 다시 포함합니다. 로그인 변경이나 권한 오류가 발생하면 등록자 선택을 포함한 준비 정보를 지웁니다.

후보 창은 로컬 선택 준비만 수행합니다. 선택을 가져온 신규 등록 부모 창에서 입력 확인 후 별도 등록 버튼을 눌러야 [신규 등록 개발 API](TASK_CREATION.md)를 호출합니다. 서버는 현재 관리자 역할·후보·필수 관리자 관계를 같은 저장 처리에서 다시 확인합니다. 선택값을 저장 성공으로 취급하지 않습니다. 기존 업무의 관리자 교체·제외 정책은 이번 신규 등록 기준으로 확정하지 않습니다. 추가로 사용자가 반려 후 흐름을 `반려완료 → 재작업 시작 → 진행중 → 재제출 성공 → 제출완료`로 확정했습니다. 재작업 시작은 제출 회차를 올리지 않으며, 최초 제출과 재제출은 기존 성공 제출·반려 기록으로 구분합니다. 수락·재작업 시작은 KST 시작일00:00 이상~마감일 다음날00:00 미만만 허용하며 시작일 전·마감 후 예외는 없습니다. 1번의 공통 버전·원자 처리 기술 규칙은 수신했으며 실제 행동별 API·action·오류의 최종 대조는 남아 있습니다. 결과물 제출·연장 날짜와 검토자 정책은 별도 합의 필요이며, 이번 준비 연결에 수락·재작업 상태 저장은 추가하지 않았습니다.

## 저장과의 경계

후보/문맥 조회나 선택값 가져오기는 최종 저장 권한·상태별 허용이 아닙니다. 업무 관리자는 제출 검토자와 별개입니다. 폼의 별도 PreparedSelection은 선택값이며 기존 CheckedInput은 로컬 제목/내용/날짜 확인값입니다. 후보 선택 변경은 이전 CheckedInput을 무효화합니다. 후보 준비 서비스·창은 등록·재배정·수락·연장 접수/상태 변경을 실행하지 않습니다. 신규 등록 부모 창만 별도 등록 서비스를 사용합니다.

기존 상세 GET와 별도 write-context가 동일 트랜잭션의 스냅샷임을 보증하지 않습니다. 신규 등록은 현재 입력·선택·등록자 포함 여부를 재검사하고 별도 불변 TaskCreationRequest를 만듭니다. 기존 업무를 수정하는 expected version을 신규 생성에 붙이지 않습니다. 수정·재배정·수락·연장은 입력 원본과 버전의 일관된 읽기·상태별 검사·현재 권한/배정/버전 재검사를 각각 맞춘 뒤 연결해야 합니다.

| 서비스 | 용도 |
|---|---|
| GetCandidatesAsync | assignment/manager-candidates · 검색·페이지·필수 필드·중복 ID 검사 |
| GetContextAsync | 업무/버전 BIGINT 문자열·담당자/관리자 INTEGER·배정 차수·5상태·UTC 검사 |
| GetRequestKeyAsync | 확정된 W1 행동/대상의 서버 키 발급. 원문은 메모리 보관, ToString에 노출하지 않음 |
| GetResultAsync | 같은 키로 completed/not_recorded 조회. 자동 재전송·새 키 생성 없음 |

401·403·업무 전용404/일반404·버전/배정 충돌·키 재사용/만료·미준비503을 구분합니다. 준비 창은 키 발급/결과 조회도 자동 호출하지 않습니다. 이 준비 서비스에는 제품 행동 API 메서드를 추가하지 않았으며, 신규 등록은 별도 HttpTaskCreationService·TaskCreationWorkflow가 담당합니다.

등록 POST 이후 결과가 불확실하면 같은 공통 ApiClient·로그인 세션의 요청을 메모리에 보관합니다. 등록 창과 업무 메뉴를 다시 열어도 이전 요청을 이어가며, 앱 종료·로그인 변경 뒤의 복구 저장소는 제공하지 않습니다. 사용자가 `처리 결과 확인`을 눌러 `completed`를 확인하면 성공으로 처리하고, `not_recorded`일 때만 `같은 요청 다시 전송`으로 같은 키·본문을 보낼 수 있습니다. POST의 키 만료 410은 보관된 결과를 먼저 조회하며, 결과 조회의 410은 수동 확인으로 전환합니다. 401·403·접속 변경은 준비 선택과 이전 쓰기를 차단하고 같은 접속의 메뉴 재진입으로 403 차단을 우회하지 않습니다. 성공 후에는 현재 범위·상태 필터를 유지해 목록/상세를 다시 읽습니다.

## 검증과 개발 환경

[TaskPreparation.Tests](../Tests/TaskPreparation.Tests/README.md)는 제어 HTTP·실제 WinForms와 새 소유 MySQL의 실제 HTTP/UI 검증을 분리합니다. 최소 크기 렌더링도 확인했으며 수동 전체 GUI 검수를 대신하지 않습니다.

이번 회차 후보 준비 87개와 업무 조회 171개 회귀가 각각 통과했습니다. 신규 등록 [TaskCreation.Tests](../Tests/TaskCreation.Tests/README.md)의 제어 79개·실제 C# HTTP 10개·독립 DB 24개는 별도 실행이며 과거 준비 검증과 합산하지 않습니다.

명시적 개발 서버와 삭제 가능한 전용 MySQL에 검토용002/004·공통 테이블을 준비하고 `REMOTEWORK_ENABLE_COMMON_WRITE_DRAFT=1`, `REMOTEWORK_ENABLE_TASK_QUERY_DRAFT=1`을 사용합니다. 신규 등록 POST에는 추가로 `REMOTEWORK_ENABLE_TASK_CREATE_DRAFT=1`이 필요합니다. 요청 중 DDL이나 공유 DB 변경을 하지 않으며 공통 version1·기본off를 유지합니다. [W1 계약](WRITE_SUPPORT.md)을 따릅니다.

## 다음 합의와 구현

미확정 내용은 모두 **협의사항**입니다.2026-10-19 팀장 답변에 따라 업무 수정·담당자 변경과 마감 연장은3번과 협의 후 결정합니다. 아래의 기술 대조·정책·배포 질문을 문서 게시나 코드 준비만으로 확정하지 않습니다.

- 신규 등록의 초기 버전/배정1/1·accepted_at=NULL과 실제 등록 개발 API·UI를 연결했고 1번 기술 수용 회신을 확인했습니다. 1번은 공통 잠금 순서·최초 mutation의 버전 증가·감사/receipt의 원자 처리도 수용했습니다. 이 기술 수신과 공유 배포 승인은 별개이며 수락·재작업의 구체 경로·action·요청/결과·상태 충돌 오류를 최종 대조한 뒤 실제 저장을 연결합니다.
- W3-01·06 중 수락·재작업 시작의 KST 기간 제한은 위 팀장 확정안을 따릅니다. [순수 날짜 판정과 대상 확인](TASK_START_PREPARATION.md)은 준비되었으며 실제 API 최초 mutation에서는 서버의 현재 날짜·권한·배정·버전·상태를 다시 검사해야 합니다. 상세와 write-context는 서로 다른 조회 시점이므로 상세 날짜를 현재 실행 자격으로 사용하지 않습니다.
- W3-02/03/04의 상태별 수정·재배정·취소, 제출/판단 원자성·버전 증가·배정/제출 참조·이력 계약을 맞춥니다.
- W3-05/06/07의 검토자·마감/연장/제출 경합·수동/자동 검토 요청은 사용자(팀장)·관련 담당과 확인합니다. 자동 결과 제출은 제외합니다.

신규 등록 외의 업무 수정·수락·재작업·연장 저장과 3번 결과/파일/회차/승인·반려, 공유DDL/버전/복구·두PC·웹 업무·장치 인증은 이번 범위 밖입니다. 이미 수신한 1번 기술 규칙과 별개로 행동별 계약의 최종 대조·정식 migration·공유 배포는 남아 있으며, 3번 업로드나 문서 게시만으로 남은 공동 정책을 확정하지 않습니다.
