# 수동 검토 요청과 업무 화면 연결

2026-10-26 팀장 확정: **제출완료된 결과에 기존 지정 검토자에게 별도 요청 내용을 저장한다. 업무 상태와 제출 회차는 유지하고 같은 제출 회차의 확인 대기 요청은 중복 방지한다.** 기존 PR98의 결과 제출창 공동 연결은 이 별도 기능으로 교체했다. 자동 결과 제출과 자동 검토 요청은 추가하지 않는다.

## 사용자 흐름

| 동작 | 조건과 결과 |
|---|---|
| 결과 제출 | 진행중인 본인 업무의 설명·첨부를 기존 결과물 서비스로 제출. 성공하면 제출완료, 필수 검토 대상이 된다. |
| 검토 요청 | 제출완료된 본인 업무에서 별도 창으로 최신 결과·회차·현재 검토자를 확인하고 요청 내용을 저장한다. 업무 상태·버전·회차는 그대로다. |
| 검토 요청함 | 직원과 관리자 모두 내가 보낸 요청을 조회한다. 관리자는 현재 지정 검토자로서 받은 요청을 조회할 수 있다. |
| 요청 확인 | 현재 지정 검토자가 명시적으로 요청을 확인한다. 결과물 승인·반려가 아니며 결과물 메뉴의 실제 검토는 별도로 진행한다. |
| 결과물 판단 이후 | 기존 제출·업무 상태를 읽어 요청함에서 검토 종료로 표시한다. 3번의 제출·판단 저장 코드를 수정하거나 별도 판단 대상을 만들지 않는다. |

관리자도 본인 업무에서는 직원과 같은 요청 흐름을 사용한다. 자기 요청 확인은 금지된다. 2026-10-26 사용자 변경 지시에 따라 **현재 지정된 활성 업무 관리자가 결과 검토자도 맡는다.** 별도 부서/상위 검토자 등록은 필요 없다. 여러 업무 관리자는 모두 같은 요청을 조회·확인하고 결과를 승인·반려할 수 있으며, 실제 요청 확인과 결과 판단은 별도 동작이다. 관리자 관계 회수·비활성·역할 변경은 매 요청에서 다시 검사하고 자기 결과 판단은 차단한다. 기존 업무도 현재 관계를 사용하며 기존 요청/제출/판단 스냅샷은 보존한다.

WinForms는 업무 메뉴의 `검토 요청`과 `검토 요청함`, 웹은 업무 상세의 `검토 요청` 및 `/tasks/review-requests`에서 사용한다. 요청 내용은 1~4,000자이다. 오류 안내·빈 목록·이전 접속 폐기·전송 결과 확인을 제공한다. 결과가 불명확하면 원래 요청 키·본문을 보관하고 공통 결과 조회로 확인하며 자동 재전송하지 않는다. Windows 클라이언트에서 권한을 잃으면 이전 내용을 숨기고 새 요청 처리를 차단한다. 결과가 불명확한 원 요청은 메모리에 보존한다. 이때 본문을 노출하지 않는 기존 키의 결과 확인만 허용하며 서버가 현재 권한을 다시 허용한 경우에만 원문과 확인된 결과를 복원한다. 로그인 변경 시에는 이전 요청을 새 계정으로 전달하지 않는다.

## API와 저장

공통 Bearer 인증·snake_case·UTC ISO8601·W1 멱등성·오류 응답을 사용한다. 웹은 기존 쿠키 인증·CSRF·로그인 결합 서명 확인과 같은 저장 함수를 사용한다.

| 경로 | 기능 |
|---|---|
| `GET /api/v1/tasks/{task_id}/review-request-context` | 본인 제출완료 업무, 최신 제출 결과, 지정 검토자, 기존 요청 조회 |
| `POST /api/v1/tasks/{task_id}/review-requests` | 별도 요청 저장 |
| `GET /api/v1/tasks/review-requests?scope=own` | 현재 본인의 요청 조회 |
| `GET /api/v1/tasks/review-requests?scope=reviewing` | 현재 검토자가 받은 요청 조회 |
| `POST /api/v1/tasks/{task_id}/review-requests/{request_id}/acknowledge` | 명시 요청 확인 |

요청 본문은 `expected_row_version`, `expected_assignment_revision`, `submission_id`, `reason`이다. 요청 확인 본문은 두 기대 버전이며 경로의 요청 번호도 서버의 멱등성 본문 비교에 포함한다. 공통 행동은 `task.review_requested`, `task.review_acknowledged`, target은 업무 번호이다.

새 `task_review_requests`에 요청·제출 식별자, 배정 차수, 요청자·수신 검토자, 내용, 생성·확인 시각을 저장한다. 요청과 확인, 감사, receipt는 공통 인증 트랜잭션과 guard 안에서 함께 저장된다. 결과물·업무·배정 테이블을 변경하지 않는다. 현재 권한·최신 제출·취소·기대 버전을 서버에서 다시 확인하며, 원래 결과물 승인·반려와 경합하면 오래된 확인을 거절한다. 같은 제출의 대기 요청은 트랜잭션 검사와 DB 유일 제약으로 중복을 막는다.

## 서버 PC 적용

1. 실제 실행 폴더에 최신 alpha를 반영한다. 기존 `.env`, 장치 비공개 설정, 파일 저장소를 보존한다.
2. 실제 MySQL DB를 백업하고 [019 SQL](../RemoteWork.Server/migrations/019_task_review_requests.mysql.sql)을 대조·적용한다. 기존 공통 사용자·002 업무·004 receipt·006 결과물 구조가 필요하다. 이미 표가 있다면 다시 생성하지 말고 현재 스키마를 검사한다. 기존 표나 자료를 삭제하지 않는다.
3. 기존 업무 조회·공통 쓰기·결과물 기능과 현재 업무 관리자 관계를 확인한다. 담당자 본인 외 활성 업무 관리자가 있어야 하며 별도 제출 검토자/계정은 만들지 않는다. 공통 schema version은 1을 유지하며 일반 시작이나 init-db가 019를 자동 설치하지 않는다.
4. 서버를 재시작하고 WinForms를 재빌드한다. 브라우저는 새 요청 페이지를 조회한다.
5. 검증용 업무로 수락→설명 입력·제출→별도 요청→지정 검토자 요청 확인→실제 승인·반려를 확인한다. 요청 저장/확인 전후의 업무 상태·회차가 같은지도 대조한다.

019가 없으면 새 요청 기능은 `TASK_REVIEW_REQUEST_SCHEMA_REQUIRED`503으로 안내한다. 이는 결과 제출창으로 대신 연결하는 조건이 아니다. 취소·연장은 별도로 [기존 통합 활성화](TASK_LIFECYCLE.md#task-lifecycle-deployment-activation)가 필요하다. 다른 PC의 최신 코드 반영·DB 적용·재시작은 이 PC의 빌드나 격리 테스트 통과만으로 완료되지 않는다.

## 이번 화면 점검에서 수정한 항목

- 결과 설명 입력: 제출 문맥을 확인하지 못한 이유가 숨겨지던 문제를 수정했다. 본인 업무 정보는 먼저 표시하고 조회 오류와 재확인 버튼을 항상 노출한다. 권한·마감·연장 대기 검사는 유지한다. 정상 문맥에서 Win32 문자 입력과 실제 제출 저장을 검사한다.
- 담당자/관리자 선택: 각 변경 버튼이 해당 종류의 후보만 조회·선택한다. 반대쪽 관계를 바꾼 것처럼 보이고 실제 저장에서는 버려지던 혼동을 없앴다.
- 검토 요청: 별도 작성·저장·목록·현재 검토자의 확인·원 요청 결과 복구를 WinForms와 웹에 연결했다.

직접 실행한 검사와 환경은 [업무→결과·검토 요청 통합 검사](../Tests/TaskResults.Integration.Tests/README.md), [제출창 입력 검사](../Tests/SubmissionForm.Ui.Tests/README.md), [후보 선택 검사](../Tests/TaskPreparation.Tests/README.md)에 기록한다. 테스트 대역·소유 MySQL 실제 HTTP·현재 로컬 서버·팀원 서버 검증을 구분하며 반복 실행 수치를 합산하지 않는다.
