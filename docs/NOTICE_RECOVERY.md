# 공지 등록 원 요청 복구

공지 등록의 본문·첨부 연결·감사·최소 성공 영수증을 같은 관리자 인증 트랜잭션에 저장한다. 원 `operation_id`를 별도 MySQL `notice_operations`에 남겨 공통 W1 영수증 정리·앱 재시작·새 W1 키에도 같은 등록을 반복하지 않는다. 공지를 나중에 삭제해도 원 성공은 유지하며 삭제된 공지를 재생성하지 않는다.

## API 계약

기존 공통 Bearer·현재 활성 관리자·공통 guard/세션 재검사·응답 형식을 사용한다.

1. 클라이언트는 등록 내용과 함께 정규 소문자 UUID `operation_id`를 한 번 정한다.
2. `POST /api/v1/write-requests/keys`에 `{action:"notice.created",target:operation_id}`를 보내 W1 키를 받는다.
3. `POST /api/v1/notices`에 기존 등록 필드와 `operation_id`, `Idempotency-Key` 헤더를 전송한다. 성공 `data`는 정확히 `{notice_id,operation_id,created_at}`이며 HTTP201이다. 본문·첨부 이름·파일 내용은 영수증에 저장하지 않는다.
4. 응답이 불명확하면 자동 재전송하지 않는다. `GET /api/v1/notices/operations/<operation_id>`는 같은 현재 관리자 본인의 원 요청만 조회한다. 결과는 `{state:"not_recorded"}` 또는 `{state:"completed",http_status:201,result:<최소 영수증>,expires_at}`이다. 공통 `/write-requests/result`도 같은 action/target/key로 사용할 수 있다.
5. 미저장을 확인한 뒤 사용자가 같은 UUID·본문·파일 목록·키로 명시 재시도한다. 내용이 달라지면409, 원 작업 만료는410이다. 401·403·410·503을 미저장으로 해석하거나 새 요청으로 자동 전환하지 않는다.

동일 원 UUID는 같은 관리자의 전체 본문 해시에 고정된다. 별도 관리자의 동일 UUID는 서로 다른 요청이며 타인의 원 결과를 노출하지 않는다. 현재 관리자 권한이 회수되면 과거 성공 결과도 읽을 수 없다. 원 성공은 보관 시점부터 공통 보관 설정과24시간 중 짧은 기간까지이며 재조회·재시도가 늘리지 않는다. 만료 뒤에도 식별·해시 tombstone을 자동 삭제하지 않아 새 키로 재등록할 수 없다.

기존 `operation_id` 없는 API 요청은 명시적인 구형 호환 경로로 `{notice:...}`를 반환한다. 새 클라이언트는 복구 기능 실패 시 이 경로로 후퇴하지 않는다. 최소 영수증 확인 뒤 상세 GET이 실패하거나 공지가 이미 삭제되었어도 원 저장 성공을 실패로 바꾸지 않는다.

## WinForms

제품의 공지 작성 창은 `IRecoverableNoticeService.CreateOrRecoverNoticeAsync`를 사용한다. 첫 전송 전에 원 UUID·복사한 입력/첨부 목록·W1 키를 고정하고 첫 통신 실패 직후 자동 재송신하지 않는다. 결과가 불명확하면 입력을 잠그고 **저장 결과 확인·재시도**를 제공한다. 다음 명시 클릭에서 원 UUID 조회→공통 W1 조회를 순서대로 확인하고 둘 다 미저장일 때만 같은 키·본문을 한 번 재송신한다. 성공·만료·권한/통신 오류를 미저장으로 바꾸지 않는다.

최소 영수증 성공으로 창의 등록 성공을 확정하며 목록/상세 재조회 실패가 이를 지우지 않는다. 같은 UUID의 호출자 배열 변경·다른 본문을 거절한다. `HttpNoticeService.CreateNoticeAsync`는 기존 호출자/검증 대역의 구형 호환 API이며 제품 새 작성 화면은 실패 시 여기에 후퇴하지 않는다. 메모리의 원 작업은 같은 캡처 접속에 묶고 창 닫기·앱 종료·새 로그인에서 자동 인수하지 않는다. 이 경우 원 공지 번호/목록·운영 기록으로 상태를 확인하며 새 UUID를 자동 발급하지 않는다.

## 웹

공통 W1 활성화 시 작성 화면은 로그인 세션에 서명 결합한 원 UUID·키를 준비한다. 입력 오류는 값을 보존하며, 저장 결과 불명확 시 원 내용·첨부 ID·키를 고정하고 **처리 결과 확인**을 제공한다. 미저장이 확인되어도 재전송하지 않고 **같은 요청 다시 등록**의 다음 사용자 클릭을 기다린다. 성공 후 응답 유실은 원 결과 조회로 처리하며 등록 POST를 다시 보내지 않는다.

브라우저 전송 오류에는 메모리에 원 FormData를 유지해 같은 원 결과를 확인한다. 페이지 재표시는 서명된 원 컨텍스트에 입력을 복원한다. 로그인 변경·잘못된 컨텍스트는 거절한다. CSRF를 우회하지 않으며 cookie를 Bearer로 전달하지 않는다. 브라우저 저장소에는 본문·키·파일을 저장하지 않는다. 완전히 새 작성 화면·다른 로그인으로 이전 작업을 자동 인수하지 않는다. 첨부 전송의 미완료 원 선택은 완료 전까지 등록·복구 전송을 막는다.

공통 W1이 꺼진 서버의 기존 웹 작성은 구형 동작이다. W1을 켰는데017이 준비되지 않은 경우 새 작성 동작은503이며 구형 경로로 자동 후퇴하지 않는다.

기존 공통32KiB 요청 제한을 유지한다. 복구 컨텍스트를 포함해 이 제한을 지킬 수 없는 입력은 저장 전에 안내하고 줄이도록 요청한다. 고정된 본문은 복구 시 중복 전송하지 않으며 원 서명 컨텍스트로 복원한다. 개별 입력의 모든 최대 길이 조합을 한 요청에 허용한다는 뜻은 아니다.

## 017 적용과 복구

`RemoteWork.Server/migrations/017_notice_operations.mysql.sql`은 별도 테이블 한 개의 명시 CREATE다. 공통 users·004 W1·기존 공지 저장소를 준비한 뒤 실제 DB·전체 비공개 백업/독립 복원·FK/문자셋·실행 SHA를 확인해 한 번 적용한다. 현재 `schema_versions[1]`과 공지/첨부/감사 테이블을 바꾸지 않는다. 시작·HTTP·`init-db`는017을 자동 생성하지 않는다. 다른 구조가 있으면 자동 ALTER·DROP·재시도하지 않는다.

문제가 있으면 신규 공지 생성을 중지하고 기존 원 작업·공지·파일 참조·감사를 보존해 원 결과를 확인한다. `notice_operations`나 만료 행을 삭제하거나 기존 DB에 덤프를 덮어써 중복 방지 근거를 없애지 않는다. 실제 운영 서버·공유 DB·계정·설정·기존 파일을 이번 코드 변경으로 변경하지 않는다. 적용/실계정·두 PC 검증은 별도다.

## 검사

`Tests/Notices.Tests/run_operations_mysql.py`는 새 datadir·임시 loopback 포트·`remote_work_test_*` DB만 만드는 기존 소유 MySQL 실행기를 재사용한다. raw017/API/W1과 cookie/CSRF·불명 결과·현재 권한·만료·삭제 후 재생성 방지·rollback을 검사하고 소유 프로세스와 runtime을 정리한다. 공유 운영 DB나 실제 파일 삭제 검증으로 표시하지 않는다.

2026-10-23 직접 실행: 새 원 요청 검사 **18통과**(대형 UTF-8 실제 multipart 복구, 동시 새 키, 앱 재시작,017 부재, 실제 C# HTTP 소비 포함), 기존 공지 API·검토·웹 회귀는 별도 새 DB에서 **73통과**했다. 실제 C# 소비는 `NOTICE_CSHARP_DLL`로 지정한 새 빌드의 `--operations-e2e`7검사를18개 중 한 검사로 실행했으며 수치를 합산하지 않는다. `--legacy`는 기존73개만 실행한다. DLL을 지정하지 않은 실행은 C# 검사를 명시 skip하므로 실제 연동 완료로 표시하지 않는다. 네이티브 브라우저·공유 운영·실계정·두 PC는 미실행이다.
