# 2번 업무 웹 목록·상세 조회

PR70 병합 후 등록·일반수정·연장 승인은 [공통 사건 기록을 연결한 같은2번 W1 실행 함수](TASK_QUERIES.md#task-deadline-journal-writes)를 사용합니다. 웹만의 추가 저장이나 DTO/키를 만들지 않으며 현재 활성 설치·오류/rollback·미확정 결과 복구를 API와 공유합니다. 실제4번 알림 UI·공유 배포까지 연결됐다는 뜻은 아닙니다.

## 후보 검색·입력 오류 뒤 첨부 표시 복원 — 2026-10-22

등록·일반수정에서 명시 업로드가 끝난 뒤 후보 검색이나 입력 오류로 같은 폼을 다시 표시하면 이전 파일명·크기와 임시 삭제 버튼을 복원합니다. 선택 파일 ID와 순서는 그대로이며, 로컬 파일 바이트를 다시 선택하거나 업로드할 필요가 없습니다. 전송 중/결과 불명인 파일은 기존대로 폼 전송을 차단하고 먼저 확인합니다.

`attachment_display`는 2번 웹 폼의 선택적 표시 정보입니다. 기존 로그인 scope와 같은 모드·업무·선택 ID 안에서 최대10개/16KiB·필드 형식을 검사하고 별도 presentation 값으로 렌더합니다. API 요청 DTO·서명된 쓰기 본문/summary·W1·DB에 포함하지 않습니다. JavaScript 저장소나 서버 세션에 초안을 보관하지 않으며, 정보가 없는 과거 폼은 기존 ID 표시를 유지합니다. 이름은 Jinja JSON 이스케이프와 `textContent`로 표시합니다.

복원 정보는 **이전 기록**이며 현재 소유권·전송 준비·미연결 상태를 증명하지 않습니다. 실제 삭제는 사용자 확인 후 기존 공개 cookie/CSRF/session discard를 호출하고 제공부가 현재 소유자·참조·만료·업무 접근 조건을 다시 검사합니다. 현재 업무 목록에서 연결이 확인되면 최신 메타정보를 우선하고 임시 삭제 자격을 해제합니다. 이후 연결이 사라져도 과거 임시 삭제 자격을 자동 복원하지 않습니다. 권한 상실·로그아웃·접속 변경·화면 이탈 때는 이전 표시를 지우며 늦은 응답으로 되살리지 않습니다.

**추가 기술 규약이 필요한 부분:** 미연결 업로드의 현재 메타정보·삭제 가능 여부를 화면 진입 전에 읽거나, 브라우저를 닫은 뒤 다시 찾는 기능은 현재 공개 제공 범위가 아닙니다. 필요하면3번과 읽기 접점·접속/소유/업무 권한·만료 의미를 별도 대조합니다. 이 복원 기능은 새 API를 만들거나 `complete` 쓰기를 조회 대신 자동 호출하지 않습니다. [검사와 미실행 범위](../Tests/TaskWeb.Tests/README.md#task-web-attachment-redisplay-checks)를 확인합니다.

## 저장 결과의 업무 식별 — 2026-10-22

성공 확인 화면에는 저장 결과가 반환한 업무 번호와 원래 서명 요청의 동작을 표시합니다. 다른 업무의 성공 화면이 같은 문구로 보이지 않게 하며, 현재 목록 선택이나 새로 조회한 제목으로 처리 대상을 바꾸지 않습니다. 결과 조회로 복구한 성공도 같은 기준을 따릅니다. 응답에 업무 번호가 없으면 목록에서 확인하도록 안내하고 번호·상세 링크를 추정하지 않습니다. 성공 화면 표시에 추가 실행 요청은 없습니다. 실제 Jinja 렌더링 26개 검사와 브라우저/DB 미실행 구분은 [검사 기록](../Tests/TaskWeb.Tests/README.md)을 따릅니다.

## PR68 실제 소비: 결과물 진입·복귀와 업무 첨부 — 2026-10-22

병합된 3번 공개 제공부만 2번 웹/쓰기에서 사용합니다. 결과물·공통 인증/HTTP·DB·DDL·설정·운영 ACK를 수정하지 않았습니다. 기존 query/common/create 또는 management opt-in에 결과물/공용 첨부 opt-in과 준비된013 저장소가 필요합니다. 선택 기능을 켰다고 공유 서버에 적용되는 것은 아닙니다.

- 결과물: `results_task_web.build_url`로 own→own, managed→read를 구분하고 원래 task/scope/status/include_cancelled와 같은 AuthSession을 묶습니다. 현재 범위 권한이 없으면 링크를 제공하지 않으며 제공부의 인증·서버 오류는 숨기지 않습니다. 복귀는 3번이 검증한 내부 경로를 사용자가 클릭해 현재 업무를 다시 조회합니다.
- 파일: `task_attachments.js`와 `_attachments.html`을 등록·일반수정·상세에서 사용합니다. 공개 `session_scope()`와 cookie/CSRF, `X-Results-Session`을 사용하며 Bearer를 브라우저에 주지 않습니다. 업로드는 명시 버튼으로16KiB씩 보내고 전체 크기/SHA256·응답 메타정보를 확인합니다. 전송만으로 업무 저장 성공을 표시하지 않습니다.
- 업무 저장: 웹 폼의 선택 `attachment_ids` JSON과 `attachment_scope`를 검사합니다. 생략/빈 배열/값의 기존 의미와 원래 배열 순서를 유지하고, 준비 시 서명된 불변 body/W1 키에 고정합니다. 미완료 업로드·불명 삭제가 남으면 확인/후보 검색을 차단합니다. 이후 업무 저장 실패·불명은 기존 확인폼의 같은 요청 결과를 조회하며 자동 삭제/새 업로드/새 키를 만들지 않습니다.
- 일반수정: 기존 파일의 선택 제외는 저장 때 업무 참조만 해제합니다. 같은 TX의 공개 read→집합 비교→필요한 replace→업무 버전/감사/receipt를 사용하며 전부 rollback합니다. 본문+첨부 불변409, 첨부만 변경1회, 성공 receipt 재생 때 파일 재검사를 추가하지 않습니다. [writer 상세](TASK_MANAGEMENT.md#task-management-attachment-selection).
- 전송 복구: 시작 응답 불명은 자동으로 새 ID를 만들지 않습니다. ID가 확인된 청크/완료는 사용자 명시 클릭으로 같은 ID·offset·파일을 재확인합니다. 임시 삭제도 별도 확인 클릭만 사용합니다. 삭제 결과 불명은 원 ID를 보존하며, 명시적 화면 선택 제외를 제공하되 서버 삭제 성공으로 표시하지 않습니다.
- 다운로드: 업무별 목록→청크→전체 크기/해시→현재 업무 참조 재확인 후 파일을 제공합니다. 다른 업무의 참조가 남아 있다는 이유로 현재 업무에서 해제된 파일을 내려받지 않습니다.401/403·접속 불일치·페이지 종료/캐시 복귀는 오래된 동작과 지연 응답을 폐기합니다. 서버는 매 요청 권한을 별도로 검사합니다.
- HTTPS/localhost: Web Crypto의 전체 SHA256 검증이 가능한 접속에서만 파일 선택·전송·다운로드를 활성화합니다. 일반 HTTP 서버 IP의 다른 PC 접근에서는 안내와 비활성화를 유지합니다. 업무/첨부 조회와 생략한 기존 첨부 유지는 가능하며 브라우저 보안 설정을 완화하지 않습니다.

[검사 명령·정확한 실행 범위](../Tests/TaskWeb.Tests/README.md#task-web-t3-consumer-checks)를 따릅니다. 실제 소유 MySQL/HTTP와 브라우저를 사용했지만 공유 DB·운영 파일 권한·HTTPS 배포·실계정/두 PC·취소/연장 ACK를 검증한 것은 아닙니다. WinForms 일반수정도 [첨부 선택 화면](TASK_MANAGEMENT.md#task-management-attachments-ui)으로 연결했습니다.

## 현재 연결: 취소·마감 연장

기존 조회·공통 쓰기와 `REMOTEWORK_ENABLE_TASK_LIFECYCLE_DRAFT=1`에서 `/tasks/<id>/lifecycle/<action>`의 GET/POST를 제공합니다. action은 `cancel`, `request-extension`, `approve-extension`, `reject-extension`, `withdraw-extension`입니다. [확정 D/E 정책](TASK_LIFECYCLE.md)을 사용하며 새 상태나 자동 제출을 추가하지 않습니다. 현재 담당자 또는 지정 관리자에게 가능한 동작만 상세에 표시하고, 서버는 직접 URL 접근과 실행에서도 현재 관계를 검사합니다.

초안은 처음 연 업무·배정 버전과 선택한 연장 신청 ID, 로그인 접속, 행동, 목록 필터를 서명해 고정합니다. 입력 확인은 기존 `prepare_lifecycle`의 권한·버전·상태·KST 날짜 검사를 거친 뒤 W1 확인폼을 만들며, 실행은 API와 같은 `execute_lifecycle`을 사용합니다. 선택한 신청 ID도 원문 요청 지문에 포함해 다른 신청에 같은 키를 재사용할 수 없습니다. 자기 연장 판단은 금지하고 승인 전에는 원래 기한을 유지합니다.

통합 ACK가 없으면 입력 화면에서 연결 필요를 안내하고 확인/실행을 차단합니다. 브라우저에서 강제로 POST해도 기존503을 유지하며 새 키·업무 변경·감사·receipt를 만들지 않습니다. 응답이 불명확하면 같은 키와 본문의 결과를 확인하고, 현재 권한403은 성공/실패를 추정하지 않은 채 기존 요청을 보존합니다. 저장된 성공 뒤의 최신 상세 GET 실패를 저장 실패로 바꾸지 않습니다.

쓰기 옵션을 끈 뒤에도 기존 공통 쓰기와 `REMOTEWORK_ENABLE_TASK_LIFECYCLE_RESULT_READS_DRAFT=1`을 명시하면 `/tasks/write/result`에서 보관된 취소·연장 결과를 확인할 수 있습니다. 실행 경로·새 키·ACK를 열지 않으며 `not_recorded`여도 재전송 버튼을 제공하지 않습니다. 열린 확인폼의 원래 로그인 바인딩과 W1 보관 기간을 유지하고, 닫힌 폼을 자동 복원하는 저장소는 제공하지 않습니다.

## 현재 연결: 수정·재배정·관리자 변경

[팀장 확정 정책](TASK_MANAGEMENT.md)을 같은 API 실행 함수로 재사용합니다. 상세에는 현재 지정 관리자에게만 진행전의 **업무 수정·담당자 변경·관리자 변경**, 진행중/반려완료의 **관리자 변경**을 표시합니다. 제출완료·승인완료·취소된 업무에는 관리 링크가 없습니다. 역할만 관리자이거나 본인 담당 업무인 것은 변경 권한이 아닙니다. 직접 URL을 열어도 현재 지정 관리자 관계를 서버에서 검사합니다.

GET은 현재 업무→배정→관리자→사용자를 잠가 변경 전 정보와 두 버전을 같은 시점에서 읽고, 현재 로그인·action/target·버전·복귀 필터가 고정된 별도 서명 초안을 만듭니다. 후보 검색·페이지 이동은 입력과 선택 및 **처음 버전**을 유지하며 저장하지 않습니다. 새 버전으로 자동 교체하지 않으므로 다른 변경이 생기면409로 다시 조회하도록 안내합니다. 최신 정보로 다시 열기는 입력 초기화를 명시합니다. POST는 CSRF·지원 필드/중복·현재 권한을 다시 검사하며, 입력 확인 뒤에만 W1 키와 불변 실행 확인폼을 준비합니다.

재배정은 기존 공통 후보의 활성 직원/관리자 1명,관리자 변경은 활성 관리자 최소1명을 사용합니다. 검색 밖 선택과 사용 불가 기존 관리자를 화면에 남겨 사용자가 직접 해제하도록 합니다. 등록자/본인 자동 재포함은 없으며 검토자 관계도 변경하지 않습니다. 이 화면의 선택100명 한도는 업무/API의 전역 최대 정책을 추가한 것이 아닙니다. 최종 실행은 원래 버전·상태·취소·과거 수락/제출 자료·현재 후보·KST 날짜를 기존 함수에서 재검사하고 업무/관계·감사·receipt를 한 트랜잭션에 저장합니다.

관리자 변경으로 자신을 제외한 최초200은 성공으로 표시합니다. 이후 상세 권한이 없으면 상세 링크를 제공하지 않습니다. 성공 응답이 유실된 뒤 현재 권한403이면 성공/실패를 추정하거나 재전송하지 않고 기존 확인 티켓을 보존해 현재 관리자에게 확인하도록 안내합니다. 현재 권한이 없는 동안 변경 전 정보도 다시 노출하지 않습니다. 웹은 열린 확인폼만 복구하며 닫힌 폼의 요청 저장소는 제공하지 않습니다.

| 3번 cookie 첨부 목록·시작/청크/완료·다운로드·discard | 웹 선택/명시 전송·해시 확인 다운로드·임시 삭제 연결. 같은 로그인과 현재 업무 참조를 재검사 |

업무 웹 등록·수정 폼은 선택 `attachment_ids`를 원래 순서로 서명합니다. 전송 바이트를 업무 POST에 섞지 않으며, 공개 cookie/CSRF 제공부를 소비합니다. 기존 첨부 생략 동작과 명시적 W1 결과 복구를 유지합니다. 공통 DELETE는 C#에서, 웹은 합의된 명시 discard POST를 사용합니다.

## 현재: 업무 상세의 취소·연장 대기 정보

기존 lifecycle 개발 옵션이 켜진 경우 업무 상세에 **업무 취소 정보**와 **마감일 연장 대기**를 표시합니다. 취소는 사유/UTC 일시와 기존 업무 상태를 구분하고,대기는 신청 당시/희망 마감일·신청 사유/UTC 일시를 표시합니다. 희망일을 승인된 새 마감일로 표시하지 않으며 업무 정보의 현재 기한·5상태는 유지합니다. 현재 배정의 pending만 사용하고 이전 배정·종료된 요청을 대기로 표시하지 않습니다. 사실이 없는 카드는 표시하지 않습니다.

동일2번 API 문맥을 `read_lifecycle_context`로 추출해 기존 JSON envelope·필드와 query 검증을 유지했습니다. 웹은 `read_lifecycle_detail`에서 공통 인증 재검사→현재 업무/배정/관리자/사용자→취소/대기 잠금 읽기와 기존 요약 형식을 재사용합니다. MySQL REPEATABLE READ에서는 같은 트랜잭션 안의 일반 SELECT도 이전 인증 조회의 snapshot을 사용할 수 있어,잠금 뒤 일반 `get_task`로 다시 읽어 섞지 않고 잠근 현재 행으로 상세를 만듭니다. 모델/추가 정보는 기존 lifecycle opt-in 뒤에만 연결되며 query-only에서는 기존 상세를 유지합니다. 읽기 실패를 기본 정보만의 부분 성공으로 숨기지 않습니다.

같은 이유로2번의 `ensure_not_cancelled` 고정 SELECT에도 `FOR UPDATE`를 추가했습니다. 현재 권한/부모/사용자 잠금 뒤 취소 마커를 현재 값으로 검사하는 기존 계약을 지키기 위한 보완입니다. 새 정책·쓰기·ACK를 추가하거나3번 제품을 수정하지 않았습니다. 그 뒤 PR52로3번의 guard/대기 facts 소비 코드가 병합됐으며,같은 배포의 소비·경합 검증과 통합 ACK 설치는 별도입니다. 이번 helper 보완만으로 실제3번 연결이 끝났다고 기록하지 않습니다.

취소/대기 사유는 이스케이프하고 줄바꿈을 표시합니다. 내부 버전·ACK 값은 화면에 노출하지 않으며, 현재 취소·연장 동작은 위 별도 실행 조건에서 제공합니다. 기본off·API DTO/DB·현재 권한·성공 복구와 연결 확인 전503을 유지합니다. 아래85개 결과와 브라우저 기록은 읽기 상세를 연결했던 당시 검증입니다.

이번 상세 후속의 소유 MySQL 실행은 **85통과·실패/생략0,186.70초**입니다. 기존62개+상세20개+현재 취소 guard3개이며 앞선62개 실행을 중복 합산하지 않습니다. 인증 조회 뒤 독립 트랜잭션의 재배정/취소/관리자 회수,현재 버전8에도 취소409,정보/상태·기한 보존·이스케이프·오류/API/무효과를 확인했습니다. 물리DDL 불변·schema1·소유 DB/프로세스/runtime 정리와 Release 경고0/오류0도 확인했습니다. 일부 기존 lifecycle 성공 변경은 여전히 TESTING·실제 results off·명시 대역이며 실제3번 연결 성공이 아닙니다. [재현과 근거](../Tests/TaskWeb.Tests/README.md)를 따릅니다.

별도 합성 브라우저에서 대기·취소 상세와 사유 줄바꿈/기존 기한·상태 표시를 직접 확인했습니다. 처음 확인한 경로 int→기존 문자열 helper 경계의400은 웹에서 정규 문자열로 전달하도록 보완한 뒤 재확인했습니다. 중간 환경 전환으로 중단된 검사/미리보기는 최종 완료 검사와 구분합니다. 실제 공유 계정·두PC·작은 폭/모바일과3번 실제 소비·웹 쓰기는 미실행입니다.

## 실행과 담당 경계

공통 서버의 기존 `REMOTEWORK_ENABLE_TASK_QUERY_DRAFT=1`을 명시적으로 켜고, 공통 웹 로그인 후 `/tasks`로 이동합니다. 기본 off에서는 웹 두 경로와 기존 업무 API가 등록되지 않으며 업무 모델도 import하지 않습니다. 새 운영 옵션·테이블·자동 초기화·시드 경로를 추가하지 않았습니다. 업무 개발 DB는 기존 [조회 안내](TASK_QUERIES.md)와 실제 002/004/006/009의 적용 조건을 따릅니다. 사용자 서버·공유 DB를 이 화면 실행만으로 변경하지 않습니다.

이번에는 2번의 `features/tasks`·전용 template/CSS만 변경했습니다. 공통 `web.py`, registry, `base.html`, `app.css`는 수정하지 않았습니다. **1번 PR59의 공통 메뉴 `/features/tasks`는 조회 기능이 등록되어 있으면 `/tasks`로 이동합니다.** 기본 off에서는 준비 화면입니다.2번이 공통 파일을 직접 수정한 것이 아니며 결과물/취소·연장 쓰기 권한까지 개방하는 변경도 아닙니다.

허용 query는 scope(own/managed), 선택적 status(5값), include_cancelled(true/false)뿐입니다. 알 수 없는 키·중복 키·빈 상태·다른 값은400입니다. 업무 ID는 기존 signed BIGINT 범위를 검사합니다. 제목·이름·내용은 Jinja 이스케이프를 유지하고 내용의 줄바꿈만 전용 CSS로 표시합니다.

공통 cookie 인증·매 요청 현재 사용자/관계 검사·no-store 응답을 재사용합니다. API의 Bearer 인증과 웹 cookie 인증을 혼합하지 않습니다. 관리자의 전체 업무·협업·과거 담당자 권한을 확대하지 않습니다. 정상200의 빈 목록만 빈 안내를 표시하며, 인증 종료는 공통 로그인 이동,403/404/503/500은 공통 오류 화면으로 구분합니다. DB 오류를 빈 성공이나 샘플로 대체하지 않습니다.

조회 화면에는 별도 JS·타이머·실시간 구독·로딩 대역을 넣지 않았습니다. 화면 이동은 브라우저의 기본 로딩을 사용합니다. 열린 페이지의 원격 로그아웃 즉시 삭제까지 보장하지 않으며 다음 요청에서 현재 인증을 검사합니다. query-only에서는 읽기만 제공하고 등록·수락·재작업·수정/재배정/관리자 변경·취소·연장은 위 명시 옵션과 기존 실행 조건을 따릅니다. 제출·파일 제공·판단은3번 소유이고, 업무 웹의 파일 전송·저장은 위 PR68 소비 절의 opt-in과 조건을 따릅니다. PR52의 코드 제공과 같은 배포의 integrated ACK·실제 검증은 [lifecycle 안내](TASK_LIFECYCLE.md)의 남은 경계를 구분합니다.

## 검증

[재현 가능한 소유 MySQL 실행기](../Tests/TaskWeb.Tests/README.md)에서 실제 공통 로그인·cookie·Flask 요청과 새 MySQL의 raw002/004/006/009를 사용해 **31개 검사 통과(66.75초)**를 확인했습니다. 현재 본인/지정 관리자·역할/관계 회수,5상태/취소,빈/없는/권한 없음,query/ID,인증/CSRF/채널 분리,이스케이프,대량 정렬,읽기/거부된 쓰기의 DB 무효과,503/500·물리DDL/schema1 보존과 소유 자원 정리를 포함합니다. 검사 대상을 지정하지 않은 무DB 실행의1통과·30생략은 이 실제 실행과 합산하지 않습니다.

별도 소유 MySQL·합성 계정으로 브라우저의 로그인→관리 목록7건→반려 필터2건→취소 상세→같은 목록 조건 복귀를 직접 확인했습니다. 본문 줄바꿈·취소/5상태 분리도 확인했습니다. 이 미리보기는 실제 공유 계정·두 PC·작은 폭/모바일·전체 WinForms 연속 흐름 검증이 아닙니다. 공통 메뉴 연결,웹 쓰기/결과물 진입,실제 3번 lifecycle 경합은 실행하지 않았습니다.

## 후속: 마감일 연장 신청함 읽기

기존 조회 옵션에 더해 `REMOTEWORK_ENABLE_TASK_LIFECYCLE_DRAFT=1`인 서버에서는 업무 목록의 **마감일 연장 신청함** 링크로 `/tasks/extension-requests`에 진입합니다. lifecycle off에서는 경로와 링크가 없고 query만으로 lifecycle 모델을 새로 import하지 않습니다. 새 별도 운영 옵션·ACK를 추가하지 않습니다. 공통 쓰기를 켜거나 integrated ACK를 설치하지 않아도 준비된009의 허용된 내역을 읽을 수 있으며 실제 변경503은 유지합니다.

기존 API의 요청함 조회를 `list_extension_requests`로 추출해 API와 웹이 같은 `authenticated_transaction`의 현재 사용자 재검사·scope/status 검증·현재 배정/신청자/지정 관리자·schema 검사·요청 번호 역순을 사용합니다. API 경로·응답 필드는 그대로입니다. 내 신청은 현재 본인 배정+본인 신청, 관리 업무의 신청은 현재 지정 관리자+현재 배정 revision의 기존 범위입니다. 과거 배정/다른 사용자/협업으로 권한을 넓히지 않습니다.

신청 상태는 업무5상태와 별개인 **대기·승인·반려·철회·취소**(`pending/approved/rejected/withdrawn/cancelled`)와 전체로 필터합니다. 허용 query는 scope/status뿐이며 상태·중복/미지원 값은400입니다. 날짜·신청/처리 사유·신청/업무 번호와 현재 업무 상세 링크를 표시합니다. 일시는 기존 UTC 값을 명시하고 사유를 이스케이프/줄바꿈 표시합니다. 업무 상세는 별도 기존 권한 검사를 다시 거치며 신청함 열람만으로 새 권한을 받지 않습니다. 신청·승인·반려·철회·취소 버튼,새 요청 상세 API·새 DTO/DB 필드는 없습니다.

별도 합성 브라우저에서 관리 내역5건→대기1건 필터→현재 업무 상세→브라우저 뒤로가기를 확인했습니다. 처음 미리보기 fixture의 배정/연장 행 flush 순서를 보완한 뒤 확인했으며 제품 FK를 완화하지 않았습니다. 중간 실행이 작업 입력 전환으로 중단된 검사와 최종 완료 검사는 구분해 기록합니다. 실제 공유 환경·두PC·작은 화면·3번 차단 소비 완료를 뜻하지 않습니다.

최종 소유 MySQL 검사는 **62통과·실패/생략0,136.57초**입니다. 기존 업무웹31·새 신청함25·기존 lifecycle6의 합이며 앞선31검사를 중복 합산하지 않습니다. 마지막6개의 성공 변경은 TESTING·실제 results off·명시 대역이고 실제3번 소비 검증이 아닙니다. 신청함25개는 현재 관계/배정·상태·스키마/인증·무효과·이스케이프와 기존 API 응답 보존을 포함합니다. 재현 명령과 근거는 [전용 안내](../Tests/TaskWeb.Tests/README.md)를 따릅니다.

게시 전 수신한 alpha `395d70d`의 PR55/56 변경은 보존해 합쳤으며 결합 소스 `129cc1c`에서 **동일62검사 재통과(138.70초)**·물리DDL/schema1 보존·소유 자원 정리·Release 경고0/오류0을 확인했습니다. 고유 검사 수를124개로 늘리지 않으며 다른 담당 지문 제품/실물·공유 적용을 이번 업무웹 검사로 검증했다고 기록하지 않습니다.
