현재 Results 구현은 로컬 시연용이며 실제 로그인 사용자·업무·서버·MySQL과 미연결입니다. HistoryControl은 기본 예시 화면이며 저장 기록 조회는 미구현입니다. 로컬 작업본이 있다는 설명은 팀장 alpha에 해당 코드가 게시됐거나 모든 폼의 적용이 끝났다는 뜻이 아닙니다.

**제출 회차는 사람이 선택하지 않습니다. 최초 제출은 1차, 반려 후 재제출 저장에 성공하면 2차·3차…로 자동 증가하며 업무상 최대 회차는 두지 않습니다.** 반려 처리·창 열기·취소·저장 실패·승인 자체로 회차를 올리지 않습니다. 제출 회차와 담당자 배정 차수는 별개입니다.

## 1번 담당자에게 필요한 연결


내 폼 → 기존 공통 통신·로그인 확인 → 제출·검토 처리 → 서버 DB·첨부 저장

1. **로그인 정보 연결:** 현재 사용자 ID·이름·직원/관리자 구분을 가져오는 코드 위치와 사용 예시를 공유해주세요. 접속이 바뀌거나 로그아웃하면 이전 사람의 결과·진행 요청을 정리하는 기존 방법도 연결합니다.
2. **저장 연결:** 제출 내용·업무 상태·처리 기록이 함께 저장되도록 공통 저장 코드를 연결합니다. 예를 들어 제출 내용만 저장되고 업무 상태는 진행중으로 남는 일이 없어야 합니다. DB·첨부파일·처리 기록에 이미 제공하는 기능은 위치와 사용 방법을, 미구현인 부분은 제공 범위와 연결 시점을 알려주세요.
3. **검토 담당 연결:** 직원의 제출물을 검토할 사람과 관리자 본인 제출물을 검토할 상위 담당자를 실제 사용자 ID로 연결합니다. 본인 제출물의 자기 승인·반려는 서버에서 막습니다. 검토자 지정/변경·부재/비활성화·조회 가능 범위는 2번·팀장과 함께 정해야 합니다.

1번의 기존 W1 회신은 확인했습니다. 관리자용 admin_transaction을 직원 제출에 그대로 적용하지 않으며, 일반 transaction만으로 권한 확인이 끝났다고 처리하지 않습니다. 직원 쓰기 재인증 지원과 중복 요청·응답 유실 처리 지원은 **미구현/협의 필요**로 구분합니다. 공통 인증·저장 도구를 3번에서 중복 구현하지 않습니다.

첨부 저장 공통 기능의 존재를 가정하지 않습니다. 서버 저장 위치·업로드/다운로드·접근 검사·파일 실패 처리는 3번 구현과 공통 지원의 경계를 확인합니다. 제출·첨부·회차·검토 기능 자체는 3번이 구현합니다. 새 테이블·파일 저장 기준·공통 DB 변경이 필요하면 1번 검토 후 진행하며 예약된 002·003 번호나 공유 DB를 임의로 변경하지 않습니다.

## 2번 담당자에게 필요한 연결

2번 업무 정보 → 내 결과물 목록·상세  
내 제출·승인·반려 처리 → 2번 업무 상태와 같은 저장 결과 반영  
2번 업무 변경 기록 → 관리자 5번 업무 이력

1. **업무 정보 연결:** 업무 번호·제목·담당자·상태를 가져오는 기존 서비스의 코드 위치와 사용 예시를 공유해주세요. 서버 GET에 있는 담당자 ID와 현재 C# 화면 모델의 필드는 구분하며, 없는 값을 이름으로 추정하거나 기존 조회 모델을 임의 변경하지 않습니다.
2. **상태 연결:** 제출→제출완료, 승인→승인완료, 반려→반려완료가 업무 메뉴와 결과물 메뉴에 동일하게 반영돼야 합니다. 1번의 저장 방법과 함께 실제 상태를 바꾸는 위치·담당, 처리 후 두 화면의 재조회 방식을 정해야 합니다. 화면에서 상태를 따로 두 번 저장해 한쪽만 성공하는 방식은 사용하지 않는 안을 제안합니다.
3. **제출 조건 연결:** 반려 후 재제출 시점, 마감 후 제출 허용 여부, 연장 승인 전후 제출 조건, 담당자가 바뀌었을 때 이전 제출물·검토 대상의 처리 기준을 공유/협의해주세요. 현재 로컬은 진행중 최초 제출과 반려완료 재제출을 허용하지만 실제 서버 조건까지 합의된 것은 아닙니다.
4. **업무 이력 연결:** 업무 생성·담당자 변경·상태 변경 기록의 저장 위치·제공 방법을 공유해주세요. 아직 없다면 기록 주체·항목·조회 방법부터 함께 정합니다. 관리자 5번 이력에서 제출·승인·반려 기록과 함께 표시합니다. 공통 감사 기록에 넣을 정보와 화면에 표시할 상세 정보는 구분해서 1번과 확인합니다.

기존 5개 상태와 소문자 표현, 업무·사용자 ID 형식, 공통 통신과 GET 읽기 계약은 재사용합니다. task_managers는 업무 조회 관계이며 제출 승인 권한으로 자동 사용하지 않습니다. 상위 검토자에게 전체 업무 조회를 허용하는 방식으로 현재 상세403을 우회하지 않습니다.

## 기존 W3 요청에 대한 현재 회신

새 질문 번호를 늘리지 않고 2번의 W3-01부터 W3-07 및 기존 M3-01부터 M3-08에 이어서 확인합니다. 아래 제안·미정 항목은 **공동 확인 완료가 아닙니다.**

| 기존 항목 | 3번 현재 구현·제안 | 함께 정할 내용·확인 담당 |
|---|---|---|
| W3-01 / M3-01·02 | 배정→진행전, 명시 수락→진행중 원칙 유지. 등록·수락은 2번 범위 | 초기 저장값·같은 수락 재요청·시작 전/마감 후/반려 후 수락 예외는 협의 필요. 2번·3번, 공통 지원 1번 |
| W3-02 / M3-01·02 | 제출/판단 기록·업무 상태·성공 처리 기록을 함께 저장하는 방향 제안 | 배정/업무 버전 검사·증가·잠금 순서·중복·응답 유실은 실제 서버 지원 전. 1·2·3번 공동 |
| W3-03 / M3-04·05 | 로컬 반려완료에서 다음 회차 재제출. 과거 제출·판단 보존, 자동 진행중 복귀 없음 | 5상태별 수정·재배정·취소 허용 표, 재작업 시작 행동·담당은 미정. 2·3번 |
| W3-04 / M3-05·08 | 회차 상한 없이 자동 증가. 실제 제출 ID·업무/배정 참조는 서버 미구현 | 제출 모델·API·DB안은 3번 작성, 업무/배정 접점은 2번, FK·보존·DB 변경은 1번 검토. 기존 GET 유지/별도 준비 정보는 협의 필요 |
| W3-05 / M3-03·08 | 자기 판단 금지와 관리자 본인 제출의 상위 검토 원칙 유지 | 검토자 지정 관계·접근 필드/경로·비활성화 처리는 미정. 팀장·1·2·3번 |
| W3-06 / M3-06 | 날짜 표현과 기록 시각 UTC 기준 유지. 마감 자동 제출 제외 | 업무 시간대·마감 시각·상태별 연장·마감 후 직접 제출·제출/연장 경합은 미정. 연장 구현 2번, 제출 조건 3번, 공통 저장 1번 |
| W3-07 / M3-07 | 모든 정식 제출은 별도 요청 버튼 없이 필수 검토 대상으로 연결하는 방향 제안 | 별도 수동 요청의 의미·자동 검토 요청 도입 여부/시점/중복 처리는 미정. 자동 결과 제출은 추가하지 않음 |

2번의 행동별 API·쓰기 준비 정보·사용자 후보 조회 제안도 확인했습니다. 문서의 새 경로가 이미 호출 가능한 API라고 가정하지 않습니다. 실제 API/DTO/DB 경로·권한·오류는 합의와 구현·검증 후 연결합니다.
