## W3-02 / M3-01·02 — 제출·판단·상태의 저장 책임

**3번의 제출/판단 서버 서비스가 제출본·판단·업무 상태·화면용 처리 이력·최소 성공 감사·receipt를 같은 DB 세션에서 저장하는 안을 제안한다.** 2번 화면이 제출 성공 후 별도 상태 변경 요청을 보내는 이중 저장은 만들지 않는다.

조립 순서 제안:

1. 기존 authenticated_transaction으로 guard→현재 수행자→현재 접속을 잠금 확인한다. 같은 guard를 사용하는 2번의 수락/재배정/연장과 직렬화한다. 부모 업무→현재 배정→관계→제출/판단 순서로 잠금을 맞추고 사용자 잠금은 공통 ID 오름차순을 따른다. 최종 자식 잠금 순서는 1·2·3번 공동 확인 전이다.
2. 행동에 등록한 authorize 함수가 현재 소유/명시적 검토 관계를 재확인하고 정확히 True를 반환한다. 메뉴 활성화·업무 조회 성공·이름 일치를 권한으로 사용하지 않는다.
3. perform_once의 최초 mutate 안에서 expected_assignment_revision, expected_row_version, 제출 대상/최신 회차·상태·마감 조건을 확인한다. 정상 재응답 전에 과거 expected 버전을 검사해 재응답을 충돌로 바꾸지 않는다.
4. 성공한 새 행동에서만 업무 row_version을 한 번 증가시키고 updated_at을 서버 UTC로 갱신한다. 제출은 새 회차·불변 제출본과 submitted를, 판단은 해당 제출본의 판단과 approved/returned를 함께 저장한다. 배정 revision은 2번의 실제 재배정에서만 바뀌며 제출/판단 때문에 증가시키지 않는다.
5. 실패·rollback이면 제출 회차·업무 상태·판단·성공 이력·성공 receipt가 남지 않는다. 같은 키/같은 본문은 기존 결과이며 중복 회차/판단을 만들지 않는다. 응답 유실은 같은 접속·action/target/key로 공통 결과 조회 후 재확인한다. 새 키로 무조건 재전송하지 않는다.

확인된 공통 오류는 401 AUTH_REQUIRED, 403 FORBIDDEN, 404 TASK_NOT_FOUND, 400 INVALID_INPUT, 409 TASK_ASSIGNMENT_CHANGED/TASK_VERSION_CONFLICT/IDEMPOTENCY_KEY_REUSED, 410 IDEMPOTENCY_KEY_EXPIRED 등이다. 상태/제출 대상/첨부 전용 오류의 세부 code는 아래 API 제안과 함께 1번 검토가 필요하다. DB/통신 실패를 빈 목록이나 성공으로 표시하지 않는다.

## W3-03 / M3-04·05 — 상태별 허용 표

**아래 표 전체는 서버 정책 제안이며 로컬 시연 조건을 서버에 이미 적용한 표가 아니다.** ‘보류’는 구현 전 공동 확인한다는 뜻이다. 취소를 표현할 새 상태 코드는 기존 다섯 상태에 임의 추가하지 않는다.

| 현재 상태 | 최초 제출 | 재제출 | 승인·반려 | 제목·본문 수정 | 재배정 | 마감 변경 |
|---|---|---|---|---|---|---|
| not_started | 거절 | 거절 | 거절 | 현재 admin+지정 관리자 허용안 | 제출 전 현재 admin+지정 관리자 허용안 | 2번 날짜 변경 규칙 협의 |
| in_progress | 현재 배정 당사자, 기존 제출 없는 경우 허용안 | 기존 반려 제출이 있고 별도 재작업 시작을 도입할 경우 보류 | 거절 | 제출본 생성 전 허용안, 변경 시 row_version 증가 | 진행 중 재배정은 보류. 허용한다면 새 revision과 이전 소유 보존 필요 | 2번 연장 승인 서비스에서만 반영하는 안 |
| submitted | 거절 | 거절 | 최신 제출본의 현재 명시적 검토자만 허용안 | 제출본 기준 변경을 막기 위해 거절안 | 검토 중 대상 변경을 막기 위해 거절안 | 검토 중 연장 보류 |
| approved | 거절 | 거절 | 재판단 거절안 | 최종 완료 보존을 위해 거절안 | 거절안 | 거절안 |
| returned | 최초 제출 아님 | 현재 배정 당사자, 최신 반려 제출을 보존하고 다음 회차 허용안 | 기존 판단 수정 거절안 | 결과 설명·첨부는 다음 제출본에 작성. 업무 제목·본문 변경은 보류 | 이전 제출 소유·차수/FK 정책 확정까지 보류 | 연장 승인 후 새 기한 적용안 |

과거 제출 설명·첨부·제출자·당시 배정 참조·판단은 덮어쓰지 않는다. 업무의 일반 수정/취소/재배정 구현은 2번이며, 3번의 승인권을 task_managers 조회 관계로 대신하지 않는다.

## W3-04 / M3-05·08 — 제출 참조와 API·DTO 초안

**이 절의 필드·경로·테이블 이름은 3번 제안이며 호출 가능한 API나 승인된 DDL이 아니다.** 기존 업무 GET/TaskSummary/TaskDetail/CheckedInput은 변경하지 않는다. 별도 write-context에 이미 제공하는 배정 차수·버전을 사용하고, 실제 저장 직전에 서버가 재검사한다.

| 개념 | 필요한 필드 제안 | 필수/NULL·제약·책임 |
|---|---|---|
| 제출본 submissions | submission_id, task_id, assignment_revision, round_no, submitter_id, description, submitted_at | 업무/제출 ID는 양의 signed BIGINT→JSON 문자열 제안. task_id와 배정 revision은 현재 배정의 복합 참조. 제출자·UTC 시각은 서버가 결정. 설명은 공백만 허용하지 않는 안 |
| 회차 | task_id와 round_no의 유일성 | 같은 업무에서 마지막 성공 회차+1을 업무 잠금 안에서 할당하는 안. 재배정만으로 회차를 초기화하지 않는 안은 2번 확인 필요. 업무상 상한은 없으며 DB/C# 정수의 기술 범위는 1번 타입 검토; 로컬 int 형식을 무한 정수로 주장하지 않음 |
| 첨부 metadata | attachment_id, submission_id 또는 업로드 준비 참조, 원본 표시명·크기·저장 키 | 클라이언트 절대 경로를 서버 저장 경로로 사용하지 않음. 실제 파일 크기/이름·업로드 소유를 서버에서 확인. 제출 연결 전 임시 단계의 NULL·고아 자료 정리는 별도 확정 |
| 판단 decisions | decision_id, submission_id, reviewer_user_id, decision, reason, reviewed_at | 제출 ID당 성공 판단 1건인 안. 반려 사유 필수·승인 의견 선택. 검토자·UTC 시각은 서버에서 결정. 판단 수정은 새 행동 협의 전 제공하지 않음 |
| 명시적 검토 관계 | 업무/배정·검토자 ID·관계 revision·변경 수행자/시각 | task_managers와 별개. 제출 당시/현재 관계, 변경 후 기존 제출 영향은 W3-05의 안으로 공동 확인 |

FK는 실제 업무/배정·공통 사용자·제출/첨부/판단을 참조하고 사용자·배정 변경으로 과거 제출/판단을 cascade 삭제하지 않는 방향이다. 과거 작성자 표시/탈퇴·비활성화 보존 정책과 실제 제약은 1번 검토 대상이다. 예약 002·003·004를 재사용하거나 새 migration 번호를 임의 확정하지 않는다.

| 제안 경로 | 요청·결과 초안 | 권한/상태·연결 |
|---|---|---|
| POST /api/v1/tasks/{task_id}/submissions | expected_row_version 문자열, expected_assignment_revision 정수, description, attachment_ids 배열 → 201 최소 결과 | 현재 배정 당사자 + W3-03/06. round_no·submitter·상태·시각은 요청에서 선택하지 않음 |
| POST /api/v1/submissions/{submission_id}/decisions | expected_row_version, expected_assignment_revision, decision=approved/returned, reason → 200 최소 결과 | 현재 활성 명시적 검토자·자기 판단 금지·최신 submitted. 승인/반려는 개별 등록 action으로 구분하는 안 |
| GET /api/v1/tasks/{task_id}/submissions | 회차·제출 상태·시각·설명·허용 첨부 목록 | 본인/허용된 관리·명시적 검토 관계의 최소 범위를 서버에서 재검사하는 안. 검토자만을 위해 업무 상세 전체 권한을 확대하지 않음 |
| GET /api/v1/tasks/{task_id}/history | 아래 업무 이력 필드·필터·최신순 목록 | 별도 이력 조회 권한 검사가 필요. 관리자라는 이유만으로 전체 업무 이력을 열지 않음 |

제출 요청 예시(합성 자료·제안):

```json
{
  "expected_row_version": "7",
  "expected_assignment_revision": 2,
  "description": "검토 의견을 반영한 결과 설명",
  "attachment_ids": []
}
```

제출 성공 data 예시(공통 envelope 안·합성 자료·제안):

```json
{
  "task_id": "42",
  "submission_id": "105",
  "assignment_revision": 2,
  "round_no": 2,
  "row_version": "8",
  "task_status": "submitted",
  "updated_at": "2026-10-17T09:00:00Z"
}
```

`submission.submitted`(target=task_id), `submission.approved`/`submission.returned`(target=submission_id)는 **새 action 이름 제안**이다. PR #17의 register_write_action을 앱 초기화에서 사용하며 해당 현재 권한 함수와 최소 결과 필드를 명시한다. 위 성공 예시 필드는 허용 필드 후보일 뿐 현재 제출 행동이 등록됐다는 뜻은 아니다. 각 action은 필수/타입도 자체 검사한다. 본문·파일·이름·사유·토큰을 receipt 결과에 넣지 않는다. 기존 task.accepted 등의 action을 제출에 재사용하지 않는다. 실제 기능 라우트·등록 위치/feature flag는 1번 registry와 대조 후 제안한다.

## W3-05 / M3-03·08 — 검토자 지정·변경·최소 열람

1번의 새 협의 제안을 **검토 기준안으로 수신**한다. 공동 승인으로 처리하지 않는다.

- 지정 주체는 현재 활성 admin이면서 해당 업무 지정 관리자, 지정 대상은 제출자와 다른 활성 admin 1명인 안. ‘상위 검토자’의 실제 조직 관계·지정 권한은 팀장이 확인한다. 단순히 다른 admin을 지정했다는 이유만으로 상위 관계가 충족됐다고 처리하지 않는다.
- 직원·관리자 본인 제출 모두 서버에서 제출자 ID와 판단자 ID가 같으면 403으로 거절한다. 이름 비교나 UI 버튼 비활성화만으로 처리하지 않는다.
- 제출 시 유효한 검토 관계가 없으면 임의 admin에게 배정하지 않는 안. 제출 차단 또는 제출 후 지정 대기의 최종 선택은 팀장·2번·3번 공동 확인 전이다.
- 비활성·강등·권한 회수된 검토자는 판단할 수 없다. 부재/비활성화 시 자동 다른 사람으로 대체하지 않고 권한 있는 지정 주체의 명시 변경과 변경 이력을 요구하는 안이다.
- 검토자 변경은 원래 제출자·제출 내용·기존 판단을 바꾸지 않는다. 미판단 제출의 검토 관계 변경 시 관계 revision과 업무 row_version 증가·성공 이력을 함께 기록하는 안이다. 이전 검토자의 열린 창은 저장 시 관계/버전 재검사로 차단한다.
- 검토 전용 최소 조회는 업무 ID·제목·당시 제출자 표시·회차·설명·첨부·제출 시각·판단 상태/허용 의견만 제공하는 안이다. 전체 업무 GET의 현행 403을 풀지 않는다. 과거 회차·판단 후 열람·담당자 변경 이후 범위는 별도 확인한다.

## W3-06 / M3-06 — 마감·연장과 동시 제출

다음은 **공동 확인용 보수적 제안**이며 아직 서버/화면에 적용하지 않는다.

- 업무 기준 시간대 Asia/Seoul, 마감일 당일 포함, 다음 날 00:00 이전까지 제출 허용안을 제시한다. DATE 열은 YYYY-MM-DD 그대로 보존하고 비교할 때만 서버의 명시적 업무 시간대를 사용한다. PC 시계·UTC 자정으로 마감 의미를 바꾸지 않는다.
- 시작 전/유효 마감일 경과 후 직접 제출은 거절하고, 연장 승인으로 유효 due_date가 바뀐 뒤 제출하는 안이다. 마감 후 제출 허용을 원하면 별도 예외 정책을 합의해야 한다.
- 연장 신청은 현재 배정 당사자가 in_progress/returned에서 하는 안. 신청 접수만으로 due_date를 바꾸지 않는다. submitted/approved의 신청·판단은 미정으로 보류한다.
- 연장 판단자·관리자 본인 신청의 상위 판단자는 2번·팀장 권한안과 W3-05를 대조한다. admin이라는 이유로 자동 승인 권한을 만들지 않는다. 2번이 연장 행동을 구현하고 3번이 제출 조건과 경합을 함께 확인한다.
- 연장 승인과 제출 모두 같은 업무 잠금·expected 버전을 사용한다. 먼저 성공한 행동이 버전을 증가시키면 후속 옛 요청은 충돌로 돌려 최신 기한/상태를 재조회하는 안이다. 연장 승인 뒤에도 이미 승인된 제출본의 설명·시각·회차를 바꾸지 않는다.

## W3-07 / M3-07 — 필수 검토·별도 검토 요청

정식 제출 성공 자체가 해당 회차의 필수 검토 대상을 만드는 안이다. 제출 후 별도 요청 버튼을 누르지 않았다고 목록에서 누락시키지 않는다. 별도 수동 검토 요청은 제출/승인과 구분하고, 알림·추가 전달 요청으로 둘지 2·3번이 확인한다. 이미 제출된 같은 회차에 두 번째 판단 대상을 만들지 않는다.

자동 결과 제출은 계속 제외한다. 자동 검토 요청/스케줄러는 도입 합의 전 구현하지 않는다. 추후 도입하더라도 요청만 만들며 제출본·회차·submitted 상태를 만들거나 바꾸지 않는다.

## 첨부와 업무 이력 — 2번에 필요한 접점

첨부의 업로드 준비·소유 확인 → 제출 시 참조 연결 → 권한 있는 다운로드 흐름은 3번이 구현안을 준비한다. 업로드/다운로드 API 경로·저장소·크기/개수/형식·만료/정리·보존은 1번·팀장과 미정이다. 파일 전송은 DB 트랜잭션 밖에서 하고, 제출 트랜잭션에서 준비 완료·소유·유효 참조를 재검사한다. DB 실패 시 파일까지 자동 rollback된다고 주장하지 않으며 임시 파일 정리/보상과 백업 복구를 별도 설계한다. 2번에 파일 기능 구현을 요청하지 않는다.

업무 이력 소비 필드 제안: event_id, task_id, assignment_revision, submission_id(해당 없는 이벤트는 NULL), round_no(해당 없는 이벤트는 NULL), actor_id/허용 표시명, occurred_at(서버 UTC), event_type, 이전/이후 상태(해당 시), 화면용 설명. 생성·수정·수락·배정·연장 이벤트는 2번, 제출·판단 이벤트는 3번이 자신의 행동과 같은 DB 트랜잭션에 기록하는 안이다. 3번 HistoryControl이 소비한다. 한 제출 행동을 다시 ‘상태 변경’으로 중복 기록할지는 공동 분류를 정하며 기본안은 한 행동당 의미 있는 사건 1건이다.

정렬은 occurred_at DESC→서버 event ID DESC, 필터는 task_id·허용 event_type이며 동률/빈 결과를 일관되게 반환하는 안이다. 전체/페이지 계약은 API 확정 전 결정하고 첫 페이지만 전체 결과로 표시하지 않는다. 내부 AuditEvent 원문이나 파일·토큰·개인정보를 노출하지 않는다. 관리자 5번이라는 메뉴 위치가 전체 이력 열람 권한을 뜻하지 않으며 업무별 관계·과거 기록·보존은 1·2·3번·팀장이 확인한다.
