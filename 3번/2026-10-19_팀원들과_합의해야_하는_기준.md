# 3번 → 1번·2번 — 결과물·검토·업무 이력 연결 합의 요청

작성·확인일: 2026-10-19 · 작성: 3번 · 회신: 1번·2번, 검토자·운영 기준은 팀장 공동 확인

**상태: 회신 요청 / 공동 합의 전.** 아래 표는 기존 W3-01~07 및 M3 항목을 담당자별로 정리한 확인표입니다. 새 요청 번호나 별도 API·DB 계약을 만들지 않습니다. 구체적인 서버 제안은 [기존 W3 구체 회신안](2026-10-17_W3_상태제출검토_구체회신안.md)을 기준으로 확인해주세요. 이전 설명은 이 문서 아래에 그대로 보존합니다.

## 연결할 화면과 구조

- 직원·관리자 **04 결과물 → 내 결과물**: ReviewsControl에서 조회하고 SubmissionForm에서 제출·재제출합니다.
- 관리자 **04 결과물 → 결과물 검토**: ReviewsControl에서 제출물을 선택하고 ReviewDecisionForm에서 승인·반려합니다.
- 관리자 **05 업무 이력**: HistoryControl에서 업무 변경·제출·승인·반려 기록을 조회합니다.

```text
2번의 업무 조회 → 3번의 결과물 목록·상세
3번의 제출·검토 → 1번의 공통 인증·저장 지원을 이용한 서버 처리
                → 제출물·판단·업무 상태·처리 기록을 함께 저장하는 안
저장 성공 확인 → 각 화면에서 서버의 최신 내용 다시 조회
2번의 업무 변경 기록 + 3번의 제출·검토 기록 → 3번 업무 이력 화면
```

제출 후 2번 화면이 업무 상태 변경 요청을 따로 보내는 이중 저장은 피하는 안입니다. 실제 서비스·저장 책임은 아래 회신으로 맞춥니다. 파일 전송까지 DB와 자동으로 함께 되돌아간다는 뜻은 아닙니다.

## 이미 정해진 내용 — 다시 선택할 항목 아님

- 업무 상태는 진행전 / 진행중 / 제출완료 / 승인완료 / 반려완료의 5개이며, 기존 소문자 코드 표현을 유지합니다.
- 배정 후 진행전 → 본인 수락 후 진행중 → 정식 제출·재제출 후 제출완료 → 검토 후 승인완료 또는 반려완료입니다. **반려 후 재작업을 시작하는 구체적 행동은 미합의**입니다.
- 모든 정식 제출은 검토하며, 승인완료만 최종 완료입니다. 자기 승인·반려는 금지합니다. 관리자 본인 제출물의 상위 검토자 관계는 별도 확인합니다.
- 최초 성공 제출은 **1차**, 반려 후 재제출 저장 성공마다 **+1차**, **업무상 최대 회차 제한 없음**입니다. 취소·실패·반려·승인·같은 요청의 재응답으로 회차를 올리지 않습니다. 배정 번호와 제출 회차는 별개입니다.
- 마감 경과만으로 결과물을 자동 제출하지 않습니다. 자동 검토 요청은 도입 여부부터 별도 합의입니다.

## 1번 담당자에게 확인 요청

로그인 정보나 공통 저장 지원을 처음부터 다시 만들어달라는 요청이 아닙니다. 제공된 공통 기능에 3번 기능을 연결할 때 필요한 검토입니다.

| 기존 ID / 내용 | 현재 확인한 내용 | 1번에게 필요한 회신 |
|---|---|---|
| W3-02 / 함께 저장·중복 방지 | 공통 인증 확인·트랜잭션·버전 검사·중복 요청 결과 확인 도구는 제공됨. 실제 제출·승인·반려 행동은 별도 연결 대상 | 3번 서비스가 제출/판단, 업무 상태, 처리 이력, 성공 결과를 같은 DB 처리로 저장하는 안을 검토해주세요. 2번 수락·재배정·연장과 같은 업무를 동시에 바꿀 때의 잠금 순서, 버전 검사/증가, 중복·응답 유실 처리와 오류 형식을 확인해주세요. |
| W3-04 / 제출 데이터와 DB 연결 | 3번이 기존 W3 문서에 제출·회차·판단·첨부 정보 및 API 초안을 제공함. 아직 확정된 DB/API 아님 | 업무·배정·사용자와 연결할 ID 타입/외래키, 이전 제출 보존, 회차 중복 방지, 최소 성공 응답, 기능 등록 위치와 새 migration 번호를 검토해주세요. 업무상 회차 제한 없음과 DB 숫자의 기술 범위를 구분해주세요. |
| W3-05 / 검토 권한 | 업무 지정 관리자가 별도 검토자를 지정하는 1번안 수신. 조회 관리자와 승인권자는 같은 뜻이 아님 | 검토자 지정·변경·비활성/강등 시 서버 권한 확인 방법을 검토해주세요. 자기 판단 차단과 검토자 전용 최소 조회 범위를 2번·팀장과 함께 확인해주세요. |
| 첨부 / 파일 저장·다운로드 | 공통 파일 저장/API는 아직 없음. **파일 기능 구현은 3번 담당** | 3번 파일안을 기준으로 사용할 서버 저장 위치·설정, 인증·DB 연결, 크기/개수/형식 기준, 업로드 후 제출 실패 시 정리, 이전 첨부 보존·삭제 기준을 검토해주세요. 운영·보관 기준은 팀장과 공동 확인이 필요합니다. |
| W3-02/04 / 화면용 업무 이력 | 기존 공통 감사 로그는 내부 감사용이며 화면 이력 API를 대신하지 않음 | 2·3번의 처리 이벤트를 화면용 이력으로 저장·조회할 DB 접점, 조회 권한, 보존·삭제 기준을 검토해주세요. 내부 감사 원문을 그대로 공개하지 않는 구조로 맞춥니다. |

공통 로그인 정보는 기존 CaptureSession과 접속 취소/변경 검사를 재사용합니다. 3번은 로그아웃·사용자 변경 시 목록·선택·대기 첨부·요청 정보를 정리하는 폼 연결을 담당합니다.

## 2번 담당자에게 확인 요청

**특히 '진행중 최초 제출 / 반려완료 재제출'은 로컬 동작 보고이며 서버 정책 합의 완료가 아닙니다.** 이 부분의 수용 또는 수정안을 우선 회신해주세요.

## 3번이 직접 진행할 구현과 공동 확인 후 진행할 부분

- 3번 구현: 네 폼의 기존 구조를 유지한 실제 조회·저장 연결, 제출·재제출·회차, 승인·반려 서버 기능, 첨부 업로드·다운로드, 업무 이력 조회, 접속 변경/취소/오류·늦은 응답 처리.
- 1번 검토: 공통 인증·쓰기 지원 재사용, 기능 등록, DB 타입·관계·migration, 파일 설정·권한·보존 접점.
- 2번 구현: 업무 등록·수락·수정·배정·연장 및 해당 업무 이벤트. 3번은 이를 대신 구현하지 않음.
- 공동 확인 후 적용: 위 표의 상태별 제출 조건·검토 권한·마감·변경 허용·실제 API/DB 연결 계약. 문서 작성이나 게시 자체를 승인으로 보지 않음.
- 향후 영향 예상 파일: 3번 Results 폼과 제출/검토/첨부/이력 서비스, 2번 Tasks의 행동·조회 접점, 1번 Infrastructure/MainForm/서버 기능 등록·DB 접점. 정확한 파일과 변경 이유는 실제 코드 변경 전에 해당 담당 폴더에 기록하고 회신을 확인함. 이번 게시에서는 이 파일들을 수정하지 않음.

## 회신 방법과 상태 추적

현재 추가 확인표의 상태는 모두 **회신 요청 / 공동 확인 대기**입니다. 이미 제공된 공통 지원·조회 기능을 미구현으로 되돌리는 표시가 아닙니다. 기존 W3 ID별로 아래 형식으로 회신해주세요. 중복 기술 문서를 새로 만들기보다 기존 구체 회신안의 항목을 참조해주세요.

```text
항목: W3-__ / 첨부 / 업무 이력
답변: 수용 / 수정안 / 보류
결정할 처리 기준:
구현·검토 담당 / 확인 날짜:
근거 문서·커밋·PR:
함께 확인할 테스트:
```

담당자와 근거를 확인한 항목만 '공동 확인 완료'로 갱신합니다. 문서 PR 병합·공통 지원 코드 병합을 제출/검토 제품 구현이나 정책 합의 완료로 표시하지 않습니다.

## 이전 채팅 설명 원문 — 보존

합의해야 하는 건 **같은 상황에서 업무 화면과 결과물 화면을 어떻게 처리할지에 대한 기준**이야.

예를 들어 네 화면에서는 제출에 성공했는데, 2번 업무 화면에는 계속 ‘진행중’으로 남으면 안 되잖아. 이런 일이 없도록 처리 방법을 맞추는 거야.

**이미 정해진 기준**

아래 내용은 기존 기준으로 유지하면 돼.

- 업무 상태는 **진행전·진행중·제출완료·승인완료·반려완료** 5개.
- 정식 제출·재제출은 검토를 거치고, **승인완료가 최종 완료**.
- 자기 제출물은 직접 승인·반려할 수 없고, 관리자 본인 제출물은 상위 검토자가 판단.
- 제출 회차는 **1차부터 시작해서 재제출 저장 성공마다 증가하며 최대 제한 없음**.
- 마감됐다는 이유로 결과물을 자동 제출하지 않음.

**아직 맞춰야 하는 기준은 다음이야.** 아래 질문들의 답은 아직 공동 확정 전이야.

| 구분 | 정해야 하는 내용 | 함께 확인할 담당 |
|---|---|---|
| **① 검토자** | 누가 검토자를 지정하고, 누가 승인·반려할 수 있는가 | 팀장·1·2·3번 |
| **② 제출·재제출 조건** | 어떤 업무 상태에서 제출할 수 있고, 반려 후 어떻게 다시 시작하는가 | 2·3번 |
| **③ 마감·연장** | 마감 후 제출을 허용하는지, 연장 승인을 언제 반영하는가 | 팀장·2·3번, 저장 방식은 1번 |
| **④ 업무 수정·담당자 변경** | 제출 중이거나 반려된 업무의 내용·담당자를 바꿀 수 있는가 | 2·3번, DB 관계는 1번 |
| **⑤ 저장·중복 처리** | 제출·판단·업무 상태를 어떻게 함께 저장하고 중복을 막는가 | 1·2·3번 |
| **⑥ 첨부파일** | 어디에 저장하고, 누가 다운로드하고, 언제까지 보관하는가 | 1·3번·팀장 |
| **⑦ 업무 이력** | 어떤 기록을 누가 남기고, 누구에게 보여주는가 | 1·2·3번 |

**① 검토자를 어떻게 정할지**

1번은 **업무 지정 관리자가 활성 관리자 1명을 검토자로 지정하는 방식**을 제안했어. 여기에 다음 답이 필요해.

- 직원의 제출물을 검토할 사람은 누가 지정할까?
- 관리자 본인 제출물의 **상위 검토자**는 어떤 관계로 확인할까?
- 검토자가 휴가·퇴사·비활성 상태라면 누가 대신할까?
- 검토자가 변경되면 이미 제출된 결과물도 새 검토자가 판단할까?
- 검토자는 해당 제출물 외에 과거 제출물까지 볼 수 있을까?

예를 들어 **A 관리자가 검토 창을 열어둔 동안 검토자가 B로 변경됐다면**, A의 승인 버튼을 눌렀을 때 저장을 막을지 정해야 해.

**② 언제 제출·재제출할 수 있는지**

현재 로컬 코드는 **진행중에서 최초 제출, 반려완료에서 재제출**하도록 만들었어. 이를 실제 서버 기준으로 사용할지 2번과 확인해야 해.

- 진행전 상태에서는 수락하기 전까지 제출을 막을까?
- 제출완료 상태에서 직원이 제출 내용을 수정하거나 철회할 수 있을까?
- 반려 후 바로 재제출할까, ‘재작업 시작’을 먼저 눌러야 할까?
- 승인된 결과물을 다시 수정해야 한다면 어떻게 처리할까?

예를 들어 **반려 후 2번은 다시 수락해야 한다고 만들고, 네 폼은 바로 재제출하도록 만들면** 두 화면의 흐름이 달라져.

**③ 마감과 연장을 어떻게 적용할지**

- 마감일이 10월 20일이면 **그날 몇 시까지** 제출할 수 있을까?
- 마감 후에도 직접 제출할 수 있을까, 연장 승인이 필요할까?
- 연장을 신청만 해도 새 마감일을 적용할까, 승인된 뒤 적용할까?
- 검토 대기 중인 업무도 연장할 수 있을까?
- 연장 승인과 제출이 동시에 발생하면 어느 정보를 기준으로 처리할까?

우리가 올린 회신안에는 **마감일 당일까지 허용하고, 연장 승인 후 새 기한을 적용하는 안**을 적었어. **아직 확정된 규칙은 아니야.**

**④ 업무 내용이나 담당자가 바뀌면 어떻게 할지**

- 제출완료 상태에서 업무 제목·설명을 수정할 수 있을까?
- 검토 대기 중에 담당자를 변경할 수 있을까?
- 반려된 업무를 다른 직원에게 넘기면 이전 제출물은 어떻게 보관할까?
- 새 담당자가 제출하면 기존 업무의 다음 회차로 이어갈까?

예를 들어 **김 직원의 2차 제출물이 있는 업무를 박 직원에게 넘겼다면**, 과거 제출자는 김 직원으로 보존하면서 박 직원의 다음 제출 회차를 어떻게 표시할지 맞춰야 해.

**⑤ 무엇을 한 번에 저장할지**

제출 버튼을 눌렀을 때 다음 내용이 함께 맞아야 해.

```text
새 제출물 저장
+ 제출 회차 증가
+ 업무 상태를 제출완료로 변경
+ 제출 이력 저장
```

여기서 정할 내용은 다음이야.

- 네 제출·검토 기능이 업무 상태까지 함께 저장하도록 할지.
- 저장 중 오류가 나면 어떤 기록까지 되돌릴지.
- 제출 버튼을 두 번 눌러도 한 번만 저장되도록 어떻게 연결할지.
- 저장은 됐지만 성공 응답을 못 받았을 때 어떻게 확인할지.
- 관리자가 같은 제출물을 동시에 판단하면 어떻게 막을지.

**1번은 이를 위한 공통 도구를 제공했어. 네 제출·검토 기능에 그 도구를 연결하는 방식은 맞춰야 해.**

**⑥ 첨부파일을 어떻게 관리할지**

- 파일을 어느 서버 폴더나 저장소에 보관할까?
- 파일 개수·크기·허용 형식은 어떻게 정할까?
- 제출자·검토자 중 누가 다운로드할 수 있을까?
- 파일 업로드는 됐는데 제출 저장이 실패하면 파일을 어떻게 정리할까?
- 재제출 후에도 이전 회차의 첨부파일을 보관할까?
- 보관 기간과 삭제 권한은 어떻게 할까?

파일 처리 기능은 **네 담당**이고, 1번은 인증·설정·DB 연결 부분을 검토하는 구조야.

**⑦ 업무 이력에 무엇을 남길지**

- **2번:** 업무 생성·수정·담당자 변경·수락·연장 기록.
- **3번:** 결과 제출·재제출·승인·반려 기록.
- **함께:** 기록 항목·저장 방법·조회 권한·보관 기준.

예를 들어 제출 한 번을 **‘결과 제출’ 1건으로 표시할지**, ‘상태 변경’까지 별도로 표시할지 맞춰야 중복처럼 보이지 않아. 관리자도 **자신이 관리하는 업무만 볼지, 다른 범위까지 볼지** 확인해야 해.

이 기준들은 우리가 `LOG/3번`에 올린 **구체 회신안의 제안 항목**이야. 팀원들의 수용·수정 의견을 받은 뒤 실제 코드에 적용해야 해.
