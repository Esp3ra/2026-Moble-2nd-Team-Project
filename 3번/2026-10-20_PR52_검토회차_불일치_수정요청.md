## R52-01 — 과거 결과물을 표시하면서 최신 제출물을 승인·반려할 수 있음

대상: [results.js 188~201행](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/0a7a57df97767e81680484222587974747bf6dab/RemoteWork.Server/remotework/static/results.js#L188), [실제 판단 요청 281~285행](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/0a7a57df97767e81680484222587974747bf6dab/RemoteWork.Server/remotework/static/results.js#L281).

`openDecision()`은 호출 순간의 `selected.submission_id`로 context를 조회합니다. 기다리는 동안 과거 제출 회차의 `선택` 버튼은 활성 상태이고, 회차 변경은 `selected`만 바꾸며 `generation`을 변경하지 않습니다. 응답을 받으면 `decisionContext`는 최초 제출물의 값인데, 확인창의 회차·결과 내용·첨부는 변경된 `selected`에서 읽습니다. 실제 POST는 `decisionContext.submission_id`를 사용하므로 검토자가 확인한 결과물과 판단 대상이 달라질 수 있습니다. 서버의 현재 권한/버전 검사는 이 화면 내용의 동일성을 검증하지 않습니다.

### 재현

1. 반려된 1차(`submission_id=201`)와 검토 대기인 최신 2차(`202`)가 있는 업무를 엽니다.
2. 2차를 선택하고 승인 또는 반려를 누른 뒤 `/results/data/submissions/202/context` 응답을 지연시킵니다.
3. context가 도착하기 전에 1차의 `선택` 버튼을 누릅니다.
4. 응답이 도착하면 확인창은 **1차·201의 본문/첨부**를 표시하지만 `decisionContext.submission_id`는 **202**입니다. 확인 시 POST는 202를 판단합니다.

검토자가 제출된 원본 JavaScript를 Node VM에서 실행하고, 명시 DOM/HTTP 대역으로 실제 등록된 회차 선택 handler와 지연 응답을 호출해 위 불일치를 재현했습니다. 출력은 `writeTarget=202`, `shownSubmission=201`, `roundButtonsEnabled=true`입니다. 이는 실제 브라우저/공유 DB에서 판단 쓰기를 실행한 결과가 아니며, 실제 POST 대상은 원본 285행으로 별도 대조했습니다.

### 수정·재검증 기준

- context 요청 전 업무/제출물을 불변 값으로 캡처하고 확인창과 실제 판단 요청 모두 같은 캡처를 사용하십시오.
- 요청 중 회차 선택을 막거나, 선택 변경 시 이전 context/확인창을 무효화하십시오. 다른 화면/회차로 전환한 뒤 지연 응답이 도착해도 잘못된 창을 열지 않아야 합니다.
- 승인과 반려 모두에서 업무 ID·제출 ID·회차·본문·첨부·context·POST 대상이 같음을 지연 응답 회귀 검사로 확인하십시오. 최신 선택 후 과거 회차 클릭·업무 변경·정상 판단도 포함하십시오.
- 기존 cookie/CSRF·세션·권한·버전·동일 키/결과 복구와 결과물 이력 보존 검사를 유지하십시오.

회신용 별도 MD/PR은 요구하지 않습니다. 기존 코드 PR52에 수정과 검증 결과를 반영하면 재검토합니다.
