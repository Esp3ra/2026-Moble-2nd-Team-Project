# 3번 → 2번 — 재작업 흐름 수신 및 서버 연결 구현 전 회신

작성·확인: 3번 · 2026-10-19 · 전달: 2번 · 공통 저장·DB 접점 검토: 1번

## 현재 구현 상태

현재 제출·검토 기능은 **로컬 구현 단계이며, 실제 서버 저장과 2번 업무 화면 연결은 아직 구현 전**입니다. 기존 로컬 JSON 저장을 실제 서버·DB 저장 기능으로 보고하지 않습니다. 새로 회신받은 재작업 시작 후 재제출 조건도 이 회신 작성 시점에는 기존 로컬 코드에 아직 반영하지 않았습니다.

제출·판단 기록과 업무 상태·이력을 함께 저장하고, 성공 확인 후 각 화면을 다시 조회하는 방향으로 준비하겠습니다. 세부 요청·응답 형식은 1번 공통 지원 및 2번 업무 정보와 맞춰 정리하겠습니다. 현재 확정된 실제 제출 API나 구현된 서버 요청·응답 자료는 없습니다. 기존 W3 문서의 경로·모델·필드는 제안 자료입니다.

## W3-01/03 — 재작업 시작 후 재제출 흐름 수신

[2번 최신 회신](../2번/2026-10-19_3번_재작업상태_확정_및_연결회신.md)에 기록된 다음 흐름을 확인했습니다. 3번 수정 기준으로 수신하며, 이전의 '반려완료에서 바로 재제출' 로컬 조건을 이 흐름에 맞춰 수정하겠습니다.

```text
진행전 → 본인 수락 → 진행중 → 최초 제출 성공 → 제출완료
제출완료 → 반려 → 반려완료
반려완료 → 본인 재작업 시작 → 진행중 → 재제출 성공 → 제출완료
제출완료 → 승인 → 승인완료
```

- 최초 제출과 재제출 모두 업무 상태가 진행중일 때 처리합니다. 기존 성공 제출·반려 기록을 확인해서 최초 제출과 재제출을 구분합니다.
- 반려완료에서는 바로 재제출하지 않습니다. 창 열기·편집·반려 직후에 자동으로 진행중으로 바꾸지 않습니다.
- 최초 제출은 1차, 반려 후 재제출 저장 성공마다 +1차이며 업무상 최대 회차 제한은 없습니다. 재작업 시작·취소·실패·승인·반려·같은 요청의 재응답만으로 회차를 올리지 않습니다.
- 이전 제출·첨부·반려 사유·판단을 보존하고, 재작업 때문에 최초 수락이나 배정 번호를 초기화하지 않습니다.
- **2번 구현:** 업무 화면의 재작업 시작 및 서버에서 현재 담당자·반려완료 확인 후 진행중 전환과 기록 저장.
- **3번 구현:** 결과물 화면의 제출 조건, 진행중에서 최초/재제출 구분, 제출 성공 시 회차 증가·제출완료 저장, 승인·반려·과거 결과 보존.
- **1번 검토:** 재작업/제출 행동의 공통 인증·기능 등록·버전·중복/응답 유실·트랜잭션 접점. 새 경로나 action 이름은 이 문서에서 확정하지 않습니다.

## W3-02/04 — 저장과 화면 갱신 연결 방향

2번이 수용한 아래 연결 방향을 확인했습니다. **방향의 수신이며 실제 서비스 구현 완료 보고가 아닙니다.**

| 처리 | 앞으로 연결할 내용 | 현재 상태 |
|---|---|---|
| 제출 요청 | 업무·현재 배정·업무 버전, 결과 설명·첨부 참조 전달. 회차·제출자·시각은 서버에서 결정하는 방향 | 세부 필드·검사·등록 계약은 검토 필요 |
| 제출 저장 | 3번 서버 기능에서 제출본·회차·제출완료 상태·성공 이력을 함께 저장 | 서버 미구현 |
| 승인·반려 저장 | 3번 서버 기능에서 대상 판단·승인완료/반려완료 상태·성공 이력을 함께 저장 | 서버 미구현 |
| 성공 응답 | 2번이 제시한 task_id, task_status, row_version, assignment_revision, updated_at과 제출 ID·회차를 검토 | 최소 필수 필드·타입·오류 계약은 1번 검토 후 확정 |
| 업무 화면 갱신 | 성공 확인 뒤 2번이 별도 상태 저장을 하지 않고 TasksControl.RefreshAsync()로 목록·상세 재조회 | 실제 통지·화면 수명·호출 위치 연결 전 |
| 결과물·이력 갱신 | 성공 확인 뒤 3번이 결과물 목록·상세·이력을 최신 조회 | 실제 조회 서비스·서버 연결 전 |

기존 업무 조회와 별도 쓰기 준비 정보 제공 위치를 수신했습니다. task_id·배정 번호·업무 버전의 연결은 기존 인터페이스를 재사용하는 방향으로 검토하며, 준비 조회만으로 최종 제출 권한·최신 상태를 보증하지 않습니다. 실제 저장 직전에 서버에서 현재 관계·배정·버전·상태를 다시 검사합니다. 마감 조건은 확정된 정책에 맞춰 연결합니다.

2번 이력은 생성·수정·배정·수락·재작업 시작·연장, 3번 이력은 제출·재제출·승인·반려를 각 성공 처리에 기록하는 방향을 수신했습니다. 화면용 이벤트 필드·조회·중복 표시·권한·보존은 1·2번과 추가 확인합니다. 공통 내부 감사 원문을 화면에 그대로 노출하지 않습니다. 파일 전송까지 DB와 자동으로 함께 되돌아간다고 가정하지 않습니다.

## 수정 순서와 남은 범위

1. **ReviewsControl / 직원·관리자 04 결과물 → 내 결과물:** 제출 진입 조건·버튼 안내부터 점검합니다. 반려완료에서는 재작업 시작 안내를 표시하고, 2번의 재작업 시작 성공 후 최신 업무 상태를 확인해 진행중에서 제출하도록 준비합니다.
2. **SubmissionForm / 같은 메뉴의 제출 창:** 저장 직전에도 진행중 조건과 기존 성공 제출·반려 기록을 검사합니다. 최신 제출물의 반려 상태를 현재 업무 상태와 혼동하지 않도록 분리하고, 최초/재제출·다음 회차를 구분합니다.
3. 이후 실제 서버 행동·첨부·조회 서비스와 업무 화면 성공 통지·이력 연결을 확정된 범위부터 구현·검증합니다. ReviewDecisionForm은 반려 후 자동 복귀를 추가하지 않고, HistoryControl은 2번의 재작업 시작 기록을 읽는 접점을 맞춥니다.

기존 Designer·레이아웃·컨트롤 이름·공개 생성자·이벤트를 최대한 유지합니다. 2번 재작업 시작 기능이나 미확정 서버 규약을 3번 폼 안에서 대신 만들지 않습니다. 최신 alpha와 로컬 작업본을 대조한 뒤 별도 로컬 수정본에서 진행합니다.

마감·검토자·재배정·수동/자동 검토 요청·파일 운영 기준의 미합의 항목은 이번 수신으로 확정하지 않습니다. 사용자 요청에 따라 해당 정책의 추가 수정은 일단 건너뛰며, 이번 재작업 흐름 확인과 기존 공통 지원 재사용을 구분합니다.
