### R21-04 · P2 — Init-Chat의 활성화 값을 배치 내부로 제한

위치: [Init-Chat.cmd 9행](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/52cc0864eb5c84899367be82a750ab713624a86b/Init-Chat.cmd#L9).

`setlocal` 없이 `REMOTEWORK_ENABLE_CHAT_DRAFT=1`을 설정합니다. 기존 cmd 창에서 `call Init-Chat.cmd`로 실행하면 배치가 끝난 뒤에도 호출자의 값이 1로 남습니다. 같은 창에서 서버나 공통 초기화를 실행하면 `.env`의 0보다 상속된 1이 우선하여 의도와 다르게 미확정 채팅을 활성화할 수 있습니다. 문서의 ‘해당 초기화 프로세스에만 설정’이라는 경계와 다릅니다.

**재현:** 원본 배치를 소유 임시 폴더에 복사하고 DB를 실행하는 Flask 명령만 무작업 대역으로 바꿔 호출했습니다. 호출자 시작값 0 → 배치 호출 → `CALLER_AFTER=1`을 확인했습니다. 실제 DB 작업 없이 환경 누출을 재현했으며 제품 파일을 수정하지 않았습니다.

**수정 방향:** 배치 시작의 `setlocal` 등으로 활성화 값을 지역화하고 성공·실패 반환 모두 호출자 값/미설정 상태를 보존합니다. 초기화 후 서버 활성화는 기존 안내대로 별도로 명시해야 합니다.

**재검토:** 호출자 값 미설정/0/1과 CLI 성공/실패 각각에서 종료 뒤 원래 값이 유지되는지 확인합니다. 기존 R21-02 기본 off 새 프로세스 등록 검사도 유지합니다.

## R21-01 · P2 — 정상 사용자 정보 갱신을 로그인 변경으로 오인

위치: [HttpChatService.cs 42–45행](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/832478e208b302e63e2cfc97f6fc1214344a6781/RemoteWork.WinForms/Features/Collaboration/HttpChatService.cs#L42-L45), 같은 검사인 [HttpChatParticipantDirectory.cs 28–29행](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/832478e208b302e63e2cfc97f6fc1214344a6781/RemoteWork.WinForms/Features/Collaboration/HttpChatParticipantDirectory.cs#L28-L29).

`MainForm`은 30초마다 사용자 정보를 갱신하고 공통 `ApiClient.RefreshIdentityAsync()`는 같은 로그인 세션이어도 `CurrentUser`를 새 객체로 교체합니다. 채팅 요청 도중 이 갱신이 끝나면 `ReferenceEquals`가 실패합니다. 정상 방·참여자·메시지 응답이 취소되며, 서버 저장 성공 뒤에도 실패로 안내할 수 있습니다.

**재현:** 정상 로그인 → 방 목록 HTTP 응답을 대기 → 같은 계정의 `/auth/me` 성공 → 원래 방 목록 성공 응답 전달. 공통 `CaptureSession().IsCurrent`는 참인데 채팅 서비스가 `OperationCanceledException`을 발생시켰습니다. 정확한 head의 C# 소스와 명시적 HTTP 대역으로 재현했으며 실제 서버/DB는 사용하지 않았습니다.

**수정 방향:** 객체 참조 대신 기존 공통 `ApiClient.CaptureSession()`의 접속 세대/취소 규약을 사용해 전체 논리 작업과 페이지 조회를 묶어 주세요. 단순 사용자 ID 비교만으로 대체하면 같은 계정 재로그인을 구분하지 못하므로 피합니다. 동일 세션의 정보 갱신은 허용하되 실제 로그아웃·재로그인·다른 계정 변경의 오래된 응답은 버려야 합니다. 저장 응답 유실 처리도 공통 규약과 맞춥니다.

**재검토:** 동일 세션 정보 갱신 중 방/참여자/메시지 조회·저장 성공, 진짜 세션 교체 시 취소, 같은 계정 재로그인·다중 페이지 응답 순서를 구분해 검증합니다.

## R21-02 · P2 — 미확정 채팅 DDL이 공통 초기화에 자동 포함

위치: [registry.py 6–7행](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/832478e208b302e63e2cfc97f6fc1214344a6781/RemoteWork.Server/remotework/features/registry.py#L6-L7), `chat/storage.py:10`, 기존 `db.init_schema()`.

`chat.routes`의 무조건 import가 `storage`와 채팅 모델을 공통 `Base.metadata`에 등록합니다. 기존 `init_schema()`의 `Base.metadata.create_all(engine)`은 그 채팅 테이블도 생성합니다. 따라서 별도 `Init-Chat`을 실행하지 않아도 공통 `init-db`에 미확정 채팅 스키마가 섞입니다. PR 설명에서도 이 영향을 공개했지만, 별도 명시적 초기화·1번 DDL 검토 전에 원본 코드로 병합하려면 경계를 정해야 합니다.

**재현:** 정확한 head를 읽고 모든 기존 기능 플래그를 끈 `create_app`에서 MySQL `create_mock_engine`으로 `init_schema()`의 DDL을 수집했습니다. `chat_rooms`, `chat_members`, `chat_messages`의 `CREATE TABLE` 3개가 출력됐습니다. 실제 DB 연결/DDL 실행은 하지 않았습니다.

**수정 방향:** 1번과 합의한 명시적 활성화/초기화 경계로 모델 등록과 공통 초기화를 분리해 주세요. 예를 들어 채팅 모델을 opt-in으로 등록하거나 공통 초기화의 대상 테이블을 명시하는 방법이 있습니다. 정식 migration 번호·schema version·공유 적용을 이 문서에서 임의로 확정하지 않습니다.

**재검토:** 기본 설정의 공통 초기화에서 채팅 테이블 미생성, 명시적 채팅 초기화에서만 필요한 3테이블 생성, 기존 사용자·업무·공지 초기화 경계 보존을 확인합니다. 실제 MySQL 검증은 별도 소유 테스트 DB에서 진행합니다.

## R21-03 · P2 — 서버와 C#의 메시지 길이 기준 불일치

위치: [HttpChatService.cs 72–75행](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/832478e208b302e63e2cfc97f6fc1214344a6781/RemoteWork.WinForms/Features/Collaboration/HttpChatService.cs#L72-L75), 발신 검사 189행. 서버 기준은 `chat/storage.py:24–27,192`입니다.

서버는 Python `len()`으로 유니코드 코드 포인트 수를, C#은 `string.Length`로 UTF-16 코드 단위 수를 셉니다. 이모지처럼 두 코드 단위인 문자가 1,001개인 본문은 서버의 2,000자 제한에는 맞지만 C#에서는 2,002자로 판단합니다. 그런 메시지 하나가 응답에 포함되면 `GetMessagesAsync`가 전체 방 대화 조회를 실패시킵니다.

**재현:** 서버 검사 함수에 해당하는 `len()` 기준에서 유효한 이모지 1,001개를 정상 메시지 JSON 응답으로 제공했습니다. 정확한 head C# HTTP 대역 검증에서 `메시지 응답 형식이 올바르지 않습니다`로 실패했습니다. 실제 MySQL 저장 결과를 확인한 테스트는 아닙니다.

**수정 방향:** 입력 UI·전송·응답·서버의 길이 단위를 하나로 맞춰 주세요. 서버가 허용하는 메시지를 조회 클라이언트가 거절하지 않아야 합니다. 현재 서버의 코드 포인트 기준을 유지한다면 C#에서도 해당 단위로 검증합니다. 새로운 길이 정책으로 바꿀 경우 1번과 API 규약을 확인합니다.

**재검토:** 한글/ASCII와 보충 평면 문자 각각의 2,000/2,001 경계, 혼합 본문, 정상 API로 저장한 본문을 다시 조회하는 통합 검증을 포함합니다.
