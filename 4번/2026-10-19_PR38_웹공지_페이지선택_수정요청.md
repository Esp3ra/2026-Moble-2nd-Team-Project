## R38-01 · P2 — 조회 버튼이 현재 페이지를 보존해야 함

위치: [templates/notices/index.html 6~9행](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/0924db4abe4ea3ab9e7c593fbe0b6d0c1f4bdadb/RemoteWork.Server/remotework/templates/notices/index.html#L6-L9), 관련 [features/notices/web.py 36~50행](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/0924db4abe4ea3ab9e7c593fbe0b6d0c1f4bdadb/RemoteWork.Server/remotework/features/notices/web.py#L36-L50).

목록의 조회 form은 `target`, `sort`, `direction`, `selected`만 전송하고 `page`를 보내지 않습니다. 2페이지에서 공지를 선택하고 조회하면 서버는 page 기본값1로 목록을 다시 읽습니다. 선택한 ID가 1페이지에 없으면 chosen_id가 그 페이지 첫 행으로 남고, 그 **다른 공지의 상세를200으로 표시**합니다. 정렬/선택은 정상이어도 2페이지 이후의 실제 조회가 틀립니다.

### 실제 재현 — 별도 소유 MySQL + Flask test client

1. 합성 공지24개를 `review-notice-00`~`23` 제목·각기 다른 본문으로 준비합니다.
2. 웹 로그인 후 `GET /notices?page=2&sort=title&direction=asc`로 이동합니다. 선택은 `review-notice-20`입니다.
3. 응답 HTML의 실제 조회 form에서 input 이름/값과 선택된 target을 읽어 그대로 GET 제출합니다. 없는 page를 테스트에서 만들어 넣지 않습니다.
4. 전송 필드는 `direction, selected, sort, target`뿐이며, 실제 상세는 **review-notice-00**, 기대 상세는 **review-notice-20**입니다. 응답200이지만 선택한 본문이 없어 추가 회귀1개가 실패합니다.

위 제목은 테스트 합성 자료입니다. 실제 사용자/운영 DB·브라우저 자동화 시험은 아닙니다. `pagination-repro.json`에 실제 form 필드·기대/표시 제목·page 누락을 기록했습니다.

### 수정·재검토 요청

- 현재 목록에서 선택한 공지를 조회할 때 page·sort·direction·target을 함께 보존해 같은 ID의 상세를 표시해 주세요.
- 대상 필터/정렬 변경에 필요한1페이지 초기화는 명시적으로 구분하고, 단순 조회와 섞지 않아야 합니다. page hidden만 추가해 필터 변경 시 빈2페이지에 남는 후속 문제도 검사해 주세요.
- 2·3페이지의 첫/중간/마지막 선택→조회, 필터/정렬 변경, 삭제 뒤 오래된 선택과 빈 목록, 키보드/JS 미사용 경로의 기대 동작을 회귀로 확인해 주세요. 기존 행선택만으로 본문을 자동 표시하지 않는 기준은 유지합니다.
- 기존 웹/API 권한·CSRF·guard·동시삭제·전체32KiB·공통3파일 범위를 유지한 새 head와 실행 결과를 전달하면 재검토합니다. 2번이4번 제품 코드를 대신 수정하지 않았습니다.
