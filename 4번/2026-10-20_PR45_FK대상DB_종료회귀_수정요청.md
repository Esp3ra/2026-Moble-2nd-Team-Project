## R45-01 [P2] FK 참조 데이터베이스도 비교하기

위치 `RemoteWork.Server/remotework/features/notices/popup_schema.py:31-35`.
현재 물리 검사는 constrained columns·referred_table/columns·ON DELETE/UPDATE만 비교하고 `referred_schema`를 버립니다. 따라서 현재 DB의 users/notices와 열·키가 같은 **다른 DB의 users/notices**를 참조하는 기존 테이블도 정상으로 승인합니다. 이름이 같아도 같은 부모가 아닙니다. 실제 공지/회원에 대한 INSERT가 FK오류로 실패하거나, 반대 DB의 우연히 같은 ID와 잘못 결합하고 다른 DB 삭제의 CASCADE를 받는 구성이 준비 완료로 표시됩니다.

소유 MySQL8.2에서 DB A의 공통/공지/팝업을 준비하고, 별도 소유 DB B에 users/notices를 만든 뒤 A.notice_confirmations의 두 FK만 B.users/B.notices로 지정했습니다. inspector가 두 `referred_schema=B`를 반환함을 먼저 확인했습니다. 기대는 불일치 RuntimeError·원래 테이블 무변경이지만, 실제 `prepare_popup_schema(A)`가 정상 반환하여 독립 회귀가 **1실패(DID NOT RAISE RuntimeError),1.76초**입니다.

최소 재현은 기존 physical 및 소유 DB fixture로 실행합니다. 사용자/공유 DB를 사용하지 않습니다.

```python
def test_foreign_database_fk_is_not_the_current_parent(physical, owned_databases):
    app, engine, _ = physical
    other = owned_databases('foreign_popup')
    User.__table__.create(other)
    Notice.__table__.create(other)
    # raw008의 두 REFERENCES만 other.url.database의 같은 이름 부모로 지정
    # notice_confirmations의 나머지 열/PK/index/engine/collation은 동일
    with app.app_context(), pytest.raises(RuntimeError, match='FK'):
        prepare_popup_schema(engine)  # current code returns successfully
```

실행 가능한 전체 독립 검사는 검토자 `audit/test_independent_popup.py`입니다. 수정 시 FK의 스키마를 현재 연결의 실제 기본 DB와 비교하고, None/명시적 동일 DB 표기는 정상으로 정규화하되 다른 DB는 거절해야 합니다. 테이블 이름만 일치하는 것으로 승인하거나 기존 FK를 자동 ALTER하지 않습니다. 재검증: 같은 DB 암시/명시 FK 정상, 각 FK의 다른 DB 부모 거절·원문 DDL/행 보존, 기존 물리9개/동시 준비 통과.

## R45-02 [P2] MainForm 새 요청을 기존 인증 종료 fixture에 반영하기

위치 `RemoteWork.WinForms/Shell/MainForm.cs:54-57`, 연관 `Tests/ActivityPresence.Tests/AuthenticationCloseTests.cs:187-191`.
최신 head는 직원 MainForm 생성 시 코디네이터를 시작해 `GET /api/v1/notices/popups/pending?after_id=0`을 추가합니다. 기존 R23 인증 종료 TCP 대역은 로그인·auth/me·기본 notices만 지원하며 새 경로에서 `Unexpected authentication fixture route`를 던집니다. 제출 원본 `dotnet run --project Tests/ActivityPresence.Tests -c Release`가 AuthenticationExpiryUi/AuthenticationCloseTests의 Serve→DisposeAsync에서 종료코드1로 실패합니다. 공지35검사/빌드 성공만으로 기존 종료 회귀가 보존됐다고 볼 수 없습니다.

검토용 별도 복사본에 **이 정확한 pending 경로의 기능off404 응답만** 추가한 뒤 같은 제품 코드로 실행하면 **294검사/12시나리오 통과**했습니다. 401/부모·자식 종료·세션 해제/로그인 복귀·프로세스 정리 검증과 다른 unknown route의 실패는 유지했습니다. 따라서 현재 확인된 것은 대역 계약 누락이며 제품 인증 종료가 고장났다고 단정하지 않습니다. 원본 회귀 실패와 보완 복사본 통과를 구분합니다.

수정은 MainForm/테스트 담당과 협의해 공식 fixture에 새 옵션off 경로를 명시하고 기존 엄격한 인증/종료 검사를 유지하는 방향입니다. 테스트를 생략하거나 모든 경로를200/404로 바꾸지 않습니다. 수정된 원본을 같은 환경에서 다시 실행해 확인해야 합니다.
