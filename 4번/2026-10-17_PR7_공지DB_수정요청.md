## R1 · P2 — 동시 삭제에서 실제 삭제 없는 성공과 감사 이력 중복

대상: [`RemoteWork.Server/remotework/features/notices/routes.py:116–119`](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/74781018af21d3fa9f30bc6c06515dd260335730/RemoteWork.Server/remotework/features/notices/routes.py#L116).

MySQL 8.2.0의 `REPEATABLE-READ`에서 두 관리자 요청이 인증 조회를 마친 뒤 같은 공지를 삭제하면, 공통 관리자 가드가 직렬화하더라도 두 번째 요청의 일반 `get_notice()` 조회가 이전 스냅샷의 공지를 읽습니다. 첫 번째 요청이 이미 삭제·커밋한 행에 두 번째 `session.delete()`가 실행되고 `notice.deleted`도 기록됩니다.

재현 순서:

1. 격리 DB에 공지 한 건과 서로 다른 두 관리자 접속을 만듭니다.
2. 요청별 독립 세션으로 양쪽 인증 조회를 끝낸 뒤, 관리자 트랜잭션 진입 전에 barrier로 맞춥니다.
3. 첫 요청이 삭제·커밋한 다음 두 번째 요청이 가드 안으로 들어가게 합니다. 임의 sleep으로 결과를 추측하지 않습니다.
4. 두 응답과 공지 행 수·해당 공지의 `notice.deleted` 감사 행 수를 확인합니다.

| 직접 확인한 DB | 첫 삭제 | 두 번째 삭제 | 남은 공지 | 삭제 감사 이력 |
|---|---|---|---|---|
| MySQL 8.2 / REPEATABLE-READ | 200 | **200** | 0 | **2건** |
| SQLite 비교 | 200 | 404 `NOTICE_NOT_FOUND` | 0 | 1건 |

MySQL에서는 `DELETE ... expected to delete 1 row(s); 0 were matched` 경고도 발생했습니다. 두 요청 종료 뒤 세 번째 순차 삭제는 404였습니다. 사용자는 이미 삭제된 공지의 두 번째 삭제까지 성공으로 안내받고 실제 변경 없는 삭제 감사 이력이 추가됩니다.

수정·재검토 조건:

- 공통 가드 진입 뒤 삭제 대상을 locking/current read로 다시 확인하거나, 실제 영향 행 수와 성공/감사 기록을 일치시키는 방식으로 수정합니다. ORM identity map 재사용도 고려합니다.
- 공통 인증·관리자 가드의 기존 규약을 우회하지 않습니다. `confirm_deleted_rows=False`로 경고만 감추는 수정은 해결이 아닙니다.
- 독립 요청·세션을 사용하는 결정적 MySQL REPEATABLE-READ 회귀를 추가해 실제 삭제와 `notice.deleted`가 한 번만 발생하는지 확인합니다.
- 현재 순차 삭제의 미존재 응답은 404입니다. 멱등 삭제 응답을 변경하려면 1번과 합의하되, 실제 삭제 없는 중복 `notice.deleted`는 남기지 않습니다.

## R2 · P2 — DB 범위를 넘는 공지 ID가 SQLite에서 500을 반환

대상: [`RemoteWork.Server/remotework/features/notices/routes.py:32–35`](https://github.com/Esp3ra/2026-Moble-2nd-Team-Project/blob/74781018af21d3fa9f30bc6c06515dd260335730/RemoteWork.Server/remotework/features/notices/routes.py#L32).

Flask의 `<int:notice_id>`가 받은 큰 정수를 범위 확인 없이 `Session.get()`에 전달합니다. 로그인한 직원의 상세 GET과 관리자의 삭제 POST에 `9223372036854775808`(2의 63승) 또는 10의 100승 ID를 전달하면 SQLite 바인딩 범위를 넘어 **500 `SERVER_ERROR`**가 납니다. 같은 요청은 MySQL에서 404 `NOTICE_NOT_FOUND`이므로 지원 DB별 외부 응답도 달라집니다.

| 입력 | SQLite 상세 GET / 삭제 POST | MySQL 상세 GET / 삭제 POST |
|---|---|---|
| `2147483648` | 404 / 404 | 404 / 404 |
| `9223372036854775808` | **500 / 500** | 404 / 404 |
| 10의 100승 | **500 / 500** | 404 / 404 |

수정·재검토 조건:

- DB에 넘기기 전에 유효 ID 범위를 검사합니다. 현재 모델의 정수 PK와 C# `int` 표현을 함께 보고 최종 허용 범위와 오류 코드(입력 오류 또는 미존재 4xx)를 1번 공통 규약과 맞춥니다. 이 요청은 BIGINT 전환을 확정하지 않습니다.
- 두 경로의 정상·최댓값·범위 초과·미존재 입력을 SQLite/MySQL에서 검증하고, 잘못된 입력 때문에 삭제나 감사 이력이 생기지 않는지 확인합니다.
- 모든 DB 예외를 일괄 404로 바꾸어 연결 장애 등 실제 서버 오류를 숨기지 않습니다. 기존 인증·권한 검사를 유지합니다.
